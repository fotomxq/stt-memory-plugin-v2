# D7 · 重要度动态计算设计稿（调用次数窗口占比 · 最近 20 条重算 · 出窗冻结）

> 文档版本：v0.1 ｜ 日期：2026-09-27 ｜ 类型：**设计稿（不发版）** ｜ 状态：**待裁决**（见 §7 的 Q1–Q12）
> 触发（用户原话）：
> 「调用次数、重要度是原子数据底层固定字段，主要记录提取记忆命中的次数、在剧情中的重要程度。
> 其中重要度是百分比，所以它本身是带有一定浮动性质的，业务上每个原子数据应根据前后 10 条的调用次数总量与当前调用次数比例来计算。
> 每次提取记忆，需根据最近 20 条原子数据的重新计算重要度，注意第 20 条应该同样通它前后 10 条计算。超出 20 条的则固定重要度，后续因为不参与计算，所以恒定。」
> 前置：`docs/01-业务架构.md`（B7 归一与夹取、B11 情节锚）、`D5`（优先级与锚定：谁说了算）、`D6`（提升阶梯）
> 定位：把「重要度」从 **AI 给的语义常量**，改为 **由调用次数在局部窗口中的占比推导的动态值**；并规定**重算范围**（最近 20 条）
> 与**冻结语义**（出窗恒定）。本文只定方案与口径，**不写实现步骤**；落地由后续实现轮次完成。

---

## 0. 一页摘要

| 项 | 内容 |
| --- | --- |
| **要解决什么** | 现在「重要度」是 AI 一次写死的语义值（0.9 主线 / 0.5 重要 / 0.2 次要），不随使用情况变化；而「调用次数」一直只有累加、没有回馈到重要度 |
| **新口径一句话** | 某条的**重要度 = 它的调用次数 ÷ 它前后各 10 条（含自身，窗口 21 条）的调用次数合计** —— 一个**局部占比**（百分比） |
| **何时算** | **每次提取记忆（分析）落库之后**，对**最近 20 条**逐条重算（第 20 条照常用它真实的 ±10 邻居，包括窗外的） |
| **何时不算** | 出窗（第 21 条及更旧）：**不再重算，值恒定**（但仍作为窗内条目的分母参与） |
| **数据模型** | **不新增容器、不新增字段**（冻结与否由「在数组中的位置」推导）→ `DATA_VERSION` 保持 1 |
| **最大牵连** | 值域从「0–1 语义量」变成「0–1 占比（典型 0–30%）」，**所有按重要度比较的阈值都会失去原意**（清扫保护 0.7、裁剪排序、召回打分权重）—— 见 §3.3 / §4.9，必须一并重标定 |
| **现状的隐藏问题** | 界面上显示的「重要度 N%」与存储里的 `importance` **本来就不是同一个东西**（前者由 `uses` 现算，后者是 AI 值）—— 本设计顺带把两者统一 |

## 1. 需求拆解（用户句子 → 设计条款）

| # | 用户原话 | 设计条款（本文对应章节） |
| --- | --- | --- |
| ① | 调用次数、重要度是原子数据**底层固定字段** | 两字段**保持存储在原子条目上**（`uses` / `importance`），不引入外部账本（§4.1） |
| ② | 调用次数记录**提取记忆命中的次数** | `uses` 的累加口径**不变**：仍是注入命中一次 +1（§3.1） |
| ③ | 重要度记录**在剧情中的重要程度** | `importance` 的**语义**改为「相对调用占比」，消费方需重新标定（§4.9） |
| ④ | 重要度是百分比，**带浮动性质** | 值域 0–1（UI 显示为整数百分比），**每次提取都会变**（§4.2） |
| ⑤ | 按**前后 10 条**的调用次数总量与**当前**调用次数的**比例**计算 | `imp(i) = u(i) / Σ u(k), k ∈ [i−10, i+10]`（§4.2；分母是否含自身见 Q1） |
| ⑥ | **每次提取记忆**需按**最近 20 条**重算 | 触发点 = 提取落库后；范围 = 各维数组**尾部 20 条**（§4.3 / §4.5） |
| ⑦ | **第 20 条**也要按它前后 10 条算 | 第 20 条的窗口**越过重算边界**，要读窗外（冻结）条目的调用次数（§4.3） |
| ⑧ | **超出 20 条**的固定重要度，后续恒定 | 出窗即冻结：不再重算、不再改写（§4.3） |

## 2. 目标 / 非目标

**目标**

1. 把「重要度」的定义、计算公式、窗口边界、取整口径、兜底值写成**唯一权威口径**（可测试、可复算、跨端可比）；
2. 明确**重算范围（20）与冻结语义**，避免「每次分析把全库重算一遍」的性能与漂移问题；
3. 把新口径对**既有阈值消费方**的冲击列全，并给出重标定方案（否则清扫会失控，见 §3.3）；
4. 给出**分阶段落地**（纯函数 → 接线 → 阈值 → UI → 跨端），每阶段可单独回退。

**非目标（明确不做）**

| # | 不做 | 原因 |
| --- | --- | --- |
| N1 | 不改 `uses` 的累加口径与时机 | 用户只定义了「命中次数」的读法，没说改记法（§3.1 现状即符合） |
| N2 | 不改 AI 提取流程 / 提示词的**结构** | 重要度字段是否继续让 AI 填，见 Q5；那是模板取舍，非本设计的算法部分 |
| N3 | 不新增容器或字段（含「已冻结」标记） | 冻结语义可由位置推导；新增字段会触发**六处接线** + `DATA_VERSION` 递增（§4.11） |
| N4 | 不改遗忘 / 清扫 / 裁剪**算法本身** | 只重标定它们读到的**阈值**；算法口径属既有契约 |
| N5 | 不做「重要度驱动注入预算」的新机制 | 注入择优仍按既有 `recallEntryScore`（§3.3），本设计只改变它读到的重要度值 |
| N6 | 不引入 AI 再评估重要度（例如让模型读回 20 条重打分） | 用户明确要求的是**可复算的算术口径**（零 AI、确定性） |

## 4. 方案

### 4.1 字段职责（不变项 / 变更项）

| 字段 | 现在 | 本设计 |
| --- | --- | --- |
| `uses` | 注入命中次数，累加，合并取大 | **不变**（N1） |
| `importance` | AI 给的 0–1 语义值（存储）+ 另一套 uses 派生值（展示） | **重定义为窗口占比**；存储与展示**统一**读它（§4.8 / Q5） |
| `strength` | V1 兼容（0–100） | 跟随 `importance`（不变式：`strength = round(importance × 100)`） |
| 新字段 | —— | **不新增**（N3） |

### 4.2 计算模型

对某维度**按数组顺序**（尾 = 最新）排出的序列 `u[1..n]`：

```text
imp(i) = u(i) / Σ u(k)      k ∈ [max(1, i−10), min(n, i+10)]        … 窗口 21 条（含自身）
       = 兜底值             当 Σ u(k) = 0（窗口内无人被调用）
```

| 规则 | 取值 | 说明 |
| --- | --- | --- |
| 窗口半径 | **10**（前后各 10） | 用户原话；可配置（Q12） |
| 分母是否含自身 | **含**（推荐） | 含自身 → `imp ∈ [0,1]`，天然满足「重要度是百分比」；不含则可能 >1（Q1） |
| 边界裁剪 | 数组两端截断（不补 0、不循环） | 第 1 条只有后 10 个邻居；无需特殊分支 |
| 0 分母兜底 | **0**（推荐）或 `1/窗口实际条数` | 「没人调用」时占比为 0 更符合直觉；若走「均值兜底」则 0 命中条目也拿分（Q8） |
| 取整与存储 | 存 **0–1**（建议保留 **3 位小数**），显示沿用整数百分比（四舍五入） | 与 `importancePct` 既有口径一致（`core/recall.js:1457`） |
| 确定性 | 纯函数：同样序列 → 同样结果；无 AI、无随机、无时间依赖 | 跨端可比（§4.12） |

### 4.3 重算范围与冻结语义（用户第 ⑥⑦⑧ 条）

| 位置（按数组尾部起算） | 处理 | 备注 |
| --- | --- | --- |
| 最新 **1 – 20** 条 | **每次提取落库后重算并写回** | 每次分析都会变（浮动） |
| 其中第 20 条 | 窗口取 `[i−10, i+10]`，**包括窗外（21–30）的邻居** | 用户原话「第 20 条应该同样通过它前后 10 条计算」 |
| 第 **21** 条及更旧 | **不重算、不写回**（值恒定） | 仍作为窗内条目的**分母**参与（只读 `uses`） |
| 新入库条目 | 天然落在窗内 → 首次分析即被算 | 无需特判 |
| 条目被裁掉 | 随容器裁剪消失（既有口径） | 不额外处理 |

> **冻结 = 不写**，而非写一个「冻结标记」：判定「是否需要重算」只看它是否属于**当前尾部 20 条**（N3）。
> 推论：一个条目在它存在的第 k 次分析时位于第 20 位，被算过一次；下一次分析它退到第 21 位 → 从此值不变（**恒定**）。

### 4.5 触发与接线点（设计级）

| 环节 | 位置（现有） | 说明 |
| --- | --- | --- |
| 算法本体 | `core/`（纯计算，无 DOM / 无宿主） | 按 `03-技术架构` 的分层，必须是**纯内核函数**，可单测 |
| 触发 | 提取落库之后 —— 与 `host/preflight.js#recalibrateAfterExtract`（`host/extract.js:225/308/417`）**同一挂点** | 三个合并点（单楼 / 批量 / 手动）都要覆盖，缺一即静默缺陷 |
| 读容器 | `state.<dim>` 数组尾部 20 条（§3.4 顺序口径） | 逐维独立计算，互不影响 |
| 写回 | 只写**窗内 20 条**的 `importance`（`strength` 同步） | 出窗一律不写（§4.3） |
| 落盘 | 复用既有 `saveState()` 时机 | 不新增存储通道 |
| 诊断 | 建议沿用 `host/preflight` 的「返回摘要」模式（本次改了哪些维度、几条、耗时） | 便于 FTT 调试入口与冒烟断言 |
| 幂等 | 同一 state 连续两次重算结果一致（除 `uses` 变化外） | 跨端/重试安全（§4.12） |

### 4.7 排序基准（「前后」指谁的前后）

| 候选 | 依据 | 评价 |
| --- | --- | --- |
| **数组顺序（尾 = 最新）** | §3.4 证据 | 无需新字段、与裁剪口径一致 → **推荐** |
| 剧情日期（`date`） | 条目自带 | 同日期大量并列；无日期的条目（计划/悬念/概念）无法排序 |
| 最后更新楼层（`floorEnd`/`updatedAt`） | 部分维度有 | 「被命中」不更新它，故与「使用热度」无关 |

### 4.8 与 AI 重要度的关系（两条路，需裁决 Q5）

| 方案 | 内容 | 影响 |
| --- | --- | --- |
| **A · 单轨替换（推荐）** | `importance` 一律由窗口占比给出；AI 模板里的「重要度」字段**废弃或忽略** | 口径唯一、与用户原话一致；需删/改 10+ 处模板文案与 `CN_KEY_MAP` 保留位、并重标定所有阈值（§4.9） |
| **B · 双轨并存** | `importance` 仍是 AI 语义值；新增**派生**「窗口占比」用于展示/排序（不加字段，运行时算） | 改动最小、阈值不受影响；**但**用户明确说「重要度……应……计算」，且现状已存在「展示值与存储值不同源」的混乱（§3.2），双轨会让混乱固化 |

> 无论 A / B，**展示口径都必须收敛**：列表行要么显示存储的 `importance`，要么显示运行时占比，不能再各算一套（`ui/list-rows.js:173` 等 vs `core/forget.js:198`）。

### 4.9 值域变化与阈值重标定（若走方案 A，必须同批处理）

| 消费方 | 现默认 | 新值域下的语义 | 建议 |
| --- | --- | --- | --- |
| C1 清扫保护 `lowUseForgetProtectImportance` | 0.7 | 成为「窗口内调用占比 ≥70%」——几乎不可能 | 改为**分位数/倍数**口径（如「占比 ≥ 窗口均值的 N 倍」）或按新值域重设（例如 0.25）→ Q6 |
| C1 清扫其它闸门 `lowUseForgetRatio` / `lowUseForgetMinItems` 等 | 0.05 等 | 读 `uses` 均值、与 importance 无关 | 不动 |
| C2 裁剪排序 | 重要度优先 | 仍成立（相对量） | 保持；确认「0 命中先出局」是否符合预期 |
| C3 召回打分权重 | `importance × 0.15` | 贡献降至约 1/10 | 要么把权重按新值域放大（如 ×3），要么把占比**归一化**（`占比 / 窗口最大占比`）后喂给打分 → Q6 的变体 |
| C5 合成默认值 | 0.6 下限 | 变成「极高占比」 | 改为「取源条最大占比」或按新值域给默认（如 1/窗口条数） |
| `importanceBase` / `importancePerUse`（展示口径） | 0.12 / 0.06 | 与新口径冲突（不再需要） | 随 Q5 一并决议：删除控件 or 保留为「未参与窗口计算时的种子」 |

### 4.11 数据模型影响

| 项 | 结论 |
| --- | --- |
| 新容器 / 新字段 | **无** → `DATA_VERSION` 保持 **1**（`core/constants.js:16`） |
| 需要走「六处接线」吗 | **不需要**（常量表 → 归一 → 哈希 → 瘦身 → 迁移 → 跨端 的清单只对**新容器/新字段**生效，`docs/02-数据架构.md` §3.4） |
| 内容哈希 | `importance` 是否参与哈希需**核实**（若参与，重算会改变内容身份 → 影响跨端同步判定与去重）→ **待核实项 R1**，见 §6 |
| 瘦身白名单 | 若 `importance` 在 `SLIM_HASHED_FIELDS` 内，重算会连带影响哈希（同 R1） |

### 4.12 跨端与迁移

| 场景 | 设计口径 |
| --- | --- |
| 跨端合并 | 条目级按 `updatedAt` 取新（`core/cross-sync.js:55-70`、`123-140`）；`uses` 与 `importance` 随条目走。设备 A 重算、设备 B 没重算 → **两边值可能不同**（Q10） |
| 收敛建议 | ① 重算是**确定性纯函数**，双方在**同一 state 快照**上会得到同一结果；② 合并后由本机对窗内 20 条**再算一次**（幂等）→ 偏差被下一次提取抹平 |
| 冻结态 | 不落标记 → 不会因跨端覆盖而「解冻」，也不会产生冲突字段 |
| V1 导入 | 旧数据 `importance` 是语义值；在其进入窗口前**保持原值**，进入窗口后被新口径覆盖（Q5 的方案 A 下） |
| 黄金样本 | 凡断言 `importancePct` / 列表行「重要度 N%」的用例（`ui/list-rows`、`panel-audit`、`recall-golden` 等）都需按 B5 **登记偏离**并固定新口径（实现轮次处理） |

## 5. 分阶段落地（每阶段独立可用、可单独回退）

| 阶段 | 内容 | 可验证性 | 风险 |
| --- | --- | --- | --- |
| **S0 · 纯口径** | 纯函数 + 单测（窗口、边界、0 分母、取整、冻结边界）+ 只读诊断入口（列出「窗内 20 条 → 当前值 / 重算值」，不写回） | 全部可单测；不改变任何现有行为 | 无 |
| **S1 · 接线重算** | 提取落库后对窗内 20 条写回 `importance`（+`strength`），带开关；返回摘要 | 冒烟：模拟一次提取 → 尾部 20 条变化、21+ 不变、uses 不变 | 展示口径与阈值暂未重标定 → S1 需**默认关**或与 S2 同批发布 |
| **S2 · 阈值重标定** | C1/C3/C5 与默认值按新值域重设（或改判据形态：分位数/倍数）；`importanceBase/PerUse` 处置 | 单测覆盖「清扫保护仍能挡住高占比条目」 | 阈值调不准 → 备选：占比归一化后再喂消费方（§4.9 变体） |
| **S3 · UI** | 列表行显示统一口径 + 「已冻结」提示；设定页新增窗口半径 / 重算条数 / 兜底值；排序按新值 | 面板审计 + 冒烟 | 文案与提示需符合「言简意赅」既定口径（v2.57.0） |
| **S4 · 跨端与迁移** | 合并后重算一次（幂等）；V1 旧值在窗内被覆盖的登记；黄金样本偏离登记 | 跨端单测 + 归档复跑 | 哈希影响（R1）在此阶段前必须核实 |

## 6. 风险与对策

| # | 风险 | 对策 |
| --- | --- | --- |
| R1 | `importance` 可能参与**内容哈希 / 瘦身白名单**，重算会改变条目「内容身份」→ 跨端判定、去重、导入合并出现意外 | **实现轮次第一步核实** `SLIM_HASHED_FIELDS` / 内容哈希字段表；若参与，需在设计上显式排除 `importance`（并登记为有意偏离） |
| R2 | 值域骤降导致**清扫保护失效**，用户数据被大量清掉 | S1 默认关；S2 与 S1 **同批**发布；上线前用真实存档跑「清扫面变化」估算（只读诊断） |
| R3 | 「占比」让**0 命中的新条目**看起来毫不重要（0%），可能被裁剪优先淘汰 | Q6 决议：是否给「窗内新条目」一个下限（如 `1/窗口条数`），或让裁剪的「新者优先」优先于重要度 |
| R4 | 冻结值**不可观测**（用户看不到「为什么这条不再变」） | S3 在列表行给「已冻结」提示；诊断入口可导出「窗内 / 窗外」清单 |
| R5 | 状态记录是「主体·字段」条目，混排窗口可能把不同角色的状态互相比 | Q2 决议：按主体分组窗口（更符合业务）或全体混排（更简单） |
| R6 | 用户反复分析（手动 + 自动）导致同一条被反复重算 | 重算幂等；`uses` 未变时结果不变；不产生额外写盘（可比较后再写） |
| R7 | AI 仍被要求输出「重要度」，产生**被立即覆盖**的无效字段（观感与 token 浪费） | Q5 决议后同步清理模板文案（属实现轮次，且需登记偏离 V1 模板） |
