## 0. 结论摘要（先回答「会不会影响」）

| 影响面 | 会不会受影响 | 现有机制是否自愈 |
| --- | --- | --- |
| **已处理楼层台账**（`state.processedFloors`，`{f,h}`） | 会（楼层号整体后移） | ✅ **自愈**：`reconcileProcessedFloors` 按**内容哈希**归位（v2.64.0），失配的旧标记被丢弃；`processedDriftGuard` 遇 `floor-shrunk` 主动跳过 |
| **`state.lastKnownFloor`**（断裂检测基线） | 会（停在 599） | ⚠️ **半自愈**：只在「记录新楼层」时取 max，**不会自动下调**（保留旧值 → 后续「断裂检测」判断持续失真） |
| **条目楼层区间** `floorStart/floorEnd`（情节/记忆/物品/角色…） | 会（指向已不存在的楼层） | ❌ **不自愈**：编号不会重映射，留下**陈旧区间**（影响排序、衰减、覆盖展示、跨端合并语义） |
| **分段总结** `plotSegments.start/end` | 会 | ❌ 不自愈（同样保留旧编号，时间范围失真） |
| **快照链内条目副本** | 会（副本内仍是旧号） | ❌ 不自愈（回滚后旧号回到主库） |
| **数据本身（正文/条数）** | **不会丢** | ✅ 条目按 id/内容存放，与楼层号解耦；删除聊天楼层**不删除插件数据** |
| **跨端同步** | 会（一端删楼 → 两端编号语义不同） | ⚠️ 台账侧靠哈希归位可自愈；条目区间仍不自愈 → 合并后**混号** |

> **一句话**：**数据不会丢，但「楼层编号」会失去一致性** —— 台账能自愈，**条目上的楼层区间与 `lastKnownFloor` 不能**，
> 需要本稿 §3 的兜底：**收缩检测 → 编号重映射/陈旧区间处理 → 人工确认项**。§4 的「内置删除操作」是**更优解**（让删除可感知、可控）。

## 3. 兜底设计（确保特殊情况安全）

### 3.1 收缩检测哨兵（**含 V1 缺失的「断裂检测」实现**）

- 触发：`getLastMessageId() < state.lastKnownFloor - 容忍值`（现成判据）**且** 当前聊天可用（复用 `chatReadyForFloors`）；
- 判定：**不是**「取文口径漂移」（由 `processedDriftGuard` 先排除），而是**真实楼层骤减**；
- 记录：进入「楼层收缩处理」（`floorShrink`）流程，并把摘要写入**人工确认项**（`core/conflicts.js`）：`已删除 N 层（旧 0-599 → 现 0-9）；台账已按内容哈希重算，条目楼层区间待处理`。

### 3.2 编号重映射（对条目与台账）

> ⚠ **本小节口径已被 v3.7.0 取代**（见文末「结论变更（v3.7.0）」）：条目**来源楼层永不改写**，改为打 `originGone`（原文已移除）+ 写 `floorNowStart/floorNowEnd/floorNowHash`（当前位置）。下表「`floorStart/floorEnd` 就地置 `0/0` + `floorStale: true`」仅作历史留痕，**实现者不得按此行实现**。

| 对象 | 处理 |
| --- | --- |
| 台账 `processedFloors` | 已由哈希归位处理；收缩时**强制走一次**（绕过 20s 节流与 `mass-mismatch` 守卫，因为此时「整体失配」是**预期**） |
| 条目 `floorStart/floorEnd` | **按内容哈希**在旧快照/台账中查其原属楼层 → 若旧楼已删，则**改为「未知区间」**（置 `0/0`）并在条目上留痕 `floorStale: true`（**不删除数据**）〔⚠ 本行口径已被 v3.7.0 取代：来源楼层原样保留 + `originGone`，见文末结论变更〕 |
| `plotSegments.start/end` | 同上：无法映射则标记 `stale`（展示为「时间范围失准」） |
| `state.lastKnownFloor` | **收紧为当前 `lastId`**（`Math.min`），避免后续断裂检测持续失真 |
| 快照副本 | 不回溯改（历史留痕）；回滚时由 §3.2 同一规则在**载入后**再跑一次 |

> 要点：**只改编号，不删数据**；无法映射一律降级为「未知区间」，并让 UI 显示「楼层信息已失效」而不是错的数字。

### 3.3 处理时机与幂等

| 时机 | 动作 |
| --- | --- |
| 检测到收缩的**首次**扫描 | 跑一次重映射 + 收紧 `lastKnownFloor` + 登记人工确认项（一次性） |
| 之后每次启动 | 幂等：无收缩则不动作；有收缩且已有 `floorShrinkAt` 记录则跳过 |
| 跨端合并后 | 复用同一规则（`floorStale` 条目在合并时**优先保留本地**，不再按楼层取新） |

### 3.4 可感知性

- **总览**：`⚠️ 待确认` 横幅（v2.92.0 已有通道）显示「楼层骤减：已按内容重算台账，M 条条目的楼层信息已标记失效」；
- **设定 → 存储**：只读诊断行显示最近一次收缩时间、影响条数；提供「**重新校准楼层**」手动动作（幂等）。

## 4. 内置「删除到最近 N 层」操作（用户提议，**建议采纳**）

> ⚠ **编号口径已被 v3.7.0 取代**：本小节「删后立即跑 §3.2 重映射」中的**就地改写**已废弃（来源楼层不再改动，改为打 `originGone` / 写 `floorNow*`，见文末结论变更）。**删除流程本身**（二次确认 + 自动备份 3 槽轮转 + 预检 + 宿主能力探测 + 降级路径）仍然有效，并已于 v2.94.0 落地。

**为什么更好**：删除由插件发起 → **删除前后都可知**（可先重映射、再删、再校验），彻底避免「事后考古」。

| 项 | 设计 |
| --- | --- |
| 入口 | 设定 → 数据管理（危险操作区），三档：**保留最近 6 层 / 10 层 / 12 层**（与用户提议一致）；另有「自定义 N」（§7 Q4） |
| 前置 | ① 二次确认（`D9` U4 清单内）；② **先导出明文备份**（自动，写 3 份轮转）；③ 预检：列出将要删除的楼层、受影响条目数、能否全部映射 |
| 执行 | 调宿主 API 删除聊天楼层（若宿主不提供 → **降级为「标记隐藏/不再注入」**或提示不支持）；删除后立即跑 §3.2 重映射 + 台账重算〔⚠ 其中**编号就地改写**部分已被 v3.7.0 取代，见本小节开头标注〕 |
| 结果 | 面板备注 + 人工确认项一条（含「备份文件已生成、备份路径」）；总览提示本次删楼摘要 |
| 回滚 | 备份文件可导入恢复；`floorStale` 条目不因回滚而错乱（回滚后按 §3.2 再跑一次） |
| 与同步的关系 | 删除是**本地动作**；若宿主把聊天同步出去，其他端同样触发 §3.1 收缩处理（幂等） |

## 8. 删楼动机与常态化管理（v0.2 新增结论）

**用户裁决要点**：删楼的原因是**减少聊天体积**（酒馆对高楼层支持差 → 用户会主动删）。因此：

| # | 结论 | 说明 |
| --- | --- | --- |
| **A** | **删楼是「常态操作」，不是「异常事件」** | §3.1 的收缩哨兵**必须低噪声**：不再每次弹人工确认项，而是 ① 调试日志必记；② 人工确认项**按类型合并计数**（如「楼层收缩 ×3，共重映射 42 条」），可由用户「全部已确认」一键清账 |
| **B** | **删的只是聊天消息，插件数据全保留** | 重映射**只改编号、不删条目**（§3.2）；用户要的是「聊天变轻」，不是「记忆变少」——文案与结果摘要都要说清这一点 |
| **C** | **载体必须比消息活得久** | 记忆数据主载体是 **`chatMetadata`（随聊天存活）**；**不得**把消息 `extra` 作为唯一载体（删楼会连带删掉 → `D11` v0.3 已改） |
| **D** | **删除前先吸收（可选，默认开）** | 执行 §4 的三档删除前，对**即将被删楼层**做一次「是否已提取」预检：未提取的楼层**先跑一次提取**（或明确提示「这些楼尚未提取，删除后将无法补提」），确保「减体积」不牺牲记忆完整性 |
| **E** | **三按钮落位「设定 → 数据管理」**（用户明确约定） | 三个按钮：**保留最近 6 层 / 最近 10 层 / 最近 12 层**；同区展示「当前楼层数 / 插件条数 / 上次删楼时间」只读诊断；仍属危险动作（二次确认 + 自动备份，§4） |
| **F** | **删楼与同步的关系** | 本地删楼 → 若聊天被宿主同步出去，其他端触发**同一条**收缩流程（幂等）；`floorStale` 条目在跨端合并时**优先保留本地**；`chatMetadata` 随聊天同步 → 其他端拿到的是同一份记忆，**不会因删楼而丢数据** |
| **G** | **世界书镜像与删楼无耦合** | 世界书是派生检索机制（`D11` §3.4 保留其参数），删楼不改变其配置与行为 |

### 8.1 界面约定（设定 → 数据管理）

```text
[危险操作区]
  保留最近 6 层   [执行]      ← 均带：楼层数 / 将删除 N 层 / 受影响条目 M 条（预检）
  保留最近 10 层  [执行]
  保留最近 12 层  [执行]
  只读诊断：当前 12 层 · 插件 1183 条 · 上次删楼 2026-09-27 14:02（备份 xxx.json）
```

### 8.2 与 §5 阶段的关系

- S1（收缩哨兵）按 **§8-A 低噪声**实现；
- S2（重映射）按 **§8-B 只改编号**实现，并在结果摘要中写明「聊天已减小，记忆保留 1183 条」；
- S4（三按钮）落位改为 **设定 → 数据管理**（原写「数据管理（危险操作区）」一致），并加 **§8-D 删前吸收** 预检；
- 新增 **S4b**：`chatMetadata` 主载体验证（与 `D11` S1 合并做只读差异报告）。

### ⑤ 陈旧比例：本轮**无法量化**（方法已定，缺真实存档）
