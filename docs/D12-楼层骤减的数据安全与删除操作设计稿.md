# D12 · 楼层骤减（600 → 10）的数据安全核对与内置删除操作设计稿

> 文档版本：v0.1 ｜ 日期：2026-09-27 ｜ 类型：**设计稿（不发版）** ｜ 状态：**待裁决**（§7 的 Q1–Q10）

## 0. 结论摘要（先回答「会不会影响」）

| 影响面 | 会不会受影响 | 现有机制是否自愈 |
| --- | --- | --- |
| **已处理楼层台账**（`state.processedFloors`，`{f,h}`） | 会（楼层号整体后移） | ✅ **自愈**：`reconcileProcessedFloors` 按**内容哈希**归位（v2.64.0），失配的旧标记被丢弃；`processedDriftGuard` 遇 `floor-shrunk` 主动跳过 |
| **`state.lastKnownFloor`**（断裂检测基线） | 会（停在 599） | ⚠️ **半自愈**：只在「记录新楼层」时取 max，**不会自动下调**（保留旧值 → 后续「断裂检测」判断持续失真） |
| **条目楼层区间** `floorStart/floorEnd`（情节/记忆/物品/角色…） | 会（指向已不存在的楼层） | ❌ **不自愈**：编号不会重映射，留下**陈旧区间**（影响排序、衰减、覆盖展示、跨端合并语义） |
| **分段总结** `plotSegments.start/end` | 会 | ❌ 不自愈（同样保留旧编号，时间范围失真） |
| **快照链内条目副本** | 会（副本内仍是旧号） | ❌ 不自愈（回滚后旧号回到主库） |
| **数据本身（正文/条数）** | **不会丢** | ✅ 条目按 id/内容存放，与楼层号解耦；删除聊天楼层**不删除插件数据** |
| **跨端同步** | 会（一端删楼 → 两端编号语义不同） | ⚠️ 台账侧靠哈希归位可自愈；条目区间仍不自愈 → 合并后**混号** |

> **一句话**：**数据不会丢，但「楼层编号」会失去一致性** —— 台账能自愈，**条目上的楼层区间与 `lastKnownFloor` 不能**，
> 需要本稿 §3 的兜底：**收缩检测 → 编号重映射/陈旧区间处理 → 人工确认项**。§4 的「内置删除操作」是**更优解**（让删除可感知、可控）。

## 1. 场景推演（600 → 删前 590 → 剩 10，逐环节核对）

| # | 环节 | 现状行为（证据） | 结果 |
| --- | --- | --- | --- |
| 1 | 宿主删除楼层 | ST 自身行为，插件不参与 | 聊天长度 600 → 10；`getLastMessageId()` 变为 9 |
| 2 | 漂移防呆 | `processedDriftGuard`：`lastId < lastKnownFloor - 5` → `return { skipped: 'floor-shrunk' }`（`host/floors.js:281`） | ✅ 主动跳过，不误判「取文口径漂移」 |
| 3 | 台账归位 | `reconcileProcessedFloors`：以「当前各楼内容哈希 ∈ 历史已处理哈希集」重建标记（`:340-372`，v2.64.0：**只要归位结果不同就写回**） | ✅ 幸存 10 楼的标记被归位到 0..9；被删楼的标记丢弃 |
| 4 | 大规模失配保护 | 同函数：`dropped / before >= 0.5 && before >= 10` → `skipped: 'mass-mismatch'`（**不写回**） | ⚠️ 590/600 失配本会命中共 50% 守卫 → 交给「断裂检测」；而**「断裂检测」在 V2 仅见注释**（`core/ingest.js:1306-1314`），未见实现 → **该分支可能停在旧台账** |
| 5 | 未摘要清单 | `scanPendingFloors` 按 0..9 扫描；`covered` 用「条目有效区间」（`core/floor-cover.js:24-34`） | ✅ 陈旧区间（如 [100,105]）不覆盖 0..9 → **不会误跳过**；但也不会帮忙覆盖 → 只是「回到未摘要」 |
| 6 | 条目楼层区间 | 条目仍带旧号（例如 `floorStart: 100`） | ❌ **陈旧**：`recallMaxFloor`（`core/recall.js:579`）拿它当锚点 → 评分偏移；排序/展示的「N 楼」不再是真实位置 |
| 7 | 分段总结 | `plotSegments.start/end` 旧号 | ❌ 时间范围标签失真；「已覆盖哪些楼」的展示误导 |
| 8 | 快照 | 快照内存的是**条目副本**（含旧号） | ⚠️ 回滚会把旧号带回主库 |
| 9 | 跨端 | `mergeProcessedFloors` 按「楼层号 + 哈希」合并 | ⚠️ 一端删楼后两端号段不同 → 台账靠哈希归位收敛，**条目区间仍混号** |
| 10 | 数据丢失 | 条目与楼层号解耦（正文/id/内容哈希存放） | ✅ **不丢**（B6 墓碑机制独立于楼层） |

## 2. 现有兜底逐条核对

| 机制 | 位置 | 覆盖范围 | 缺口 |
| --- | --- | --- | --- |
| 哈希归位对账 | `host/floors.js#reconcileProcessedFloors` | **台账**（哪些楼已分析） | 只管台账，不管条目区间 |
| 大规模失配守卫 | 同上（`mass-mismatch`） | 防止「整体失配」时乱删标记 | 与「交给断裂检测」的约定**没有落地实现** |
| 收缩跳过 | `processedDriftGuard`（`floor-shrunk`） | 防误判漂移 | 不触发任何重映射 |
| 覆盖判定 | `core/floor-cover.js#meaningfulFloorRange`（`0/0` 视为未知） | 未摘要清单的跳过 | 陈旧区间**不会**被识别为陈旧 |
| 聊天未就绪守卫 | v2.87.0 `chatReadyForFloors` | 启动期不误清台账 | 与「骤减」无关 |

## 3. 兜底设计（确保特殊情况安全）

### 3.1 收缩检测哨兵（**含 V1 缺失的「断裂检测」实现**）

- 触发：`getLastMessageId() < state.lastKnownFloor - 容忍值`（现成判据）**且** 当前聊天可用（复用 `chatReadyForFloors`）；
- 判定：**不是**「取文口径漂移」（由 `processedDriftGuard` 先排除），而是**真实楼层骤减**；
- 记录：进入「楼层收缩处理」（`floorShrink`）流程，并把摘要写入**人工确认项**（`core/conflicts.js`）：`已删除 N 层（旧 0-599 → 现 0-9）；台账已按内容哈希重算，条目楼层区间待处理`。

### 3.2 编号重映射（对条目与台账）

| 对象 | 处理 |
| --- | --- |
| 台账 `processedFloors` | 已由哈希归位处理；收缩时**强制走一次**（绕过 20s 节流与 `mass-mismatch` 守卫，因为此时「整体失配」是**预期**） |
| 条目 `floorStart/floorEnd` | **按内容哈希**在旧快照/台账中查其原属楼层 → 若旧楼已删，则**改为「未知区间」**（置 `0/0`）并在条目上留痕 `floorStale: true`（**不删除数据**） |
| `plotSegments.start/end` | 同上：无法映射则标记 `stale`（展示为「时间范围失准」） |
| `state.lastKnownFloor` | **收紧为当前 `lastId`**（`Math.min`），避免后续断裂检测持续失真 |
| 快照副本 | 不回溯改（历史留痕）；回滚时由 §3.2 同一规则在**载入后**再跑一次 |

> 要点：**只改编号，不删数据**；无法映射一律降级为「未知区间」，并让 UI 显示「楼层信息已失效」而不是错的数字。

### 3.3 处理时机与幂等

| 时机 | 动作 |
| --- | --- |
| 检测到收缩的**首次**扫描 | 跑一次重映射 + 收紧 `lastKnownFloor` + 登记人工确认项（一次性） |
| 之后每次启动 | 幂等：无收缩则不动作；有收缩且已有 `floorShrinkAt` 记录则跳过 |
| 跨端合并后 | 复用同一规则（`floorStale` 条目在合并时**优先保留本地**，不再按楼层取新） |

### 3.4 可感知性

- **总览**：`⚠️ 待确认` 横幅（v2.92.0 已有通道）显示「楼层骤减：已按内容重算台账，M 条条目的楼层信息已标记失效」；
- **设定 → 存储**：只读诊断行显示最近一次收缩时间、影响条数；提供「**重新校准楼层**」手动动作（幂等）。

## 4. 内置「删除到最近 N 层」操作（用户提议，**建议采纳**）

**为什么更好**：删除由插件发起 → **删除前后都可知**（可先重映射、再删、再校验），彻底避免「事后考古」。

| 项 | 设计 |
| --- | --- |
| 入口 | 设定 → 数据管理（危险操作区），三档：**保留最近 6 层 / 10 层 / 12 层**（与用户提议一致）；另有「自定义 N」（§7 Q4） |
| 前置 | ① 二次确认（`D9` U4 清单内）；② **先导出明文备份**（自动，写 3 份轮转）；③ 预检：列出将要删除的楼层、受影响条目数、能否全部映射 |
| 执行 | 调宿主 API 删除聊天楼层（若宿主不提供 → **降级为「标记隐藏/不再注入」**或提示不支持）；删除后立即跑 §3.2 重映射 + 台账重算 |
| 结果 | 面板备注 + 人工确认项一条（含「备份文件已生成、备份路径」）；总览提示本次删楼摘要 |
| 回滚 | 备份文件可导入恢复；`floorStale` 条目不因回滚而错乱（回滚后按 §3.2 再跑一次） |
| 与同步的关系 | 删除是**本地动作**；若宿主把聊天同步出去，其他端同样触发 §3.1 收缩处理（幂等） |

## 6. 风险与对策

| # | 风险 | 对策 |
| --- | --- | --- |
| 1 | 重映射把好数据标成失效 | 只在**确认收缩**时执行；映射失败才置 `0/0`；**绝不删除条目** |
| 2 | 宿主不提供删除楼层 API | 降级为「隐藏/不注入」或明确提示不支持（不静默失败） |
| 3 | 用户连续删楼 | 幂等 + 每次都有备份轮转；人工确认项合并计数 |
| 4 | 与跨端混号相互放大 | 合并时 `floorStale` 条目优先本地；台账靠哈希归位 |
| 5 | 备份占空间 | 3 份轮转 + 只备份一次（删楼前） |
