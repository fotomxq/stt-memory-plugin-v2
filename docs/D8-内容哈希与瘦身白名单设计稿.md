## 4. 哈希口径：4 基本槽 + 3 扩展槽

### 4.4 角色档案：**内容副本**设计（用户 ④，v0.2 新增）

| 项 | 设计 |
| --- | --- |
| **权威与副本** | **结构化字段是唯一权威**（展示 / 注入 / 向量 / 编辑器照旧读它们）；`content` 是**派生副本**（只读派生，**不反向回写字段**），服务「内容存储 + 哈希 + 通用检索」 |
| **标题** | `title = name`（现状已如此，`core/model/snapshot.js:658`）；`name` ↔ `title` 由 `hydrateSlimEntry` 的「缺一补一」兜底（`core/slim.js:131-134`） |
| **副本构成** | 由**全部**结构化字段按**固定顺序**确定性拼接：`identity`（姓名/性别/物种/职业/生死/出生）→ `appearance` → `personality`（性格 + 特质）→ `background`（出身 + 经历）→ `relationships[]` → `social` → `future`（待办 / 承诺）→ `tags` → `extra` 的**具名扩展槽**（R13） |
| **拼接规范** | 段内固定分隔符（如 `；`）、固定段标签（如 `身份：…`）；**集合类字段（标签 / 关系 / 特质）先排序再拼** → 跨端同内容必得同哈希（R3） |
| **生成时机** | **每次变更即整合**：落点在**归一化**（`core/model/snapshot.js#normalizeSnapshot` 已是所有写入路径的必经之地：提取合并 / 修复 / 提升 / 编辑器保存 / 跨端合并）→ **无需新增触发点** |
| **字段扩展不受影响** | 既有字段与新增字段**都保留原样**；新增字段**只需登记进副本的拼接顺序**（登记即生效）—— 即「字段扩展不影响功能，只是内容里多一份副本」 |
| **截断上限** | 现为 300 字（`core/model/snapshot.js:659`）→ 必须放宽（R14），否则副本装不下全字段 |
| **影响面（已核）** | 展示 `ui/list-rows.js:236-249` ✗不读；注入 `core/recall.js:939-946`、`:1426` ✗不读；向量 `core/vector.js:54`、`:60` ✗不读；**通用检索读**（`core/recall.js:554`、`:646`、`:1234`）→ 命中面变大（**正向**，需回归，R15） |
| **风险与对策** | ① 副本与字段可能不一致 → 规定「副本只在归一化时生成、字段变更必经归一化」；② 体量上升 → 由 `dimCap` / 瘦身控制；③ 检索命中变宽 → R15 用真实数据回归 |

## 5. 瘦身白名单：业务定位 + 决策事项

### 5.1 业务定位（用户 ⑥ 要求先呈现）

**一句话**：瘦身白名单是「**同义字段消歧表**」—— 回答「**两个字段说的是同一件事时，存哪一个**」，**不回答**「哪些字段要保存」。

| 层次 | 事实 | 证据 |
| --- | --- | --- |
| **瘦身在做什么** | 写盘时**丢弃空值 / 默认值**（`''`/`null`/`[]`/`{}`/`0`/`false`）、丢弃 `extra` 里与顶层重复的槽位、丢弃历史脏数据 `name`（以 `.json` 结尾）—— 目的是**缩小存档与同步体量**（gzip 通道见 `P9c`） | `core/slim.js:81-85`、`:100-109` |
| **白名单在做什么** | 只在**同义字段组**里决定「保留哪一份」（`keeper = 组内第一个在白名单里的字段`），**值相同才丢另一个**；读回时用同一 keeper 规则**反向补齐** | `core/slim.js:87-99`（写）、`:114-137`（读） |
| **它不做什么** | 非空字段**根本不经过它判断**；它**不参与**哈希计算本身 | 同上；`core/model/hash.js` 全文无该表引用 |
| **谁在用它** | 只有两处（写盘 keeper / 读回 keeper）—— V1 同样只有这两处 | `core/slim.js:30`、V1 `:5495`、`:5533` |
| **真正的硬约束** | **同义组 keeper 必须让「瘦身后的哈希 = 瘦身前」** —— 黄金样本强制 | `tests/unit/slim-gzip-golden.test.js:159`（R3） |

### 5.2 核对后的审计结论

| # | 结论 | 影响 |
| --- | --- | --- |
| **F1** | 注释写「瘦身时**绝不删除**」**与实现不符**：白名单实际只管同义字段 keeper（空值/默认值是无条件丢弃的）。V1 同款 → 属**注释误导**，非移植缺陷 | 后续维护者会按注释理解 → 必须改注释（R17） |
| **F2** | 白名单与哈希字段表**两处手写**，已漂移 **3 处**：`snapshots` 缺 `mind`/`location`、`plans` 缺 `title`/`targetTime`、`suspense` 缺 `title`/`resolveTime` | 当前**无实际后果**（漏项从未被读）；一旦给这些维度加同义组 → keeper 落到非哈希字段 → **破 R3** |
| **F3** | 真正要守住的不变量有两条：① keeper 落在哈希字段集合内；② `hydrate` 能由 keeper **无损重建**组内其它字段（`pathArr`↔`pathStr` 已有双向特例） | 建议写成测试（R18） |
| **F4** | 10 个同义组**当前全部满足** F3①（逐组核过：`atoms` text/content、`scenes` 三组、`rumors` 两组、`items`/`currentStates`/`snapshots`/`concepts`/`parallels` 各一组） | 派生改造可安全落地 |

## 6. R1：一种哈希，还是两种？

槽位加回**标签/类型/状态**后，「变更检测漏检面」比 v0.1 大幅缩小，但**未归零**：

| 方案 | 内容 | 漏检面 | 评价 |
| --- | --- | --- | --- |
| **甲 · 单哈希** | 所有消费方都用 7 槽位哈希 | `time` / `qty` / `carried` / `progress` / `phase` / `statusNote` / `ferment` / `media` / `carriers` / `chain` / `lineage` / `promotedTo` / 结构化块（视 R7） | 最简；代价：**快照差异**与**情节签名**看不出上述字段变化（例：物品数量 100→50 在快照里「没变」；传言发酵度推进在签名里「没变」） |
| **乙 · 双哈希**（建议） | `atomIdentityHash`（7 槽）→ 去重 / 墓碑 / 复活防护 / 控制台；`atomChangeHash`（现逐维字段表）→ 快照差异 / 情节签名 | 无 | 身份照裁决收窄，**变更检测不受损**；代价：多一个纯函数 + 两处调用点切换 + 黄金样本分两类登记 |
| **丙 · 单哈希 + 关键元数据** | 身份 7 槽 + 少量关键字段（`qty`/`progress`/`stage`/`ferment`）内联进「签名/差异」的拼接 | 少量 | 拼接散落在消费方，不如乙集中 |

> 三案都**不影响**：`DATA_VERSION`（无新字段）、瘦身输出、V1 导入（哈希只在运行时算；落盘的只有 `it.h` 缓存，可重算）。

## 7. 迁移与兼容（无论裁决如何都必须满足）

| 场景 | 要求 |
| --- | --- |
| `it.h` 缓存 | 口径一变，**首次保存会全量刷新**（`core/sweep.js:33`）；`sweep` 用 `prev/cur` 两代索引比对（`:47-62`），口径切换当次存在「新旧哈希并存」的过渡 → 实现须用**保守序列**（同周期认新旧两代，或先全量重算再比对），避免把条目**误判为删除**（会写墓碑）⚠️ |
| 内容墓碑 `deletedH` | 收窄后墓碑**变粗**（同槽位内容一概不复活）—— 这正是「不复活」的强度，但**删除后重新提取出同题同日同内容的条目也会被挡住** → 需在 UI/文档明示 |
| 跨端 | 两端口径必须**同版本升级**；异口径建议给哈希**加口径前缀**（如 `i2:`/`c1:`）并规定「前缀不同 → 跳过内容去重，只按 id 合并」；墓碑**只认同前缀**（R19） |
| V1 导入 | V1 数据无 `h`；导入后按新口径重算即可（字段名同构） |
| 黄金样本 | `tests/unit/model-golden.test.js:47`（`atomContentHash` vs V1）按 B5 登记为**有意偏离**并改为归一化比对；`slim-gzip-golden` R3 必须继续全绿（两类哈希都要满足瘦身不变） |
