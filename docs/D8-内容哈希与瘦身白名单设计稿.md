## 4. 哈希口径：4 基本槽 + 3 扩展槽

### 4.1 槽位定义

| 组 | 槽位 | 含义 | 取值规则 |
| --- | --- | --- | --- |
| 基本 | **标题** | 人读短名 | 该维的「名字」字段（`title` / `name` / `subject` / `header`） |
| 基本 | **日期** | **剧情日期** | `date` 类字段；`time`（早/晚）**不进**（R2）；`targetTime`/`resolveTime`（目标时间）不算发生日期 |
| 基本 | **内容** | 实质正文 | 该维**内容字段**统一取槽（`text`/`content`/`desc`/`lines`）；角色档案见 §4.4 |
| 基本 | **地点（如有）** | 发生/所在位置 | 有 `location`/`locations`/`pathArr` 的维度才进 |
| 扩展（v0.2） | **标签（如有）** | `tags` | 用户 ⑤：**进哈希**（集合语义 → 建议先排序再拼，保跨端稳定，R3） |
| 扩展（v0.2） | **类型（如有）** | 该维「类目」字段 | `atoms.type` / `parallels.type` / `memories.memCategory` / `links.kind` |
| 扩展（v0.2） | **状态（如有）** | 该维「状态」字段 | `currentStates.status` / `plans`·`suspense.status` / `atoms.validity`(R4) / `rumors.stage`(R9) |
| 兜底 | 全空 | → 哈希 `''` | 与现状「无分支 → `''`」同义：该维不参与身份判定 |

**必须沿用现归一化**（`core/model/hash.js:24-27`）：缺失 ≡ `''` ≡ `[]` ≡ `0` ≡ `false`，否则瘦身/默认值丢弃会让哈希漂移（R3 破）。

### 4.3 与现表的差异：**移出**哈希的字段（收窄后清单）

## 5. 瘦身白名单：业务定位 + 决策事项

### 5.1 业务定位（用户 ⑥ 要求先呈现）

**一句话**：瘦身白名单是**技术层自行建立的「同义字段消歧表」**—— 回答「**两个字段说的是同一件事时，以哪一个为准**」；
它**不是业务规划出来的内容**，也**不是**「哪些字段要保存」的清单。

| 层次 | 事实 | 证据 |
| --- | --- | --- |
| **它的性质** | **技术产物**：为消除「同一件事有两种字段名」的歧义而建立；随字段命名演进补充，与业务能力无关 | `core/slim.js#SLIM_HASHED_FIELDS`（`:38-43`）、`#SLIM_SYNONYM_GROUPS`（`:44-59`） |
| **它服务谁** | **提取记忆 / 分析记忆**：消歧让「AI 写成 `content`、归一化写成 `text`」这类差异**不再产生两套数据**（详见 §5.5 的流水线位置） | `core/model/dims.js:45`、`:69`、`:171`（`normText(e?.content \|\| e?.text …)`）、`mergeTags(tags, keywords)` 等归一化里的同义合并 |
| **瘦身本身做什么** | 写盘时**丢弃空值 / 默认值**（`''`/`null`/`[]`/`{}`/`0`/`false`）、丢弃 `extra` 里与顶层重复的槽位、丢弃历史脏数据 `name`（以 `.json` 结尾）—— 目的是**缩小存档与同步体量**（gzip 通道见 `P9c`） | `core/slim.js#isSlimDefault`（`:62-67`）、`#slimEntryForStorage`（`extra` 去重 `:96-103`；脏 `name` `:94`） |
| **白名单在做什么** | 只在**同义组**里决定 keeper（`组内第一个在白名单里的字段`，否则取组内首个 present），**且只在该同义字段值完全相同时**才丢弃另一份；读回时由同一 keeper 规则**反向补齐** | `core/slim.js#slimEntryForStorage`（`:81-93`，写）、`#hydrateSlimEntry`（`:113-123`，读） |
| **它不做什么** | 非空字段**根本不经过它判断**（不会被删）；**值不同**的同义字段**两份都留**（不丢数据）；它**不参与**哈希计算本身 | `core/slim.js:91`（`if (same) delete out[f]`）；`core/model/hash.js` 全文无该表引用 |
| **谁在用它** | 只有两处（写盘 keeper / 读回 keeper）—— V1 同样只有这两处 | `core/slim.js#SLIM_HASHED_FIELDS`（`:38`）、V1 `:5495`、`:5533`（**外部 oracle 坐标**） |

### 5.2 核对后的审计结论（v0.3：按用户口径复核并更正）

| # | 结论 | 影响 / 处置 |
| --- | --- | --- |
| **F1** | 注释写「瘦身时**绝不删除**」**与实现不符**：白名单实际只管同义字段 keeper（空值与默认值是无条件丢弃的）。V1 同款 → 属**注释误导**，非移植缺陷 | 后续维护者会按注释理解 → **采纳 R17**：改注释为「同义字段 keeper 优先级 + 空值无条件丢弃」 |
| **F2（v0.3 更正）** | 白名单与哈希字段表两处手写，存在 3 处**字段差异**（`snapshots` 缺 `mind`/`location`；`plans`/`suspense` 缺 `title`/`targetTime`\|`resolveTime`）。**v0.1/v0.2 把它写成「会破 R3 的潜在缺陷」属过度告警** —— 经复核有两点：① 白名单的字段**从不被其他逻辑读取**，差异本身不产生行为；② 真正决定 R3 的是「**值相同才丢 + hydrate 对称**」（见 F3），而**不是**「keeper 必须落在哈希字段集合内」 | 结论降级为**可维护性差异**（两表目的不同：一张管消歧、一张管唯一性）。**采纳 R16** 仍做「同源派生」—— 但理由是**消除双表维护成本**，**不是**哈希正确性的前提 |
| **F3（v0.3 更正）** | 保证「瘦身不改变内容哈希」（R3，`tests/unit/slim-gzip-golden.test.js:159`）的**唯一必要不变量**有两条：① **只丢等值同义**（值不同两份都留，不丢数据）；② **`hydrate` 由 keeper 无损重建**被丢的那一份（`pathArr`↔`pathStr` 有双向特例）。原「keeper 必须落在哈希集合内」**不是必要条件** —— 即使 keeper 是非哈希字段，只要 hydrate 能把哈希读的字段补回来，R3 仍成立 | **采纳 R18**：把 ①② 写成测试（比原拟的「keeper 在哈希集合内」更贴合真实约束） |
| **F4** | 10 个同义组当前全部满足 F3①（逐组核过：`atoms` text/content、`scenes` 三组、`rumors` 两组、`items`/`currentStates`/`snapshots`/`concepts`/`parallels` 各一组） | 「同源派生」（R16）可安全落地，输出逐字节不变 |

**由用户口径直接得到的结论（本稿定案）**：白名单是**消歧（上游）**、哈希是**唯一性（下游）**，二者**不存在设计冲突**；
只要「消歧在哈希之前完成」，哈希就是**结果导向**的计算（见 §5.5）。

### 5.5 流水线位置：消歧（上游）→ 哈希（下游）

| 阶段 | 与消歧的关系 | 与哈希的关系 | 证据 |
| --- | --- | --- | --- |
| **提取记忆**（AI 产出入库） | **归一化即消歧**：`content \|\| text`、`tags \|\| keywords`、`pathArr \|\| pathStr` 等在同一处收敛为规范字段 | **不做任何哈希判定**（提取流程不读哈希） | `core/model/dims.js:45`、`:69`、`:171`；`core/merge.js`/`core/ingest.js#mergeDelta` 无哈希调用 |
| **分析记忆**（落库 / 合并） | 同上（所有写入路径必经归一化） | 落库后刷新 `it.h` 缓存（**为墓碑服务**，不做内容判定）；分析后另算**情节签名**判断是否需要同步时钟 | `core/sweep.js#entryIndexBuild`（`:26-40`，`entryIndexBuild(true)` 刷新 `it.h`）；`host/preflight.js#atomsSignature`（`:104`） |
| **存储边界**（写盘 / 读回） | `slimEntryForStorage` 收敛同义字段（只丢等值）；`hydrateSlimEntry` 反向补齐 | 哈希**只读规范字段**，故**瘦身前后一致**（R3 的由来） | `core/slim.js#slimEntryForStorage`（`:81-93`）、`#hydrateSlimEntry`（`:113-123`） |
| **唯一性判定**（去重 / 墓碑 / 跨端） | 已在更早阶段完成 | **哈希的主职责**：载入去重、内容墓碑、跨端同内容去重、复活防护 | `core/migrate.js#contentDedupeArray`（`:32`）、`core/merge.js#tombEntry`（`:134`）、`core/cross-sync.js#mergeDataObjects`（`:122`）、`core/sweep.js#tombstoneSweep`（`:58`） |

> 一句话：**消歧是为了「不产生两套数据」，哈希是为了「认出同一条数据」**；前者是后者的**前提**，不是它的**同义词表**。

## 6. R1 详解：一个「指纹」还是两种「指纹」？

### 6.1 先把三个词说清楚

| 词 | 大白话 | 代码位置 |
| --- | --- | --- |
| **指纹**（= 内容哈希） | 给一条原子数据算出的短码：**内容一样 → 短码一样；内容变了 → 短码多半会变** | `core/model/hash.js#atomContentHash` |
| **用途一：认身份**（唯一性） | 「这两条是不是**同一条**」—— 跨端合并去重、载入去重、**删除墓碑**（删掉的不许复活） | `core/migrate.js#contentDedupeArray`（`:32`）、`core/merge.js#tombEntry`（`:134`）、`core/cross-sync.js#mergeDataObjects`（`:122`）、`core/sweep.js#tombstoneSweep`（`:58`） |
| **用途二：看变化**（变更检测） | 「相对**上一次快照 / 上一次分析**，这条改了没有」—— **增量快照**只备份变了的条目；**情节签名**不变就判定「情节没更新」 | `core/snapshots.js#snapshotCreateIncr`（`:138-163`）、`host/preflight.js#atomsSignature`（`:104`） |

**现状**：这两件事**共用同一个函数、同一张字段表**。你现在把字段表收窄成 7 槽（标题/日期/内容/地点 + 标签/类型/状态），
所以 R1 真正要回答的是：**收窄后的指纹，还能不能继续承担「看变化」这件事？**

### 6.2 为什么这两件事的性格是**相反**的

| | 认身份（唯一性） | 看变化（快照 / 签名） |
| --- | --- | --- |
| 想要的性格 | **保守、迟钝**：细节改了也**不该**变成「新的一条」，否则跨端会重复累积 | **敏感**：任何实质改动都**必须**被发现，否则快照还原会对不上、时钟不会同步 |
| 例子（同一条数据） | 物品数量 100→50 → 它**还是那把剑**，不是新物品 | 物品数量 100→50 → **必须**被记进增量快照，否则「↩ 还原」会退回更早的数量 |

一个指纹**不可能**同时迟钝又敏感：收窄（迟钝）必然漏掉细节变化；放大（敏感）必然把细节改动当成新身份。

### 6.3 收窄后「会看不见」的真实场景（每一条都对着现有链路）

| 场景 | 现在（逐维字段表） | 若只用 7 槽指纹 |
| --- | --- | --- |
| 物品数量 `qty` 100→50，然后做增量快照 | 指纹变 → **备份这一条** → 「↩ 还原」能精确回到该时刻 | 指纹不变 → 增量快照**认为「没变化」**、不备份 → 还原时这条退回**更早**的版本（数量回退过头）⚠️ |
| 改情节时段 `time`（清晨→深夜）后分析记忆 | 指纹变 → 签名变 → 触发「按最新情节同步日期/**时间**/地点/在场角色」（v2.81.0） | 指纹不变 → 签名不变 → **不触发同步**（`time` 按 §4.1 不进 7 槽）⚠️ |
| 计划进度 `progress` 30%→70% | 指纹变 → 快照记录 | 指纹不变 → 快照漏记 |
| 传言发酵度 `ferment` +1 | 指纹变 → 快照记录 | 指纹不变 → 快照漏记 |
| 删掉一条物品，之后又提取出同名同内容的 | 身份指纹命中墓碑 → **不复活** | **一样不复活**（这一侧收窄是好事）✅ |
| 两端各记一条记忆（标题/日期/内容/归属相同，只有标签不同） | 指纹不同 → 各自保留（现状） | **仍然不同**（标签已进 7 槽）✅ |

> 一句话：**收窄对「认身份」是好事**（少把细节改动误判成新条目）；**对「看变化」是坏事**（漏检）。

### 6.4 三条路（R1 只需选一条）

| 方案 | 一句话 | 认身份用哪个指纹 | 快照 / 签名用哪个指纹 | 代价与风险 |
| --- | --- | --- | --- | --- |
| **A · 一个指纹** | 四处都用新的 7 槽指纹 | 7 槽（新） | 7 槽（新） | 改动最小、概念最简单；**但要接受 6.3 的漏检**（快照还原回退过头、改时段不触发时钟同步） |
| **B · 两个指纹（推荐）** | 身份用新指纹；**变更检测原样不动** | 7 槽（新） | **沿用现在的逐维字段表**（零改动、零回归） | 多一个纯函数 + 两处调用点改指向；代价仅是「两套指纹」的概念要在文档与调试界面写清 |
| **C · 一个指纹 + 变更检测改直接比较** | 指纹只服务唯一性；快照/签名不再用指纹，直接比较条目正文 | 7 槽（新） | **不用指纹**：直接比较序列化内容 | 最贴合「哈希只做唯一性」的字面口径；代价：快照的 `atomsHashes` 失去用途（只剩覆盖统计与链去重）、`atomsSignature` 换判据 → **改动面最大**，快照差异与签名的实现与测试都要重做 |

**推荐 B**：
① 你的裁决（身份指纹收窄为 7 槽）完整落地；
② 快照与时钟同步**行为不变**，没有隐藏回归；
③ 语义清楚 —— **身份指纹（认人）** 与 **变更指纹（看变化）** 各司其职（实现上前者是新函数、后者就是今天的 `atomContentHash`，可改名为 `atomChangeHash` 避免误解）。

**若你更希望「哈希只出现在唯一性这一处」**（严格字面口径），则选 **C**：我会把快照差异与情节签名改为直接比较内容，
并同步梳理快照链去重（`core/cross-sync.js#mergeSnapshotStores`，`:209-219`；`atomsHashes` 去重键 `:212`）、覆盖统计（`ui/snapshots.js:70`）等对 `atomsHashes` 的依赖。

> 变体说明：「身份指纹 + 只把 `qty`/`progress`/`stage` 等少数关键字段内联进差异拼接」等价于 B 的简化版，仍属 B 的范畴（不单列为第四案）。

## 11. 结论变更（v3.22.1）：**非哈希字段（溯源 / 降级标记）的合并口径**

**为什么补这一节**：§5 / §6 只回答了「哪些字段**进**哈希、哪些**不进**」，**没有**回答「**不进**哈希的字段在合并 / 去重时怎么处理」——
实现上默认成了「跟着整对象一起被替换」，于是**标记会随合并消失**。真机由此复发时钟异常（旧聊天情节复活压住时钟）。

**口径（补定，与 v3.8.0 的 NSFW 等级「只升不降」同款）**

| 类别 | 字段 | 合并口径 | 为什么 |
| --- | --- | --- | --- |
| **只升不降** | `originGone`（原文已移除）、`hidden`（已总结隐藏）、`summarizedBy` / `mergedSummary`（情节总结相关） | 任一侧成立即成立；**合并从不清除** | 这些是**已核实过的结论**；清除必须由**本地已核实路径**改写（`host/floors.js#handleFloorShrink.mapEntry` 按内容哈希确认原文仍在 → `clearGone`） |
| **补空不覆盖** | `originGoneAt`、`floorNowStart` / `floorNowEnd` / `floorNowHash`（当前位置指纹）、`chatKey`（聊天归属） | 目标侧缺失（`undefined` / `null` / 空串 / `NaN` / 负数 / 非整数）时从另一侧补齐；**绝不覆盖已有值** | 已有值来自**本地已核实的当前位置 / 归属**，比另一端的滞后副本更可信 |

**一句话**：**进哈希的字段按「谁新谁赢」；不进哈希的字段按「只升不降 + 补空」**（两者并存，不冲突）。

**落点**：`core/floor-cover.js#mergeEntryProvenance`（唯一实现）· `core/cross-sync.js#mergeDataObjects`（同内容哈希分支 + 冲突胜出分支）·
`core/migrate.js#contentDedupeArray`（同内容异 id 去重）。**单测** `tests/unit/entry-provenance-merge.test.js`；
**批次档** `docs/history/P10c41-合并去重不丢溯源标记.md`。

**顺带澄清一个易混点**：本口径**不影响**「同内容异 id 去重」的收敛能力（身份哈希仍是判据，条数语义不变），
只是**存活下来的那一条**要同时继承两侧的标记。`validity: 'inactive'`（情节失效）属于**同一类**非哈希字段，
本轮**未**纳入（登记为后续项）。
