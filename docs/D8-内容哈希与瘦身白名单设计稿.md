**实现里它到底做什么**（`core/slim.js:76-137`）：

| 环节 | 实际行为 | 证据 |
| --- | --- | --- |
| 丢弃 | 无条件丢弃**空值 / 默认值**（`''`/`null`/`[]`/`{}`/`0`/`false`）、丢弃 `extra` 里与顶层重复的槽位、丢弃历史脏数据 `name` 以 `.json` 结尾者 | `:81-85`、`:100-109` |
| **白名单的唯一作用** | **同义字段组**里决定「保留哪一份」：`keeper = 组内第一个在哈希白名单里的字段`，值相同才丢其余 | `:87-99`（写盘）、`:119-129`（读回） |
| 读回 | `hydrateSlimEntry` 用同一 keeper 规则**反向补齐**同义字段（`pathArr`↔`pathStr` 有双向特例），另对 10 个维度做 `name`↔`title` 缺一补一 | `:114-137` |
| 同义组 | 10 维有组（`atoms` text/content、`scenes` 三组、`rumors` 两组…） | `:50-65` |

> **审计结论 F1**：白名单注释「瘦身时**绝不删除**」**与实现不符** —— 非空字段**根本不会被删**（只有默认值被删），白名单实际是「**同义字段 keeper 优先级表**」。
> V1 的实现完全相同（V1 `slimEntryForStorage` 同序逻辑），所以这不是 V2 的移植缺陷，而是**注释一直在误导**。
> **审计结论 F2**：白名单与哈希字段表**两处维护**，已漂移 3 处（上表标注）。当前**无实际后果**（漏项从未被读），
> 但一旦给这些维度加同义组（如 `snapshots` 的 `mind`/`心理`），keeper 选择就会落到非哈希字段上 → **破坏 R3**。
> **审计结论 F3**：真正必须守住的不变量只有一条 —— **同义组 keeper 必须让「瘦身后的哈希 = 瘦身前」**，
> 已由黄金样本 `R3`（`tests/unit/slim-gzip-golden.test.js:159`：`hashKeep.before = hashKeep.after`）强制。

## 4. 决策二：身份哈希 = 「标题 / 日期 / 内容 / 地点（如有）」

### 4.1 四槽位定义

| 槽位 | 含义 | 取值规则 |
| --- | --- | --- |
| **标题** | 人读的短名 | 该维的「名字」字段（`title` / `name` / `subject` …），无则空 |
| **日期** | **剧情日期**（不是现实时间，也不含「时间点」） | `date` 类字段；`time`（早/晚）**不进**；「目标时间」不算发生日期 |
| **内容** | 实质正文 | 该维的正文/描述字段；**结构化子字段按「内容」归并**（见映射表） |
| **地点（如有）** | 发生/所在位置 | 有 `location`/`locations` 的维度才进；无则空 |
| （建议新增）**归属（如有）** | 「这条属于谁」 | 见 Q2：`memories.owner` 若不进哈希，**同一内容记在两个角色名下会被判为同一条**（跨端误合） |
| 兜底 | 四槽位**全空** → 哈希 `''` | 与现状「无分支 → `''`」同义：该维不参与身份判定 |

**归一化必须沿用现状**（`core/model/hash.js:13-19`）：缺失 ≡ `''`、数组缺失 ≡ `[]`、数值缺失 ≡ `0`、布尔缺失 ≡ `false` —— 这是「瘦身/默认值丢弃后哈希不变」的前提（R3）。

### 4.2 逐维槽位映射（建议）

| 维度 | 标题 | 日期 | 内容 | 地点（如有） | 备注 |
| --- | --- | --- | --- | --- | --- |

| 长期记忆 `memories` | `title` | `date` | `content` | — | **`owner` 必须处理**（归属槽 → Q2） |
| 角色档案 `snapshots` | `name` | — | 8 个散文字段全部归并（`identity`/`appearance`/`personality`/`background`/`relationships`/`mind`/`social`/`future`） | `location` | 「内容」= 多个散文块的拼接（顺序固定） |
| 物品 `items` | `name` | — | `desc` | `location` | `qty`/`carried` 是**状态** → 移出 |
| 概念 `concepts` | `name` | `date` | `content` | — | `source`（来源引用）→ 移出 |
| 场景 `scenes` | `name` | — | `desc` | `pathArr`（层级路径）| 场景的「地点」就是它的路径 |
| 计划 `plans` | `title` | — | `content` + `steps`（步骤文本） | — | `targetTime` 是**目标时间**不是日期 → 移出 |

| 传言 `rumors` | `subject` | — | `content` | — | 无日期字段 → 「如有」不适用；`lineage`/`chain` 待定（Q4） |

| 状态记录 `currentStates` | `subject`（+`field` 限定，Q5）| — | `value` | — | `status`（有效/失效）是**状态** → 移出 |
| 关联层 `links` | — | — | — | — | **纯引用型**：四槽位不适用 → Q6（建议保留现「引用型身份」字段集或整维退出身份哈希） |
| 货币 `currencies` | — | — | — | — | **现状本就不参与哈希**（`:61`）→ Q7（是否纳入） |

### 4.3 与现表的差异：**移出身份哈希**的字段（→ 变更哈希候选）

| 字段类别 | 涉及维度 | 移出后的语义 |
| --- | --- | --- |
| `tags` | atoms / memories / items / plans / suspense / concepts / parallels / rumors | 改标签**不再**改变身份（跨端不因标签差异重复；但也不再被识别为「内容更新」） |
| `type` | atoms | 改类型（发现/转折…）不改身份 |
| `time` | atoms / parallels(`at`) | 改时段不改身份 |
| `owner` / `entities` / `characters` | memories / atoms / parallels | **风险**：见 Q2/Q3（跨对象误合） |
| `status` / `phase` / `statusNote` / `progress` / `goalOdds` | states / plans / suspense / parallels | 状态类字段退出身份（改状态不产生新条目） |
| `qty` / `carried` | items | 数量与携带是状态 |
| `objectivity` / `stage` / `ferment` / `media` / `carriers` / `pending` | rumors | 传言的**演化状态**退出身份（同一传言发酵不产生新条目） |
| `gua` / `causalLine` / `promotedTo` | parallels | 推演/转正标记是**机制字段**，退出身份（`promotedTo` 退出需评估，见 Q8） |
| `source` / `memCategory` / `view` / `deviation` / `note` / `kind` / `public` | concepts / memories / links / rumors | 分类与认知标记退出身份 |
| 结构化块（`history` / `chain` / `lineage` / `participants` / `prereq` / `blockers` / `resolveCondition` / `level` / `planner`） | plans / suspense / rumors | 待定：并入「内容」还是移出 → Q4 |

## 5. 决策三：瘦身白名单**与哈希同源**（审计后的明确决策）

| --- | --- | --- |
| **D-S1** | **哈希字段表成为唯一事实源**；瘦身白名单**由它派生**（同源生成，不再手写第二张表） | §2.3 F2：两表已漂移 3 处；同源后不可能再漂移 |

| **D-S3** | 同义组 keeper 加**不变量**并写进测试：① keeper 落在哈希字段集合内；② `hydrate` 能由 keeper **无损重建**组内其它字段（`pathArr`↔`pathStr` 已有双向特例） | §2.3 F3 / R3：`slim-gzip-golden.test.js:159` |
| **D-S4** | 若采纳 Q1 的**双哈希**，keeper 的参照集合 = **身份哈希 ∪ 变更哈希**（并集）；若维持单哈希，则 = 身份哈希 | 保证无论哪种裁决都不破 R3，且不为 keeper 引入新的失败模式 |
| **D-S5** | 补齐审计发现的 3 处漏项（`snapshots.mind/location`、`plans.title/targetTime`、`suspense.title/resolveTime`） | 由 D-S1 自动消解（同源后不再有独立清单） |

> **D-S1 的实际收益**：白名单从「13 维手写清单」变成「从字段元数据派生」，**输出保持逐字节不变**（keeper 结果不变），
> 因此 `slim-gzip-golden` 的 V1 逐项比对**不需要改**（属可安全落地的内部重构）。

## 6. 设计冲突与建议：一种哈希，还是两种？

收窄到四槽位后，「变更类」消费方（§2.2 下半）会**漏检**这些改动：**标签、类型、时段、状态、进度、阶段、载体、链路进度**……

| 方案 | 内容 | 代价 | 影响 |
| --- | --- | --- | --- |
| **甲 · 单哈希（严格照用户口径）** | 所有消费方都用四槽位身份哈希 | 最简 | ① 快照差异**漏检**元数据改动 → 快照「看不出标签改了」；② `atomsSignature` 漏检 → **改标签后分析不再触发时钟同步**（`host/preflight.js:102`） |
| **乙 · 双哈希（建议默认）** | `atomIdentityHash`（四槽位+归属）→ 去重 / 墓碑 / 复活防护 / 控制台；`atomChangeHash`（现逐维字段表）→ 快照差异 / 情节签名 | 多一个纯函数与一处调用点切换 | 身份口径**照用户裁决收窄**，同时**不牺牲**变更检测；黄金样本需分两类登记（`model-golden` 的哈希值按身份口径重算，`slim-gzip-golden` R3 两类都断言） |
| **丙 · 单哈希 + 变更检测另用字段清单** | 身份哈希收窄，快照/签名改用「身份哈希 + 关键元数据字段」的内联拼接 | 拼接逻辑散落在消费方 | 不如乙集中 |

> 三种方案都**不影响**：`DATA_VERSION`（无新字段）、瘦身输出、V1 导入（哈希只在运行时算，不落盘为业务字段——落盘的只有 `it.h` 缓存，可由任一方案重算）。

## 7. 迁移与兼容（无论裁决如何都必须满足）

| 场景 | 要求 |
| --- | --- |
| `it.h` 缓存 | 存的是**上一次算出的哈希**（`core/sweep.js:33`）；口径一变，**首次保存会全量刷新** → 需确认「刷新前后不会误判删除」：`sweep` 用 `prev/cur` 两代索引比对（`:47-62`），口径切换当次可能出现「同一条两条哈希都算过」的过渡 —— 实现轮次须用「同一保存周期内同时认旧新两代哈希」或「先全量重算再比对」的**保守序列**，避免把条目误判为删除（`tombstoneSweep` 会写墓碑）⚠️ |
| 内容墓碑 `deletedH` | 收窄后墓碑**变粗**（同标题+日期+内容+地点的条目一概不复活）→ 这正是「不复活」的强度所在，但**删除后重新提取出同题同日的不同条目**也会被挡住 → 需在 UI/文档明示（Q9） |
| 跨端 | 两端口径必须**同时升级**：一端四槽位、一端旧字段集 → 跨端去重**判不出同一**（会重复累积）。版本兼容策略见 Q9（建议：哈希**带口径版本前缀**，如 `v2:` 前缀，遇到异口径哈希一律跳过内容去重，只按 id 合并） |
| V1 导入 | V1 数据没有 `h`；导入后按新口径重算即可（V1 的字段名与 V2 同构） |
| 黄金样本 | `tests/unit/model-golden.test.js:47`（`atomContentHash` 逐字比对 V1）必须按 B5 **登记为有意偏离**并改为「归一化后比对」；`slim-gzip-golden` R3 保持（两类哈希都要满足瘦身不变） |
