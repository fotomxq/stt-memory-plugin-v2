## 0. 一页摘要

**问题**：14 个大类今天靠**各自的私有字段**互相引用，关系只有一个「谁知道」的窄层（且只连角色、只覆盖 4 维）；「约束」则完全不是数据 —— 除 60 字的自由文本 `constraintNote` 外，约束只存在于提示词与代码分支里，**不能积累、不能校验、不能驱动演化**（D1 §3、§4）。

**主张**：在维度之下加一层**边 + 约束**的显式数据（本文称「关系约束层」）：

1. **边（relations）**：统一的原子引用 `{dim, id}` 为端点，表达「知情 / 因果 / 先后 / 归属 / 位置 / 隶属 / 来源 / 矛盾 / 互斥 / 镜像」等**有类型的连接**；
2. **约束（constraints）**：在边与原子之上表达**规则**，「谁知道 / 什么必须先于什么 / 什么不许同时成立 / 下一步更可能怎样」，带严重度、作用域、剧情时间窗与生命周期；
3. **三条用途**：**注入**（规范 AI 生成，机械、确定性）· **校验**（规范落库，检出幻觉与倒挂）· **演化**（规范推演，让传言 / 平行 / 时钟 / 遗忘读约束而不是只读标签相似度）。

**兼容优先**：`state.links` 与各维度现有引用字段**一律保留**，RCL 先做**只读派生 + 新增容器**，不要求任何数据迁移（阶段 S0/S1 可零风险上线）。

**建议的第一步**（若只做一件事）：**S0 只读派生 + 冲突清单** —— 不动数据模型、不改注入字节，就能让用户第一次看到「系统认为哪些关系成立、哪些互相矛盾」。

## 3. 数据模型（v0.1）

### 3.1 统一原子引用 `AtomRef`

```text
AtomRef = { dim: string, id: string }        // dim 取 DIMENSIONS[].kind（14 类之一）
```

- 全层唯一寻址方式；替代今天「某维度专用引用字段 + 隐式约定」。
- 特殊端点：`to.who`（角色名）用于表达「与某个自然人有关」而该角色暂无档案条目 —— 与 `links.who` 同名同义，保证兼容。

### 3.2 边容器 `state.relations[]`

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | string | 稳定 id（见 §3.4），跨端去重键 |
| `from` | AtomRef | 起点（主体） |
| `to` | AtomRef 或 `{who}` | 终点（客体）；两者互斥 |
| `type` | enum | 关系类型（下表） |
| `how` | enum? | 细分方式（沿用 `links.how` 词表：亲历/目击/被告知/推断/传闻/策划/参与/当事人/在查…） |
| `public` | bool | 是否为公开信息（沿用锚行语义） |
| `deviation` | enum? | 认知偏差（沿用 `links.deviation`） |
| `at` | string? | 关系成立的**剧情日期** `YYYY-MM-DD` |
| `strength` | number | 0–1，随剧情时间衰减（复用 `calcTimeDecay`） |
| `status` | enum | `active` / `expired` / `retracted` |
| `source` | enum | `ai` / `mech` / `manual` / `inferred`（**分源标记是防幻觉的关键**） |
| `evidence` | object | `{ floorStart, floorEnd, date, quote? }` —— 事实锚点，便于回查 |
| `note` | string | 备注（上限与维度一致） |
| `updatedAt` | number | 真实墙钟时间戳（非剧情时间） |

**关系类型词表（v0.1，10 类）**：

| type | 语义 | 典型端点 | 今天由什么表达 |
| --- | --- | --- | --- |
| `knows` | 谁**知道**某原子 | 原子 ↔ 角色 | `links`（`how` / `deviation` / `public`） |
| `knows-not` | 谁**明确不知情** | 原子 ↔ 角色 | `links.deviation = unaware` / 无关联（隐式） |
| `caused` | 因果：A 导致 B | 原子 ↔ 原子 | 散落的 `sourceRefs` / `causalLine` 文本 |
| `before` | 时序：A 先于 B（非因果） | 原子 ↔ 原子 | 剧情日期 + `atomTimeKey` 排序（隐式） |
| `co-occur` | 同场：A 与 B 同时同地 | 原子 ↔ 原子 | `location` + `date` + `characters`（隐式） |
| `owns` | 归属：角色/原子持有某物或额度 | 角色 ↔ 物品/货币 | `owner` / `carried` |
| `located-at` | 位置：原子发生在某场景 | 原子 ↔ 场景 | `location` / `pathArr` |
| `member-of` | 隶属：原子属于某计划/悬念/概念 | 原子 ↔ 原子 | `planRef` / `suspenseRef` / `conceptRef` / `memRefs` |
| `derived-from` | 来源：由 X 派生（含转正 / 裂变 / 分段 / 总结） | 原子 ↔ 原子 | `promotedTo` / `splitFrom` / `mergedSummary` / `plotSegments.atomIds` |
| `mirrors` | 镜像：平行事件 ↔ 现实事件 | 原子 ↔ 原子 | `rumors.parallelRefs` / 平行事件与情节的标签关联（隐式、不可靠） |

> 矛盾类关系（`contradicts` / `exclusive-with`）**不**放进 `relations`，而是由约束表达（§3.3）—— 它们描述的是「不许同时成立」，属规则而非事实。

### 3.3 约束容器 `state.constraints[]`

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | string | 稳定 id（见 §3.4） |
| `kind` | enum | 约束类型（下表） |
| `subject` | AtomRef / `{who}` / `{dim, tag}` | 约束主体（可指向原子、角色或「某一类」） |
| `target` | 同上? | 约束客体（互斥、因果等双元约束使用） |
| `params` | object | 类型专属参数（如 `{ rounds: 3 }` / `{ cap: 12 }` / `{ weight: 0.7 }`） |
| `severity` | enum | `hard`（不得违反）/ `soft`（倾向 / 加权） |
| `weight` | number | 0–1，软约束的强度 |
| `scope` | object | `{ dims: [], tags: [] }` —— 作用范围（便于批量约束） |
| `time` | object | `{ from, to }` 剧情日期窗口（约束的有效期） |
| `status` | enum | `pending` / `active` / `expired` / `violated` / `retracted` |
| `pending` | object? | `{ need, progress, target }` —— **延迟生效**，语义复用传言既有机制 |
| `source` | enum | `ai` / `mech` / `manual` / `inferred` |
| `evidence` | object | 同边（锚点） |
| `note` | string | 备注 |
| `updatedAt` | number | |

**约束类型词表（v0.1，9 类）**：

| kind | 语义 | 例子 | 用途 |
| --- | --- | --- | --- |
| `knowledge` | 知情边界 | 「A 尚未得知计划 P」 | 注入 · 校验 |
| `causal` | 因果先决：B 不得先于 A 发生 | 「必须先拿到钥匙，才能打开仓库」 | 校验 · 演化 |
| `temporal` | 时间先后 / 共现窗口 | 「这两件事不能在同一天」 | 校验 · 时钟 |
| `existence` | 存在 / 缺失 / 失效 | 「X 在第 12 楼之后不应再出现」 | 校验 · 遗忘 |
| `exclusivity` | 互斥：不得同时成立 | 「若走了分支甲，则分支乙作废」 | 校验 · 平行 |
| `identity` | 身份一致性 | 「同一角色的状态与档案不得矛盾」 | 校验 |
| `resource` | 额度 / 数量上限 | 「货币额度不得超过 N」 | 校验 |
| `evolution-bias` | **演化倾向**：加权 / 优先 / 降低可能 | 「这条传言在码头一带更易发酵」 | 演化 |
| `propagation` | 传言传导规则 | 「只能经『被告知』传播，不得凭空扩散」 | 演化 |
| `protection` | 保护标记：禁止合并 / 删除 / 覆盖 | 「这条情节是主锚点，不可淘汰」 | 遗忘 · 修复 |

> `hard` + `knowledge` / `causal` / `exclusivity` 是「规范剧情」的硬边界；`soft` + `evolution-bias` / `propagation` 是「引导剧情」的软倾向。**两者必须分开**，否则要么约束不住、要么把剧情锁死（见 Q3）。

### 3.4 稳定 id 与去重键

| 对象 | 去重键 | 理由 |
| --- | --- | --- |
| 边（事实） | `hash(type + from.dim + from.id + to + how)` | 同一条关系重复出现时收敛为一条（沿用 `links` 的稳定 id 思路） |
| 约束（规则） | `hash(kind + subject + target)` | 同一规则的多次观察收敛为一条；`pending` 的进度不参与 id |

两端独立演化时，同 id 视为同一条 → 跨端合并天然收敛（与 `links` 的跨端口径一致）。

### 3.5 与既有容器的关系（兼容策略）

| 既有物 | RCL 中的角色 | 阶段 1 处理 |
| --- | --- | --- |
| `state.links[]` | `type = knows` 的**只读投影源** | **不迁移**；RCL 读它、不写它（继续由 `upsertRelLinks` 写） |
| 各维度私有引用字段（`sourceRefs` / `planRef` / `owner` / `location` / `parentSceneId` …） | 边的**机械派生来源** | 不迁移；派生带 `source: 'mech'`，与手工边区分 |
| `constraintNote`（60 字自由文本） | 过渡期的自由约束 | 保留；RCL 可将其显式化为 `causal` / `evolution-bias` |
| `rumors.pending` | 延迟生效的**原型** | 语义被 `constraints.pending` 复用（同一套「N 轮才提交」口径） |
| 提示词模板里的「硬性约束」条文 | 人工口径 | 保留（软约束的自然语言面） |

### 3.6 新增容器的接线清单（**必须一次性齐活，否则数据会丢**）

按 `links` 的先例（D1 §2.1），任何进入原子层的容器都必须同时接线 6 处：

1. 常量与维度表：`core/constants.js`（`DIMENSIONS` / `ATOM_DIM_KEYS` / `STATE_KEYS`）；
2. 归一化：`core/model/`（新文件，参照 `rel.js` 的纯函数风格）；
3. 内容哈希投影：`core/model/hash.js`（**注意：哪些字段进哈希要显式决策** —— 引用类字段今天不进，规则类字段若也不进，则约束变更不触发快照）；
4. 瘦身白名单：`core/slim.js`（`SLIM_HASHED_FIELDS` + 同义字段组）；
5. 结构迁移与去重：`core/migrate.js`、`core/merge.js`（墓碑 + 逐条合并）；
6. 跨端：`core/cross-sync.js`（`dataAggHash` / 逐条合并 / 条目计数）+ `DATA_VERSION` 递增（`core/constants.js:16`）。

> 建议：`relations` 与 `constraints` 作为**两个**容器（而不是一个大容器），因为它们的合并语义不同 —— 边是「事实」，约束是「规则」（冲突解决策略不同，见 §4.3）。

## 4. 生命周期

### 4.1 状态机

```text
生成(source)  →  pending（可省）  →  active  →  expired（时间窗结束 / 强度衰减到阈值）
                                        ↘  violated（被校验判定违反，仅 hard 约束）
                                        ↘  retracted（人工撤销 / 主体被删除）
```

- **生成**：`mech`（机械派生，零 AI）· `ai`（窄契约产出）· `manual`（界面）· `inferred`（保守推断，优先被覆盖）。**分源标记不可丢** —— 它决定冲突时的优先级与界面上的可信度提示。
- **延迟生效**：`pending{need, progress, target}`，每过一轮 `progress+1`，达 `need` 提交为 `active`（口径与传言 `rumorChangeNeedRounds` 一致 —— D1 §3.2）。
- **衰减**：`strength` 按**剧情时间**衰减（复用通用时间衰退）；`scope`/`time` 之外的约束自动 `expired`。
- **上限**：两个容器各自条数上限（建议与维度同级可配），超出按「`source` 权重 → `strength` → 时间新」保留。

### 4.2 校验（可判定子集）

只做**局部可判定**的检查（守则 N1），每条输出 `finding`：

| 检查 | 判据 | 例 |
| --- | --- | --- |
| 知情违反 | 文本/条目引用了某原子，但 `knows-not` 或不存在 `knows` 边（且非公开） | 角色 A 说出了只有 B 知道的秘密 |
| 因果倒挂 | `caused` 边的两端剧情时间次序相反 | 结果早于原因 |
| 互斥同真 | 两条 `exclusivity` 约束的 subject 同时 `active` | 两个平行分支同时转正 |
| 时间越界 | 原子日期落在 `temporal` / `existence` 约束的禁区 | 「第 12 楼后不应再出现」却出现了 |
| 身份矛盾 | 同一角色的状态 / 档案 / 关系互相冲突 | 已去世角色仍在场 |
| 额度越界 | `resource` 约束被突破 | 货币额度超上限 |

`finding` 形状：`{ id, severity, kind, subject, target, message, evidence }` —— 只报告，不改数据；供「设定 → 约束」与调试页展示。

### 4.3 冲突解决（同一 subject + kind 出现多条时）

优先级（草案）：`severity: hard > soft` → `source: manual > ai > mech > inferred` → `updatedAt` 更新者 → **保守合并**（不确定就不合并，保留两条并报告冲突）。

> **完整裁决链已独立成稿**：`docs/D5-关系层优先级与悖论防护设计稿.md` —— 五级链 **L0 删除恒胜 → L1 强度/状态 →
> L2 来源 × 维度权威序 → L3 剧情时间 → L4 内容哈希字典序（禁止「本地/远端优先」）→ 兜底保留双条 + 标记**，
> 并含边的方向归一（对称边 canonical 化）、六项悖论检测与传播单调性三律。**本节以 `D5` §2 为准。**

## 5. 三条用途

### 5.1 注入：约束段分区升级（T6 前提，S2）

现状是一个「【注入约束】」整段（D1 §3.1）。升级为**分区段**，每区只出有内容的：

```text
【注入约束】（硬约束，优先级高于上文任何区块）
1. 当前在场：…
2. 知情边界：…（逐条点名 / 聚合计数，沿用现状口径）
3. 因果与先后：…（B 尚未发生，不得先于 A 引用）
4. 禁止与互斥：…（不得同时成立）
5. 演化倾向：…（软引导，若开启）
```

**机械不变量**（必须守住，否则回归「不可预测的注入字节」）：零 AI、排序稳定（`severity → kind → id`）、字符上限沿用 `injectConstraintMaxChars`、超限整段降级、位置沿用 tail/head 开关、约束段预算预留比例不变。

### 5.2 校验：落库前后各一次（T4，S3）

- **落库后**（提取 / 修复管道）：`mech` 派生 + 校验 → `finding` 进质检报告与调试页；仅对 `hard` 且高置信的项提示，不自动删改（N4）。
- **落库前**（若引入 AI 产出约束）：检查 AI 给的 `evidence` 是否指向真实楼层/原子，不满足则拒收该条（防幻觉）。

### 5.3 演化：用约束规范剧情（T5，S4 —— 用户诉求的核心）

| 引擎 | 今天依据什么 | RCL 之后 |
| --- | --- | --- |
| 传言机械演化 | 载体耐久、发酵度、**与平行事件按标签 Jaccard 联动**、种子概率 | 传导走 `propagation` + `knows` 边（谁能传给谁）；联动改读 `mirrors` / `member-of` 边；`evolution-bias` 调整发酵与裂变概率权重 |
| 平行事件推演 / 推进 | AI 产 `goalOdds[].likelihood`；`sourceRefs` 限已成事实 | `goalOdds` 受 `evolution-bias` 加权；转正前用 `causal` / `exclusivity` 校验；`mirrors` 边保持与现实线一致 |
| 时钟提取 / 巡检 | 只取最新情节 + 日期异常判据 | 日期判据形式化为 `temporal` 约束（可解释、可审计） |
| 遗忘 / 衰退 | 时间衰退 + 上限 | `protection` 约束阻止删除主锚点；`existence` 约束表达「该消失的必须消失」 |

> **关键原则**：约束只**改变权重与准入**，不直接改写内容；所有演化结果仍落回原维度条目（用户可见、可编辑）。
>
> **传播（联动）不在本文范围**：谁变了、谁该跟着变、如何留痕与终止，见 `docs/D4-原子关系层联动设计稿.md`
> （本文的 `relations` / `constraints` 是其数据基础；`D4` 的 R0–R2 阶段不需要改本文的数据模型）。

## 6. 分阶段落地

| 阶段 | 范围 | 动数据模型 | 交付 | 回退 |
| --- | --- | --- | --- | --- |
| **S0** | **只读派生 + 冲突清单**：从既有 `links` 与各维度私有引用机械派生边与约束，**只算不存**，进调试页 / 设定页只读区 | 否 | 用户第一次看到「系统认为哪些关系成立、哪些互相矛盾」 | 关开关即消失 |
| **S1** | 修 G1（开关键名统一 + 界面入口） | 否 | 关联层真正可关；两键归一 | 恢复旧键 |
| **S2** | `relations` / `constraints` 两容器落地 + 迁移 + **6 处接线** + 注入约束段分区升级 | 是（`DATA_VERSION+1`） | 约束成为数据、注入段可解释 | 容器可为空 → 行为退化到现状 |
| **S3** | 校验落地（§5.2）：finding 清单进质检与调试页 | 否 | 幻觉与倒挂可见 | 关校验即无影响 |
| **S4** | 演化接线（§5.3）：传言 / 平行 / 时钟 / 遗忘 | 否 | 「用约束规范剧情演化」真正生效 | 逐引擎开关 |
| **S5** | UI：「设定 → 约束」扩展（约束清单 / 编辑 / 冲突面板 / 关系总览增强） | 否 | 可看可改 | 隐藏入口 |
| **S6** | 跨端逐条合并 + 快照 + 聚合指纹 | 否 | 多端收敛 | — |

> **每阶段的验收口径**：该阶段必须能**独立交付且可单独回退**；S2 起每次改数据模型都必须过 `git archive` 归档级复跑（守则 §3.2）。

## 7. 风险与对策

| # | 风险 | 对策 |
| --- | --- | --- |
| R1 | **AI 幻觉约束**：模型编造「不许发生」 | `evidence` 强制锚点 + 校验拒收 + 默认**不开** AI 写约束（Q4）+ 界面按 `source` 区分可信度 |
| R2 | **约束膨胀**：每条楼都产出约束 | 稳定去重键 + 条数上限 + 时间衰减 + `scope` 批量归并 |
| R3 | 与 `links` 语义重复、两套真相 | 阶段 1 只读投影、单一写入口；若 Q1 选「取代」则需一次性迁移与黄金样本重制 |
| R4 | **性能**：每次渲染全图遍历 | 线性扫描 + 轻索引（按 `from`/`to` 建 Map，惰性构建）+ 上限（沿用既有 200 行护栏口径） |
| R5 | 跨端漂移 / 复活 | 稳定 id + 墓碑 + 逐条合并（与 `links` 同口径） |
| R6 | 黄金样本与门禁冲击 | 不改 V1 oracle；新容器一律按「有意偏离」在测试显式归一 + 文档登记（守则 §4） |
| R7 | 把剧情锁死（硬约束过多） | 硬 / 软分离 + `severity` 默认 `soft` + UI 明示「硬约束会显著限制 AI」 |
| R8 | 约束与维度的模板文案冲突 | 注入段由 RCL 统一生成，提示词模板只保留口径描述，不重复列举规则 |

## 8. 待用户裁决（Q1–Q8，含建议默认）

| # | 问题 | 建议默认 | 影响 |
| --- | --- | --- | --- |
| Q1 | 关系层是否**物理取代** `links`？ | **不取代**（只读投影；Q1 保持兼容） | 取代 = 大迁移 + 黄金样本重制；不取代 = 两容器长期共存 |
| Q2 | 边的端点粒度：原子↔原子 / 原子↔角色 / 角色↔角色 都要吗？ | **前两者要，角色↔角色 暂不做** | 角色↔角色（如亲属 / 敌对）今天已在档案 `relationships` 里 |
| Q3 | 演化用**硬禁止**还是**概率偏置**？ | **默认软**（`severity: soft`），硬约束由用户显式开启 | 硬约束多 → 剧情可预测但呆板；软约束多 → 灵活但引导弱 |
| Q4 | AI 可以直接写约束吗？ | **默认否**（先只 `mech` 派生 + 人工） | 开启需先有 evidence 校验与拒收（R1） |
| Q5 | 首个试点域选哪个？ | **传言**（已有 `pending` / 传导链 / 联动，最接近 RCL 语义） | 试点域决定 S4 的顺序 |
| Q6 | 约束要不要在 UI 里可编辑？ | **要**（S5；先只读） | UI 工作量集中在 S5 |
| Q7 | 各维度私有引用字段要**逐步统一**到 `relations`，还是永久共存？ | **逐步统一写入口，读路径保留** | 统一 = 长期简洁；共存 = 短期安全 |
| Q8 | RCL 是否跨角色共享（当前 `state` 按角色隔离）？ | **按角色隔离**（与现状一致） | 跨角色共享涉及存储与隐私边界，另议 |

## 10. 名词表

| 名词 | 含义 |
| --- | --- |
| 原子（atom / 条目） | 14 个维度里的一条记录（情节 / 记忆 / 角色 / 物品 / 计划 / 悬念 / 场景 / 概念 / 平行事件 / 状态 / 货币 / 分段 / 传言 / 关联行） |
| 边（relation） | 两个端点之间的**事实**连接（谁知道 / 因果 / 归属 / 位置…） |
| 约束（constraint） | 关于边与原子的**规则**（不得违反 / 倾向 / 禁止合并…） |
| 硬约束 / 软约束 | 校验上「不得违反」/ 演化上「加权引导」 |
| 派生（derive） | 由既有数据机械推出边或约束（`source: mech`），零 AI |
| 冲突（finding） | 校验发现的矛盾项（只报告，不改数据） |
| `pending` | 延迟生效：需 N 轮后才提交的变化（沿用传言口径） |
