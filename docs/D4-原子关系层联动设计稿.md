# D4 · 原子关系层联动设计稿（Ripple：一处变动 → 跨大类迭代）

> 文档版本：v0.1 ｜ 日期：2026-09-27 ｜ 类型：**设计稿（不发版）** ｜ 状态：草稿（待评审）
> 触发（用户原话）：「原子关系层继续优化，将各大类都能稳定串接到一起，当一处发生变动，联动发生改变。例如情节已发生的，平行和传言都应该迭代。」
> 前置：`D1`（现状与缺口 G1–G9）、`D2`（边 + 约束的数据模型）、`02-数据架构` §4、`04-应用架构` §3
> 分工：**D2 定义「数据」**（谁知道谁、什么必须成立）；**本文定义「传播」**（谁变了 → 谁该跟着变）。

## 0. 一页摘要

**现状**：全仓库只有 **3 处硬编码级联** 与 **1 处单向启发式联动**：

| 现有联动 | 机制 | 落点 |
| --- | --- | --- |
| 删除条目 → 清关联行 / 依赖该角色的状态 | 硬编码 | `core/entries.js:121/123/132` |
| 条目合并 → 引用改挂保留条（`retargetRelRefs`） | 硬编码 | `core/entries.js:158-159` |
| 平行事件转正 → 写情节 + 移除平行条（留墓碑） | 硬编码 | `core/parallel.js:510-548` |
| 传言演化 → 按**标签相似度**找平行事件 → 发酵/消退/推动 | 启发式、单向、只在传言引擎 tick 时发生 | `core/rumor-evolve.js:152-195` |

**缺口**：没有**变更事件**、没有**反向索引**（「谁依赖我」）、没有**联动规则表**、没有统一的**幂等与终止约定**。
所以今天做不到「一处变动、跨类迭代」——而且同一类变动在不同路径下行为还不一致（删除走级联、修改什么都不走）。

**主张**：在 D2 的边 / 约束之上补**第三层能力 = 传播（Ripple）**，由三个基础件 + 一个引擎构成：

1. **变更事件**（发生了什么：新增 / 更新 / 合并 / 转正 / 失效 / 删除 / **确认已发生** / 时钟推进）；
2. **反向索引**（谁依赖我）：由既有引用字段与 D2 的边**派生**（不要求迁移）；
3. **联动规则表**（谁该怎么变）：源事件 × 依赖边 → 目标动作（重算 / 标记 / 收敛 / 留痕），带强度与「机械 or AI」；
4. **传播引擎**：求依赖闭包 → 应用规则 → 先算后写 → 留痕 → 若有新事件再走一跳，**有界、幂等、无随机**。

**建议第一步**：**R0 只读影响面** —— 不改任何数据，先让用户看见「这条改了，谁会受影响」，再谈自动联动。

## 1. 目标 / 非目标

### 1.1 目标

| # | 目标 | 对应诉求 |
| --- | --- | --- |
| T1 | **稳定串接**：14 个大类能互相寻址与反查（不再依赖各自私有字段的隐式约定） | 「将各大类都能稳定串接到一起」 |
| T2 | **一处变动 → 依赖方迭代**：确认 / 失效 / 删除 / 合并 / 转正 / 时钟推进都触发一致的传播 | 「当一处发生变动，联动发生改变」 |
| T3 | **可追溯**：每次联动都留下「谁因谁而变」的记录，用户可查 | 「稳定」的可解释性 |
| T4 | **确定性 + 幂等 + 有界**：两端各自传播得到同结果；重复执行不叠加；有跳数/条目/耗时上限 | 跨端收敛 + 防风暴 |
| T5 | **受约束**：传播不得违反 D2 的 `hard` 约束（互斥、因果、知情边界） | 与 D2 分工 |
| T6 | **零 AI 优先**：机械能做的先做；只有「需要改写文本」的动作才考虑 AI（且需开关 + 证据） | 成本与可预测性 |

### 1.2 非目标

| # | 非目标 | 理由 |
| --- | --- | --- |
| N1 | 事件总线 / 持久消息队列 / 常驻定时器 | 插件形态不允许；传播只在既有触发点同步跑完 |
| N2 | 通用规则引擎 / 用户自定义 DSL | 复杂度失控（同 D2 N1） |
| N3 | 自动**删除**用户数据 | 只做标记与收敛；删除仍由人工或既有修复管道 |
| N4 | 跨角色传播 | `state` 按角色隔离（D2 Q8 同口径） |
| N5 | 把「传播」做成第二套业务逻辑 | 传言 / 平行 / 遗忘的**演化算法不动**，Ripple 只负责**触发、收窄与留痕** |

## 2. 三个基础件

### 2.1 变更事件 `ChangeEvent`

| 字段 | 说明 |
| --- | --- |
| `dim` / `id` | 变更主体（`AtomRef`） |
| `op` | `add` / `update` / `merge` / `promote` / `invalidate` / `delete` / **`confirm`**（确认为已发生） / `clock`（时间推进） |
| `at` | **剧情时间**（`state.state.date`），不是墙钟 |
| `floor` | 触发楼层（可空） |
| `source` | `ai` / `mech` / `manual` |
| `prevHash` / `nextHash` | 内容哈希前后值（用于判定「真的变了」） |
| `seq` | 本轮传播内的序号（**运行期概念，不落库**） |

- **来源**：提取落库差异（`core/ingest.js#mergeDelta` 前后对比）、修复 / 合并管道、平行转正、删除、遗忘、时钟推进、人工编辑；
- **不新增容器**：事件是**运行期产物**（R0/R1）；需要留痕时写目标条目既有的留痕字段（§2.4）。

### 2.2 反向索引（「谁依赖我」）

今天全仓库**没有任何** dependents 查询（`D1` §2.3）。索引由两类来源**派生**：

| 来源 | 例 | 现状落点 |
| --- | --- | --- |
| **显式引用字段** | `parallels.sourceRefs` / `previews`、`plans.atomRefs` / `suspenseRefs` / `memRefs`、`suspense.*`、`rumors.splitFrom` / `parallelRefs`、`scenes.parentSceneId` / `pathArr`、`items.location`、`memories.owner`、`links`（锚行的 `atomRef` / `planRef` / `suspenseRef` / `conceptRef` / `memRefs` / `sourceRefs`） | `core/model/dims.js:126-131`、`:203-205`、`:246-248`、`core/model/rel.js:45-50` |
| **隐式关系** | `links` 的 `knows`（原子 ↔ 角色）、`rumors.subject/content` 的实体命中、D2 的边（`caused` / `mirrors` / `member-of` / `derived-from` …） | `core/model/rel.js:27-51`、`D2` §3.2 |

**稳定性要求**（对应「稳定串接」）：

1. **稳定 id**（`D2` §3.4）：同内容两端派生出同 id，索引才可比；
2. **悬空引用可检测**：孤儿报告已有口径（`relOrphanStats`，`core/model/rel.js:96-115`）→ 扩展为「全类型死链清单」；
3. **惰性构建 + 上限**：按需构建、缓存到 `state` 变更代数（generation）失效；单次扫描上限（沿用 200 行护栏口径）；
4. **不要求迁移**：索引是**派生视图**，不落库、不改现有字段。

### 2.3 联动规则表（「谁该怎么变」）

规则形状：

```text
Rule = {
  from:  { dim, op, when? }        // 源事件（when = 可选条件，如「该平行条目的目标已发生」）
  edge:  [边类型]                   // 依赖必须成立的边（D2 词表）
  to:    { dim }                    // 目标维度
  effect: 'recompute' | 'narrow' | 'mark' | 'dissolve' | 'advance' | 'annex'
  scope:  'item' | 'dim'            // 单条 or 全维（如时钟推进）
  engine: 'mech' | 'ai'             // 默认 mech；ai 需显式开关
  trace:  'chain' | 'history' | 'previews' | 'statusNote'
  strength: 0-1
}
```

**effect 词表**：

| effect | 含义 |
| --- | --- |
| `recompute` | 用新事实重算派生量（概率 / 进度 / 评分） |
| `narrow` | 收窄候选（平行目标减少、传播链收束） |
| `mark` | 标记为「受影响 / 待复核」（不改正文） |
| `dissolve` | 因互斥或已发生而**作废**（标记，不删除） |
| `advance` | 推进状态机（传言阶段、计划进度、悬念层级） |
| `annex` | 追加留痕（链路 / 进展 / 预演） |

### 2.4 留痕（复用既有字段，不新造）

| 目标 | 载体 | 现状 |
| --- | --- | --- |
| 传言 | `chain[]`（传导链路） | `core/model/rumor.js:34`、`:201` |
| 计划 / 悬念 | `history[]`（进展） | `core/model/dims.js:202`、`:245` |
| 平行事件 | `previews[]`（预演） | `core/model/dims.js:127` |
| 其它 | `statusNote` / `note` | 各维度归一 |

> R1 先复用这三套载体（它们的上限与归一已存在）；若后续需要**统一可查的变更史**，再在 R2 评估单一 `revisions` 容器（见 Q5）。

## 3. 传播引擎（Ripple）

### 3.1 触发点（全部是既有同步点，不新增常驻任务）

| 触发点 | 说明 |
| --- | --- |
| 提取落库后 | `host/extract.js` 的 `mergeDelta` 成功处（已有被动调度：`scheduleParallelWeave` / `scheduleAtomCompact`，`host/extract.js:11-12`） |
| 修复 / 合并后 | 各 `*-repair.js` 收尾（`retargetRelRefs` 已有先例） |
| 平行转正后 | `core/parallel.js#promoteParallelEvent` |
| 删除后 | `core/entries.js#deleteEntry` 的级联段 |
| 时钟推进后 | 时钟落盘处（`core/clock*.js`） |
| 人工动作 | 面板按钮（复用同一入口） |

### 3.2 一轮传播的算法（语义，非实现步骤）

```text
队列 = 本轮事件
已处理 = {}                      # dim|id|op → 已应用
while 队列非空 and 跳数 < D上限 and 动作数 < N上限:
    事件 = 队列.shift()
    if 已处理[事件]:  continue
    依赖 = 反向索引(事件)          # 谁引用 / 谁与之有边
    动作 = 规则表.匹配(事件, 依赖)  # 去重合并同类动作
    先算后写: 全部动作在副本上求值 → 通过 hard 约束校验 → 一次性应用
    留痕(动作)                     # chain / history / previews
    队列 += 由动作产生的新事件      # 例如「平行 dissolved」不再产生新事件
```

### 3.3 引擎不变量

| # | 不变量 | 说明 |
| --- | --- | --- |
| I1 | **幂等** | 同一事件 + 同一状态 → 同一结果；「已处理」集合保证不重复叠加 |
| I2 | **确定性** | 禁止 `Math.random`；必须随机的场景沿用种子哈希口径（`rumorRoll`，`core/rumor-evolve.js:86`），保证两端一致 |
| I3 | **有界** | 跳数上限 D、动作数上限 N、单轮耗时上限；超限**如实记录**并停止（不静默丢） |
| I4 | **先算后写** | 全部动作在副本上求值并过 `hard` 约束校验后一次性应用（失败即整轮放弃） |
| I5 | **可回退** | 单轮前后可落快照（复用快照链）；用户可撤销一轮联动 |
| I6 | **零 AI 优先** | `engine: 'mech'` 的动作不调 AI；`ai` 动作受总开关 + 证据锚点约束 |

### 3.4 与既有引擎的职责划分

| 引擎 | 谁触发 | 负责什么 | 不负责什么 |
| --- | --- | --- | --- |
| **Ripple**（本文） | 变更事件 | 找依赖、判定影响、触发下游、留痕 | **不重写**传言/平行/遗忘的业务算法 |
| 传言演化 | Ripple 或每 N 楼 | 发酵 / 消退 / 裂变 / 传导链 | 不知道「哪条情节已发生」 |
| 平行推演 | Ripple 或用户 | 目标概率、预演、转正 | 不判断现实事实 |
| 遗忘 / 时间衰退 | 管线或载入 | 老化与移除 | 不管依赖关系 |

> 一句话：**Ripple 只决定「该不该动、动谁」，具体怎么动仍归各域引擎。**

## 5. 示例走查：情节已发生，平行与传言迭代

> 场景：情节 `a1`「木箱已到手」（`date=1919-11-20`）落库；平行事件 `p1`「木箱被第三方拿走」；传言 `r1`「听说木箱被第三方拿走了」。

| 步 | 发生什么 |
| --- | --- |
| ① 事件 | `mergeDelta` 落库差异产出 `{dim:'atoms', id:'a1', op:'confirm'}`（`D2`：有 `date` 且 `validity=active` 即「已发生」——见 Q2） |
| ② 反查 | 反向索引命中：`p1.sourceRefs` 含 `a1`；`r1.subject/content` 含「木箱」且 `r1.parallelRefs` 含 `p1` |
| ③ 约束校验 | `exclusivity` 约束（`D2` §3.3）判定 `p1` 与 `a1` 互斥 → `p1` 允许 `dissolve` |
| ④ 动作 | `p1`：`narrow`（目标概率整体下调）+ `dissolve`（标记作废，**不删除**）+ `previews` 追加「因『木箱已到手』已发生而作废」；`r1`：客观性 → 证实、`ferment −25`、阶段推进、`chain` 追加 `{kind:'证实', from:'a1', note:…}` |
| ⑤ 下一跳 | `p1` 的作废不需要新事件（注入侧已有过滤口径）；`r1` 的传闻若曾推动过 `p1`，其 `chain` 中已有的「联动」记录保留，形成完整因果链 |
| ⑥ 注入 | 下一轮注入重算（既有机制）；`D2` §5.1 的「禁止与互斥」分区会自动反映 `p1` 的状态 |
| ⑦ 用户可见 | 平行页该条显示「已作废（因情节『木箱已到手』）」；传言页链路新增一笔「证实」；若不满意可撤销该轮联动（快照回退） |

## 6. 分阶段落地

| 阶段 | 范围 | 动数据模型 | 交付 | 回退 |
| --- | --- | --- | --- | --- |
| **R0** | **只读影响面**：由反向索引算出「这条变了，谁会受影响」，在「设定 → 约束」与调试页展示；**不改任何数据** | 否 | 用户第一次看见跨类依赖；验证索引正确性 | 关开关即消失 |
| **R1** | **机械联动**：实现 §4 关键行（`atoms.confirm → parallels/rumors/plans`）+ 幂等/有界 + 留痕 | 否（复用既有字段） | 「情节已发生 → 平行与传言迭代」真正生效 | 逐规则开关 |
| **R2** | **反向索引与引用完整性**：索引缓存、全类型死链清单、孤儿/悬空引用进质检 | 否 | 「稳定串接」可度量 | 仅报告 |
| **R3** | **受约束的 AI 迭代**：只对需改写文本的目标启用（传言说法、平行描述），带证据锚点与 hard 约束校验 | 否 | 迭代质量提升 | 总开关（默认关） |
| **R4** | **UI**：变更溯源视图（谁因谁而变）、影响面预览、联动开关与频率上限 | 否 | 可解释、可控 | 隐藏入口 |
| **R5** | **跨端一致**：联动留痕参与哈希 / 逐条合并（`chain` / `history` / `previews` 已在瘦身白名单内） | 否 | 两端收敛 | —— |

> **注意 R5 的前置**：`chain` / `history` / `previews` 目前**已参与内容哈希**（`core/slim.js:30-46`），
> 因此联动会改动内容哈希 → 触发跨端「同 id 取更新」路径。这是**期望行为**，但需在 R1 的测试里显式断言（否则会被当成「同步抖动」）。

## 7. 风险与对策

| # | 风险 | 对策 |
| --- | --- | --- |
| R1 | **级联风暴**（一次提取触发大量迭代） | 只在**强事件**（`confirm` / `delete` / `promote`）传播；跳数 / 动作数 / 耗时上限；同类动作合并 |
| R2 | **循环依赖** | 「已处理」集合（`dim|id|op`）+ 深度上限；环上动作只应用一次 |
| R3 | **跨端不一致** | 禁随机（I2）；依赖稳定的边 id 与排序（`D2` §3.4） |
| R4 | 与既有引擎**两套真相** | 职责划分（§3.4）：Ripple 只触发与收窄 |
| R5 | **自动改动用户数据**的顾虑 | 默认只「标记 + 留痕」，不改正文；`dissolve` 只标记不删除；正文改写（R3）默认关 |
| R6 | 性能 | 惰性索引 + 按依赖数遍历（非全库笛卡尔）；上限 + 缓存代数 |
| R7 | **联动改动内容哈希 → 同步抖动** | 明确为期望行为并在测试断言；必要时把留痕字段移出哈希（需与 `02-数据架构` §7 一致性清单同步决策） |
| R8 | 黄金样本与门禁 | 新行为按「有意偏离」登记；R0/R1 各配专测 + 冒烟 |

## 8. 待确认（Q1–Q8）
