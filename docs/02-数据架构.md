## 2. 原子模型的三条不变量

| # | 不变量 | 含义 |
| --- | --- | --- |
| I1 | **一切都由 id 寻址** | 同维度内 id 唯一；无 id 时按内容派生稳定 id（保证跨端一致：两端各自归一得到同一 id） |
| I2 | **归一即夹取** | 每个字段都有类型、长度（`DIM_CHAR_LIMITS`，`core/constants.js:60`）与合法值域；非法值**丢弃**，不写入 |
| I3 | **引用不进哈希** | 引用类字段（`sourceRefs` / `memRefs` / `planRefs`…）**不参与内容哈希**（`core/model/hash.js:42` 注释明示）→ 引用变更不触发快照 / 同步更新。**新增引用类字段时必须显式决策是否沿用此口径** |

## 3. 生命周期

### 3.1 删除：双墓碑

| 墓碑 | 键 | 挡住什么 |
| --- | --- | --- |
| 按 id | `deleted[dim][id] = ts` | 对端仍持有同 id 条目 |
| 按内容哈希 | `deletedH[dim][hash] = ts` | 对端把**同内容以新 id** 重写（AI 重生成 / 快照还原 / 哈希换 id） |

合并判据：对方条目「更新时间 ≤ 墓碑时间」→ 双方一并删除（`core/state.js:40-46`、`core/merge.js`）。

### 3.2 瘦身与内容哈希

**双指纹**（v2.86.0，依据 `docs/D8` R1=B）：

| 指纹 | 函数 | 用途 | 口径 |
| --- | --- | --- | --- |
| **身份指纹** | `core/model/hash.js#atomIdentityHash`（`i2:` 前缀） | 跨端/载入**去重**、**内容墓碑**、复活防护、控制台 | 4 基本槽（标题/日期/内容/地点·如有）+ 3 扩展槽（标签/类型/状态·如有）；集合类先排序；旧的未归一化数据退化为 `i2:legacy:<变更指纹>` |
| **变更指纹** | `#atomContentHash`（= `atomChangeHash`） | **增量快照差异**、**情节签名**（分析后是否同步时钟） | V1 逐维字段表（逐字不变） |

`importance` / `uses` / 楼层 / 时间戳**都不进任何指纹**（D8 §3）。

`core/slim.js` 的 `SLIM_HASHED_FIELDS` 是**同义字段消歧表**（决定同义组保留哪一份 = keeper），**不是保留字段清单**；
它由 `core/model/hashfields.js` **派生**（变更字段 ∪ 身份字段）。瘦身只丢弃**空值/默认值**与**等值同义**的另一份，
读回由 keeper 无损重建 → 「瘦身不改变两种指纹」（黄金样本 R3）。

角色档案另有**内容副本**（v2.86.0，`docs/D8` §4.4）：角色名 → 原子层标题，其余结构化字段在**每次归一化时**确定性拼进 `content`
（原字段不动），使角色与其它维度同口径参与身份指纹。

### 3.3 上限与衰减

| 机制 | 落点 |
| --- | --- |
| 入库硬截断 | 各维度单条字数（`DIM_CHAR_LIMITS`）、条数（`stateMaxPerSubject` 等） |
| 库存总上限 | **`storeTotalMax`（默认 3000 条，涵盖全部原子数据总量）× `storeShare`（各大类占比，合计恒 100）**；某维有效上限 = **四舍五入(总上限 × 占比 ÷ 100)**（`core/ingest.js#storeCapFor`，占比推导值是**权威**）。**保底被动下移**：配置的 `storeMin*` 高于上限时，被 `clampStoreFloors` **只降不升**地写回上限之下（提交占比 / 改总上限 / 手填保底 / 启动自愈四处触发，v2.85.0）。旧的逐维 `storeMax*` 键保留为兼容口径：`storeTotalMax` 为 0 / 缺键时回落逐维绝对条数、且保底**不动**（V1 逐字一致） |
| 注入预算 | `charBudget` + 各维条数上限（`core/config.js:735-777`） |
| 重要度（v2.86.0） | **窗口调用占比**：`imp(i) = uses(i) ÷ Σ uses(窗口 ±R)`（含自身，R=10）；每次提取后重算**最近 N=20 条**，更旧的**冻结**；**逐维独立**、状态按主体分组；`core/importance.js`。消费方**直接用该值**（不归一化）：清扫保护阈值 0.2（比例类滚动条）、裁剪排序、召回打分权重 0.15（C3 重标定待迁移轮） |
| 时间衰减 | 通用多级时间衰退（按**剧情时间**）；各域开关/比例/阈值 —— 状态、记忆、平行事件、传言 |
| 收敛触发 | 条目数 > 上限 × 比例时触发清扫；达阈值自动移除（留墓碑） |
| 已处理楼层台账 | `state.processedFloors`（`{f, h}` 哈希台账 + `processedVer` 版本签名）记录「哪些楼层分析过」；升级/重启且**聊天尚未就绪**时，三条维护路径（迁移 / 漂移防呆 / 归位对账）一律**延后而不丢弃**（`host/floors.js#chatReadyForFloors`，v2.87.0）—— 否则「无正文 → 丢标记」会清空整本台账，早期楼层成片变回未摘要 |

### 3.4 迁移与版本

- `DATA_VERSION`（`core/constants.js:16`）与代码版本解耦，**仅在需要数据迁移时递增**；
- 结构迁移 `core/migrate.js`：补容器、字段归一、中文键映射（`CN_KEY_MAP`）、旧存档兼容；
- 新增原子容器的**六处接线**（缺一即静默缺陷）：常量表 → 归一化 → 内容哈希 → 瘦身白名单 → 迁移/合并 → 跨端（`core/cross-sync.js`）+ `DATA_VERSION` 递增。

## 5. 存储分层（写五层 · 读五层 · 聊天载体只读）

**写**（每次保存即时落盘；`💾 保存（对齐所有存储）` 可强制逐层对齐）：

| 层 | 载体 | 触发 | 落点 |
| --- | --- | --- | --- |
| 本机缓冲 | `localStorage`（存档键 `SPreset_FTTMemory_<scope>`） | 每次保存即时写 | `adapters/store.js` |
| 本机内存库 | `IndexedDB`（`localforage`，键 `ftt2_state_<scope>`） | 每次保存即时写（宿主提供 `localforage` 时） | `adapters/store.js` |
| 服务端 / 用户目录文件 | 酒馆用户目录 JSON（可选 gzip + 魔数校验） | 保存后按策略落盘 | `adapters/file-transport.js`、`adapters/user-file.js`、`adapters/gzip.js` |
| 宿主原生存储 | TauriTavern 官方契约 | 检测到宿主且开关为 auto/on | `adapters/tt-store.js` |
| 分片 + 清单（v3.0.21） | `ftt2-shard-<角色>-<维度>.json` + `-manifest.json` | 只写内容变化过的片 | `adapters/shards.js` |
| 聊天载体（只读） | `chatMetadata[ftt_memory_v2]`（随聊天备份 / 同步一起走） | **本阶段不写**（写路径属后续阶段） | `adapters/chat-meta.js` |

**读**（v3.0.23 起「全层对齐」，顺序固定、各层只作并集补充，**绝不整体覆盖**基底）：

| # | 读取层 | 基底判据 | 说明 |
| --- | --- | --- | --- |
| ① | 服务端主文件（含 gzip / 宿主原生路由） | **有则必为基底** | 信封哈希校验不过 → 不丢弃整次载入，转 ② |
| ② | 分片 + 清单 | 主文件缺失 / 哈希不过 / 无数据体时**由分片重建** | 以 `mainAt = 0` 应用全部片（逐片内容哈希校验） |
| ③ | 本机缓冲 `localStorage` | 无 ①② 时按 `updatedAt` 竞争基底 | **始终**作并集（保存流水线同步写，清空/导入也写 → 不会复活旧数据） |
| ④ | 本机内存库 `IndexedDB` | 同上 | 同上（v3.0.23 起**真的读**：此前写而不读） |
| ⑤ | 聊天元数据 `chatMetadata` | 同上 | **只在比基底更新时**才并集（V2 不写它，无条件并集会让「清空记忆」被旧副本复活）；取的是**快照**，绝不改动聊天里的对象 |

载入竞态（v3.0.23）：载入是「读各层 → 合并 → 注入」的异步过程，期间若用户导入 / 清空 / 跨端合并注入了更新的状态
（内核 `stateSeq` 变化）→ **本次载入不覆盖**，如实回报 `superseded`。

**「最新情节」的判定口径**（v3.6.0，用户要求「注意最新的情节指根据**内置的天数**判断」）：
`core/recall.js#trustedPlotList` 是时钟解析与在场解析**共用**的情节顺序 ——
**两边都有内置天数 `storyDay`（>0）时以天数大者为准**；任一侧没有天数则完全沿用原口径（楼层优先 → 剧情日期 → id）。
`storyDay` 来自情节正文头「第 N 天」（`recordReservedStoryDay`，预留计数器：只记录、随存档往返）。
该顺序同时服务：总览时钟显示、分析后同步、以及「🛠 自动修复」第 1 段的「剧情时钟」步骤（v3.6.0）。

**楼层溯源口径**（v3.7.0，用户要求「原子数据来源记录了楼层，**原始楼层不应该变动**……如找不到对应楼层哈希值，
则**标记原文已移除**处理。同时新的楼层必须**结合新的位置**来记录，修复无法分析、跳过的问题。」）：
「来源」与「当前位置」彻底分开，且**来源永久不可变**：

| 字段 | 含义 | 可变动 |
| --- | --- | --- |
| `floorStart` / `floorEnd` | **原始来源楼层（溯源）**：条目在哪几楼产生 | **创建后永不变动** |
| `floorNowStart` / `floorNowEnd` | **当前位置**（按内容哈希匹配出的新位置；缺省 = 与来源相同） | 每次突变可重算 |
| `floorNowHash` | 当前位置那一段的**内容指纹**（复核「当前位置还作不作数」） | 随位置重算 |
| `originGone` / `originGoneAt` | **原文已移除**：哈希找不到该楼原文；内容与来源保留，但**不占用任何楼层** | 原文复现即解除 |
| `floorStale`（历史） | 老数据的「当前位置未知」 | 兼容读：不占用楼层，下次突变自动升级 |

- 覆盖判定（`core/floor-cover.js#currentFloorRange` → `meaningfulFloorRange` → `floorRanges/floorCoverage`）按**当前位置**：
  `originGone` / `floorStale` **不覆盖任何楼层**；有 `floorNow*` 以它为准（含 `0/0`：删楼重映射里「跨越删除线、只有原第 M 楼幸存」
  的条目恰好落在新第 0 楼，是**精确位置**）。这正是「无法分析、跳过」的修复点：旧条目不再用旧楼号压住新正文。
- 溯源字段**不参与内容哈希**；归一化 / AI 更新（`mergeDelta`）由 `preserveFloorProvenance` 与 `normalizeAtom` 原样保留，
  情节「更新」路径从旧条目**继承**。设定 → 存储「🧱 楼层校准」的失效计数 = `originGone || floorStale`。

## 7. 一致性检查清单（改数据模型时逐项过）

1. 新字段是否参与**内容哈希**？（不参与 = 变更不触发快照/同步；决策必须显式）
2. 是否进入**瘦身白名单**？否则瘦身后会丢字段。
3. 是否需要**同义字段组**（中英/别名）？
4. 是否有**稳定 id** 与去重键？跨端是否两端一致？
5. 是否进**跨端逐条合并**名单？不进则整侧取较新（可能丢改动）。
6. `DATA_VERSION` 是否需要递增 + `migrate.js` 是否需要补迁移？
7. 上限与衰减是否配置化（`core/config.js`）？是否有护栏避免无限增长？
8. 删除路径是否写**双墓碑**？
9. 若该字段参与**冲突裁决**：是否声明了它在 `D5` 裁决链（L0–L4）中的位置？同 id 同 `updatedAt` 时两端是否**收敛**（L4 确定性键）？
