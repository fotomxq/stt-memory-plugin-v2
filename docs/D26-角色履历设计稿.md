## 0. 一页摘要

在**角色档案（`snapshots`）内**新增第 9 个区块 **`resume`（履历）**：记录该角色**类长期记忆**的结构化条目，与 `memories` 维度**双向呼应**，并按「**重要性 × 剧情时间**」做**上限 30 条 + 自动遗弃 + 自动凝练**。

| 要点 | 设计结论 |
| --- | --- |
| **载体** | **不是新维度**，而是 `snapshots` 条目内的新字段 `resume: ResumeEntry[]` —— 因此**不需要**「进入原子层的六处接线」，只需走 `02` §7 的九项一致性清单 |
| **条目结构** | `{ date, time, summary, importance, refs?, source }` —— 剧情年月日 / 简述 / 重要性 / 与记忆关联（可选）/ 来源 |
| **与既有字段的分工** | 既有 `background.history` 是**一条自由文本**（上限 200 字，已在内容副本内）；`resume` 是**多条结构化**。**分工**：`history` 写"一生的概览性经历"，`resume` 写"按剧情时间的逐条大事记"。两者**不互相复制**（§3.1） |
| **与记忆呼应** | ① 履历条目可带 `refs`（指向 `memories` 的 id）；② 长期性事实可从 `memories` **回填**为履历；③ `refs` 按 `02` §2 **I3「引用不进哈希」**处理 |
| **历史 / 同人人物预填** | 新增可编辑标记 **`identity.canon`**；当该标记为真且**剧情时钟当前日期**已知时，可自动补全「**剧情时间之前**」的履历；**硬护栏：不得写入剧情内尚未发生的事**，每条标 `source` |
| **触发** | ① 角色页**新增按钮**「📜 补全 / 修复履历」（针对该个体）；② 既有「🔧 修复角色」在**抽到该角色时一并修复履历** |
| **留存** | **上限 30 条/角色**；留存核心依据 = **重要性 + 剧情时间**；**低重要且时间久远 → 自动遗弃**；高重要条目**免疫** |
| **凝练** | 每次修复中自动把冗长简述**言简意赅地压缩**；凝练**不新增信息**、不改变时间与重要性 |
| **落盘成本** | **`DATA_VERSION` 不变**（加可选字段 + 归一化补默认值即可）；**不进瘦身白名单**（避免瘦身改动履历）→ 见 §3.2 |

**6 条开口已裁决**（v1.1，用户裁决「按你的建议来约定」→ 全部采纳建议默认；完整裁决见 §6 决策记录）：
履历**部分进**身份指纹（`importance` / `refs` 不进）· 遗弃**不需要**复活抑制 · **30 为软阈值**（≤30 从不自动遗弃）· 凝练 **≤60 字**且每次修复幂等执行 · `canon` 为**新增三态字段** · 「🔧 修复角色」**默认连修**履历。

## 3. 方案

### 3.1 定位与分工（履历 vs 背景·经历 vs 记忆）

| 载体 | 形态 | 写什么 | 谁写 |
| --- | --- | --- | --- |
| **`resume`（本稿新增）** | **多条结构化** `ResumeEntry[]` | 按**剧情时间**的**逐条大事记**：某年月日发生了与"我"相关的什么 | AI 抽取 / 修复 / 历史·同人预填；用户可编辑 |
| **`background.history`（既有）** | 一条自由文本（≤200 字） | 该角色**一生的概览性经历**（不分条、不带时间） | AI 修复 / 用户 |
| **`memories`（既有维度）** | 独立维度条目 | 任何角色都可能知道的**事实**（公开 / 私密 / 秘密） | 提取管线 |

**分工规则（三条）**

1. **不互相复制**：同一件事**不得**同时以全文出现在 `resume` 与 `background.history`；`history` 保留"概览"，`resume` 承担"逐条"。
2. **双向呼应**：履历条目 `refs` 可指向 `memories` 条目 id；修复时**长期性事实**（属于该角色本人、且具时间性）可从 `memories` 回填为履历条目。
3. **引用口径**：`refs` 属引用类字段 → 按 `02` §2 **I3**「引用不进内容哈希」，且**新增引用字段须显式决策是否进哈希**（本稿结论：**不进**）。

**与重要度的关系**：履历的 `importance` 是**条目自带标注**（0–1），**不参与** `core/importance.js` 的窗口重算（那是"被调用热度"，语义不同，见 K8）。

### 3.2 数据模型与一致性清单

**`ResumeEntry` 字段**

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `date` | 字符串 | **是** | **剧情年月日**（沿用剧情时钟的日期写法，支持公元前；缺失时该条**不予入库**） |
| `time` | 字符串 | 否 | 剧情时刻（年月日精确到天的条目可留空） |
| `summary` | 字符串 | **是** | **简述**（言简意赅；凝练后的目标长度 **≤60 字**，见 §6 决策记录 Q4） |
| `importance` | 数字 0–1 | 否 | **重要性**（默认取该条抽取时的上下文权重；用于留存判据） |
| `refs` | 字符串数组 | 否 | **与记忆关联（可选）**：`memories` 的条目 id；**不进哈希** |
| `source` | `story` / `canon` / `manual` | 否 | 来源：剧情内抽取 / 历史·同人预填 / 用户手填 |

**归属与上限**：`resume` 挂在**该角色自己的 `snapshots` 条目**内 → **天然按个体隔离**（`scope` 已是角色作用域），无需新增容器。

**一致性清单逐项结论（`02` §7 九项）**

| # | 清单项 | 本稿结论 |
| --- | --- | --- |
| 1 | 是否参与内容哈希 | **部分参与**：`date` + `summary` + `source` 进内容副本（新增「履历：」段）；`importance` / `refs` **不进**（与 `importance`/`uses` 先例一致）。**已裁决**：采纳"部分进"（§6 决策记录 Q1） |
| 2 | 是否进瘦身白名单 | **不进** —— 瘦身只丢空值/默认值与等值同义；履历非空即实质内容，不应被消歧表处理 |
| 3 | 是否需要同义字段组 | **不需要** |
| 4 | 稳定 id 与去重键 | **不需要独立 id**：条目是档案的子数组，按 `date + summary 哈希` 作为**数组内去重键**（去重不跨条目） |
| 5 | 是否进跨端逐条合并 | **随 `snapshots` 条目走**（`snapshots` 已在原子层、逐条合并），**不另立合并口径** |
| 6 | `DATA_VERSION` 是否递增 | **不递增** —— 加可选字段 + 归一化补默认空数组即可；老存档读到 `undefined` 视为 `[]` |
| 7 | 上限与衰减是否配置化 | **是**：`snapshotResumeMax`（默认 **30**）· 触发比例 · 免疫阈值 · 凝练开关（§3.3） |
| 8 | 删除路径是否写双墓碑 | **不适用**（子数组无独立 id）。**已裁决**：**不需要**复活抑制，随档案整体按 `updatedAt` 取新（§6 决策记录 Q2） |
| 9 | 是否参与冲突裁决 | **不参与** `docs/D5` 的裁决链（履历是档案内部字段，随档案整体按 `updatedAt` 取新） |

> **结论**：因为载体是"**既有原子维度内的新字段**"而非"新容器"，**不需要**「进入原子层的六处接线」；只需在 `core/model/snapshot.js#snapshotContentCopy` 登记拼接顺序（K4）+ 归一化补默认值。

### 3.3 留存与凝练

**上限**：`snapshotResumeMax`（默认 **30** 条/角色）。

**留存判据（重要性 × 剧情时间）**

- **时间基准**：一律用**剧情时间**（与 `docs/D18` §4 / `业-6` 的裁决一致），**不用现实时间**。
- **留存分**：`keep = importance × timeWeight(剧情时间距今)`，其中 `timeWeight` 沿用既有衰退函数的多级时间尺度思路（`core/ingest.js#calcTimeDecay` 的形态），**距剧情当下越远权重越低**。
- **触发**：条目数 **> 上限 × 触发比例** 时触发一次遗弃清算（与既有各维"上限 × 比例触发清扫"同款形状）；**不超过上限时从不自动遗弃**。
- **免疫**：`importance ≥ 免疫阈值`（默认建议 0.7）的条目**永不自动遗弃**，无论多久远 —— 这是"重要性是留存核心依据"的体现。
- **遗弃顺序**：先遗弃 `keep` 最低者；`keep` 相同时**先遗弃时间更久远者**；再相同则按 `summary` 字典序（**确定性**，避免两端结果不同）。

**凝练**：每次修复中，对**超长** `summary` 做**压缩**（**目标 ≤60 字**，§6 决策记录 Q4）：
- **只压缩、不新增信息**；**不得**改动 `date` / `time` / `importance` / `refs`；
- **幂等**：已达标的不再改动；
- 压缩属**系统自动改写**；按 §6 决策记录 Q1，`summary` **进**身份指纹 → 压缩会触发跨端「同 id 取更新」，**属期望行为**。

### 3.4 历史 / 同人人物的履历预填

| 项 | 口径 |
| --- | --- |
| **判据** | 新增可编辑三态标记 **`identity.canon`**（沿用 `identity.immortal` 的同款形态，K5）：`true` = 该角色是**史实 / 原作人物**（有独立于本剧情的既有生平） |
| **补全范围** | **仅补「剧情时间之前」**的履历 —— 即以**剧情时钟当前日期**为上界，把该角色在本剧情开始前**已成立**的经历补成履历条目 |
| **硬护栏（三条）** | ① **不得**写入剧情内**尚未发生**的事（上界 = 剧情当下）；② 每条**必须**标 `source: 'canon'`，与剧情内抽取的 `story` 条目**在界面上可区分**；③ 无法确证的一律**不写**（宁可留空，不编） |
| **触发** | ① 手动：角色页「📜 补全 / 修复履历」；② 自动：既有「🔧 修复角色」在抽到该角色时一并执行 |
| **无剧情时钟时** | **不预填**（没有上界就无法保证护栏①），如实提示「缺少剧情时钟，暂不补全历史履历」 |
| **开关** | `snapshotResumeCanonFill`（默认建议**开**） |

### 3.5 入口与联动

| 入口 | 行为 |
| --- | --- |
| **角色页「📜 补全 / 修复履历」**（新增按钮，针对**该个体**） | 机械段（排序 / 去重 / 遗弃 / 凝练，零 AI）→ 需要时一段窄契约 AI（补全 + 凝练）；结果如实回报：新增 N · 凝练 M · 遗弃 K · 跳过原因 |
| **角色页「🔧 修复角色」**（既有） | 抽到某角色时，**在同一轮里一并修复其履历**；`docs/D25` 的自动修复若含角色修复，则同口径生效 |
| **总览「🛠 自动修复」联动** | **不在本稿新增总览步骤** —— 履历修复挂在"角色修复"内部（`docs/D25` §3 的编排不变） |
| **展示**（角色页档案卡片内） | 「📜 履历」区块：按**剧情时间倒序**列出，每条显示 `剧情年月日 · 简述 · 重要性 · 关联记忆(可点开)`；`canon` 条目带来源标记；条数显示「N / 30」 |
| **解除 / 关闭** | `snapshotResumeEnabled`（默认建议**开**）：关闭后不读不写、界面隐藏区块 |

## 6. 决策记录（2026-10-10 · 用户裁定：6 条**全部采纳建议默认**）

> 用户原话：「角色履历，按照你的建议来约定即可。」→ 本表原为「待确认问题清单」，现**转为决策记录**；
> 正文（§3）已按本节口径落定，不再保留「待裁决」措辞（`开发守则.md` §2.7 A1：正文只写当前生效设计）。

| # | 问题 | **裁决** | 落实位置 |
| --- | --- | --- | --- |
| **Q1** | 履历是否进内容副本（身份指纹）？ | **部分进**：`date` + `summary` + `source` 进；`importance` / `refs` **不进** | §3.2 一致性清单第 1 项 · `core/model/snapshot.js#snapshotContentCopy`（依 `docs/D8` §4.4「新增字段登记即生效」） |
| **Q2** | 遗弃是否需要复活抑制（墓碑）？ | **不需要** —— 随档案整体按 `updatedAt` 取新；若实测出现"复活"再补 | §3.2 一致性清单第 8 项 |
| **Q3** | 30 条是硬上限还是**软阈值**？ | **软阈值**：≤30 时**从不**自动遗弃，仅超限时清算 | §3.3 留存判据的"触发"条 |
| **Q4** | 凝练的目标长度与触发时机？ | 单条 `summary` **≤60 字**；**每次修复**时对超长条目压缩（**幂等**） | §3.3 凝练 · §3.2 字段表 `summary` 行 |
| **Q5** | `identity.canon` 是新增字段还是复用现有标记？ | **新增三态字段**（`immortal` 是"长生者"、穿越者正则语义不同，**不可复用**） | §3.4 判据 |
| **Q6** | 「🔧 修复角色」是否默认连修履历？ | **默认连修**（`snapshotResumeEnabled` 关闭时不修） | §3.5 入口与联动 |

> **裁决的实际影响（小结）**：Q1 的"部分进"意味着**遗弃与凝练会改变 `snapshots` 的身份指纹** → 跨端触发「同 id 取更新」，这是**期望行为**（内容确实变了），
> 但把 `importance` / `refs` 排除在指纹外可显著减少无谓变更；Q2 的"不需要墓碑"使实现**不需要**新增账本字段（成本显著低于 `docs/D22` 的 `数-4` 那一类）。
