## 2. 不注入口径（V1 原样）

- **分段总结产物不注入**：`state.plotSegments` 不进召回 / 注入 / 世界书 / 遗忘 / 质检；V2 的注入体构建（`core/recall.js#buildMemoryBodyForInject`）
  与召回候选都不读该容器（冒烟 AC3 直接断言注入体不含分段标题与「感情线」字样）。
- **已总结情节（`hidden` / `summarizedBy`）不参与任何自动动作**：注入 / 召回 / 淘汰裁剪 / 再次聚合 / 修复质检 / 分段总结批次 / 世界书关键词归纳
  —— V2 由 `core/merge.js#activeAtoms` / `atomIsHidden` 统一承担（B8-6c 各批次已接线）；面板情节页也有同款提示文案。
- **两条入口产物的区别**（V1 v1.206）：`🧷 情节总结` 产出的是一条**真情节原子**（带 `mergedSummary.by='manual'`，正常参与注入与运作）；
  `🧩 分段总结` 产出归档段落（不注入）。半自动聚合产物也是真情节原子（`by='auto'`）。

## 3. 与 V1 的差异（逐条明示）

1. **AI 通道**：V1 走自建 OpenAI 兼容请求（`callChatCompletion`）；V2 走注入钩子 `core/ai-hooks.js#aiCallText`（酒馆 `generateRaw`），故 `apiTemperature/apiMaxTokens/apiTopP` 不设控件（与既有批次同口径）。
2. **互斥**：V1 有 `busy.repair` 与 `busy.summary|compact|weave|advance|sync` 两道判据、两种文案；V2 由宿主互斥钩子 `aiBusy()` 统一表达 ——
   `runAtomMergeSummary` / `runPlotSegmentSummary` / `runPlotSegmentSummarySelected` 取「**当前任务占用中** + 摘要/情节总结/推演/推进结束后再…」那一道文案（最贴近 V2 的占用语义），
   V1「`busy.repair` → 任务进行中」那一道的文案在 V2 不复刻（单一钩子无法区分）。
3. **定时器**：`scheduleAtomCompact` 从 V1 的全局 `setTimeout` 改为注入的 `timerHooks.set(fn, 4000)`；未接线时 no-op（不调度）——单测用定时器桩验证排程/忽略/禁用三态。
4. **任务管线 UI 未移植**：`newTaskStart` / `abortTick` / `abortQuiet` / `pipeStart` / `pipeUpdate` / `pipeEnd` / `renderPanel` 在 V2 不存在；
   中断分支（V1 `abortQuiet(e) → {aborted:true}`）不再可达，V2 的 `catch` 一律按异常告警并返回 `{ok:false,error}` / `{made:0,error}`。
5. **`pipelineBlockInfo` 的「存储同步进行中」分支未移植**：V2 的同步占用同样由 `aiBusy()` 表达（宿主 `extractBusy`）。
6. **界面细节**：
   - 「🧷 立即聚合早期情节」在 V1 属于设定页「早期情节压缩」节；V2 的同节（标题 + 说明 + 按钮）由 `ui/panel.js#settingsBody` 在**设定 → 提示词**页追加，
     6 个配置控件仍由 `SETTINGS_CONTROLS.prompts` 平铺渲染（V2 不重复出控件）。
   - 按钮结果落点：V1 写 `[data-ftt-compact-result]` 元素；V2 统一写面板 note（`r.state.note`），同时保留该 span 供 V1 同构渲染。
   - 分段子页的行操作沿用 V2 既有动作名（`edit` / `delete` + `data-kind="plotSegments"`），而非 V1 的 `editEntry` / `delEntry`（V2 已判定为改名等价，见总表口径）。
   - 分段子页省略 V1 的**分页搜索框 / 排序切换控件**（V1 的分段搜索与「排序」在 V2 面板的通用搜索体系下未移植）→ **未实现**（见 §5）。
   - 分段列表默认按时间范围**倒序**（v1.190），与 V1 默认一致；V2 未提供切换到「最早在前」的按钮。
7. **V2 额外导出**：`core/atom-compact.js` 直接导出 `buildAtomCompactPrompt` / `applyCompactGroup` / `compactGrainLabel` / `atomDateGrainKey` / `grainStartDateStr`
   （V1 未导出这几个内部助手）；`FTT.*` 也因此比 V1 多这几项（V2 自测需要，不影响行为对齐）。
8. **面板 note 文案**：V2 的面板动作把结果写入 `state.note`（如「情节总结：未选中情节…」「分段总结：新增 2 段 · …」），
   V1 只弹 toast / 写 DOM；两侧的**内核服务提示（toast/notify）文本**才做逐字比对（黄金样本已固化）。

## 4. V1 原生缺陷 / 怪癖（如实保留，未"顺手修正"，黄金样本已固化）

1. **`grainStartDateStr` 对负年份返回空串**：`String(key).split('-').map(Number)` 对 `-0221-01-02` 得到 `Number('') = 0` → 提前 `return ''`。
   V2 逐字保留（单测 H3 断言 `grainStartDateStr('-0221-01-02') === ''`）。
2. **`atomMergeSummary` 的 `reason:'exists'` 在真实路径不可达**：首次合并后来源已被隐藏，再次调用 `usable.length === 0` → 走 `reason:'empty'`；
   只有"人为构造出同 id 总结条 + 来源仍可见"时才会命中。测试两侧都构造成立场景以覆盖该分支（H14 `exists`），**行为原样**。
3. **`parseAtomMergeResult` 对"只有标题没有内容"的 JSON 会把整段 JSON 当正文**（退化分支），V2 原样（H13 `titleOnly` 固化）。
4. **`buildPlotSegmentPrompt` 用批对象的 `b.index`，而 `plotSegmentBatchesFrom` 不产出 `index`** → 直接把原始批次交给提示词时出现「第 undefined 批」。
   只有 `plotSegmentPlan` / `plotSegmentPlanForIds` 会补 `index`。V2 原样（P6 fixture 固化该字符串）——生产路径都走计划，故只影响直接调用。
5. **`plotSegmentBatchSize` 对 `-5` 也回落到 30**（判据是 `n > 0` 而非 `Math.max(1,…)`），V2 原样（P1 固化）。
6. **`applyPlotSegmentResult` 关闭保护时只覆盖 `lines`/`raw`/`updatedAt`**：`header`/`start`/`end`/`atomIds` 保持原值（可能与新正文不一致），V2 原样（P10 `applyRewrite`）。
7. **`runAtomCompact` 的"保底优先于 force"**：`force` 只跳过体量阈值，跳不过 `storeMinFor('atoms')` 与「池 <2 / 已 ≤ 目标」早退（V1 v1.147/v1.206 设计），V2 原样（H6）。
8. **调度重试窗口**：`compactWaitDeadline` 只在 `scheduleAtomCompact` 里刷新；手动 force 不排队（V2 原样）。
9. **`runPlotSegmentSummary` 默认只处理前 12 批**（`maxBatches = max(1, min(40, Number(o.maxBatches) || 12))`）——库大时需反复点击，V2 原样。
