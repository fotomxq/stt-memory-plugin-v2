## 0. 一页摘要

| 维度 | ST-BaiBai-Book（参考） | 本仓库（现状） | 本稿目标 |
| --- | --- | --- | --- |
| **配置** | ST `extensionSettings['baibai_book']` + `saveSettingsDebounced()` → 落**服务器 settings.json** → **跨设备/局域网同步**；**明确不用 localStorage** | 已用 `extensionSettings`（`adapters/settings.js`、`adapters/config-store.js`）✅ 与参考一致 | 保持 |
| **记忆数据** | **`chatMetadata`（随聊天走）+ 各消息 `extra.bbs_leaf`（在 chat 文件里）** | **自研状态文件**（明文/gzip/瘦身三态）+ 缓冲 + 快照链 + 世界书镜像 + TauriTavern 原生 KV/blob | **改为宿主原生载体**：`chatMetadata` 为主、消息 `extra` 为兜底；自研通道降级为备份/迁移 |

| **失败姿态** | 不阻断聊天；宿主 API 缺失即降级 | 已有异常提示与并集哨兵（v2.92.0） | 保留并纳入新流程 |

## 1. 参考实现怎么做的（逐条摘录，来源：其 `CLAUDE.md`）

| # | 做法 | 对我们的启示 |
| --- | --- | --- |
| R1 | **设置写进 ST `extension_settings` → 服务器 `settings.json` → 跨设备/局域网同步**；注释明确「**不要改回 localStorage**」（localStorage 只在每台设备本地，换设备不同步 —— 他们修过这个 bug） | 我们**配置**已对齐；但**记忆数据**仍放在自研文件/缓冲里 → 跨端丢数据的根源之一 |
| R2 | **`ready` 守门**：ST 就绪后先 `hydrateSettings()` 从服务器载入真实值，**之后才放行回写**，否则默认值会覆盖服务器已存设置；旧 localStorage 值一次性迁移 | 我们的「载入 → 合并 → 保存」缺少等价的时序守门：**同步/载入未完成时的一次保存即可覆盖远端** |
| R3 | **摘要森林 → `chatMetadata`**（随聊天走）；**叶子 → 消息 `extra.bbs_leaf`**（在 chat 文件里） | **记忆数据应当随聊天走**（chatMetadata / 消息 extra），而不是自成一套文件同步协议 |
| R4 | UI 渲染在 **Shadow DOM**，样式与主题变量隔离在 `.bbs-root` | 与同步无关，但说明「原生扩展」能把复杂度交给宿主 |
| R5 | 数据模型是**单一森林**（压缩节点 + 叶子），没有多容器 + 上限裁剪 + 墓碑账本 | 我们的多容器模型是为 V1「脚本注入 + 自研存储」设计的，可按 `D10` 继续简化 |

## 2. 现状机制梳理（本仓库，带证据）

### 2.1 通道与入口

| 环节 | 实现 | 关键点 |
| --- | --- | --- |
| 保存编排 | `adapters/store.js`（`saveStateNow` / `setPersistHooks`） | 写 localStorage/IndexedDB 缓冲 → 写状态文件（可 gzip + 瘦身）→ 触发快照增量 → 世界书镜像（可选） |
| 传输 | `adapters/sync.js`（1356 行）：`stateFileWrite` / `stateFileReadAny` / `stateFileReadCandidates`（`:176-180`）/ `snapshotFile*` / `syncLogServer*`（`:160-161`）/ `fileCache*`（`:184-189`） | 读写候选顺序由「是否 gzip」决定；**文件通道与原生通道并存** |
| 原生通道 | `adapters/tt-store.js`：`ttKvPut/TryGet/Del`、`ttBlob*`、`ttKeyOf`（`:186`）、miss 缓存（`:191-210`） | TauriTavern 原生 KV/blob；`tauriMirror` 控制是否**再镜像一份文件** |
| 合并 | `core/cross-sync.js`：`dataAggHash` / `mergeDataObjects` / `mergeSnapshotStores` / `mergeProcessedFloors`；`core/sweep.js#applyDeletedToArray` | 三方合并（base/local/remote）+ **id 墓碑 + 内容墓碑**双账本；v2.92.0 起加并集哨兵与人工确认项 |
| 快照 | `core/snapshots.js`：根快照 + 增量（`atomsHashes` 去重），上限 30 / 并入批次 15 | 自研回滚与备份机制 |
| 台账 | `state.processedFloors`（已处理楼层哈希） | 与同步无关但随状态文件走；v2.87.0 起有「聊天未就绪不清台账」守卫 |

### 2.2 现有机制的复杂度来源（为什么「差劲」）

1. **通道多且并存**：缓冲 / 文件（明文+gzip+瘦身）/ 快照 / 世界书 / 原生 KV —— 任一环节时序错位都会表现为「像丢数据」（`D10` R5）；
2. **自研传输协议**：文件名、gzip 魔数、瘦身信封、快照链去重、跨端 meta 探测……全部要自己保证一致性（`sync.js` 1356 行即成本）；
3. **墓碑 + 上限裁剪**：合并后裁剪与墓碑过滤都会「删数据」，且**判据与被删对象的口径必须严丝合缝**（v2.86.0 身份指纹收窄、v2.91.0 内容墓碑加严、v2.92.0 账本收敛，都是在补这一类洞）；
4. **载入时序无守门**：缺少参考项目的 `ready` 等价物 → 载入/同步未完时的保存可能覆盖远端（R2）。

## 3. 目标方案

### 3.1 载体分层（核心改动）

```text
配置         → ST extensionSettings（服务器 settings.json，跨设备同步）      ← 与参考一致，保持
记忆数据     → **chatMetadata**（随聊天文件同步/备份）为主载体
               + 消息 extra（叶子级锚点，随 chat 消息走）为兜底/增量
自研文件     → 降级为「**导出/导入 + 迁移 + 灾备**」：不再作为在线主通道
快照链       → 降级为可选（默认只保留「手动快照 + 一个自动根」）
世界书镜像   → 默认关（只读派生视图）
TauriTavern  → 原生 KV/blob 作为 `chatMetadata` 不可用时的**等价替代**（大对象分片），而非第二套协议
```

**判据**：**聊天怎么同步，记忆就怎么同步** —— 宿主负责传输/冲突时间戳，插件只做「合并 + 防复活 + 上限」。

### 3.2 时序守门（对齐 R2）

1. 启动 → `ready` 之前**只读不写**（禁止任何 `saveState` 落盘）；
2. `hydrate()`：按 ① chatMetadata → ② 消息 extra → ③ 原生 KV → ④ 文件 顺序读，取**最新且完整**的一份；
3. 载入完成 → **合并本地残留**（并集）→ 才放行写回；
4. 写入：先写 chatMetadata（原生 API），成功后按需写备份文件（失败不回滚主数据）；
5. 任何一步失败：保留双方 + 登记「需人工确认项」（复用 v2.92.0 的 `core/conflicts.js`，总览与设定双处提示）。

### 3.3 自研逻辑保留清单（简化后）

| 保留 | 理由 |
| --- | --- |
| **并集合并**（`mergeDataObjects`） | 跨端同时写时必有合并；按 id + 指纹取并集是必要能力 |
| **墓碑（id + 内容）** | 删除不复活是用户明确要求（B6），且已有 v2.91/v2.92 的收敛与守卫 |
| **上限裁剪** | 库存上限是既有业务规则（`storeTotalMax × storeShare`） |
| **冲突登记** | v2.92.0 已落地（人工确认项 + 总览提示） |
| 台账 / 快照 / gzip / 瘦身 / 世界书 | **降级为可选或备份**（`D10` Q5–Q9 已裁决） |

## 6. 风险与对策

| # | 风险 | 对策 |
| --- | --- | --- |
| 1 | `chatMetadata` 体积上限（聊天文件膨胀） | 分片存储 + 只存必要字段（瘦身保留）+ 超限回落文件并提示 |
| 2 | 宿主 API 版本差异（ST 各分支 / TauriTavern） | 能力探测 + 缺失降级 + 存储页显示实际通道 |
| 3 | 老用户数据迁移丢失 | 「不删源文件 + 3 份轮转备份 + 迁移前后条数对比（并集哨兵）」 |
| 4 | 与酒馆「聊天备份/导出」的耦合 | 聊天导出即携带记忆数据（**这正是优点**）；同时保留独立导出 JSON |
| 5 | 载入守门导致「首次启动不保存」观感 | 守门期间动作仍可用，只延后落盘；UI 给出「数据载入中」提示（管线状态复用） |
