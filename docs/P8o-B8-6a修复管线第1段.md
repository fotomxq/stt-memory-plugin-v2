## 2. 本批范围与未完成项（**明确标注，不伪造**）

V1 的修复是**三段式**：① JS 机械清理（零 AI）→ ② 候选筛选（客观缺陷 + 标签组相关性 + 按比例抽查轮询）
→ ③ 窄契约 AI 修订（只允许改标题/正文/标签等白名单字段）。本批交付**第 1 段**（含编排、闸门、报告、日志与界面动作），
第 2/3 段属 **B8-6b**，届时补齐 `repairCollectCandidates` / `repairCorrelationMap` / `repairDefectOf` /
`buildRepairPrompt` / `repairApplyAiResult` 与 7 类专用修复（记忆/原子/物品/概念/角色/场景/计划悬念）。

- 因此 `repair` 动作在 `cfg.repairAutoAi`（V1「AI 修订措辞」开关）为开时，会在提示里明确写出「第 2 段候选筛选与第 3 段 AI 修订属后续批次（B8-6b），本次未执行」。
- 该开关**关闭**时，V1 的行为正是「只做机械清理」——即本批所交付的范围，此时 V2 与 V1 完全一致。
- 设定「投喂范围」页的 `repairAutoAi` / `autoRepairOnMergeFail` / `characterBirthInfer` 三个开关已在 B8-5 的控件补齐中入库。

## 3. 与 V1 的其它差异（逐条明示）

1. **楼层面板哈希经注入钩子**：`latestFloorHash` 在 V1 直接调 `hashFloorText(i)`；V2 经 `setRepairHooks({ floorHash })`
   （`index.js` 接 `host/floors.js`）注入，内核保持零宿主依赖（`check-core-purity` 门禁要求）。
2. **任务管线 UI 未移植**：V1 的 `pipeStart/pipeUpdate`/`abortTick`（顶部管线提示与中断）在 V2 不存在；
   第 1 段为同步快操作（毫秒级），不影响使用；B8-6b 的 AI 段将以「长任务在途拒绝」的口径处理（同 B8-3/4）。
3. **报告来源**：V1 在 `runAutoRepair` 内拼装通知文案；V2 由 `runRepairMech` 返回结构化结果 + `report` 文案，供面板/命令/调试共用。
