## 0. 一页摘要

「🛠 自动修复」是一个 **3 段 + 2 个补充步 + 4 步收尾** 的编排：第 1 段零 AI、第 2 段零 AI、第 3 段最多 1 次 AI 请求。本稿把它写成**可逐步执行、可逐步验收、可解释机理**的规格。

| --- | --- | --- | --- | --- |
| **闸门** | 占用 / 频率 / 同楼层上限（+ 触发源前提） | —— | 3 道 + 1 前提 | §3.1 · 机理 §3.9.3 |
| **①** | 机械清理 | **零 AI** | 9 步（固定顺序） | §3.2 · 机理 §3.9.2 |

## 1. 定义 · 范围 · 目标 / 非目标

### 1.1 定义（它是什么 · 不是什么 · 判据）

**一句话定义**：**「🛠 自动修复」= 对当前角色整库记忆的一次"分成本层"维护编排** —— 先用**零 AI 的确定性规则**把机械可判的问题清理干净（第①段），再把剩下"值得花 token 的少数条目"按缺陷与相关性**择优**选出（第②段），最后交模型在**严格受限于候选清单**的契约内改写或删除（第③段），统一汇总、记账、通知（收尾）。

| 维度 | 口径 |
| --- | --- |
| **它是什么（结构）** | 一次调用 = 闸门 → ①9 步机械清理 → ②候选筛选 → ③窄契约 AI 修订（③ / ③-b / ③-c）→ 收尾；**主编排在 `core/repair.js#runRepair`**，机械段可单独调用（`core/repair.js#runRepairMech`） |
| **它是什么（性质）** | ①**跨域编排**（不是单维修复）；②**成本分层**（能机械判定的绝不花 AI）；③**窄契约**（AI 只在候选内改/删）；④**删改留痕**（删除一律写墓碑，跨端不复活）；⑤**闸门保护**（占用 / 频率 / 同楼层次数） |
| **它不是什么** | **不是**"AI 全库重写"——模型看不到候选之外的条目；**不是**"各页的 🔧 修复"——那些是单维/单域专门修复（`docs/04-应用架构.md` §2.2 各维度行），本功能只把"计划/悬念修复"以**同一条处理**调进来当 ③-c；**不是**"新增通道"——AI 禁止新增，新增只能走提取 / 提升（`core/ingest.js` / `core/promote.js`）；**不是**"审计日志"——`state.repairLog` 是**运行时槽位**（末 5 条、不参与跨端同步）；**不是**"一键清库"——条数类操作受各维有效上限与四域衰退阈值约束，不做无差别删除 |
| **完成判据** | `made = stage1.merged + stage1.deleted + ai.revised + ai.deleted + planSusp.made`（`planSusp` 出错时不计）。**`made = 0` 也是一次正常完成**（"本轮无改动"），通知用 `info` 而非 `success` |
| **跳过判据** | 闸门不过 → 返回 `{ made: 0, blocked: true, reason }`：`auto-repair-frequency`（G2）· `auto-repair-limit(n/max)`（G3）· `blocked: true` 且无 `reason`（G1 占用）。跳过时**不改任何记忆数据**（G3 例外见 §3.1 注） |
| **失败判据** | 单步失败 → 被该步的 `try/catch` 吞掉，**不影响后续步**，只在计数上留痕（现状）→ 由 `技-37` 补逐步留痕；AI 段失败 → `ai.error` 有值且 `ai.revised = 0`、`ai.deleted = 0`（**不写任何 AI 结果**）；`③-c` 失败 → 记入 `notes`，`made` 不计它 |
| **幂等含义** | **机械段幂等**：同输入再跑不产生新改动（哈希 / 名称 / 条数 / 结构判据都收敛）；**①第 8 步（楼层突变）显式幂等**（同一对"情节楼层 / 末楼"已修过则只报告不写盘）；**AI 段契约幂等**（同样的候选清单 + 同样的模型输出 → 同样的落库结果），但**不承诺逐字幂等**（模型非确定性）→ 故用 G3 的"同楼层内容未变至多 N 次"做重复保护 |

### 1.2 范围（四张边界表）

**A. 入口范围**

| 入口 | 触发方式 | 参数 | 是否弹二次确认 |
| --- | --- | --- | --- |
| 总览 · D 维护区「🛠 自动修复」 | 用户点击（`ui/panel.js` 的 `repair` 分支 → `core/repair.js#runRepair({ cause: '手动' })`） | `cause: '手动'` → G3 **重置**同楼层计数 | **不弹**（`ui/panel.js#DANGER_ACTION_PROMPTS` 无 `repair` 键）→ 安全边界靠算法（不新增 + 写墓碑 + 各步幂等 + 闸门），见 Q7 |
| 提取合并失败后自动 | `host/extract.js` → `core/repair.js#scheduleAutoRepairOnMergeFail`（`cfg.autoRepairOnMergeFail` 默认开；无在途修复；延迟 `cfg.repairFailDelaySec` 默认 15s；**一次在途只排一次**） | `{ silent: true, cause: '提取合并失败后自动触发' }` | 不弹（自动） |
| 调试桥 / 命令 | `FTT.repairMech`（只跑第①段）· `FTT.repairGateTake(reset)` · `FTT.repairGateDue` · `FTT.repairBumpOp` · `FTT.repairLog` · `FTT.repairFailArmed` | 见 `index.js` / `devtools.js` | 不弹 |

> **本功能是唯一的"跨域编排"入口**；各页的 🔧 修复（记忆 / 概念 / 场景 / 物品 / 角色 / 状态 / 货币 / 计划悬念）是**各自独立**的动作，不经过本编排（只有 ③-c 复用了计划悬念那一条处理）。

**B. 数据范围（改什么 / 不改什么）**

| 段 | 覆盖 | 不覆盖 |
| --- | --- | --- |
| ① 机械清理 | **10 维**去重与并集：情节 / 状态记录（`currentStates`）/ 角色档案 / 长期记忆 / 物品 / 场景 / 概念 / 平行事件 / 计划 / 悬念（`core/repair.js#repairMergeDedupe`）；垃圾与残留清理（含计划 / 悬念的已了结 / 已揭晓残留）；四域衰退；**关联层**（`links`）两类清理；**楼层台账**（突变识别）；**剧情时钟**（`state.state` 的日期 / 时间 / 地点 / 在场） | 不新增任何条目；不改非白名单字段；`snapshots` / `rumors` / `plotSegments` / `currencies` 只参与"机械去重"的并集，**不做 AI 修订** |
| ② 候选筛选 | `core/repair.js#REPAIR_DIM_SPEC` 的 **10 个维度**：情节（≤180 字）· 记忆（≤120）· 概念（≤160）· 平行事件（≤336）· 物品（≤80）· 计划（≤100）· 悬念（≤100）· 场景（≤120）· 状态记录（≤60）· 名册（≤60）；可打标签维（除场景 / 状态）另查标签数 3–5 | 不遍历其它容器；机械段**不受** `cfg.repairMaxItems` 约束（候选上限只管 AI 段） |
| ③ AI 修订 | **只改候选内条目**：正文（`REPAIR_FIELD_KEYS` 的 内容 / 值 / 说明 / 描述）· 标题（截 40 字）· 标签（3–5 个，写回时清空 `keywords`）；删除候选内条目（**先写墓碑**） | 不新增；不改候选外条目；不改 id / 哈希 / 时间戳 / 关联 / 墓碑账本；不动 `DATA_VERSION`（无数据模型变化） |

## 3. 方案：步骤 · 顺序 · 分支明细

### 3.0 总览（一次自动修复的完整序）

```text
[触发] 手动（面板） ──┐
       合并失败（延迟 15s）─┤
                          ↓
[闸门] G1 占用 → G2 频率 → G3 同楼层上限 ──(任一不过)→ 直接返回 blocked（不改记忆数据；G3 可能写运行时计数）
                          ↓
① 机械清理（零 AI，9 步固定顺序；每步失败被 try/catch 吞掉，不影响后续步）
   1 机械去重 → 2 遗忘清扫 → 3 条数裁剪 → 4 垃圾清理 → 5 衰退清扫
   → 6 关联层维护 → 7 清理无效关系 → 8 楼层突变识别 → 9 剧情时钟刷新
                          ↓
② 候选筛选（零 AI；5 类计数）
                          ↓
③ AI 窄契约修订（最多 1 次请求；自动模式可被 cfg.repairAutoAi 关闭）
   ③ 主修订 → ③-b 关系层二次维护 → ③-c 计划/悬念修复
                          ↓
[收尾] 汇总 made → repairLogPush → saveState → repairReport → 通知 → 返回结构
```

### 3.1 闸门 G1–G3（任一不过即 `blocked`）

| 闸门 | 判据（现行） | 不过时的行为 | 开关 |
| --- | --- | --- | --- |
| **G1 占用** | `aiBusy()` 为真（有修复/摘要/同步在跑） | 自动模式提示「自动修复被占用，已跳过」；手动模式提示「修复进行中」；返回 `{made:0, blocked:true}` | —— |
| **G2 频率** | 自动模式 + 未 `force` + `autoRepairOpDue()` 为假 | 返回 `blocked`，`reason='auto-repair-frequency'`（**静默**，不提示） | `cfg.autoRepairEveryOps`（默认 **8**） |
| **G3 同楼层上限** | 未 `force` 时 `autoRepairTake()` 不通过 | 自动模式提示「已达上限，本次跳过」（同楼层内容未变已修复 n/max 次）；返回 `blocked`，`reason='auto-repair-limit(n/max)'` | `cfg.maxAutoRepairRounds`（默认 **3**；**不是** `maxAutoRepairPerFloor`） |

**G3 的重置规则（两条）**：① **手动修复**传 `forceReset=true` → 计数归零；② **最新楼层内容哈希变化** → 计数归零。

> **口径修正（v1.1）**：闸门不过 = **不改任何记忆数据**（语义数据一律不动）。**G3 是例外**：`core/repair.js#autoRepairTake` 在重置分支里会写 `state.autoRepair` 并 `saveState()` —— 那是**闸门自身的运行时计数**，不是记忆数据。凡出现"不写任何数据"的表述，都应读作"不改记忆数据"。
> ⚠️ **G2 的已知缺陷（U145③）**：`autoRepairOpDue()` 读 `a.lastAt`，但该字段**无处写入** → `0` 恒成立 → 判据退化为 `累计 ops >= N`，即"一旦达标就永久放行"，与"距上次修复已过 N 次操作"的原意不符（`应-17`）。

> 落点：`core/repair.js#runRepairMech`。每步独立 `try/catch`（**任一步抛错不影响后续步**）。
> 落盘：步 1–3 任一有变化 → 一次 `saveState()`；步 4 有删除 → 一次；步 6/7/8/9 各自在有变化时落盘。

> **仍存在的可观测性缺口**：第①段**每一步**的 `try/catch` 仍然静默（哪一步抛错只能在计数上看出来）→ 立项 `技-37`（U184）。

### 3.3 第 ② 段 · 候选筛选（零 AI）

> 落点：`core/repair.js#repairCollectCandidates(cfg.repairMaxItems, pickStat)`。
> 逐维遍历 `core/repair.js#REPAIR_DIM_SPEC` 的 **10 个维度**，对每条按「客观缺陷 / 与同维其他条目的相关性」分类，产出 **5 类计数**：

| 计数 | 含义 | 分支行为 |
| --- | --- | --- |
| `defects` | **客观缺陷**条数（结构/字段类，机械可判：空占位 / 超目标字数 / 模糊措辞 / 计划悬念裸问句 / 日期格式 / 标签数） | **直接入选** |
| `corrHigh` | **高相关**（标签组/正文相似度 ≥ `cfg.repairTagSimHigh`，越可能重复） | **直接入选** |
| `corrLowSkipped` | **低相关**（≤ `cfg.repairTagSimLow`）且无缺陷 | **跳过**（不入选） |
| `sampled` | 中段（不缺陷也不高相关）中**抽样**者 | 抽样入选 |
| `topped` | 候选不足 `cfg.repairMinCandidates` 时**补足**者 | 补足入选 |
| `total` | 遍历到的条目总数 | —— |

- **上限**：`cfg.repairMaxItems`（默认 **20**，范围 1–60）；**机械清理不受该上限约束**。
- **产物**：`cands`（编号化的候选清单，编号 `n` 用于第 ③ 段的按编号改删）+ `pickStat`；游标写回 `state.repairCursor`。

### 3.4 第 ③ 段 · 窄契约 AI 修订（最多 1 次请求）

**进入条件**：`cands.length > 0` **且**（非自动模式 **或** `cfg.repairAutoAi !== false`）。

| 步 | 落点 | 分支明细 |
| --- | --- | --- |
| **③ 主修订** | `core/repair.js#buildRepairPrompt` → `core/ai-hooks.js#aiCallText` → `core/util.js#extractJsonObject` → `core/repair.js#repairApplyAiResult` | **①** 提示词为空 → **不调用**（`ai.used=false`） |
| | | **②** 响应为空 / JSON 解析失败 → `ai.error='AI 未返回有效 JSON'` |
| | | **③** 抛错 → `ai.error='<消息前 80 字>'` |
| | | **④** 成功 → 逐条应用（见下方「应用分支」） |
| | | **⑤** 有 `revised>0` 或 `deleted>0` 才 `saveState()` |
| **③-b 关系层二次维护** | `core/rel-maint.js#relRepairMaint` + `core/rel-maint.js#mergeRelMaint` | **仅当** `ai.revised>0 或 ai.deleted>0` 时执行；AI 可能产生新的孤儿行与悬空引用 → 再跑一次并与第 ① 段的口径**合并**（`mergeRelMaint(前, 后)`）；结果追加进 `notes` |
| **③-c 计划/悬念修复** | `core/plan-repair.js#runPlanSuspRepair({silent:true, cause})` | **跳过原因三选一**：`disabled`（调用方传 `opts.planSusp===false`）· `no-hook`（钩子未接线）· `ai-off`（**自动模式**且 `cfg.repairAutoAi===false` —— 该开关语义是「自动修复只做机械清理」，故本步一并跳过） |
| | | **结果计数**：`closedP`（了结计划）· `closedS`（揭晓悬念）· `mergedP` / `mergedS`（合并组数）· `removedDup` · `revised` · `deleted` · `merged` · `made` · `skipped` · `blocked` · `error` |

**`repairApplyAiResult` 的逐条应用分支（硬约束：禁止新增）**

| 子步 | 分支 |
| --- | --- |
| **删除** | 编号不在候选内 → `skipped++`；条目已不存在 → `skipped++`；通过 → `core/merge.js#tombMany` 写墓碑后从容器移除，`deleted++` |
| **修订** | 项非对象 → `skipped++`；编号不在候选内 → `skipped++`；字段名不在 `REPAIR_FIELD_KEYS` → `skipped++`；条目已不存在 → `skipped++`；维度不在 `REPAIR_DIM_SPEC` → `skipped++`；文本经 `repairNormText` 后为空 → `skipped++`；超 `hardCap`（该维硬上限）→ **截断**；截断后仍判为垃圾（`repairIsGarbage`）→ `skipped++`；通过 → 写回，`revised++` |
| **标题** | 归一并截 **40 字**；空 → `skipped++` |
| **标签** | 允许字符串（按 `，,、#` 与空白切分）；长度须 **3–5**；写回时 **`keywords = []`**（`tags` 为唯一事实源） |

> **口径**：AI **只能**改/删给定候选，**不能新增**条目，也不能改候选之外的任何条目 —— 这是"窄契约"的含义（机理见 §3.9.5）。

### 3.5 收尾

| 序 | 步 | 口径 |
| --- | --- | --- |
| 1 | **汇总** | `made = stage1.merged + stage1.deleted + ai.revised + ai.deleted + planSusp.made`（`planSusp` 出错时不计） |
| 2 | **记账** | `core/repair.js#repairLogPush`（环形记录，上限 **5**：auto / cause / merged / deleted / revised / candidates / aiUsed / skipped / ms / 候选五类计数 / notes 前 8 条）+ `saveState()`。**现状：一次修复占两条** —— `core/repair.js#runRepairMech` 自记一条（供单独调用时也有记录），`core/repair.js#runRepair` 收尾再记一条（字段更全）→ 见 Q6 |
| 3 | **报告** | `core/repair.js#repairReport`（人读一句）+ `dbgLog('修复', {...})`（**20+ 字段**，含 `floorJump` / `clockSync` / `planSusp` 分支或跳过原因 / 各计数 / `aiError` / 条目总数） |
| 4 | **通知** | 非 `silent` 时 `notify(...)`：有 AI 改动 → `success`，否则 `info`；文案 = 机械清理 4 项 + 候选 4 项 + AI 3 项 + `report` |
| 5 | **落盘** | 收尾**无条件** `saveState()` 一次（把日志与计数写盘）；闸门被拦下的路径**不改记忆数据**（G3 例外，见 §3.1） |

**返回结构**（供调用方与调试桥取用）：`{ made, ms, stage1, ai, cands, pickStat, mech, report, aiUsed, relMaint, relCounts, planSusp, planSuspSkipped, floorJump, floorJumpSkipped, clockSync, clockSyncSkipped }`。

### 3.6 触发源（**当前只有两个**）

| 触发源 | 落点 | 条件 | 参数 |
| --- | --- | --- | --- |
| **手动** | `ui/panel.js#panelAction` 的 `repair` 分支 | 用户点「🛠 自动修复」 | `{ cause: '手动' }`（→ G3 **重置**同楼层计数） |
| **提取合并失败** | `host/extract.js` → `core/repair.js#scheduleAutoRepairOnMergeFail` | `cfg.autoRepairOnMergeFail`（默认 **开**）且无在途修复 | 延迟 `cfg.repairFailDelaySec`（默认 **15s**）后 `{ silent:true, cause:'提取合并失败后自动触发' }` |

> ⚠️ **U145②**：`cfg.autoRepairEveryOps` 的注释语义是「每 N 次提取/摘要后最多自动修复一次」，但**没有任何地方"只因计数到期"而触发修复** —— `host/extract.js` 只做了 `bumpRepairOp()` 计数（两处），而 `autoRepairOpDue()` 只在 `runRepair` 内部被检查。因此**频率闸门当前的实际作用是给"合并失败自动修复"限流**，而不是周期性触发。**已裁决：收敛为"仅合并失败"**（Q1），实现归 `应-17`。
> **另**：手动入口**不弹二次确认**（`ui/panel.js#DANGER_ACTION_PROMPTS` 无 `repair` 键），与 `docs/D23` §3.2 的"维护区动作须走既有二次确认口径"不一致 → 见 Q7。

### 3.9 步骤机理（为什么这样编排 · 每一步在内部做什么）

#### 3.9.1 编排机理（三段式 = 成本分层）

| 层 | 做什么 | 机理（为什么这样分） |
| --- | --- | --- |
| **闸门** | 先判"要不要跑" | 修复是**读-改-写整库状态**的长任务：与在途任务并发会互相覆盖（G1）；内容没变时重复修复只会重复烧 AI（G3）；也不必每次都跑（G2）。**闸门在改数据之前**，这是"跳过时零副作用"的结构保证 |
| **① 机械清理（零 AI）** | 全库机械合并 / 清扫 / 裁剪 / 关系层 / 台账 / 时钟 | 这些问题的判据**完全可机械判定**（内容哈希、条数配额、调用次数、结构合法性）→ 不需要模型；先跑它还能**缩小** ② 的候选面（重复项已合并、垃圾已清掉） |
| **② 候选筛选（零 AI）** | 把全库压到 ≤ `cfg.repairMaxItems` | AI 的输入成本与输出不确定性都与条数正相关 → 必须先择优；低相关孤例没有重复风险，直接不进候选 |
| **③ 窄契约 AI 修订（最多 1 次）** | 只让模型在候选内改 / 删 | 模型擅长"改写措辞"这类语义工作，**不擅长"找出全库哪里有问题"**（那由 ①② 负责）；1 次请求是成本与效果的折中 |
| **收尾** | 汇总 / 记账 / 报告 / 通知 | 三处出口（通知 / 日志 / 返回值）**同源**，避免各算一套数 |

> **顺序的硬约束**：AI 段必须排在机械段**之后** —— 机械段会**删除与合并条目**；若先跑 AI，模型可能正在为"即将被机械清理掉的条目"浪费改写，而且 AI 删掉条目后关系层还要再修一次（这就是 ③-b 存在的原因）。

#### 3.9.2 九步逐步机理

| 序 | 步 | 内部做了什么（机理） | 为什么在当前位置 / 换序或不做会怎样 |
| --- | --- | --- | --- |
| **1** | 机械去重 | 按**内容哈希**做并集（`core/migrate.js#contentDedupeArray`，10 维）+ 同名称并集（`core/repair.js#repairMergeByName`：物品/概念/档案/名册，字段只增不减、货币数量合计）+ 场景两级并集（同路径 + 相似地名）+ 状态主体「全名 / 名」归并 | 必须在 ② 之前：重复条目会推高"相关性"判定，也会让第 3 步的配额裁剪把**本可合并的两条**裁掉一条 |
| **2** | 遗忘清扫 | 只清"调用次数 ≤ 全局均值 × `cfg.lowUseForgetRatio`（默认 0.05）"的**极端**低使用条目；机理是"按使用情况"做语义清理 | 排在配额裁剪之前：先按使用情况清，再让配额兜底；阈值刻意低（0.05）是为了**只清极端**，避免顺手删掉有内容的条目 |
| **3** | 条数裁剪 | 按各维**有效上限**裁剪（`core/ingest.js#enforceDimCaps`；上限 = 存储总上限 × 该维占比，`core/ingest.js#storeCapFor`） | 配额类问题在这里一次性解决；排在 1/2 之后，避免"先按条数裁掉、后才发现本来可以合并或该被遗忘清扫" |
| **4** | 垃圾清理 | 空 / 占位 / 过短（`core/repair.js#repairIsGarbage`：`REPAIR_PLACEHOLDER` 命中、有效字符不足）+ 已了结 / 已揭晓的计划悬念残留；**写删除墓碑** | 清掉"结构上没有意义"的条目，减少 ② 的候选噪声；放在 3 之后是因为裁剪只看条数、不看内容质量 |
| **5** | 衰退清扫 | 状态 / 记忆 / 平行 / 传言四域各自在"条数 > 上限 × 比例"时触发，并按各域阈值删除（`core/repair.js#repairDecayPass` 转调三处实现） | 与第 2 步的区别：2 看"使用次数"，5 看"时间 / 剧情时间衰退 + 拥挤度"；两者判据不同、都必须在 AI 之前 —— 否则会把即将被衰退清掉的条目送给模型 |
| **6** | 关联层机械维护 | V1 口径五件事：孤儿关联行清理（**写墓碑**）· 去重（同 `dim+refId+who`）· 角色名按档案全名归一 · 锚行悬空引用清理 · `how` / 偏差非法值归一；孤儿**条目**按 `cfg.relOrphanAction`（默认 `keep` 只提示） | 必须在 1/3/4/5 **之后**：条目被合并或删除后，它们的关联行**才变成**孤儿（`dangling`）—— 先清条目、再清关系，顺序反过来就会产生"清完又冒出来"的二次孤儿 |
| **7** | 清理无效关系 | 五类结构无效行：`dangling` / `badDim` / `badRef` / `empty` / `ghost`；被清行写墓碑 | 紧接第 6 步：6 是 V1 口径（黄金样本锁定，不能改），7 是 v3.2.0 的**追加**步；两者口径独立、都留痕 |
| **8** | 楼层突变识别 | 判据在宿主层（**最新情节楼层 − 当前末楼 ≥ 9** → 大幅手动删减）→ 按**内容哈希**归位已处理台账 + 越界区间降级 + 收紧基线；**只改编号、不删条目**、幂等 | 放在最后两步之一：它依赖"条目与台账**已经收敛**"；若跑在前面，后面的删除会让刚归位的台账再次失配 |
| **9** | 剧情时钟刷新 | 取"最新情节"（按内置天数 `storyDay` 判：`core/recall.js#trustedPlotList`）的日期 / 时间 / 地点 / 在场，写回 `state.state` + 可解释来源（`clockSrc`）；`cfg.clockManualLock` 时只维护在场与来源 | 同样放最后：它读的是**最新情节**这一派生结论，而情节可能刚被 1/3/4/5 改动过；在改动之前刷新会写入过期值 |

#### 3.9.3 闸门机理（何时"不跑"，以及为什么不跑也不能乱写）

| 闸门 | 机理 |
| --- | --- |
| **G1 占用** | 修复要**读-改-写整库 `state`**；与摘要 / 提取 / 同步并发会互相覆盖（同一对象、非事务）。故用 `core/ai-hooks.js#aiBusy` 做互斥：宁可跳过，也不并发 |
| **G2 频率** | "每 N 次提取最多一次"是**限流**：`state.autoRepair.ops` 由 `core/repair.js#bumpRepairOp` 在提取成功后 +1（`host/extract.js` 两处），判据 `ops - lastAt >= N`。**已知缺陷**：`lastAt` 全仓无写入点 → 退化为累计计数（U145③） |
| **G3 同楼层上限** | "同一楼层内容未变至多修 N 次"是**幂等保护**：`core/repair.js#latestFloorHash`（宿主注入的楼层正文哈希）判断"内容是否变过"；哈希变 → 归零；手动修复 → 显式归零（用户意图优先）。**注意**：判定过程会写 `state.autoRepair`（运行时计数）并 `saveState()` |
| **触发源前提** | 只有 `silent === true && cause` 才被当作**自动**路径（于是 G2 生效、G3 不重置）；手动路径必然重置 G3。这是"用户点一次算一次"的语义来源 |

#### 3.9.4 候选择优机理（为什么是这 5 类计数）

| 计数 | 机理（为什么它这样判、这样排） |
| --- | --- |
| `defects` | 判据机械可判：空占位 / 超目标字数 / 模糊措辞（`core/repair.js#REPAIR_BANNED`）/ 计划悬念裸问句 / 日期格式 / 标签数不在 3–5 → **必须修**，排在最前（`rank 0–5`） |
| `corrHigh` | 相似度 ≥ `cfg.repairTagSimHigh`（默认 0.5）→ **最可能是重复**，第二优先 |
| `corrLowSkipped` | 相似度 ≤ `cfg.repairTagSimLow`（默认 0.15）→ 同维孤例、无重复风险 → **不进候选**（省 AI） |
| `sampled` | 中间带按 `cfg.repairSampleRatio`（默认 0.2）抽样；用 `state.repairCursor` 游标 + 随机步长 `1 + rand(⌊n/3⌋)` 逐轮推进 → **多轮覆盖全库**而不必每轮全量 |
| `topped` | 每维候选不足 `cfg.repairMinCandidates`（默认 5）时按相似度从高到低补足 → 保证**每维都有机会**被修，不被"某维条目多"挤掉 |

- **相似度择一机理**：同维"标签 ≥ 2 的条目数 ≥ max(2, ⌊n×0.3⌋)"→ 用**标签 Jaccard**（`core/repair.js#repairJaccard`），否则用**正文相似度**（`core/ingest.js#repairSimilarity`）；标签丰富时标签比正文更稳、更便宜。
- **规模封顶机理**：两两比较仅当 `n ≤ REPAIR_CORR_MAX_N`（400）时全量，否则每条随机比 `REPAIR_CORR_SAMPLE`（120）条 → 把 O(n²) 压到常数级，长会话也不会卡在候选筛选上。
- **排序机理**：`rank` 升序 → 相似度降序 → 文本长度降序，然后 `slice(0, cfg.repairMaxItems)`（默认 20）并编号 `n = 1…N`；**编号是第 ③ 段唯一的定位键**（AI 只按编号引用，不回传 id）。

#### 3.9.5 窄契约机理（为什么 AI 只能改候选、不能新增）

1. **信息层限制**：提示词只含候选清单（`core/repair.js#buildRepairPrompt`：`#n ｜ 维度 ｜ 字段 ｜ 标题 ｜ 目标字数 ｜ 相关度 ｜ 来源 ｜ 问题` + 该字段文本**前 400 字**）—— 模型看不到候选之外的任何条目，从信息上就不可能改到别处。
2. **应用层再校验**：`core/repair.js#repairApplyAiResult` 逐条复核 —— 编号必须在 `byN` 映射内、字段名必须落在 `REPAIR_FIELD_KEYS` 闭集、条目必须仍存在、正文非空且非垃圾、超 `hardCap` 截断；任一不过即 `skipped++`（**双保险**：提示词限制 + 落地校验）。
3. **为什么禁止新增**：新增条目 = **创造事实**，必须走提取（`core/ingest.js`）或提升（`core/promote.js`）通道，并参与内容哈希、去重与墓碑体系；让"修复"顺手新增会绕过哈希 / 去重 / 台账，属**数据契约**层面的破坏（§2.4 类别①）。
4. **字段细节机理**：标题截 40 字（显示用短字段）；标签必须 3–5 个且写回时清空 `keywords`（`tags` 是唯一事实源，`keywords` 为遗留镜像）；正文经 `repairNormText` 归一，与入库同一套文本卫生。
5. **删除机理**：一律先写**删除墓碑**（`core/merge.js#tombMany`）再移出容器 → 跨端合并时不会"复活"被修复删掉的条目。

#### 3.9.6 幂等 · 失败 · 落盘机理

| 主题 | 机理 |
| --- | --- |
| **幂等** | 机械段：同输入重复跑不再产生新改动（哈希 / 名称 / 条数判据都收敛）；第 8 步**显式幂等**（同一对"情节楼层 / 末楼"已修过则只报告不写盘）；③-c 自身幂等（同内容去重） |
| **失败隔离** | 第①段每步独立 `try/catch`：**任一步抛错不影响后续步**。代价是"某步静默失败"在读数上不可见 → `技-37` 补逐步留痕 |
| **落盘时机** | 只在"有实际变化"时 `saveState()`：①的 1–3 步合并一次、第 4 步一次、6/7/8/9 各自在变化时一次；③有 `revised>0 或 deleted>0` 时一次；收尾**无条件**再写一次（把日志与计数写盘） |
| **返回值** | 完整对象（含三段计数 + 各 `*Skipped`）→ 调用方与调试桥共用；`cands` 只含编号与维度 / 字段（**不含正文**） |

#### 3.9.7 记账与出口机理

| 出口 | 机理与现状 |
| --- | --- |
| **通知** | 非 `silent` 时一条 toast：机械 4 项 + 候选 4 项 + AI 3 项 + 报告句；自动路径（`silent`）**不弹**，只在被闸门拦下时提示一次原因 |
| **调试日志** | `dbgLog('修复', {…})` 20+ 字段（三段计数、`floorJump` / `clockSync` / `planSusp` 的分支或跳过原因、`aiError`、条目总数）→ **排障第一落点** |
| **修复记录** | `state.repairLog`（**runtime 槽位**、环形 **5** 条、不参与跨端同步）。**现状一次写两条**（机械段自记 + 总编排再记）→ Q6 |
| **状态** | `state.autoRepair`（G2 `ops`/`lastAt`、G3 `hash`/`n`）—— 同为 runtime 槽位 |
