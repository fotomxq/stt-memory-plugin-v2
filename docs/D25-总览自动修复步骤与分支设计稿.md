## 0. 一页摘要

「🛠 自动修复」是一个 **3 段 + 2 个补充步** 的编排，第 1 段零 AI、后两段可关。本稿把它写成**可逐步执行、可逐步验收**的规格。

| 段 | 名称 | 是否用 AI | 步数 |
| --- | --- | --- | --- |
| **闸门** | 占用 / 频率 / 同楼层上限 | —— | 4 道 |
| **①** | 机械清理 | **零 AI** | 9 步（固定顺序） |
| **②** | 候选筛选 | 零 AI | 1 步（5 类计数分支） |
| **③** | 窄契约 AI 修订 | **有 AI**（最多 1 次请求） | 3 步（③ / ③-b / ③-c） |
| **收尾** | 汇总 · 记账 · 通知 · 返回 | —— | 4 步 |

**本轮新发现三条**（均已在 `docs/D17` 登记）：

| 编号 | 发现 | 性质 |
| --- | --- | --- |
| **U145** | **触发与闸门缺陷簇**：① `cfg.autoRepair`（默认 `false`）**全仓无任何读取** → 死键；② `cfg.autoRepairEveryOps` 的"到期即触发"**没有调用点**（只在"合并失败"这一条路径上被检查，实际作用是限流而非触发）；③ `state.autoRepair.lastAt` 被**读取**却**全仓无写入点** → 频率判据 `a.ops - a.lastAt >= N` 退化为 `a.ops >= N`（一旦达标永不重置） | **实现缺陷** |
| **U146** | 第 1 段末两步（**楼层突变识别**、**剧情时钟刷新**）经 `repairHooks` 调用；**钩子未接线时不写 note、不记日志** → 用户无法分辨"这一步没跑"与"跑了没变化" | 可观测性缺口 |

## 3. 方案：步骤 · 顺序 · 分支明细

### 3.0 总览（一次自动修复的完整序）

```text
[触发] 手动（面板） ──┐
       合并失败（延迟 15s）─┤
                          ↓
[闸门] G1 占用 → G2 频率 → G3 同楼层上限 ──(任一不过)→ 直接返回 blocked（不写任何数据）
                          ↓
① 机械清理（零 AI，9 步固定顺序；每步失败被 try/catch 吞掉，不影响后续步）
   1 机械去重 → 2 遗忘清扫 → 3 条数裁剪 → 4 垃圾清理 → 5 衰退清扫
   → 6 关联层维护 → 7 清理无效关系 → 8 楼层突变识别 → 9 剧情时钟刷新
                          ↓
② 候选筛选（零 AI；5 类计数）
                          ↓
③ AI 窄契约修订（最多 1 次请求；自动模式可被 cfg.repairAutoAi 关闭）
   ③ 主修订 → ③-b 关系层二次维护 → ③-c 计划/悬念修复
                          ↓
[收尾] 汇总 made → repairLogPush → saveState → repairReport → 通知 → 返回结构
```

### 3.1 闸门 G1–G3（任一不过即 `blocked`，**不写任何数据**）

| 闸门 | 判据（现行） | 不过时的行为 | 开关 |
| --- | --- | --- | --- |
| **G1 占用** | `aiBusy()` 为真（有修复/摘要/同步在跑） | 自动模式提示「自动修复被占用，已跳过」；手动模式提示「修复进行中」；返回 `{made:0, blocked:true}` | —— |
| **G2 频率** | 自动模式 + 未 `force` + `autoRepairOpDue()` 为假 | 返回 `blocked`，`reason='auto-repair-frequency'`（**静默**，不提示） | `cfg.autoRepairEveryOps`（默认 **8**） |
| **G3 同楼层上限** | 未 `force` 时 `autoRepairTake()` 不通过 | 自动模式提示「已达上限，本次跳过」（同楼层内容未变已修复 n/max 次）；返回 `blocked`，`reason='auto-repair-limit(n/max)'` | `cfg.maxAutoRepairRounds`（默认 **3**） |

**G3 的重置规则（两条）**：① **手动修复**传 `forceReset=true` → 计数归零；② **最新楼层内容哈希变化** → 计数归零。
> ⚠️ **G2 的已知缺陷（U145③）**：`autoRepairOpDue()` 读 `a.lastAt`，但该字段**无处写入** → `0` 恒成立 → 判据退化为 `累计 ops >= N`，即"一旦达标就永久放行"，与"距上次修复已过 N 次操作"的原意不符。

### 3.2 第 ① 段 · 机械清理（零 AI，**9 步固定顺序**）

> 落点：`core/repair.js#runRepairMech`。每步独立 `try/catch`（**任一步抛错不影响后续步**）。
> 落盘：步 1–3 任一有变化 → 一次 `saveState()`；步 4 有删除 → 一次；步 6/7/8/9 各自在有变化时落盘。

| 序 | 步 | 落点 | 分支细节 | 开关 | 计入 |
| --- | --- | --- | --- | --- | --- |
| **1** | 机械去重 | `core/repair.js#repairMergeDedupe` | 同内容条目合并；产 `merged` 计数与 `notes` | —— | `stage1.merged` |
| **2** | 遗忘清扫（低使用） | `core/repair.js#sweepLowUseForget` | 只清「调用次数 ≤ 全局均值×比例」的极端低使用条目 | `cfg.lowUseForgetEnabled`（默认开）· `cfg.lowUseForgetRatio`（默认 **0.05**） | `sweep.swept` |
| **3** | 条数裁剪 | `core/ingest.js#enforceDimCaps` | 按各维有效上限裁剪（上限由总上限 × 占比派生） | 存储上限与占比（`cfg` 遗忘组） | `caps.cut` |
| **4** | 垃圾 / 残留清理 | `core/repair.js#repairPruneGarbage` | 判据 `core/repair.js#repairIsGarbage`；黑名单 `core/repair.js#repairBannedOf` | —— | `stage1.deleted` |
| **5** | 衰退清扫 | `core/repair.js#repairDecayPass` | 状态 / 记忆 / 平行 / 传言四域各自按开关与比例清扫 | 四域 `*Enabled` / `*Ratio` / `*Cutoff` | `decay.deleted` |
| **6** | 关联层机械维护（V1 口径） | `core/repair.js#relRepairMaint` | ① 孤儿关联行清理（**写删除墓碑**）② 去重（同 dim+refId+who）③ 角色名按档案全名归一 ④ 锚行悬空引用清理 ⑤ `how` / 偏差非法值归一；**孤儿条目**另按开关处置 | `cfg.relOrphanAction`：`keep`（**默认**，保留并只提示）/ `clean`（自动清） | `relMaint` |
| **7** | 清理无效关系 | `core/repair.js#cleanInvalidRelLinks` | **五类**：`dangling`（目标不存在）· `badDim`（非法维度）· `badRef`（空指向）· `empty`（无角色且无锚属性的纯空行）· `ghost`（`who` 不在任何已知名册）。被清行一律**写删除墓碑** | 层关闭时不动作 | `relInvalid.removed` / `relInvalid.reasons` |
| **8** | 楼层突变识别 | 经 `repairHooks.floorJump` → `host/floors.js#fixFloorJump` | 判据：**最新情节所在楼层 − 当前末楼 ≥ 9** → 判为大幅手动删减；修正 = 按**内容哈希**归位台账 + 越界区间降级 + 收紧基线；**只改编号、绝不删条目**；**幂等**。分支：`jumped=false`（不提示）· `jumped=true` + `acted=true`（已修正，报台账 n 条 / 越界 m 条）· `jumped=true` + `acted=false`（记录已修正过，本次无新改动） | —— | `stage1.floorJump` |
| **9** | 剧情时钟刷新 | 经 `repairHooks.clockSync`（= 与分析后同步**同一条**处理） | 按**最新情节**刷新 时间 / 地点 / 在场（「最新情节」按内置天数判断）。分支：`manualLock=true` → **只维护在场与来源说明，不覆盖日期/时间/地点**（如实写「已跳过（手工锁定…）」）· `changed=true` → 「已按最新情节刷新（…）」· `changed=false` → 「已是最新（本轮无改动）」 | `cfg.clockManualLock`（默认 **true**） | `stage1.clockSync` |

> ⚠️ **第 8 / 9 步的已知缺口（U146）**：两者都写成 `if (fn) {...}`，**钩子未接线时既不写 `notes` 也不记日志** —— 从通知与日志上看，"没接线"与"跑了但无变化"**无法区分**。建议补一条「跳过原因：钩子未接线」。

### 3.3 第 ② 段 · 候选筛选（零 AI）

> 落点：`core/repair.js#repairCollectCandidates(cfg.repairMaxItems, pickStat)`。
> 逐维遍历候选容器，对每条按「客观缺陷 / 与同维其他条目的相关性」分类，产出 **5 类计数**：

| 计数 | 含义 | 分支行为 |
| --- | --- | --- |
| `defects` | **客观缺陷**条数（结构/字段类，机械可判） | **直接入选** |
| `corrHigh` | **高相关**（标签组/正文相似度高，越可能重复） | **直接入选** |
| `corrLowSkipped` | **低相关**且无缺陷 | **跳过**（不入选） |
| `sampled` | 中段（不缺陷也不高相关）中**抽样**者 | 抽样入选 |
| `topped` | 候选不足时**补足**者 | 补足入选 |
| `total` | 遍历到的条目总数 | —— |

- **上限**：`cfg.repairMaxItems`（默认 **20**，范围 1–60）；**机械清理不受该上限约束**。
- 产物：`cands`（编号化的候选清单，编号 `n` 用于第 ③ 段的按编号改删）+ `pickStat`。

### 3.4 第 ③ 段 · 窄契约 AI 修订（最多 1 次请求）

**进入条件**：`cands.length > 0` **且**（非自动模式 **或** `cfg.repairAutoAi !== false`）。

| 步 | 落点 | 分支明细 |
| --- | --- | --- |
| **③ 主修订** | `core/repair.js#buildRepairPrompt` → `core/ai-hooks.js#aiCallText` → `core/util.js#extractJsonObject` → `core/repair.js#repairApplyAiResult` | **①** 提示词为空 → **不调用**（`ai.used=false`） |
| | | **②** 响应为空 / JSON 解析失败 → `ai.error='AI 未返回有效 JSON'` |
| | | **③** 抛错 → `ai.error='<消息前 80 字>'` |
| | | **④** 成功 → 逐条应用（见下方「应用分支」） |
| | | **⑤** 有 `revised>0` 或 `deleted>0` 才 `saveState()` |
| **③-b 关系层二次维护** | `core/repair.js#relRepairMaint` + `core/repair.js#mergeRelMaint` | **仅当** `ai.revised>0 或 ai.deleted>0` 时执行；AI 可能产生新的孤儿行与悬空引用 → 再跑一次并与第 ① 段的口径**合并**（`mergeRelMaint(前, 后)`）；结果追加进 `notes` |
| **③-c 计划/悬念修复** | `core/plan-repair.js#runPlanSuspRepair({silent:true, cause})` | **跳过原因三选一**：`disabled`（调用方传 `opts.planSusp===false`）· `no-hook`（钩子未接线）· `ai-off`（**自动模式**且 `cfg.repairAutoAi===false` —— 该开关语义是「自动修复只做机械清理」，故本步一并跳过） |
| | | **结果计数**：`closedP`（了结计划）· `closedS`（揭晓悬念）· `mergedP` / `mergedS`（合并组数）· `removedDup` · `revised` · `deleted` · `merged` · `made` · `skipped` · `blocked` · `error` |

**`repairApplyAiResult` 的逐条应用分支（硬约束：禁止新增）**

| 子步 | 分支 |
| --- | --- |
| **删除** | 编号不在候选内 → `skipped++`；条目已不存在 → `skipped++`；通过 → `core/repair.js#tombMany` 写墓碑后从容器移除，`deleted++` |
| **修订** | 项非对象 → `skipped++`；编号不在候选内 → `skipped++`；字段名不在 `REPAIR_FIELD_KEYS` → `skipped++`；条目已不存在 → `skipped++`；维度不在 `REPAIR_DIM_SPEC` → `skipped++`；文本经 `repairNormText` 后为空 → `skipped++`；超 `hardCap`（该维硬上限）→ **截断**；截断后仍判为垃圾（`repairIsGarbage`）→ `skipped++`；通过 → 写回，`revised++` |

> **口径**：AI **只能**改/删给定候选，**不能新增**条目，也不能改候选之外的任何条目 —— 这是"窄契约"的含义。

### 3.5 收尾

| 序 | 步 | 口径 |
| --- | --- | --- |
| 1 | **汇总** | `made = stage1.merged + stage1.deleted + ai.revised + ai.deleted + planSusp.made`（`planSusp` 出错时不计） |
| 2 | **记账** | `core/repair.js#repairLogPush`（环形记录：auto / cause / merged / deleted / revised / candidates / aiUsed / skipped / ms / 候选五类计数 / notes 前 8 条）+ `saveState()` |
| 3 | **报告** | `core/repair.js#repairReport`（人读一句）+ `dbgLog('修复', {...})`（**20+ 字段**，含 `floorJump` / `clockSync` / `planSusp` / 各计数 / `aiError` / 条目总数） |
| 4 | **通知** | 非 `silent` 时 `notify(...)`：有 AI 改动 → `success`，否则 `info`；文案 = 机械清理 4 项 + 候选 4 项 + AI 3 项 + `report` |

**返回结构**（供调用方与调试桥取用）：`{ made, ms, stage1, ai, cands, pickStat, mech, report, aiUsed, relMaint, relCounts, planSusp, planSuspSkipped, floorJump }`。

### 3.6 触发源（**当前只有两个**）

| 触发源 | 落点 | 条件 | 参数 |
| --- | --- | --- | --- |
| **手动** | `ui/panel.js#panelAction` 的 `repair` 分支 | 用户点「🛠 自动修复」 | `{ cause: '手动' }`（→ G3 **重置**同楼层计数） |
| **提取合并失败** | `host/extract.js` → `core/repair.js#scheduleAutoRepairOnMergeFail` | `cfg.autoRepairOnMergeFail`（默认 **开**）且无在途修复 | 延迟 `cfg.repairFailDelaySec`（默认 **15s**）后 `{ silent:true, cause:'提取合并失败后自动触发' }` |

> ⚠️ **U145②**：`cfg.autoRepairEveryOps` 的注释语义是「每 N 次提取/摘要后最多自动修复一次」，但**没有任何地方"只因计数到期"而触发修复** —— `host/extract.js` 只做了 `bumpRepairOp()` 计数（两处），而 `autoRepairOpDue()` 只在 `runRepair` 内部被检查。因此**频率闸门当前的实际作用是给"合并失败自动修复"限流**，而不是周期性触发。**需裁决**：补上周期触发，或明确"自动修复只由合并失败触发"并清理相关键（§6 Q1）。
