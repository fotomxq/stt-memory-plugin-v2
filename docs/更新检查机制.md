# 更新检查机制（Git 通道）

> 文档版本：v1.1 ｜ 日期：2026-09-26 ｜ 状态：生效（P0 实施；v2.11.1 修复「宿主后端错误」并改为 HTTP 优先）
> 定位：V2 的更新检查与更新执行机制 —— 触发时机、判定通道与优先级、配置项、状态持久化、失败姿态与测试覆盖。
> 事实源：`core/update.js`（纯逻辑）、`host/update.js`（编排）、`adapters/update-state.js`（持久化）、`docs/P0-探针报告.md`（ST 端点源码证据）。
> 用户要求：「github 的项目地址，为后续更新检查的地址，请构建首次启动插件自动检查、设定手动检查更新的机制。」

---

## 1. 触发时机

| 时机 | 行为 | 判定 |
| --- | --- | --- |
| **首次启动**（安装后第一次初始化） | 自动检查一次 | `shouldAutoCheck()` → `first-startup` |
| 后续启动 | 距上次检查 ≥ 间隔（默认 **24h**）才自动检查 | → `interval-elapsed` |
| 设定内「🔍 检查更新」 | 手动检查（不受开关与间隔限制），并**落盘**本次结果 | → `manual` |
| 设定内「⬆ 立即更新（ST）」 | 显式调用 ST 更新端点执行 `git pull` | **仅用户点击**，自动路径永不调用 |
| 关闭「启动时自动检查更新」 | 自动路径完全不发起任何请求 | → `disabled` |
| 无宿主（Node / 非酒馆环境） | 直接跳过 | → `no-host` |

实现：`index.js` 在 `init()` 末尾以**不 await**方式调用 `startupUpdateCheck()`（失败静默，绝不阻塞初始化、发送与提取）；
手动检查走 `maybeAutoCheckOnStartup({ manual: true })`，与自动检查共用同一入口，因此同样会写入 `lastCheckAt` / `lastResult`。

## 2. 判定通道与优先级

**v2.11.1 起默认为「HTTP 优先」**：宿主 Git 端点（`/api/extensions/version|update`）默认**关闭**，
版本判定只用 GitHub raw 清单；仅当用户在设定里显式开启「使用宿主 Git 更新端点」时，才走 git 真值通道。

```text
runUpdateCheck()  · cfg.useStGitEndpoint 默认 false
 ① 远端清单（默认唯一的通道；纯 HTTP，无需 git）
    GET <repo>/manifest.json   → version
    GET <repo>/CHANGELOG.md    → 更新要点（首个版本段落前 5 条）
    · GitHub → raw.githubusercontent.com；Gitee → /raw/<branch>
    · 仓库根没有 manifest.json 时（例如 V1 形态仓库）→ 用 CHANGELOG.md 首条版本兜底判定
 ② 宿主 Git 端点（**仅当 useStGitEndpoint=true**；Git 真值）
    POST /api/extensions/version { extensionName, global }
    → { isUpToDate, currentCommitHash, currentBranchName, remoteUrl }
    · 先试用户态（global:false），失败再试全局态
    · 传输层失败（handshake/IO error）→ 短路 + 6h 会话退避（不再翻倍后端日志）
 ③ 交叉判定
    · 端点说「有更新」但清单版本与本地相同 → 判为**同版本新提交**（以 Git 为准）
    · 端点不可用 → 完全以版本号比较为准
```

### 2.1 为什么默认关掉宿主 Git 端点（v2.11.1 修复）

**现象**：安装后宿主弹出「后端错误 / Failed to get extension version: Internal error: Git handshake failed:
An IO error occurred when talking to the server」；其它插件不触发。

**根因（两条，均已修）**：

1. `manifest.json` 里的 `auto_update: true` 会让**酒馆自身**在加载期对第三方扩展做 Git 版本校验
   （`POST /api/extensions/version` → 服务端 `checkIfRepoIsUpToDate()` 做 `git fetch`）。
   在**没有 git 能力 / 到 GitHub 不通的宿主**（如 TauriTavern 原生移植）上该请求必然 500，
   宿主把它当作「后端错误」弹窗暴露给用户 —— 其它插件没有 `auto_update: true`，所以只有本插件触发。
   → 现改为 `auto_update: false`（本插件自带更新检查，不依赖酒馆代做 git 检查）。
2. 本插件的首次启动自动检查会**主动**请求同一个端点（端点优先）——同样会触发后端 git handshake。
   → 现改为默认只用 GitHub raw 清单（纯 HTTP）；Git 端点仅在设置开关打开时使用。

**用户可见行为**：默认情况下更新检查完全走 HTTP，宿主的 Git 端点不再被触碰（回归断言见 §6）；「立即更新（ST）」按钮
在开关关闭时**不发起任何请求**，只给出引导文案（提示可用设置开启，或按仓库说明手动更新）。

要点：

- **端点优先**是因为它反映真实的 Git 状态（`isUpToDate` 由服务端 `checkIfRepoIsUpToDate()` 得出）；
- 回退通道**只读**：不写扩展目录、不执行远端代码（V2 不建第二条代码更新通道，见 `docs/P0-探针报告.md` §3）；
- 所有网络请求带 **8s 超时**（`AbortController`），超时即放弃并如实回报；
- 远端地址由**设置项** `updateRepo` + `updateBranch` 推导，默认 `https://github.com/fotomxq/stt-memory-plugin-v2`（分支 `main`）。

## 3. 配置项（`extensionSettings.ftt_memory_v2`）

| 键 | 默认 | 说明 |
| --- | --- | --- |
| `autoUpdateCheck` | `true` | 启动时自动检查（仅检测与提示；关闭后零远端请求） |
| `updateRepo` | `https://github.com/fotomxq/stt-memory-plugin-v2` | 更新检查仓库地址（GitHub，可改） |
| `updateBranch` | `main` | 检查分支 |
| `updateCheckIntervalHours` | `24` | 自动检查间隔（小时） |
| `useStGitEndpoint` | `false` | **是否使用宿主 Git 端点**（`/api/extensions/version`、`/api/extensions/update`）。默认关：无 git 的宿主会对该端点返回「Git handshake failed」并被宿主当「后端错误」弹窗 |

更新状态（由本机制自动写入，不需用户维护，位于 `extensionSettings.ftt_memory_v2.update`）：

| 字段 | 含义 |
| --- | --- |
| `firstRunAt` | 首次运行时间（幂等，只写一次） |
| `startupCheckedAt` | 首次启动检查完成时间（用于「首次启动必查」判定） |
| `lastCheckAt` | 最近一次检查时间（自动或手动） |
| `lastResult` | 最近一次结果摘要：`{ ok, via, current, remote, status, remoteCommit, isUpToDate, commitOnly, points, error }` |

## 4. 界面与状态文案

| 元素 | 标识 | 行为 |
| --- | --- | --- |
| 启动时自动检查更新 | `#ftt_v2_autoupd` | 勾选即写 `autoUpdateCheck` |
| 更新检查仓库 | `#ftt_v2_updrepo` | 失焦即写 `updateRepo` |
| 使用宿主 Git 更新端点 | `#ftt_v2_usegit`（浮层同名 `data-ftt-v2="useStGitEndpoint"`） | 勾选即写 `useStGitEndpoint`；关闭时「立即更新」不发请求、只给引导 |
| 检查更新按钮 | `#ftt_v2_checkupd` | 手动检查 → 回填状态行 |
| 立即更新按钮 | `#ftt_v2_doupd` | 开关开启时调用宿主 Git 更新端点 → 回填 commit 与「请重载页面」；关闭时只回填「未执行：…」引导 |
| 状态行 | `#ftt_v2_updstate`（`data-ftt-update-state`） | 显示「时间 · 文案」 |

状态文案（`core/update.js` `updateReport()`，纯函数、可断言）：

| 情形 | 文案 |
| --- | --- |
| 远端版本更高 | `发现新版本 2.1.0（当前 2.0.0） · 来源 remote-manifest:github` |
| 同版本 | `已是最新版本 2.0.0` |
| 本地版本更高 | `本地版本（2.1.0）高于远端（2.0.0）—— 可能是开发版` |
| 端点可用且最新 | `已是最新（Git 校验） · 来源 st-endpoint` |
| 端点报有更新但版本相同 | `远端有更新（Git 校验 · 同版本新提交） · <短 commit>` |
| 全路径失败 | `检查更新失败：<原因>` |

其它入口：`/ftt` 状态输出含「更新：…」一行；`FTT.update()` 调试导出返回 `{ config, state, status, hasUpdate }`。

## 5. 失败姿态与安全

| 项 | 约定 |
| --- | --- |
| 网络失败 / 超时 | 静默（只写 `lastResult.error`），**不弹错、不阻塞**任何功能 |
| 宿主无 git 能力 | 默认不触碰宿主 Git 端点 → **不再产生「后端错误」弹窗**；版本判定由 HTTP 清单完成 |
| 无宿主 | 自动检查直接跳过；手动入口返回明确原因 |
| 端点 403/404（多用户权限、非 Git 安装） | 先试全局态，再回退远端清单；都不行则如实回报 |
| 代码分发 | **扩展自身不下载、不写入、不执行远端代码**；`git pull` 一律由 ST 端点或用户手工完成 |
| 隐私 | 只请求配置仓库的 `manifest.json` 与 `CHANGELOG.md`（公开文件），不发送任何本地数据 |

## 7. 与 ST 原生更新的关系

| 层次 | 由谁负责 | 说明 |
| --- | --- | --- |
| 检测（是否有更新） | ST 端点 + 本机制远端回退 | ST 侧 `isUpToDate` 为 Git 真值；本机制补版本号与更新要点 |
| 执行（拉取代码） | **ST**（`Manage extensions → Update` → 服务端 `git pull`）或用户在服务器手工执行 | 本机制的「立即更新」按钮只是**代为调用**该端点 |
| 自动更新（随 ST 包版本） | 已关闭（`manifest.auto_update: false`） | v2.11.1 起不再让酒馆对本扩展做加载期 git 校验（无 git 宿主会弹后端错误）；更新提示与版本判定由本机制负责 |
