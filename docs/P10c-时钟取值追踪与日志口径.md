# P10c · 剧情时钟「取值追踪」与日志口径（v2.37.0）

> 文档版本：v1.0 ｜ 日期：2026-09-26 ｜ 状态：生效（v2.37.0）
> 触发（用户原话）：「**时钟日志记录有问题，需明确从哪里取值，取值逻辑是什么。以方便追踪问题。**」
> 涉及：`core/clock-trace.js`（新）· `core/clock-extract.js` · `core/clock-patrol.js` · `core/clock-ai.js` · `ui/debug.js` · `ui/clock.js` · `index.js` · `devtools.js` · `tests/unit/clock-trace.test.js` · `tests/smoke-test.js`

## 1. 原来的日志缺什么（问题定位）

时钟域原有 6 条 `dbgLog('时钟', …)`（逐字移植自 V1），但**不足以回答「这个值是从哪里取的」**：

| # | 缺口 | 后果 |
| --- | --- | --- |
| 1 | **只有日期与在场标了来源**（`dateFrom`/`presentFrom`），**时间与地点没有** | 时间/地点被改错时无从判断是正文正则、正文头结构还是情节侧给的 |
| 2 | 来源中文标签表**残缺**（旧表仅 6 项：regex/plot/atom-latest/prev/scene/manual） | 命中「纯时段词 / 自定义正则 / 标记式 / 相对推进 / 第 N 天换算 / 最新场景 / 移交锚点」等来源时，日志直接打印**英文键**，看不懂 |
| 3 | 只记「**取值**」不记「**判据**」 | 不知道为什么选了它（正文头带加成？同源优先？异常闸门？） |
| 4 | 只记「取值」不记「**落选**」 | 正文里明明有另一个日期，为什么没被采用 —— 无法判断 |
| 5 | 降级只记 `degraded: true/false`，**不记原因与细节** | `degradeReason`（force / anomaly:jump / anomaly:backward / no-date）算出来了却没进日志，异常对比的日期与年差也丢失 |
| 6 | 只记「解析结果」，**不记本次实际改了什么** | 日志说的是「自动解析剧情时钟」，但可能只有在场/见面标记变了（误导排查方向） |
| 7 | 「日期来自正文头结构」会被记成「正文正则」 | V1 的 `resolveStoryClock` 对正文侧**统一**写 `source.date='regex'`（v1.206 20055 起，`regexCand = { date: probeDate, src: 'regex' }`），即便实际命中 `▷…` 结构头 → 日志误导 |

## 2. 现在的口径：一条日志回答四个问题

每条时钟日志（`kind='时钟'`）都带下面四类信息（另有 `traceId` 关联到内存追踪）：

| 类别 | 字段 | 含义 |
| --- | --- | --- |
| ① **值** | `date` / `time` / `location` / `present` | 落盘后的值（与 `state.state.*` 同源） |
| ② **来源** | `dateFrom` / `timeFrom` / `locationFrom` / `presentFrom` | **中文来源名**（取自 §3 的全量登记表）；另附 `dateFromV1`（V1 口径的原始标记，便于对旧日志/文档） |
| ③ **判据** | `dateWhy` / `timeWhy` / `locationWhy` / `presentWhy` | 为什么取它（命中规则 + 比较口径） |
| ④ **落选** | `rejects[]`（前 6 条）+ `rejectsTotal` | 未采用的候选：`字段=值←来源（原因）`（完整清单在追踪里，含原文片段） |
| ⑤ **降级** | `degradeReason`（中文） | `正文未识别到日期` / `日期异常：年份远超当前时钟` / `日期异常：剧情时间大幅倒退` / `日期异常：格式非法` / `强制降级（设定已开启）` |
| ⑥ **落盘** | `applied[]` / `unchanged` / `seenStamped` | 改了哪些（`字段：旧 → 新`）、没改哪些（含「手工锁定」）、是否更新了见面标记 |
| ⑦ **上下文** | `textMode` / `textFloors` / `textChars` / `sample` / `chain[]` | 取文来源与楼层、样本前 80 字、本次参与的取值环节（按判定顺序） |
| ⑧ **指引** | `how` | 指向 `FTT.clockTrace()` 与「设定 → 调试 → 🕒 时钟取值追踪」 |

**动作名如实区分**：本次真的改了日期/时间/地点才叫「自动解析剧情时钟/在场（多源择优 + 降级）」；
只有在场/见面标记变化时叫「在场/见面时间维护（日期·时间·地点本轮无改动）」；**什么都没变则不写日志**（V1 同口径，避免噪声）。

## 3. 逐字段取值来源与逻辑（**核心表**）

来源键 → 中文名（`core/clock-trace.js#CLOCK_SRC_LABEL`，共 17 项；`FTT.clockSrcLabels()` 可列）。

### 3.1 日期 `state.state.date`

| 顺序 | 来源键 / 中文名 | 取值逻辑（判据） | 代码 |
| --- | --- | --- | --- |
| 0 | `manual` 手工强制改写 | 手工值直接采用；`cfg.clockManualLock`（**默认开**）→ 自动提取不再覆盖日期/时间/地点 | `clock-patrol.js`；V1 20055 |
| 1 | `header` 正文头结构（▷/▶） | 命中 `▷0051年1月2日（纪年）·冬(场景)` 这类结构头；带**位置加成**（压过同文本零散命中） | `extractClockFromHeader`（V1 19696） |
| 2 | `regex` 正文正则（最新正文） | 预设正则族 `CLOCK_DATE_SCAN` 扫描正文，**取最后一次命中**；命中位置须非长日期尾部 | `extractClockFromText`（V1 19748） |
| 3 | `custom` 自定义正则（设定页） | `cfg.clockDateRegex`（设定页或 AI 捕捉写入），捕获组 1/2/3 视为 年/月/日 | 同上 |
| 4 | `marker` 标记式 | `【日期：…】` 或行内 `日期：…` | 同上 |
| 5 | `relative` 相对日期推进 | 未给绝对日期时，按「明天/次日/3 天后/N 天前」在**上一个日期**上加减（`cfg.clockRelative`，需已有日期） | 同上 |
| 6 | `storyday` 「第 N 天」纪元换算 | 正文只给 `第 N 天` 且设了 `cfg.clockStoryDayEpoch` → 仅当**没有**任何日期时才换算 | `resolveStoryClock` |
| 7 | `plot` 最新情节 | 正文侧没有可用日期、或正文日期被异常闸门拦下 → 取最新情节节点的日期 | V1 20055 |
| 8 | `atom-latest` 原子数据（最新存在日期） | 正文与情节都拿不出日期时的降级来源 | 同上 |
| 9 | `prev` 沿用已有值 | 没有任何候选日期 → 保留 `state.state.date` | 同上 |

**择优（多候选时）**：先按日期字符串**取最大**（最新），同一天按优先级 `最新情节 > 正文 > 原子降级 > 沿用旧值`。
**异常闸门**（`clockDateAnomaly`）：格式非法 / 年份远超当前时钟（`cfg.clockAnomalyJumpYears`）/ 剧情时间大幅倒退 → 该正文日期**不采用**并进入降级路径（原因写进日志 `degradeReason` 与追踪 `degrade.detail`，含对比锚点与年差）。

### 3.2 时间 `state.state.time`

| 来源键 / 中文名 | 取值逻辑 |
| --- | --- |
| `header` 正文头结构 | `▶第17602天 08:52->09:05(状态)` / `▷…09:10` → 取起止时间的起始值（`timeEnd` 另存） |
| `regex` 正文正则 | `24 小时制`（`08:52`）或「中文点数」（`晚上九点`）→ **带数字优先** |
| `custom` 自定义正则 | `cfg.clockTimeRegex`，捕获组 1 优先 |
| `marker` 标记式 | `【时间：…】` / 行内 `时间：…` |
| `daypart` 纯时段词 | 正文只有「清晨/傍晚/深夜」等词（**权重低于带数字**，落选时日志给出该原因） |
| `plot` / `atom-latest` | 取**与胜出日期同源**的节点优先，其次取「同一天」的其它来源；都无 → 该节点自身的时间 |
| `manual` | 手工强制改写（锁定中不覆盖） |

**取值逻辑链**：`与胜出日期同源优先 → 同日期的其它来源 → 正文 → 最新情节 → 原子数据`（日志 `timeWhy` 原样给出该链）。

### 3.3 地点 `state.state.location`

同 §3.2 的来源与「同源优先」链，另有两个特有来源：

| 来源键 / 中文名 | 取值逻辑 |
| --- | --- |
| `header` 正文头结构 | `▷凉州卫-中央大街-钟鼓楼下`（无日期/天数/时间的短行、无句读、含中文 → 判为地点行） |
| `scene` 最新场景（降级） | 仅**降级路径**且前面没给出地点时，取场景库「最新场景」（按 `floorEnd` → `uses` → 路径深度排序） |

### 3.4 在场角色 `state.state.present`

| 来源键 / 中文名 | 取值逻辑 |
| --- | --- |
| `latest-ai` 最新 AI 正文点名 | 在**最新 AI 正文**里匹配到已建档角色（别名匹配，别名长度 ≥2） |
| `plot-atom` 最新情节涉及角色 | 正文无点名 → 用最新情节的 `entities` |
| `keep-prev` 沿用旧名单 | 都没有 → 保留上一次名单（**不清空**，仅当拿到正文但无已知角色时才判空 = 严格限制） |

> 楼层窗口回退文本**不参与**在场判定（避免跨楼层角色堆叠）—— 日志 `textMode` 会显示 `floor-window`。

### 3.5 巡检锚点（`clockPatrolAnchorInfo`，V1 20351）

| 顺序 | 来源键 / 中文名 | 取值逻辑 |
| --- | --- | --- |
| 1 | `manual` 手工强制改写 | 最高可信；与库内多数年份冲突时记 `conflict`（由调用方决定是否放行） |
| 2 | `clock` 当前剧情时钟 | 有效即用 |
| 3 | `atoms-majority` 原子数据多数派 | 年份占比 ≥60% 且 ≥2 条才可信（单条脏数据可能正好是最新情节，故多数派优先于「最新情节」） |
| 3b | 同上（全库一致） | 无多数派时，只有「全部有效日期年份一致」才采用 |
| — | 无 | 彻底没有有效日期 → `usable=false`（宁可不修） |

**为什么不修**：自动路径遇「锚点与库内多数年份冲突（≥3 条）」→ 只统计不修改；写回前一律先建**全量快照**（可回滚）。
这些判据都写进日志 `anchorFrom` / `anchorWhy` / `conflict` / `reasons` / `samples` 与追踪 `chain`。

## 4. 追踪结构（`core/clock-trace.js`）

```text
{ id, stage, at, action,
  text:    { mode, floors, chars, sample },          // 取文来源
  chain:   ['① 锚点/手工判定', '② 取文', '③ 正文侧候选', …],   // 按判定顺序
  picks:   { date|time|location|present: { value, from, fromLabel, why } },
  rejects: [{ field, value, from, fromLabel, idx, raw, why }],  // 落选候选（含原文片段）
  degrade: { degraded, reason, reasonLabel, detail },
  applied: { fields: [{field, from, to, changed}], locked, unchanged, present },
  notes:   [ … ] }
```

- `stage`：`resolve`（自动解析）· `patrol`（巡检锚点与修复）· `regex-ai`（AI 捕捉正则）· `time-repair`（AI 时间修复）。
- **环形缓冲**：每阶段保留最近 `CLOCK_TRACE_KEEP = 5` 条；**仅内存**（不落 localStorage，避免日志膨胀）。
- **纯记录**：追踪只读 `cfg`/`state`，**不参与任何取值判定**（黄金样本 `J(got)===J(oracle)` 强制约束 —— 见 §5）。
- 排障入口：`FTT.clockTrace()`（全局最近一条）/ `FTT.clockTrace('resolve'|'patrol'|'regex-ai'|'time-repair')` / `FTT.clockTraceAll()` / `FTT.clockTraceSummary()` / `FTT.clockTraceClear()`。
- 界面入口：**设定 → 调试 → 「🕒 时钟取值追踪」**（`ui/debug.js`，只读，含四阶段折叠面板：取值环节 / 取文 / 值←来源+判据 / 未采用候选 / 降级 / 备注 / 落盘）；总览时钟区多一行 `🕒 取值 [resolve] …` 摘要。

## 5. 顺带修复的两个真实缺陷（本批实测）

| # | 缺陷 | 影响 | 处置 |
| --- | --- | --- | --- |
| 1 | **追踪构造自身的作用域错误**（本批引入后立即发现）：`floorsTxt` 闭包引用了块级 `last`（`if (text) { const last = … }` 之外不可见）→ `ReferenceError` 被外层 `catch` 吞掉 → **解析结果突然变空**（日期/时间/地点全丢） | 严重（values 丢失） | 追踪构造改为重新取楼层号；**并把这条踩坑写成回归断言**（单测 R2、文档 §6） |
| 2 | **`storyDay` 误判「有改动」**（V1 移植遗留）：V1 写的是 `Number(state.state.storyDay) !== sd`，而 V2 的 `emptyState()` **没有 `storyDay` 键** → `Number(undefined)=NaN ≠ 0` 恒成立 → **每次提取都判为有改动**（多写一次 state、日志恒为「自动解析剧情时钟」，正是用户感到的「日志有点乱」） | 日志噪声 + 多余落盘 | 比较前把缺失键视作 0（V1 的 state 本就带该键 → 语义等价），单测断言「无改动 → 不写日志」 |

另：时钟日志**构造失败不再静默** —— 三个日志点的 `catch` 会写一条 `kind='异常'`（v2.34.0 的异常通道），
避免「日志缺口本身也查不到原因」（缺陷 #1 就是这么被掩盖的）。

## 6. 排障手册（症状 → 看哪里）

| 症状 | 先看 | 判据 |
| --- | --- | --- |
| 日期被改错 | `dateFrom` / `dateWhy` / `rejects` | 若 `dateFrom=正文头结构` → 检查正文 `▷` 行写法；若 `rejects` 里有你期望的日期 → 看它的落选原因（更早出现 / 同值副本 / 异常闸门） |
| 日期没被更新 | `degradeReason` / `textMode` / `dateFrom` | `正文未识别到日期` → 正则与标记式都没命中；`日期异常：…` → 正文日期与锚点冲突（看 `degrade.detail` 的对比锚点与年差）；`textMode=floor-window` → 最新 AI 正文为空，退到窗口文本 |
| 时间/地点不对 | `timeFrom` / `locationFrom` / `*Why` | 是否被「同源优先」从情节侧取走；地点是否走了 `最新场景（降级）` |
| 在场角色不对 | `presentFrom` / `textMode` | `沿用旧名单` = 本轮无点名；`floor-window` 下**不会**判定在场（设计如此） |
| 巡检没修数据 | `anchorFrom` / `anchorWhy` / `conflict` | 锚点不可信 / 自动路径遇多数年份冲突 → 只统计；需先在总览「✏️ 手工改写」设定锚点再手动点巡检 |
| 日志本身缺字段 | `kind='异常'` 的「时钟…日志构造失败」 | 说明日志构造抛错（缺陷 #1 类型），修复方向见该条 `message` |
