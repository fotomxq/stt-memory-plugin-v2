## 0. 怎么用这份清单（与 `D17` 的分工）

| | `docs/D17-未落实事项台账.md` | **本稿 `docs/D22-开发待办清单.md`** |
| --- | --- | --- |
| 回答 | 「**还有什么没做**」 | 「**轮到做哪个、做完了标哪一版**」 |
| 组织 | 按**来源文档**（`D*` / `01`–`05`） | 按**维度序 + 批次**（业务 → 应用 → 数据 → 技术；零风险批先行） |
| 粒度 | `U<n>` = 事实条目（**213 条**，含文档治理类） | 只收**开发项**（四维修订稿 + 后续设计稿的「实施规格」行），文档治理类不入本清单 |
| 完成标记 | 状态改 `✅` | 状态 + **版本号** + **呼应**（`CHANGELOG.md` 条目 + `docs/history/` 批次档） |

> **判据（硬性）**：一行**只有同时**具备「版本号」与「呼应」两项，才可标 `✅ 已开发`；缺任一项 → 记 `🟡 待补留痕`，**不得**只写"已完成"。
> **不复述设计**：事项的落点 / 前置 / 步骤 / 验收 / 回退一律**指向来源稿的对应行**，避免与设计稿二次漂移（同 `D17` §5.4 口径）。

## 8. 销账与维护约定

1. **销账**：一行开发完成后，**同时**填「版本」与「呼应」，状态改 `✅ 已开发`，并在 `docs/D17` 把对应 `U<n>` 改 `✅ 已落地（vX.Y.Z）`；**不删行**（与 `docs/history/` 的只增口径一致）。
2. **留痕缺一不可**：`版本` = 实际发布版本（四处一致）；`呼应` = `CHANGELOG.md` 的 `vX.Y.Z` 条目 **＋** `docs/history/` 的批次档。缺一记 `🟡 待补留痕`。
3. **新增**：发现新的开发项时**追加新条目号**（照抄来源稿编号，不复用已用过的号）；来源稿没有的，先在对应维度的设计稿里立条目，再进本表。
4. **裁决**：标 `⛔ 需先裁决` 的行，裁决后先回填**来源稿**（`D18`–`D21`）的裁决段，再改本表状态。
5. **数字**：本表**不写任何会随版本变的计数**（测试规模 / 控件数 / 桥方法数等），需要时指向 `docs/README.md` §3。
6. **一致性**：本表被 `docs/README.md` §1 目录树收录，受 `scripts/check-docs-facts.js` 的 C5 / C8 引用检查约束（引用本仓库源码写 `文件#符号`，不写绝对行号）。
