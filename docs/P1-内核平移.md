## 1. 移植口径（三条硬规则）

| # | 规则 | 说明 |
| --- | --- | --- |
| 1 | **算法与字段名逐字保持** | V2 的 `core/model/*` 由 V1 源码**逐段提取**生成（不改语义、不改字段顺序），确保 V1 数据可导入、跨端内容哈希一致 |
| 2 | **只做最小适配** | ① IIFE/全局依赖 → ESM 显式导入；② `cfg.*` 全局 → 可注入的 `cfg` 视图（`setModelOptions()`）；③ `dimCap` 的维度上限从 `cfg.dimCharLimits` 读取（默认值取自 V1 `defaultCfg`） |
| 3 | **保真度由测试强制** | 用 V1 源码切片在固定输入下产出**黄金样本**，V2 输出必须**逐字符相等**（含键顺序） |

哈希与作用域口径特别注意：

- `hashText` = V1 的 **djb2 → base36**（不是 FNV/十六进制）—— 它决定 id 派生与删除墓碑，换实现会导致跨端去重与墓碑失效；
- `atomContentHash` = V1 的**双哈希**（FNV-1a + 变体，`h1_h2` base36），其值直接用于跨端内容去重与墓碑；
- 角色作用域 = `char:<hashText(角色稳定标识)>`，稳定标识优先 `characters[characterId].avatar`（ST 的角色文件名，最接近 TH 的角色 id）→ `name2` → 索引。

### 2.3 生成方式：传递闭包 + 「重抛探针」

V2 模块由 V1 源码按**传递闭包**生成（目标函数 + 其引用的所有纯辅助/常量），避免手抄遗漏。闭包无法发现的一类风险是
**被 `try/catch` 静默吞掉的缺失依赖**（函数返回 `null`/`''` 而不报错）。因此黄金样本生成侧增加「**重抛探针**」：
把 V1 切片里 `catch (e) { return ...; }` 临时改写为 `catch (e) { throw e; }`，逐个调用目标函数，
把 `ReferenceError` 暴露出来再补齐 —— 批次 2b 借此补上了 `REL_LINK_HOW_CN` / `REL_LINK_DEVIATION_CN` /
`RUMOR_STAGES` / `RUMOR_ROLES` / `RUMOR_MEDIA_ALIAS` 等 10 项常量。

### 2.5 经验：宽依赖函数不要用闭包移植

批次 1–2b 的目标函数依赖面窄，**传递闭包**（目标 + 全部纯辅助）工作良好。
批次 3 首次尝试对 `migrateState` / `upsertEntry` / `relMaintRun` 用闭包，结果闭包分别膨胀到 **148 / 1067 项**
（连带拉入配置、提示词、NSFW、UI、存储与初始化等整插件），既不可审也不可用。

结论（已固化为流程）：

1. **只对「依赖面可枚举」的函数用闭包**；宽依赖函数拆批，或按显式清单移植；
2. 显式清单模式须跑**严格静态检查**（引用但未声明/未导入的标识符），并对已知「非依赖」噪声（属性名、字符串）人工过滤；
3. 每个新模块都要有**黄金样本**兜底 —— 它是唯一能证明「逐字一致」的手段。

## 3. 保真度：黄金样本门禁

```text

  → 固定输入（10 维度共 20 条夹具，含边界：过短/缺字段/重复标签/非法楼层/换行正文）
  → V1 切片输出（含 6 组内容哈希 + 7 项标量助手）
  → tests/fixtures/v1-golden.json（16674 B，随 V2 仓库提交）
  → V2 复放同一输入 → 与黄金样本 **JSON.stringify 严格相等**（含键顺序）
```

## 7. 复现方式（黄金样本再生成）

黄金样本由 V1 仓库的源码切片生成（脚本与输入见 `tests/unit/model-golden.test.js` 头部与本文 §3 流程）：

1. 从 V1 `src/modules/*` 逐段提取目标函数（按顶层声明边界，避免大括号误配）；
2. 以 `cfg.dimCharLimits` 默认值 + 固定夹具运行；
3. 输出 `tests/fixtures/v1-golden.json`；
4. V2 侧跑 `node tests/unit/model-golden.test.js` 复放比对。

> 用途：V1 一旦发现归一化缺陷（或在 V2 修改算法），先更新黄金样本，再让 V2 对齐 —— 避免「两边算法悄悄分叉」。
