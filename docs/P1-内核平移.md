## 1. 移植口径（三条硬规则）

| # | 规则 | 说明 |
| --- | --- | --- |
| 1 | **算法与字段名逐字保持** | V2 的 `core/model/*` 由 V1 源码**逐段提取**生成（不改语义、不改字段顺序），确保 V1 数据可导入、跨端内容哈希一致 |
| 2 | **只做最小适配** | ① IIFE/全局依赖 → ESM 显式导入；② `cfg.*` 全局 → 可注入的 `cfg` 视图（`setModelOptions()`）；③ `dimCap` 的维度上限从 `cfg.dimCharLimits` 读取（默认值取自 V1 `defaultCfg`） |
| 3 | **保真度由测试强制** | 用 V1 源码切片在固定输入下产出**黄金样本**，V2 输出必须**逐字符相等**（含键顺序） |

哈希与作用域口径特别注意：

- `hashText` = V1 的 **djb2 → base36**（不是 FNV/十六进制）—— 它决定 id 派生与删除墓碑，换实现会导致跨端去重与墓碑失效；
- `atomContentHash` = V1 的**双哈希**（FNV-1a + 变体，`h1_h2` base36），其值直接用于跨端内容去重与墓碑；
- 角色作用域 = `char:<hashText(角色稳定标识)>`，稳定标识优先 `characters[characterId].avatar`（ST 的角色文件名，最接近 TH 的角色 id）→ `name2` → 索引。

**注入视图为何必要**：V1 这批函数按 `cfg.*` / `state.*` / `getStoryNow()` 读取环境。V2 保持**同一读取方式**（逐字移植、黄金样本可比），

`setPersistHooks({ saveCfg, saveState })`。内核因此仍**零宿主依赖**（只读注入的数据视图），V1 代码无需改写。

## 4. 语义适配点（与 V1 的差异，仅此三处）

| 适配 | V1 | V2 | 影响 |
| --- | --- | --- | --- |
| 配置来源 | 全局 `cfg`（IIFE 内可变） | 导出的 `cfg` 视图 + `setModelOptions(patch)` | host 层在启动时把设置注入内核；核心不读宿主 |
| 模块形态 | 19 段拼接 + IIFE + `window.__FTT` | 原生 ESM 多文件 | 无构建产物；内核可 Node 单测 |
| 作用域键 | `char:hashText(getCurrentCharacterId())`（TH 角色 id） | `char:hashText(avatar → name2 → 索引)` | 导入 V1 数据时用导入器的显式 scope 覆盖对齐（P2 实现） |

## 7. 复现方式（黄金样本再生成）

黄金样本由 V1 仓库的源码切片生成（脚本与输入见 `tests/unit/model-golden.test.js` 头部与本文 §3 流程）：

1. 从 V1 `src/modules/*` 逐段提取目标函数（按顶层声明边界，避免大括号误配）；
2. 以 `cfg.dimCharLimits` 默认值 + 固定夹具运行；
3. 输出 `tests/fixtures/v1-golden.json`；
4. V2 侧跑 `node tests/unit/model-golden.test.js` 复放比对。

> 用途：V1 一旦发现归一化缺陷（或在 V2 修改算法），先更新黄金样本，再让 V2 对齐 —— 避免「两边算法悄悄分叉」。
