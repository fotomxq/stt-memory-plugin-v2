## 0. 纪律与复现（先说清楚）

* 本次核对**只读**：① 读宿主扩展存储里的落盘文件；② 把数据喂给插件**自带的只读体检函数**（`dataHealthReport()` / `ledgerHealth()` / `importancePct()`）；
  ③ 经**调试接口**（`tests/local/bridge.mjs` → 运行中的插件，49 个只读方法）取运行态事实。**不修改任何数据、不调用任何写接口**；
* 本文档**不记录任何正文、角色名、聊天标识、绝对路径**；全部结论以**计数与比例**表述（正文一律不外传）；
* 复现方式（两条路，结论一致）：
  * 落盘文件：state 落盘文件 → `dataHealthReport(state)` / `ledgerHealth()` / 逐维统计（§2 指标）；
  * 运行态：`node tests/local/bridge.mjs --call <方法>`（§7 列出本次用过的方法）。

## 1. 结论（TL;DR）

数据的**容量**远没到瓶颈（各维占用率仅 **4%–10%**），异常集中在**语义与卫生**上（下列 1–8 为落盘口径，9–12 为**运行态**新发现）：

1. **台账证据与当前聊天脱钩**：8 个「已分析」标记**全部越界**（`marksOutOfRange=8`、`coverFloors=0`），而丢弃留痕有 **120** 条；
2. **关联行悬空 / 失锚**：体检报 `link-orphan 29`、`origin-gone-with-floornow 78`（真机 `ftt.errors.dataHealth.findings = 107` 同上）；记忆类关联行 **149/149 缺知情时间**、**145/149 无告知人**；
3. **重要度信号大面积失效**：3 个维度**没有** `importance` 字段（场景 48/48、NPC 13/13、货币 21/21），
   `importancePct` 零值率在记忆 **72%**、场景 **65%**、传言 **67%**、当前状态 **100%**；
4. **字段名/字段集不统一**（同一语义 4 种字段名；`chatKey` 归属覆盖 0%–100% 不等）；
5. **计划 / 悬念永不开环**：各 30 条**全部 open**，`stats.plansClosed=0`、`suspenseResolved=0`；
6. **墓碑与留痕膨胀**：墓碑数 **5 倍于**存活条目（如某维 live 115 / deleted 577），丢弃留痕 **120 条无时间戳**，
   `snapFp` 指纹 **676** 条 vs 快照 **22** 条；单条快照最大 **3.11 MB**（**全量副本**，`baseId` 的增量设计没生效）；
7. **落盘 ≈28.5 MB / 角色**（快照链 8.81 · 分片 5.41 · 主文件 5.28 · 备份 5.28 · 本机副本 3.37 · 辅助 0.35），
   运行态 JSON **7.46 MB**（`ftt.stateSize`）；
8. **少量空壳条目**（场景 5/40、NPC 快照 6/27 正文 < 12 字，最短 0 字）；
9. **本机层「配了却读不到」**：磁盘层写 67 次全部成功、文件确实在（单文件 5.55 MB），但**载入期 3 次未命中** → 回退浏览器层 +
   **标记路径无效** + 1 条 error 级日志（`ftt.errors` 唯一一条错误即此）；
10. **结构化分片没有替代单文件，而是多存一份**：单文件 5.55 MB + 逐维分片 + 快照分片 21 个 + 日志分片，**四套副本同时写入**；
11. **调试日志环被「存储」淹没**：300 条环里「存储」占 **248（83%）**，其中最近 200 条只有 **3 种 action**、
    **166 条是同一句**「写入并回读校验通过」→ 摘要 / 异常 / 同步类诊断被挤出；
12. **注入开关是关的**（`injectCurrentPrompt=false`）→ 第 3/4 条里的 `uses=0`、`importance=0` 是**必然结果**（注入不发生，用量就不增长）。

## 2. 指标定义（本次体检口径）

| 指标 | 定义 |
| --- | --- |
| 字段缺失率 | 该维条目中**不存在**该字段的条数 / 总条数 |
| `importancePct` 零值率 | `importancePct(item) === 0` 的占比（插件自身函数） |
| `uses=0` 占比 | `Number(item.uses) === 0` 的占比 |
| 归属缺失 | 条目**没有** `chatKey`（或与当前 `state.chatKey` 不同）的条数 |
| 悬空关联 | `links[].refId` 指向的条目已不在该维度（体检项 `link-orphan`） |
| 失锚关联 | 记忆类关联行的 `atomRef/conceptRef/planRef` 全空（无法指回依据条目） |
| 墓碑比 | 该维 `deleted` 键数 / 该维存活条数 |
| 单条快照体积 | `snapStore[i]` 序列化字节数 |

## 3. 异常清单（现象 → 实测 → 影响 → 建议）

### A1 台账「已分析」标记与当前聊天脱钩（**影响最大**）

* **实测**：`ledgerHealth()` → `marks=8 / marksReadable=0 / marksUnreadable=0 / marksOutOfRange=8 / coverFloors=0 / dropped=120 / lastId=-1`。
  即：**8 个标记全在楼层范围之外**，覆盖楼层 0，而丢弃留痕 120 条（仅 5 条与台账重叠）。
* **影响**：这正是历史上「突然冒出大量未分析楼层 / 登记了却仍显示未分析」的同一根因族 —— 换聊天 / 删楼后，
  标记既不能证明「已分析」，也不能安全丢弃；用户侧表现为**清单与实情不一致**。
* **建议**：① 每条标记与留痕都写 `chatKey` + `at`；② 载入与维护时**按 `chatKey` 分区**，越界标记**归档**（而非静默保留）并如实回报数量；
  ③ 面板「登记为已分析」时同时写 `chatKey`；④ `ledgerHealth` 把「越界 / 跨聊天 / 无时间戳」分成三个可见数字。

### A2 关联行悬空与「来源已删但保留现址」

* **实测**：体检 → `link-orphan 29`、`origin-gone-with-floornow 78`（扫描 710 条 / 15 维，等级 `warn`）。
* **影响**：悬空关联会让「谁知道什么」继续参与注入 / 关系表渲染；`floorNow*` 与已删来源并存会让楼层校准读数自相矛盾。
* **建议**：① 删楼 / 收缩 / 墓碑生效时**级联**处理 `links`（`originGone` 置位或删行），并在 `dataHealth` 保留可核对计数；
  ② 提供**一键清理**（幂等、可回退、写调试日志），而不是静默删除；③ `floorNow*` 在来源消失后应清空。

### A3 记忆类关联行普遍失锚 / 缺时间

* **实测**：记忆关联行 149 条 → `at(知情时间)` 空 **149/149**、`from(告知人)` 空 **145/149**、`view(片面视角)` 空 **98/149**。
* **影响**：① 关联行无法溯源到依据条目（`atomRef/conceptRef/planRef` 全空）→ 关系表只能给结论不能给证据；
  ② 没有知情时间 → 「今天/昨天」相对时间对关联行无效。
* **建议**：① 抽取提示词强制输出锚点，缺失时以条目自身 `floorStart/date` 回填；② `dataHealth` 增设「失锚关联」项；
  ③ 关系表在缺锚点时如实标注「无依据」，不伪装成有据。

### A4 「重要度」信号大面积失效（**与 `docs/D7` 设计不符**）

* **实测**：`importance` 字段**整维缺失** —— 场景 48/48、NPC 13/13、货币 21/21；
  `importance === 0` —— 记忆 53/75、传言 12/18、NPC 快照 9/27、当前状态 3/3；
  `importancePct` 零值率 —— 记忆 **72%**、场景 **65%**、传言 **67%**、当前状态 **100%**、NPC 快照 33%。
* **影响**：清扫 / 遗忘 / 注入排序都吃「重要度 × 用量」，一半以上条目在这个信号上是 0 → 排序退化为纯近度；
  界面显示 0% 会让人误判为「插件坏了」。
* **建议**：① 二选一并**统一**：把 `importance` 补成**跨维统一字段**（派生维按来源继承或按 `uses` 现算），
  或在 UI / 体检里明确「该维不参与重要性」；② `importancePct` 对「无该字段」的维度返回**不适用**（而不是 0）；
  ③ `docs/D7` 增补「整维缺失时的口径」。

### A5 `uses` 语义不统一

* **实测**：`uses>5` —— 物品 44/45、概念 63/65、货币 18/21；`uses===0` —— 记忆 53/75、NPC 13/13、场景 13/40、当前状态 3/3。
* **影响**：同类「用量」在不同维度含义不同（有的像「被提及次数」、有的像「注入次数」），跨维比较与重要度计算失真。
* **建议**：① 明确「**被注入即 +1**」为唯一口径并在写入处统一；② 体检给出逐维 `uses=0` 占比；
  ③ 历史脏值只做「向后统一」，不批量改写。

### A6 字段名 / 字段集不统一

* **实测**：日期字段 4 种 —— `date`（情节 / 记忆 / 概念 / 平行 / 传言 / 计划 / 悬念）、`seenDate`（物品 44/45 无 `date`）、
  `floorSeen`（场景 48/48 无 `date`）、`lastSeenDate`（NPC 快照 24/27 无 `date`）；
  `validity` 只有情节有（115/115），其余维度没有，而代码多处按 `validity !== 'inactive'` 过滤；
  `chatKey` 覆盖：记忆 75/75、平行 15/15、传言 18/18，但情节 **70/115**、物品 **2/45**、概念 24/65、货币 11/21、NPC 快照 19/27、场景 **0/48**。
* **影响**：① 「同维不一致」让过滤 / 排序 / 展示分支变多；② **归属缺失**的条目不参与聊天分层 → 会在别的聊天里出现（历史真机问题同族）；
  ③ `validity` 缺失让「隐藏 / 失效」语义只对情节生效。
* **建议**：① 迁移期**写规范化字段**（`date` / `validity` / `chatKey` 一律补齐，旧字段保留只读一版）；
  ② `dataHealth` 增设「归属缺失」与「无效字段名」两项计数；③ 分片瘦身时把冗余字段纳入白名单（`docs/D8` 口径）。

### A7 计划 / 悬念永不开环

* **实测**：`plans` 30 条全 `open`、`suspense` 30 条全 `open`；`stats.plansClosed=0`、`suspenseResolved=0`；两条维度各占 10% 存储上限。
* **影响**：注入候选池长期是 30 条（注入上限各 8），一半以上永远进不了注入，也让「剧情推进感」变差。
* **建议**：① 面板提供「一键闭环（完成 / 放弃）」；② 按剧情日期做**老化策略**（久未变动 → 降权 / 归档，可配置）；
  ③ 体检给出「长期 open」计数与最老日期。

### A8 墓碑 / 留痕 / 快照指纹膨胀

* **实测**：墓碑比（`deleted` / live）—— 情节 577/115、记忆 538/75、场景 539/40、概念 539/65、关联 650/213；
  `deletedH` 与 `deleted` **近等量**（同一份知识的两个索引）；
  `processedDropped` **120 条全部无时间戳**（只有 `{f, h}`）；
  `snapFp` 指纹 **676** 条 vs `snapStore` **22** 条 / `snapshots` **27** 条；
  单条快照最大 **3.11 MB**（字段含 `atoms` + `deleted` → **全量副本**，`baseId` 的增量意图未生效）。
* **影响**：主文件 5.28 MB 里相当部分是「已删的东西」；快照链 2 份（服务器 + 目录镜像）合计 8.81 MB；
  指纹表几乎是快照数的 30 倍 → 载入 / 保存 / 跨端同步的**载荷与耗时**都被放大。
* **建议**：① 墓碑按 `at` + **按 `chatKey` 回收** + 每维上限（当前只有 365 天，且实测 2 天就 5:1 增长）；
  ② `processedDropped` 补 `at` / `chatKey`，让留痕可过期；③ 快照链改**真增量**（只存变化条目）并设**单链体积上限**；
  ④ `snapFp` 随快照回收（或改为「最近 N 条快照的指纹集合」）；⑤ 目录镜像与服务器副本**去重**（同一 4.6 MB 存两份）。

### A9 落盘体积与副本职责

* **实测（单角色）**：快照链 2 文件 **8.81 MB** · 分片 31 文件 5.41 MB · state 主文件 1 个 5.28 MB · 备份 1 个 5.28 MB ·
  本机副本信封 2 个 3.37 MB · 辅助数据 13 个 0.35 MB → **≈28.5 MB**。
* **影响**：同一份数据存在 **5 类副本**（主文件 / 分片 / 快照 / 本机信封 / 备份 + 目录镜像），读写与同步成本线性放大。
* **建议**：① 明确「**分片为权威、主文件仅兜底**」并给主文件瘦身（或按周期重建）；
  ② 备份轮转（保留 N 份，按体积与时间双阈值）；③ 目录镜像只镜像**辅助数据**，不再重复快照链（或镜像前校验同哈希跳过）。

### A10 空壳条目

* **实测**：场景 5/40、NPC 快照 6/27 的正文字符数 < 12（最短 0）；其余维度最短 ≥ 20 字。
* **影响**：空壳条目会占用注入名额与存储，也让「场景 / 人物快照」列表显得嘈杂。
* **建议**：① 入库前校验最小长度与必需字段，不合格**不入库**（或合并到已有条目）并留痕；
  ② `dataHealth` 增设「空壳条目」项；③ 面板提供筛选视图。

### A11 时钟 / 楼层保留字段越界

* **实测**：`weaveLastFloor=199`、`rumorTick.parallelFloor=199`，而当前聊天实际层数仅 **14**；条目里最大 `floorStart=404`；
  `state.storyDay=53143`（来自正文「第 N 天」的抽取，当前校验只有 `<1e6`）；`lastKnownFloor` 与 `lastChatFloor` 一致（14）。
* **影响**：越界楼层参与「越界判据 / 楼层校准」时会误报；`storyDay` 这类异常大值会被写进条目，属「看起来就是脏数据」。
* **建议**：① `weaveLastFloor` / `parallelFloor` 换聊天时按 `chatKey` 清零或分区；② 条目 `floorStart` 写入时做**上界校验**（> 当前楼层数即截断 / 拒绝并留痕）；
  ③ `storyDay` 加上界与来源标记（抽不到就置 0）。

### A12 空转的功能位

* **实测**：`protagonist` 为空对象（0 键）；`vars` 仅 1 项，而 `varTemplates` 三组（global / char / chat）齐备；`state.present` 仅 1 人。
* **影响**：「主角档案 / 变量模板」这类有界面入口却长期空转 → 用户会以为坏了；`present` 只有 1 人会让「在场角色」判据退化。
* **建议**：① 要么接线（AI 抽取写入 + 注入使用），要么从界面移除并在文档标注「未启用」；② `present` 为空时回退到实时楼层解析（已有逻辑）并在体检里显示来源。

### 7.2 运行态**新增**的异常（落盘看不到）

**L9 本机层「配了却读不到」（当前唯一 error 级日志）**

* `ftt.errors.logErrors = 1`：`载入：本地磁盘目录读不到本机副本 → 已回退浏览器本地存储（该路径已标记为无效）`（`level=warning`）；
* 同一时刻 `ftt.diskFiles`：`dir=@browser/<目录名>`、`writes=67 / reads=2 / failures=0 / mechanism=browser-opfs`，
  根目录里**确实有**单文件 `ftt2-local-<scope>.json`（5,554,193 字节），另有 `<scope>/` 子目录（逐维分片 / 快照 / 日志分片）；
* `ftt.localDir`：`disk.misses=3`，而 `invalid.invalid=false`（**后续写入已清除无效标记**）。
* **判读**：写盘没问题，**载入期的读发生得太早**（OPFS / 句柄尚未就绪那一次）→ 一次 miss 就造成「回退 + 标记无效 + 一条 error 级提示」。
* **建议**：载入期对磁盘层做**一次延迟重试**；把「miss（可能只是未就绪）」与「路径不可用（真的写不进去）」**分级**，
  前者只记 `info`、**不标记无效**；读到后清除标记。**这是本批最该先修的一条**（用户每次刷新都可能看到）。

**L10 四套副本同时写（体积 / 耗时被放大）**

* 运行态可见同一份数据同时存在：① 单文件 `ftt2-local-<scope>.json`（5.55 MB）② `<scope>/<维度>.json` 逐维分片 ③ `<scope>/snapshots/*` 21 个分片
  ④ `<scope>/logs/*` 日志分片；再叠加服务端主文件 / 备份 / 本机信封 → 落盘总量 ≈28.5 MB（§3-A9）。
* `ftt.writeStats`：`queued=done=2901 · failed=0 · maxInFlight=1`，最近一次 `blob-put:<state>` 136 ms，
  **`lastSlow` = `kv-put:<meta>` 3031 ms**（长尾 3 秒）。
* **建议**：明确**单一权威**（建议「逐维分片为权威、单文件降级为兜底且按周期重建」），并把「本机层体积 / 副本数」纳入体检；
  写入长尾（kv-put 3s）登记为性能项（可与「存储日志合并」一起做）。

**L11 调试日志环被「存储」淹没**

* `ftt.debugLogStats`：环 `n=300 / cap=300`，分类 **存储 265（88%）** · 读取 13 · 摘要 12 · 发送记忆 6 · 校对 3 · 同步 1；
* `ftt.debugLog(kind=存储, limit=200)`：只有 **3 种** action —— **166 条**「本地磁盘目录：写入并回读校验通过」、
  17 条「本机层结构化分片已写入」、17 条「快照链结构化分片已写入」。
* **建议**：成功写盘按「计数 + 最近时刻」**合并**为一条（失败逐条）；或给存储类**独立环**。否则异常 / 摘要类诊断会被挤出（与 v3.10.4 修过的「读取占 69%」同族，这次换成了存储）。

**L12 关键开关状态（解释「用量 / 重要度为什么长不起来」）**

* `ftt.config`：`injectCurrentPrompt=false`（**注入关闭**）· `useVector=true` · `charBudget=8000` · `maxSnapshots=10`（注入上限）·
  `debugLevel=debug`（所以存储类逐条记）· `uiShowDrawer=false` · 提示词模板 34 个 · 生效配置键 231 个。
* **判读**：注入不发生 → `uses` 不增长 → `importance`（= 窗口调用占比）恒 0 → §3-A4/A5 的「大片 0」是**因果必然**，不是算错。
* **建议**：体检里对「注入关闭」直接给出说明句（避免用户把「0%」当成插件坏了）；`debugLevel` 与「存储日志合并」联动（debug 下也不该刷屏 88%）。
