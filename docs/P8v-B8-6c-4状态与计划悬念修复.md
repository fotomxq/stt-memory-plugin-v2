## 2. 与 V1 的差异（逐条明示）

1. **AI 通道**：V1 自建 OpenAI 兼容请求（`callChatCompletion`）；V2 统一走注入钩子 `core/ai-hooks.js#aiCallText`（酒馆 `generateRaw`），采样参数由酒馆预设控制（`{ preset: cfg.activeApiPreset }` 不移植）。
2. **正文投喂**：V1 `buildFeedFloorText(n)` → V2 `core/ai-hooks.js#aiFeedText(n)`（宿主 `host/floors.js`），`slice(-8000)`（计划悬念）与 `slice(-10000)`（状态）长度口径逐字保留。
3. **任务管线 UI 未移植**：V1 的 `pipeStart`/`pipeUpdate`/`pipeEnd`/`abortTick`/`abortQuiet`/`newTaskStart`/`renderPanel` 在 V2 不存在；互斥改为 `aiBusy()`（等价 V1 `busy.repair` + 摘要 / 压缩 / 推演 / 推进 / 同步占用两道判据的并集），重绘由 UI 层负责。
4. **`opts.aiText` 注入点**：两个 `run*` 均增设可选 `opts.aiText`（与 `runRepair`/`runMemoryRepair`/`runItemRepair` 同约定），供测试显式提供 AI 返回；缺省仍走 `aiCallText`。
5. **通知形态**：`notify(kind, title, text)` 统一经 `notifyHooks.toast`；V1 `notify('repair', …)` 的 toastr 类型是 `warning`，V2 取等价 `'warning'`（黄金样本比对时做 kind 映射，**文本逐字符一致**）。`dbgLog` 类别沿用 V1 的 `'摘要'` / `'修复'`。
6. **复用而非复制**：
   - 状态域复用 `core/ingest.js#statesSubjectUnionMerge` / `applyStateBounds`、`core/model/dims.js#normalizeCurrentState`、`core/model/scalars.js#dimCap`、`core/model/snapshot.js#snapshotAgeIsLocked`、`core/merge.js#tombMany`·`tombEntries`、`core/repair.js#repairReport`；
   - 计划悬念域复用 `core/group-repair.js`（`GROUP_REPAIR_SPECS.suspense` / `groupPick`）、`core/rel-maint.js#relRepairMaint`·`relMaintSummary`·`relMaintCounts`·`logRelMaint`、`core/entries.js#retargetRelRefs`、`core/ingest.js#mergeDelta`、`core/clock.js#dateStrCmp`、`core/model/scalars.js#clockDateTrim`·`dimCap`；
   - 为此**新增两处导出**：`core/ingest.js#stateSubjectSamePerson` 与 `core/ingest.js#mergeStateHistory`（V1 私有，`stateRepairMatch` / `stateRepairClean` 需要；**实现未改动**，仅加进导出清单 —— 沿用 B8-5「共用助手导出，避免重复实现」的既有做法）。
7. **V1 `characterRepairContext` 未导出且属禁改文件**：V1 `buildStateRepairPrompt` 调用的 `characterRepairContext(names)` 在 V2 属 `core/character-repair.js`（本批按纪律**未改动**该文件）且未导出 → `core/state-repair.js` 就地实现等价的 `stateRepairContext`（与 V2 该文件内的实现逐字相同），由黄金样本的提示词**逐字符比对**强制校验。

9. **`getCurrentCharacterId()` → `identityView.characterName`**：V1 名册的**弱来源**「当前角色」用 `getCurrentCharacterId()`（角色 **id**，实测 mock 值 `char_abc`）；V2 由宿主注入的身份视图 `core/model/runtime.js#identityView.characterName`（当前角色**名**）承担同一位置 —— 该来源**不计入 `strong`**，不参与「未匹配即删除」安全阀，故不影响删除判定；单测/oracle 两侧统一注入「角色甲」以保证逐字节可比。

### 2.1 与 V1 一致的既有缺陷（如实保留、不擅自修正）

1. **状态修复的「删除」段在真实 AI 回包下不命中**：`applyStateRepair` 只认 `ops['删除']` / `ops.delete`，而提示词合同的中文键「删除」经 `normalizeDeltaKeys` → `remove`（见 `CN_KEY_MAP`）→ 生产路径永远不会进入删除分支。V2 逐字保留同一写法（**未修正**），并在单测 I11 用「中文键未归一」的 delta 直接覆盖该分支的真实行为。
2. **计划修复的「计划库.合并」段同样不命中**：`applyPlanSuspMerge` 只读 `delta[cat].merge`，而中文键「合并」**不在 `CN_KEY_MAP`** 内 → 真实回包落在 `delta.plans['合并']`，计划合并分支不生效（`mergedP === 0`）。V2 逐字保留（**未修正**），单测 I6 用英文 `merge` 键单独覆盖该函数的真实行为，单测 I8 固化生产路径现象。
   - 附注：悬念域与记忆/概念/物品域的 `apply*` 均写作 `ops['合并'] !== undefined ? ops['合并'] : ops.merge`（兼容两种形态），因此**只有计划合并**受此影响；这对 V1 是同一行为，非本批引入。
3. **「无高相关悬念组且无进行中计划」早退分支不可达**：首个「无可修复条目」判据（`pOpen0` / `sOpen0` 全空）已先行返回，故 `!pick.entries.length && !plans.length` 永不成立。V2 逐字保留该分支（后续若调整判据顺序即按 V1 语义生效）。
4. **`made` 不计已去世固定规则**：`runStateRepair` 的 `made` 只由 `match.removed` / `clean.junk` / `clean.merged` / `clean.renamedField` / AI `changed` 决定 —— 仅因「已去世清理」而无其它改动时 `made === 0`（V1 原样，单测 P5 固化）。
