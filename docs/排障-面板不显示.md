# 排障 · 安装后看不到面板

> 文档版本：v1.1 ｜ 日期：2026-09-24 ｜ 状态：生效
> 适用版本：v2.0.2 起（v2.0.0/v2.0.1 的差异见 `CHANGELOG.md`）
> 相关：`index.js`（装配与探针）、`ui/settings-panel.js`（容器候选）、`ui/menu.js`（魔杖菜单入口）

---

## 1. 面板在哪儿（先确认这一点）

FTT 面板挂在**扩展设置抽屉**里，不是顶栏、也不是魔杖菜单：

1. 左侧栏 → **扩展（Extensions）** 按钮（或顶栏扩展图标）；
2. 抽屉内找到 **「FTT记忆组件 V2」** 标题行 —— 这是一条**可点开的折叠抽屉**（默认收起）；
3. 点击标题展开，即可看到「基础开关 / 记忆与注入 / 状态与动作 / 数据台 / 更新」各区块。

> TauriTavern 等原生移植里，扩展抽屉的入口与分组可能与 Web 版略有差异；
> 若抽屉里确实没有「FTT记忆组件 V2」，按 §2 自查。

## 2. 三步自查（v2.0.1 起）

在聊天输入框里依次执行：

| 命令 | 看什么 |
| --- | --- |
| `/ftt` | 首行是否显示「装配：已初始化」；是否列出「触发 load→…」；「面板 已挂载 #<容器>」还是「未挂载：<原因>」 |
| `/ftt-panel` | 强制重新挂载一次，并报告：面板容器候选命中情况（`extensions_settings2✓ / extensions_settings✗ / rm_extensions_block✗`）、菜单入口状态、以及面板位置提示 |
| `/ftt-analyze list` | 顺带确认提取链路是否可读（楼层清单） |

浏览器控制台（`F12` → Console）还可直接调用：

```js
FTT.panelInfo()      // { ok, via, container, reason, found:{...}, mounted, candidates:[...] }
FTT.menuInfo()       // { menuId, menuFound, installed, candidates, mount:{...} }
FTT.forceMount()     // 强制挂载（返回同上诊断）
FTT.snapshot()       // 版本 / 宿主 / 探测 / 绑定 / 拦截器 / 存储 / 提取 全量状态
```

## 3. 常见原因与处理

| 现象（`/ftt-panel` 输出） | 原因 | 处理 |
| --- | --- | --- |
| 面板 `未挂载：未找到扩展设置容器（候选：extensions_settings2 / extensions_settings / rm_extensions_block）` | 该宿主的扩展设置区块 id 与三者都不同 | 把 `/ftt-panel` 的输出发给我；同时可先用魔杖菜单入口（§4）打开面板 |
| 面板已挂载，但界面看不到 | 扩展设置抽屉未展开，或面板在抽屉底部需滚动 | 展开扩展设置抽屉；面板标题为「FTT记忆组件 V2」 |
| `/ftt` 都不存在（命令未注册） | 插件脚本未加载（多半是安装不完整或 JS 报错） | 看 `F12 → Console` 的红色报错；确认扩展目录里 `index.js`、`manifest.json`、`settings.html` 都在 |
| 版本仍在 `2.0.0` | 未更新到修复版 | 在扩展管理里对本扩展执行 Update（或重新安装），确认 `manifest.json` 版本为 `2.0.1` |

## 4. 主入口：魔杖菜单（**强制开启，不可关闭**）

扩展魔杖菜单（`#extensionsMenu`）里的 **「FTT记忆」** 一项就是面板的主入口，点击即打开面板。
v2.65.0 起该入口按用户要求**强制开启**（设置页「显示界面开关」里不提供它的开关，`cfg.buttonLocations.menu=false` 不生效）。

v2.67.0（用户报告「底部扩展菜单看不到面板激活的按钮」）修复了两处真实缺陷：

- **陈旧标志**：此前安装成功后模块只记一个节点引用，`menuInstalled()` 恒为真。酒馆**每次打开魔杖菜单都会重建
  `#extensionsMenu` 的内容**，我们插入的那一项被清掉后模块仍以为「已安装」→ 再也不会补回（表现就是看不到按钮）。
  现在会校验节点是否仍挂在文档里，并回查 `#ftt-menu-button`。
- **安装时机**：`#extensionsMenu` 由酒馆按需创建，插件初始化时可能还不存在，一次失败后此前不再重试。
  现在幂等的 `ensureMenuEntry()` 会在这些时机补回：初始化与每次入口同步、可见性探针每一轮、
  **点击魔杖按钮之后**（重建完再补）、以及 `#extensionsMenu` 的 `MutationObserver`（内容被清空即补回）。

自查：控制台执行 `FTT.menuInfo()`（看 `menuFound / installed / watched / observing`）、
`FTT.ensureMenu()`（手动补一次）；`/ftt` 的「入口：」一行也会如实列出各入口是否显示。

## 4b. 兜底入口之二：右下角悬浮「FTT」按钮（v2.0.2）

若**三个候选容器都不存在**（宿主设置区块结构不同），插件会在**点挂载连续失败约 3 秒后**自动显示右下角悬浮按钮 **「FTT」**：

- 点击 → 以**弹窗**形式展示完整面板（`callGenericPopup`），可正常改配置；
- 抽屉容器一旦恢复（例如宿主稍后才建好 DOM），插件会自动把面板挂回抽屉并**移除**悬浮按钮；
- 若连 `callGenericPopup` 也不可用，点击会退化为「再次尝试挂载抽屉 + 提示」。

## 6. 关于日志里的 `Git handshake failed: An IO error occurred`

```text
ERROR tauritavern::user_error: Failed to get extension version: Internal error:
Git handshake failed: An IO error occurred when talking to the server
```

- **性质**：宿主（TauriTavern）在执行**更新检查**时尝试对扩展仓库做 git 握手失败 —— 即**本机到 GitHub 网络不通**
  （墙/代理/离线）或 git 凭据不可用。宿主把它记为「用户级错误」，**不会阻止扩展加载，也不影响注入/提取/面板**。
- **谁触发的**：① 宿主的扩展管理器会对每个扩展查一次版本（日志里能看到几十个扩展名）；
  ② 本插件的启动自动检查与「检查更新」按钮也会调用 `POST /api/extensions/version`。
- **v2.0.2 的处理**：识别为**网络级失败**后**短路**（不再重复调用 `global` 端点，避免后端日志翻倍）并进入
  **会话内 6 小时退避**；状态行/`/ftt` 会显示「更新检查失败：…（网络不通…）」。
  想立即重试：`FTT.snapshot().update` 查看详情，或在控制台执行 `FTT.checkUpdate()`；
  也可在设置面板关闭「启动时自动检查更新」以彻底静默。
- **注意**：「⬆ 立即更新（ST）」同样依赖 git 网络，断网环境下必然失败，属预期。

## 5. 设计上的防复发

- 装配**不再依赖单一事件**：`APP_READY` / `APP_INITIALIZED` / `DOMContentLoaded` / `window.load` / 有限轮询（20×750ms）/
  命令调用，任一先到即初始化（`ensureReady()` 去重）；
- 已初始化但容器不存在时，探针会**继续只重试挂载**，容器一出现即自动补上；
- 诊断入口在**模块加载期**就注册，因此「出问题时没有任何自查手段」这类二次伤害不会再有；
- **最后一道兜底**：抽屉容器全不存在时改用「右下角悬浮按钮 + 弹窗面板」（v2.0.2），任何宿主都能看到入口；
- 相关回归测试：`tests/unit/bootstrap.test.js`（零事件装配 / 容器回退 / 无容器可诊断自愈 / 无事件源宿主 / 菜单入口 / teardown 恢复）
  与冒烟 L1–L4。
