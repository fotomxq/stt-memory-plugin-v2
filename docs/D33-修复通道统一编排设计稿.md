## 0. 一页摘要

**现状：修复有两条互不相通的通道，且「全面」名不副实。**

| 通道 | 今天的实际覆盖（只读核对） | AI 请求数 |
| --- | --- | --- |
| **总览 · 🛠 自动修复**（`core/repair.js#runRepair`） | ①9 步机械（10 维去重 + 关联层 + 台账 + 时钟）· ②候选（`core/repair.js#REPAIR_DIM_SPEC` 10 维）· **③ 一次窄契约 AI（10 维平铺契约）** · ③-b 关系层（零 AI）· **③-c 计划/悬念（第二次真实请求）** | **2 次** |
| **各大类自带的 🔧 修复**（9 个入口） | 计划/悬念（1 次）· 记忆（1）· 概念（1）· 物品（1）· 角色（≤2，含履历另 1）· 状态（1）· 场景（1）· 货币（**0**，纯机械）· 关联层（**0**，纯机械） | 用户逐个点 → 再 **7–9 次** |

**十个修复入口里，只有 1 个（计划/悬念）真正被总览编排到自己的修复管道**（`repairHooks.planSuspRepair`）；
> 十个入口 = 计划/悬念 · 记忆 · 概念 · 物品 · 角色 · 履历 · 状态 · 场景 · 货币 · 关联层。
角色档案与货币**完全不在**总览覆盖内；记忆 / 概念 / 物品 / 场景 / 状态的**自有机械段与聚类 AI 段被绕过**（只被通用段"沾到"）。

**主张：两档修复，一份实现。**

| 档 | 入口 | 范围 | AI 请求 | 行为变化 |
| --- | --- | --- | --- | --- |
| **全面修复** | 总览「🛠 自动修复」 | 注册表里**全部可 AI 域**（逐条修订 10 维 + 记忆/概念/物品/计划悬念四域聚类 + 状态 + 角色档案 + 场景） | **1 次**（聚合） | 覆盖域扩大、请求数 2 → 1 |
| **单域修复** | 各页 🔧（9 个按钮） | 只跑注册表里**该域那一行** | 1 次（不变） | **零变化**（按钮 / 文案 / 二次确认 / 返回结构全不动） |

**三条支撑事实（本轮只读核出，是本设计能成立的前提）**：

1. **每个域修复都有同一个 AI 注入点** —— `String(o.aiText != null ? o.aiText : await aiCallText(prompt, '<label>'))`
   （`core/plan-repair.js` · `core/group-repair.js` · `core/item-repair.js` · `core/state-repair.js` · `core/character-repair.js` · `core/scene-repair.js` · `core/repair.js` 逐处同型）
   → 聚合器只要**给出每域那一段文本**，各域应用器**零改造**即可落库。
2. **「一次请求输出多域」在本仓库已有成熟先例**：`core/prompt.js#buildSummaryPrompt` 的**15 键契约**
   （`当前状态 / 情节 / 状态记录 / 角色档案 / 记忆库 / 物品库 / 计划库 / 悬念库 / 名册 / 场景库 / 概念库 / 货币 / 传言 / 平行事件 / 变量`）；
   计划/悬念修复本身也已是「悬念库 + 计划库」两键一请求。
3. **两处硬前置缺口**（不补则聚合会"看起来跑了、实际什么都没落"）：
   ① 除 `core/plan-repair.js` 外，**其余域的入口没有 `silent`**（`core/group-repair.js#runMemoryRepair` 的 JSDoc 写了 `silent` 却从不读；状态 / 角色 / 物品 / 场景全无）→ 聚合调用会**逐域弹 toast**；
   ② 除记忆 / 概念 / 物品 / 计划悬念外，**没有可注入的候选（`opts.pick`）** → 聚合后各域若**重新挑选**候选，编号与提示词里的编号对不上，应用器会**整批判为 `skipped`**（静默空转）。

## 3. 方案

### 3.1 两档修复的定义（基准：能力边界）

| 档 | 名称 | 定义 | 范围（做什么） | 明确不做 |
| --- | --- | --- | --- | --- |
| **全面修复** | 总览「🛠 自动修复」 | 对**整库**的一次跨域维护编排：机械段全跑 → 候选按域择优 → **一次 AI 聚合** → 统一落库、记账、报告 | ① `docs/D25` 的九步机械清理；② 全部可 AI 域的候选与聚合修订；③ 关系层二次维护；④ 按域分列的报告 | 不新增条目；不改候选外条目；不越**任何域**的既有窄契约（各域应用器原样复用） |
| **单域修复** | 各页 🔧 按钮（9 个） | 对**本域**的一次专门修复：本域机械段 + 本域候选 + 本域 AI（1 次）+ 本域应用器 | 只该域（计划/悬念域天然含计划 + 悬念两库；记忆域触关联层维护，属既有行为） | **不得修改它域的数据**；不得因为"顺便"而扩大范围（今天亦如此，本稿把它写成硬约束） |

**两档的关系（一句话）**：**单域是全面的子集，且是同一份实现的子集** —— 全面 = 把注册表里所有 `inTotal` 的行**顺序编排 + 聚合一次请求**；单域 = 只跑其中一行。

### 3.2 修复注册表（唯一事实源）

新增 core/repair-registry.js（待建），导出 `REPAIR_REGISTRY`。每行字段固定（缺一即不合规）：

| 字段 | 含义 |
| --- | --- |
| `id` | 域标识（如 `memory` / `concept` / `item` / `planSusp` / `state` / `character` / `scene` / `currency` / `rel`） |
| `label` | 中文名（用于报告与日志；**不得**与既有按钮文案冲突） |

### 3.3 全面修复的新编排（在原三段上扩展，步骤与闸门不动）

```text
[触发] 手动（总览）／合并失败自动          ← 不变
[闸门] G1 占用 → G2 频率 → G3 同楼层上限   ← 不变（docs/D25 §3.1）
① 机械清理（零 AI，9 步固定顺序）          ← 不变（docs/D25 §3.2）
② 候选筛选（零 AI）                        ← 扩展：从「REPAIR_DIM_SPEC 的 10 维」扩为「注册表 inTotal 行的逐域候选」
③ 聚合 AI（**1 次请求**）                  ← 变化点：③/③-c 两次请求合并为一次，覆盖全部 inTotal 域
③-b 关系层二次维护（零 AI）                ← 不变
[收尾] 汇总 → 记账（1 条）→ 报告（按域分列）→ 通知 → 返回
```

**② 的变化**：逐域调用注册表该行的候选选择器（`repairCollectCandidates` / `groupPick` / `pickStateRepairTargets` / `buildCharacterRepairQueue` / 场景封顶清单），
**各域仍用自己的上限键**（K17 的六键 + `repairMaxItems`），再受两个**新聚合闸**约束（`cfg.repairAggMaxItems` / `cfg.repairAggMaxChars`，`数-37`）。
候选结果写进返回结构（按域分列），并在返回里给出 `aggKeys`（本次实际进入聚合的域）。

**③ 的变化（核心）**：把 `core/repair.js#buildRepairPrompt` 的调用改为**聚合构造**（§3.4），一次 `core/ai-hooks.js#aiCallText(messages, '全面修复')`；
响应解析后**逐域拆回**，对每个域以 `opts.aiText = <子树 JSON>` 调它的应用器（§3.4）。**不再单独调用 ③-c**（其 AI 段已并入聚合；其**零 AI 的机械段**（`suspenseMergeExact` 等同内容去重）仍在第①/②段范围内执行）。

**顺序（硬约束，与 `docs/D25` §3.9.5 同理）**：
**结构类先、文本类后** —— 聚类合并 / 了结 / 场景重建先落库，逐条正文修订后落库。
理由：逐条修订若先跑，可能把即将被合并掉的条目改写一遍（白烧 token，且合并后改写结果被丢弃）。

**同一域的候选互斥**：被聚类选中的条目，从「逐条修订」的候选里**剔除**（共享黑名单），避免同一条目在一轮里被两个域契约各改一次。

### 3.4 AI 聚合契约（分节 → 一次响应 → 按域拆回）

**提示词结构（三段）**：

| 段 | 内容 | 来源 |
| --- | --- | --- |
| **system** | 聚合引导词（新增模板键 `repairAgg`）：角色定位 + **「按节作业、节内编号独立、只输出需要改动的域键、不要 Markdown 代码块」** + 全局禁止项（不得新增条目 / 不得改候选外条目 / 不得改 id 与时间戳） | `core/config.js#PROMPT_TEMPLATES_V2` |
| **各域节** | 每域一段：`【域：记忆（聚类合并）】` + 该域**既有 build 函数产出的 user 段正文**（含该域候选与编号） | 各域 `buildSection`（**与单域调用同一份文本**） |
| **输出契约句** | 单一 JSON 的顶层键清单（按下表）+ 「未改动的域键可省略；每键内沿用该域既有字段名」 | 注册表的 `aggKey` 表 |

**聚合契约键表（`aggKey` → 该域子树形状 → 拆回后的 `aiText`）**：

| 域 | `aggKey` | 子树形状（= 该域既有契约，**原样**） |
| --- | --- | --- |
| 逐条修订（10 维） | `逐条修订` | `{"修订":[{"编号","字段","值"}],"删除":[n]}` |
| 记忆 | `记忆库` | `{"合并":[…],"修订":[…],"删除":[…]}` |
| 概念 | `概念库` | `{"合并":[…],"修订":[…],"删除":[…]}` |
| 物品 | `物品库` | `{"合并":[…],"修订":[…],"删除":[…]}` |
| 计划 / 悬念 | `悬念库` + `计划库` | `{"悬念库":{…},"计划库":{…}}`（**两键同属一行**，拆回时整块回灌） |
| 状态 | `状态记录` | `{"状态记录":{…}}` |
| 角色档案 | `角色档案` | `{"角色档案":{"更新":[…]}}` |
| 场景 | `场景库` | `{"场景库":{"重建":[…]}}` |

**拆回规则（这是"各域应用器零改造"的关键）**：

1. 解析整包 JSON（`core/util.js#extractJsonObject`）；
2. 对注册表每行取 `aggKey` 子树；**子树不存在 → 该域跳过**（`aggMissingDomains`），不影响其它域；
3. 把子树 `JSON.stringify` 后作为 `opts.aiText` 调该域应用器（**不重跑 AI**）；
4. **必须同时回灌候选**（`opts.pick` 或等价的候选快照），否则该域会重新挑选候选、编号对不上 → 全批 `skipped`（K10 的硬前置）；
5. **必须带 `silent`**（K9 的硬前置），否则每域弹一条 toast；
6. 逐域 `try/catch` 隔离：某域应用抛错 → 只记该域 `err`，其余域照常（这是聚合方案能安全落地的前提）。

**编号作用域**：**节内编号独立**（每节从 1 开始），system 明确「编号只在本节有效」；跨节引用一律无效 —— 该约束与各域应用器的"编号必须在候选内"复核天然一致（越界即 `skipped`），形成双保险。

### 3.6 八个联动点（「相关功能需和总览联动起来」的具体清单）

| # | 联动点 | 现状 | 目标口径 |
| --- | --- | --- | --- |

### 3.7 失败、降级与上限

| 场景 | 行为 |
| --- | --- |
| 聚合前预算超限（各节字数之和 > `cfg.repairAggMaxChars`，或域候选总数 > `cfg.repairAggMaxItems`） | 按域**裁剪候选**（优先保留 `defects`，其次 `corrHigh`），**如实计数** `aggTruncated`，并在报告里注明 |
| 聚合响应**不是有效 JSON**（含被截断，K13） | **降级**：按域分批重发（每批 ≤ `cfg.repairAggFallbackBatches`，默认 2 批），批内仍多域聚合；逐批如实计数 |
| 降级后仍失败 | `aggError` 有值，**不写任何 AI 结果**（保持今天"AI 段失败即零写入"的口径），机械段成果照常保留 |
| 某域子树缺失 / 形状不对 | 该域跳过（`aggMissingDomains` / `aggSkippedDomains`），其余域照常落库 |
| 某域应用抛错 | 逐域 `try/catch` 隔离；记该域 `err`（消息前 80 字），其余域照常 |
| 某域被闸门挡下（如计划/悬念的 `disabled` / `ai-off`） | 该域**不进聚合**并给跳过原因（沿用既有 `planSuspSkipped` 三值口径） |

### 3.8 可见性与留痕

| 面 | 内容 |

### 3.10 与既有通道的边界（不是什么）

- **不是 AI 全库重写**：模型仍只看到各域**候选**（窄契约不变）；
- **不是新增通道**：新增条目仍只能走提取（`core/ingest.js`）与提升（`core/promote.js`）；
- **不是修复的替代**：本稿不减少任何既有能力，只减少**请求次数**与**重复劳动**；
- **不是"把各域按钮删掉"**：单域入口是用户的可控粒度，本稿明确保留并写进硬约束（§3.1）。

## 5. 风险与对策

| # | 风险 | 对策 |
| --- | --- | --- |
| R1 | **一次请求内容过大** → 响应被截断（无截断检测，K13） | 双闸（`repairAggMaxItems` / `repairAggMaxChars`）+ 每域只输出"需要改动的项"+ 降级分批（§3.7） |

## 6. 待确认问题清单（Q1–Q8 · 每条给建议默认与影响）

| # | 问题 | **建议默认** | 采纳 / 不采纳的影响 |

| **Q1** | 聚合契约用「按域分键的单一 JSON」还是「多段文本各带自己的 JSON」？ | **按域分键的单一 JSON**（有 15 键摘要先例，K12） | 采纳：解析一次、拆回直接、可域级隔离；不采纳（多段文本）：模型更容易漏段，且解析要自己切分 |

| **Q3** | 全面修复是否引入"先出计划后应用"的预览确认？ | **不引入**（保持今天 8 域"AI 回包即落库"的形态），预览制留给货币 | 采纳：与现状一致、零交互变更；不采纳：安全但每轮多一次交互，且要为 8 个域各造 `*Plan()`（K8 无此分离） |
| **Q4** | 货币修正与关联层清理是否也并入"全面修复"？ | **不并入 AI 聚合**（零 AI）；货币保留其"预览 + 确认"独立入口；关联层维持第①段第 6/7 步 | 采纳：不动既有安全设计；不采纳：会把"用户确认制"变成"自动执行"，风险反向 |
| **Q5** | 履历修复（`runResumeRepair`，按角色单人、带 canon 护栏）是否进全面修复？ | **不进**（它是"按角色补全"，不是"全库维护"；进聚合会把每角色一次的任务变成一次大请求） | 采纳：全面修复的范围稳定；不采纳：范围膨胀 + 护栏语义被稀释 |
| **Q6** | 角色域的"第 2 次 strict 重试"在聚合路径下是否保留？ | **保留**：聚合出结果后，若该域应用结果为 0 改动，仍按既有逻辑触发 1 次 strict 补发（**额外 1 次请求**，如实计数） | 采纳：质量不下降，代价是偶发第 2 次请求；不采纳：聚合路径与单域路径行为不一致（更难解释） |
| **Q7** | 两档按钮的忙态互斥范围？ | 全面修复进行中 → 9 个 🔧 置灰；单域修复进行中 → 总览 🛠 置灰（§3.6-2） | 采纳：避免"边扫边改"；不采纳：并发下计数与游标互相干扰 |
| **Q8** | 是否给"参与全面修复"的逐域开关？ | **不给逐域开关**，只给总开关 `cfg.repairAggEnabled` | 采纳：配置面小、口径简单；不采纳（逐域开关）：`cfg` 键与控件成倍增长，且"半开的全面修复"难解释 |
