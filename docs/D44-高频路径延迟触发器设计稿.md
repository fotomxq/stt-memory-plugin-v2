## 0. 一页摘要：审计结论（先量，再改）

审计方法：用 **4000 条目**（3000 记忆 + 1000 情节 + 60 角色 + 200 传言 + 150 场景）+ **2000 条聊天消息**的存档，
在真实引导路径（`index.js` + 内核 + 界面）下**逐项实测**，并按「触发频率 × 单次成本」排序。

| # | 高频点 | 触发频率 | 单次成本（实测） | 处置 |
| --- | --- | --- | --- | --- |
| 1 | `nsfwSoftenState()`（全库全字段扫描） | **总览每次渲染**（每次点击） | **245 ms** | ✅ v3.49.0 已改（事件触发 + 10s 延迟去抖） |
| 2 | **`pushMemoryInject()`（重建整份注入体）** | **每条消息渲染**（`CHARACTER_MESSAGE_RENDERED` / `USER_MESSAGE_RENDERED` / `GENERATION_ENDED` / `CHAT_CHANGED`） | **16 ms**（+ 开向量检索还会再发一次 embedding 请求） | ✅ **v3.50.0 本稿**（延迟 1.5s + 生成为界补做/作废） |
| 3 | `wireKernelChatHooks()`（聊天视图重建） | 每条消息渲染 | 1.39 ms（2000 条聊天） | ⏸ **保留即时**：注入构建依赖它刷新的 scope / 楼层，且成本可控 |
| 4 | `scheduleClockExtract()`（剧情时钟自动提取） | 每条消息渲染 | **已是 1.8s 防抖** | ✅ 既有（正是本稿「延迟触发器」的同款先例） |
| 5 | 管线状态心跳（`updatePipelineStatusDom`） | 总览驻留时 500ms | ≈0 ms（只刷新一个块，且离开页面即停表） | ⏸ 保留 |
| 6 | 调试桥状态心跳（`updateBridgeStatusDom`） | 设定→调试驻留时 1s | 廉价（文本未变不写 DOM） | ⏸ 保留 |
| 7 | `saveStateNowQuiet('generation')`（落盘） | 每次生成结束 | 序列化 3.5 ms + 落盘 | ⏸ 保留：**数据安全不得延迟** |
| 8 | `dataAggHash()`（全库聚合指纹） | 镜像推送 / 一致性读数 | 12.7 ms | ⏸ 观察：不在高频突发路径（同步与诊断专用） |
| 9 | 面板整页重绘（`panelBodyHtml`） | 每次用户动作 | 5–14 ms（各页） | ⏸ 保留：一次动作一次，不属「高频突发」 |
| 10 | 滚动条 `input` 联动 | 拖动每帧 | 只改读数（不落盘、不重绘） | ✅ 既有（v2.84/2.85 已优化） |
| 11 | 调试日志 / 追踪缓冲 | 每次动作 / 管线结束 | 环形上限恒定（`TRACE_ITEM_MAX` / `DEBUG_CAP`） | ✅ 既有（内存不随会话增长） |

**结论**：全仓只有一个真正的「高频 × 重负载」组合 —— **第 2 项（每条消息渲染都重建注入）**。
其余要么已被既有的防抖/心跳停表机制覆盖，要么频率虽高但成本可忽略，要么属于**不得延迟**的数据安全路径。

## 1. 目标 / 非目标

### 1.1 目标

1. **注入刷新改为延迟去抖**：楼层事件到达只**排一次**延迟刷新（1500ms），窗口内重复事件**合并**为一次构建；
2. **发送前绝不漏**：生成开始（`GENERATION_STARTED`）时——拦截器开着则**作废**待做（它自己会权威构建），
   拦截器关着则**立刻补做**（那时事件路径是唯一刷新源）；
3. **拦截器侧去重**：`host/interceptor.js` 在自建之前作废待做，避免「刚刷完又刷一次」；
4. 机制**落新模块**（`host/inject-schedule.js`），`index.js` 只留接线（体量棘轮 `C11`）；
5. **读数可见**：把「信号 / 合并 / 补做 / 作废 / 失败」计入调试桥（`ftt.injectSchedule()`），事后可核对。

### 1.2 非目标（明确不做）

* **N1 不动「发送前注入」的权威路径**：`host/interceptor.js` 的构建时机与内容**一字不改**（只加一行作废）；
* **N2 不动落盘**：`saveStateNow*` 是数据安全路径，**不得**延迟（第 7 项保留即时）；
* **N3 不动既有两个心跳**（管线 500ms / 调试桥 1s）——它们已有「离开页面即停表」；
* **N4 不动 `wireKernelChatHooks`**（第 3 项）：注入构建依赖它，且实测 1.39ms；
* **N5 不优化 `buildMemoryBodyForInject` 本身**（16ms 的召回打分与预算择优）：本轮只改「**何时**构建」，
  「**构建多快**」另立条目（与 `docs/D41` N6 同款边界）。

## 3. 方案

### 3.1 新模块 `host/inject-schedule.js`（口径与 `技-50` 一致）

| API | 作用 |
| --- | --- |
| `scheduleInjectRefresh(reason)` | 楼层事件信号：排一次 `INJECT_REFRESH_DELAY_MS`（**1500ms**）后的刷新；窗口内重复信号 → `coalesced`（**不重排**） |
| `flushInjectRefresh(reason)` | **立刻补做**待做（生成开始且拦截器关着；无待做 → `false`） |
| `cancelInjectRefresh(reason)` | **作废**待做（拦截器即将权威构建 / 生成开始且拦截器开着） |
| `injectScheduleState()` | 读数：`signals` / `coalesced` / `runs` / `flushed` / `cancelled` / `failed` + 原因环形（≤20 条） |
| `setInjectScheduleHooks({now, setTimeout, clearTimeout, push})` | 测试注入点（生产不调） |

### 3.2 接线（`index.js` 三处，全部 1 行级）

| 位置 | 改动 |
| --- | --- |
| `onFloorChanged` | `pushMemoryInject(...)` → `scheduleInjectRefresh('floor-changed')` |
| 事件绑定 | 新增 `GENERATION_STARTED: onGenStarted` |
| `onGenStarted` | 拦截器**开着** → `cancelInjectRefresh`；**关着** → `void flushInjectRefresh` |
| 调试桥读数 | `injectSchedule: () => injectScheduleState()` |

### 3.3 时序

```text
CHARACTER_MESSAGE_RENDERED ─┐
USER_MESSAGE_RENDERED      ─┼─► scheduleInjectRefresh ─► 排一次 1.5s ─┐
GENERATION_ENDED           ─┤        （窗口内重复 → coalesced）        │
CHAT_CHANGED               ─┘                                          │
                                                                       ▼
                        ┌────────────── 1.5s 到 / 被 flush ──────────────┐
                        │  pushMemoryInject（一次，参数与旧实现同口径）  │
                        └───────────────────────────────────────────────┘

GENERATION_STARTED ──┬─ 拦截器开着 → cancelInjectRefresh（它自己会权威构建）
                     └─ 拦截器关着 → flushInjectRefresh（立刻补做，绝不让发送用上过期注入）
```

### 3.4 为什么这样是安全的（三条不变量）

1. **发送时一定是最新的**：拦截器开着 → 它在生成时刻构建；拦截器关着 → `GENERATION_STARTED` 补做。
2. **不会重复构建**：拦截器路径先作废待做；`GENERATION_STARTED` 在拦截器开着时也只作废不构建。
3. **失败静默**：推送抛错 → 计入 `failed`，绝不影响聊天与生成（旧实现同样是 `.catch(() => {})`）。

### 3.5 落点与体量

| 文件 | 改动 |
| --- | --- |
| `host/inject-schedule.js`（新） | 机制全部在内（延迟 / 合并 / 补做 / 作废 / 读数 / 注入点） |
| `index.js` | 接线（import 1 + `onFloorChanged` 1 + `onGenStarted` 4 + 绑定 1 + 读数 1；注释压到最简） |
| `host/interceptor.js` | **2 行**（import + 自建前作废） |
| 测试 | 新增 `tests/unit/inject-schedule.test.js`（16 项，含 3 条反向探针）；冒烟 `G2` 重写为「延迟 + 补做」双断言、`B2` 事件清单 +1 |

### 3.6 回退

`onFloorChanged` 里把 `scheduleInjectRefresh` 换回 `pushMemoryInject` 即可回到 v3.48.x 行为
（新模块留着不接线也不生效）。

## 4. 风险与对策

| # | 风险 | 对策 |
| --- | --- | --- |
| R1 | 注入在「事件之间」短暂陈旧（≤1.5s） | 只影响**预览与状态**；发送前由拦截器或 `GENERATION_STARTED` 补做（§3.4 不变量 1） |
| R2 | 拦截器关着时用户「事件后立刻发送」 | `GENERATION_STARTED` 在拦截器关着时**同步补做**（`await` 在一次生成开始之内完成） |
| R3 | 重复构建 | 拦截器与 `GENERATION_STARTED` 双向去重（作废优先） |
| R4 | 沉默失败 | `failed` 计数 + 调试桥读数；失败不影响聊天（与旧实现同口径） |
| R5 | 定时器泄漏 | `cancel` / `flush` / `reset` 都会 `clearTimeout`；单测覆盖「作废后不再构建」 |
| R6 | 体量棘轮 | 机制整体落新模块；`index.js` 注释压到最简（实测恰好 +40，未上调基线） |
