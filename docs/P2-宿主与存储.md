## 2. 保存流水线（`adapters/store.js`）

**V1 顺序，逐字复刻**（批次 5 黄金样本已证明「内容哈希墓碑与原子 `h` 刷新都在此流水线」）：

```text
saveStateNow()
 ① entryIndexInit()        —— 首次建立索引基线（此后消失的条目才会被留痕）
 ② entryIndexBuild(true)   —— 刷新全部原子 h + 建当前索引（单遍）
 ③ tombstoneSweep()        —— 对照上次索引：消失条目写「id + 内容哈希」双墓碑（先于写库）
 ④ storageEnvelope(state)  —— { v, scope, payload:{scope,updatedAt,data}, hash, ts }
 ⑤ 写后端：localStorage 信封 → IndexedDB（SillyTavern.libs.localforage）→ 服务端用户目录文件
 ⑥ saveSettings()          —— 配置随设定落盘
```

| 入口 | 说明 |
| --- | --- |
| `saveStateNow({ skipFile })` | 立即保存；`skipFile: true` 跳过服务端文件（测试/离线） |
| `scheduleSave(reason)` / `cancelScheduledSave()` | 防抖保存（默认 800ms，可 `setSaveDebounce` 覆盖） |
| `loadFromLocalStorage()` | 读本机信封并**校验 `storageHash(payload)`**，不一致即丢弃（交服务端文件兜底） |
| `loadFromServerFile()` | 读服务端信封并同样校验 |
| `wirePersistHooks()` | 把内核 `saveState()`/`saveCfg()`/`log()` 接到本模块（内核不知宿主） |
| `storeStatus()` / `lastSaveInfo()` | 调试：作用域 / 上次落盘 via / 字节数 |

失败姿态：任何后端缺失或异常都**只降级不抛出**；写库失败不影响交互（`lastSave.error` 记录原因）。

## 3. 服务端文件通道（`adapters/user-file.js`）

| 项 | 约定 |
| --- | --- |
| 命名 | `ftt2-state-<slug>.json`（V2 自有前缀，**与 V1 的 `ftt-state-*` 并存不冲突**，便于导入器读取 V1 文件） |
| slug | V1 口径：只允许 `[A-Za-z0-9_.-]`；中文名 → 短哈希 `n<base36>` |
| 写入 | `POST /api/files/upload`，`{ name, data: base64(UTF-8 JSON) }`（ST 原生，V1 生产已验证） |
| 读取 | `GET /user/files/<name>`（失败返回 `ok:false`，不抛） |
| 删除 | `POST /api/files/delete`，`{ path: '/user/files/<name>' }` |
| 编码 | 无 `TextEncoder/btoa` 环境自动降级（返回空 → 调用方静默跳过） |

## 5. 入口接线（`index.js`）

`init()` 在挂载设置面板后调用 `loadMemoryState()`，链路为：

```text
wireKernelChatHooks()            —— 聊天只读视图 → 内核注入视图（消息 / 最新 AI 正文 / 楼层号 / 角色稳定键）
wirePersistHooks()               —— 内核 saveState()/saveCfg() → 本模块落盘
loadFromLocalStorage()           —— 本机缓冲（哈希校验，不一致即丢弃）
   ↓ 无
await loadFromServerFile()       —— 服务端 ftt2-state-<slug>.json（同样校验）
   ↓ 无
emptyState()                     —— 空容器
   ↓
migrateState()                   —— 结构健壮性清洗 + 多版本迁移链
   ↓
attachKernelState() + setLastMessageId()
```

`loadMemoryState()` 返回 `{ via }`（`local` / `file` / `new`），并写入 `runtime.store` 供 `/ftt`、`FTT.status()` 查看。

事件侧（P2 接线，仍只读、不写用户数据）：

| 事件 | 动作 |
| --- | --- |
| `USER_MESSAGE_RENDERED` / `CHARACTER_MESSAGE_RENDERED` | 刷新内核聊天视图（楼层号会变） |
| `GENERATION_ENDED` | 刷新视图 + `scheduleSave('generation')` 防抖落盘（P3 在此处接提取） |
| `CHAT_CHANGED` | 清注入 → 刷新视图 → **重新载入该作用域容器**（角色切换即换 scope） |

冒烟覆盖：`B2`（四个事件全部绑定）+ `B2b`（容器载入来源与聊天视图注入）；本阶段冒烟 21 项全绿。

## 6. V1 数据导入器（`adapters/import-v1.js`）

设计约束（用户要求「不丢数据 / 可回退」）：**只读源、干跑优先、显式 apply 才写入、绝不删除 V1 任何文件**。

### 6.1 数据源发现

| 源 | 说明 |
| --- | --- |
| 服务端记忆文件 | `ftt-state-<slug>-<scope8>.json.gz`（V1 默认写 gzip）与 `.json`；同目录 `-bak` 备份 |
| 旧 settings 信封 | `SPreset_FTTMemory_char:<hash>`（v1.127 之前形态，裸 JSON 或信封） |
| 本机命名缓存 | `SPreset_FTTMemory_FileSlug_/FileNames_/ArchiveName_<scope8>` —— 反推 V1 作用域与**实际写过的文件名** |
| 配置 | `SPreset_FTTMemoryConfig`（随报告返回，暂不写入 V2 配置） |

### 6.2 关键事实：两边作用域**定义不同**（黄金样本 9 实测）

```text
V1：scope = 'char:' + hashText(TH getCurrentCharacterId())        → char:1157z2a
V2：scope = 'char:' + hashText(角色稳定键 avatar → name2)          → char:2mcm47
```

故导入器**枚举候选作用域**（TH 身份 → V2 当前作用域 → 名称/头像/角色号 → 本机缓存反推），
逐个构造文件名去试（同一 `scope8` 只展开一次）；读取顺序＝本机历史名 → slug 缓存名 → 派生名。

命名派生已与 V1 oracle 逐字符对齐（`tests/fixtures/v1-golden-importer.json`）：

| 函数 | 规则（V1 逐字） | 实测样本 |
| --- | --- | --- |
| `v1ScopeHash8` | `(hashText(scope) + hashText('ftt-scope:'+scope)).slice(0,8)` | `zxg18scl` |
| `v1SlugFallback` | `'n' + hashText(scope).slice(0,6)` | `nzxg18s` |
| `v1SlugFromName` | 只留 `[A-Za-z0-9_-]` 取 24；全非 ASCII → `'n'+hashText(name).slice(0,6)` | `角色甲 → n2mcm47` |
| `v1FileNames` | `ftt-state-<slug>-<scope8>` + `.json.gz` / `.json`（`-bak` 同规则） | `ftt-state-n2mcm47-zxg18scl.json.gz` |

### 6.3 解码与完整性

- gzip：`isGzipBytes`（魔数 `1f 8b`）+ `gunzipToText`（`DecompressionStream`，Node 18+/现代浏览器）；
- 信封：`decodeV1Envelope` 校验 `hash`（双轮 FNV-1a，独立实现以免自证）→ 不一致即拒收；裸 state 兼容（旧存档变量形态）；
- 不可读/损坏只记录在报告的 `sources[].reason`，不影响其余候选。

### 6.4 报告与合并（append-only）

`buildImportReport` 逐维度给出 `v1 / current / add / exist / conflict` 与墓碑计数，**不写入任何数据**；
`mergeV1IntoCurrent` 按 id 并集：当前容器为基准、V1 独有条目追加、**同 id 以当前为准**（不覆盖用户现有数据）、
`deleted`/`deletedH` 墓碑**并集**（避免导入把已删除条目唤醒）、单值容器仅在当前为空时采用 V1 值、`scope` 归位 V2 当前作用域。
合并前对两侧做**深拷贝**：V1 源对象零改动（测试 I9 断言 `JSON.stringify(v1State)` 不变）。

### 6.5 入口

| 入口 | 用法 |
| --- | --- |
| `/ftt-import` | 默认**干跑**并提示「确认写入请用 `/ftt-import apply`」；`apply` 才写入 |
| `FTT.importV1({ apply:true })` / `FTT.importStatus()` | 控制台调试入口 |
| `index.js#runV1Import` | 干跑 → `attachKernelState(merged)` → `saveStateNow()` 走完整保存流水线（含墓碑/信封） |

导入后 V1 源文件仍在原处；用户可随时用 V1 或手工备份回退（导入器不调用任何删除接口，冒烟 F3 断言无 `/api/files/delete` 调用）。
