## 1. 「最新情节」改用内置天数判定

- 情节可带 `storyDay`：正文头「第 N 天」由 `core/clock-extract.js#recordReservedStoryDay` 记到该情节上
  （**预留计数器**：只记录、只随存档往返，此前不与时钟联动、不参与注入）。
- `core/recall.js#trustedPlotList`（时钟解析与在场解析**共用**的情节顺序）新增一条规则：

  ```text
  两边都有 storyDay(>0) 且不等  →  天数大者在前            ★ v3.6.0 新增
  否则                          →  楼层优先 → 剧情日期 → id（原口径，完全不变）
  ```

  为什么这样定：**两边都有天数**才用天数（用户要的「按内置天数判断谁最新」）；
  任一侧没有天数就完全沿用原口径 —— 否则「新情节还没写第 N 天」会被老情节压下去，时钟反而倒退。

## 2. 自动修复新增「剧情时钟」一步（第 1 段 · 零 AI）

```text
runRepairMech 固定顺序（v3.6.0）：
  机械去重 → 遗忘清扫 → 条数裁剪 → 垃圾清理 → 衰退清扫
  → 关联层维护（V1 口径）→ 无效关系清理（v3.2.0）
  → 楼层突变识别与修正（v3.5.0）→ **剧情时钟：按最新情节刷新时间/地点/人物（v3.6.0）**
```

- 接线：`core/repair.js` 的 `repairHooks.clockSync` → `index.js` 的 `clockAutoExtractOnce({ force: true })`，
  即 v2.81.0「分析后按最新情节同步剧情时钟」**同一条处理**（手工锁定优先 → 逐字段取最新情节 →
  写 `state.state.date/time/location/present/storyDay` + `clockSrc` 可解释来源）。
- 因为它在**第 1 段**，所以「手动点自动修复」与「关闭 AI 修订的自动路径」**都会执行**（零 AI、无网络）。
- 报告/日志（如实、可核对）：
  - `剧情时钟：已按最新情节刷新（第 30 天 · 日期 1919-11-10 · 时间 10:30 · 地点 仓库 · 在场 角色甲）`
  - `剧情时钟：已跳过（手工锁定，不覆盖日期/时间/地点）（日期 …）` —— 手工锁定（`cfg.clockManualLock`，默认开）时**不覆盖锚点**
  - `剧情时钟：已是最新（本轮无改动）` —— 取到的值与现值一致
  - 调试日志 `kind='时钟'` + `stage1.clockSync`（含 `changed` / `manualLock` / `storyDay` / `plotId` / **`plotStoryDay`**）
- 「人物」= 在场名单（既有口径）：最新 AI 正文 → **最新情节的涉及角色**（`entities` → `plot-atom`，v2.81.0 修复后可用）→
  保留旧名单（**不清空**）。

## 4. 兼容与回退 / 风险

- **排序升级是保守的**：只有「两边都带 `storyDay`」时才改为天数优先；其余情况一行代码都没动 → 老数据、导入数据、
  无「第 N 天」正文的剧情行为与 v3.5.0 完全一致（既有黄金样本逐项通过）。
- **不覆盖手工锚点**：`cfg.clockManualLock` 默认开，锁定时本步骤只维护「在场」与来源说明，不改日期/时间/地点。
- **不引入他源**：仍只从「情节」取值（v2.51.0 起的硬口径）；没有可用情节时**不清空**旧值。
- **回退**：`repairHooks.clockSync = null` 即跳过该步骤（其余修复步骤不受影响）。
- **未核实**：`storyDay` 只在正文头写出「第 N 天」时才有值（用户剧情不写天数时该判据不生效 → 自动退回楼层口径，
  属预期）；如需强制要求天数，可在后续版本加设置项（本轮按用户口径「按内置天数判断」实现，未新增开关）。
