# P10c87 · 数据导出卡死修复与分段导出（v3.45.7）

> 文档版本：v1.0 ｜ 日期：2026-10-12 ｜ 状态：生效（v3.45.7）
> 用户原话：「新版本，小版本更新。数据导出功能会直接卡死，可能和数据量有一定关系。建议本地保存时，应考虑动态注入备份的形式，或其他优化措施提高导出效率。」
> 关联：`CHANGELOG.md` v3.45.7 · `core/export.js`（新）· `docs/04`（数据管理 · 导出）· `docs/README` v2.77 · `docs/05` §2 ·
>   `tests/unit/export-chunks.test.js`（新）· `tests/unit/file-io.test.js`（+E3/E4/F3b）· 上一轮 `P10c86`（v3.45.6）

## 1. 现象与真机取证（为什么「和数据量有关系」）

**用户报告**：点「⬇ 导出 JSON 文件」→ 界面**直接卡死**。**真机读数**（本机 TauriTavern + 只读调试桥 `ftt.fileTransport`）：

```text
lastWrite: { backend: "tt-native", bytes: 10432694, at: 1791803322228 }   ← 主文件 ≈ 10 MB
```

即**同一份存档的导出文本约 10 MB**。旧实现（`index.js#exportStateJson`）在这份数据上连做四件重活（逐条取证见下），
任一条都足以让 WebView 卡死 —— 这就是「与数据量正相关」的来源。

| # | 旧实现做的事 | 代价（10 MB 存档量级） | 取证落点 |
| --- | --- | --- | --- |
| ① | `JSON.parse(JSON.stringify(state))` —— **整份深拷贝** | 一次全量序列化 + 一次全量解析（另加等量临时内存） | `index.js#exportStateJson`（旧） |
| ② | `JSON.stringify(envelope, null, 2)` —— **2 空格美化** | 体积再涨约 **1.3×**（实测 872 KB → 1.13 MB），且逐键缩进显著变慢 | 同上；`tests/unit/export-chunks.test.js#D3` 实测两者体积 |
| ③ | 把整串塞进 `<textarea>` 渲染 | 页内渲染 MB 级文本 = 布局/绘制灾难（真卡死主因） | `ui/panel.js#settingsBody`（`ps.exportText` → `<textarea data-ftt-export>`） |
| ④ | 把整串写剪贴板 `navigator.clipboard.writeText` | MB 级写入长时间阻塞、且多半失败 | `ui/panel.js`（`exportState` 动作，旧） |

> 附带发现：只读桥方法 `ftt.stateSize` 也是「**跑一遍完整导出再量长度**」（`ui/debug.js`）——
> 于是**一个只读诊断动作也会把页面卡住**。本版一并改掉（见 §3 ④）。

## 2. 修复口径（分段导出 = 用户建议的「动态注入」形态）

| 落点 | 改动 |
| --- | --- |
| **`core/export.js`（新，纯内核）** | `exportChunks(state, meta)` —— **生成器**，逐段产出 JSON 片段 `{section, part, index, total}`；`exportParts()`（收集为片段数组，**不拼接**）· `exportTextOf()`（等价整串，小数据用）· `exportEnvelopeValue()`（信封值形态）· `exportSectionKeys()`；常量 `EXPORT_INLINE_MAX`（1 MB，页内内联上限）· `EXPORT_PRETTY_MAX`（512 KB，保留人读美化的上限）· `EXPORT_YIELD_CHARS`（256 KB，分批让出主线程的粒度） |
| `index.js#exportStateJson(opts)` | **不再深拷贝**；**大存档不再美化**（`> EXPORT_PRETTY_MAX` 一律紧凑；`{pretty:true}` 才显式美化）· 新增 `{parts:true}`（已分段、不拼接）与 `{stream:true}`（交出**生成器**，`{source,total,chars:null}`）两种模式；**缺省仍是字符串**（devtools / 命令 / 测试的历史契约不变） |
| `ui/file-io.js#downloadTextParts`（新） | `new Blob(parts)` **直接吃片段数组** → **不需要**先把片段拼成一整串（省一份等量内存与一次全量拷贝）；与 `downloadTextFile` 共用同一个下载实现（`downloadBlob`，行为/返回值形状不变） |
| `ui/panel.js#exportState` 动作 | ① 经 `exportState({stream:true})` 拿生成器 → **逐段组装**（累计 ≥ `EXPORT_YIELD_CHARS` 才 `await` 一次宏任务；小存档一次组装即结束）；② 片段直接进 `Blob`；③ **超过 `EXPORT_INLINE_MAX` 时不进文本框、不写剪贴板**，note 如实写明原因；④ 无分段能力（旧钩子 / 测试桩）时回落整串路径 |
| `ui/panel.js#panelState` | `exportChars` 改为「**上次导出字符数**」（不再由 `exportText` 反推）—— 大存档不内联时读数仍如实可见 |
| `ui/debug.js#ftt.stateSize` | 改走 `{parts:true}`（只累计片段长度、**不拼接**），并回报 `parts` 与 `via` —— 只读探针不再触发整串导出 |
| `devtools.js` | `FTT.exportState(opts)` **转传 opts**（`{stream:true}` / `{parts:true}` 经调试导出可用） |

**语义等价**（硬判据）：`parts.join('') === JSON.stringify(exportEnvelopeValue(state, meta))` ——
由 `tests/unit/export-chunks.test.js#A1`（普通对象 / 空 / `null` / `undefined` / 数组 / 含 `undefined` 值的键 / 转义字符 / 嵌套）
逐个强制。导入侧只认 JSON，故「紧凑 vs 美化」不影响兼容。

## 3. 测试与反向探针

| 断言 | 内容 |
| --- | --- |
| `tests/unit/export-chunks.test.js`（**9 项**，新） | A 组：分段拼接**逐字节等价** + 可 `JSON.parse` + 段结构（`@meta` / `@state-open` / 各键 / `@end`）；B 组：不拼接（片段数组）+ `chars` 自洽 + **不修改入参**；C 组：内联上限判据与常量关系；D 组：`index.js` 三模式（字符串 / `parts` / `stream`）+ **小存档仍美化、大存档紧凑** |
| `tests/unit/file-io.test.js` +**3 项** | `F3b` 分段数组直接进 `Blob`（不拼接）；`E3` 生成器路径 → 分段下载（小数据仍内联 + 剪贴板）；`E4` **大存档不内联、不写剪贴板、仍成功下载**且 note 如实说明 |

**同轮修掉一处门禁盲区**（不是为本轮开绿灯，而是它本来就漏判）：`scripts/check-core-refs.js#declared()` 的「函数声明」正则
`/\bfunction\s+([A-Za-z_$][\w$]*)/g` **不识别生成器语法**（`function*` / `function *name`）→ 生成器名不被登记为「已声明」，
却在同一文件内被引用 → **误报「未定义标识符」**（本轮新增 `core/export.js#exportChunks` 即被误报）。
已改为 `/\bfunction\s*\*?\s*([A-Za-z_$][\w$]*)/g`；**反向探针** = 改回旧正则 → 门禁立刻报 `core/export.js → exportChunks`（实测）。

**反向探针（实测会失败，证明判据不是恒真）**：

| 反向改动 | 必须失败 | 实测 |
| --- | --- | --- |
| `ui/panel.js` 内联判据写死为「总是内联」 | `file-io` **E4** | ✅ 15 通过 / 1 失败 |
| `index.js` 默认导出改回「总是 2 空格美化」 | `export-chunks` **D3** | ✅ 8 通过 / 1 失败 |

**顺带修掉的一处时序风险**：分段组装最初「每 6 段让出一次」（含开始时无条件让出一次），
在小存档上引入了可感知的额外延迟、并让「点击后立刻落文件」的既有冒烟断言（AY1）在 20 ms 窗口内看不到结果。
现改为「**只有累计 ≥ `EXPORT_YIELD_CHARS`（256 KB）才让出**」：小存档一次组装即结束（零额外延迟，冒烟恢复绿），
大存档才分批让出。该取舍写在 `core/export.js` 常量注释与 `ui/panel.js#buildExportPartsForPanel` 里。

## 4. 未做 / 有意不动（明确非目标）

1. **不改导出文件格式与文件名**（`ftt-memory-v2-export` / `FTT记忆_<hash>_<日期>_<时间>.json` 不变）—— 导入与既有备份照旧可用；
2. **不改 `exportStateJson()` 的默认返回类型**（仍是字符串）—— `devtools` / 命令 / 既有测试的契约不变；
3. **不把导出写进本机数据层**（用户提到的「本地保存时动态注入备份」在本版落在**下载通道**：片段直接进 `Blob`，不拼整串）。
   「导出同时落一份到本机目录」属新增能力（会动数据管理页文案与存储路径语义），未做 —— 如需，另行立项；
4. **同类隐患只登记、未在本轮修**（都**不含记忆正文**，体量有上限，故风险远低于本轮的 10 MB 导出）：
   - 导入的**粘贴路径**（`<textarea data-ftt-import>`）—— 没人会把 10 MB 主动粘进去，但判据一旦要做，应与导出的内联上限共用 `core/export.js#exportInlineAllowed`；
   - 调试页的**导出调试包**（`ui/debug.js#exportDebugBundle`：`JSON.stringify(…, null, 1)` + 剪贴板 + `lastDebugExport` 进 `<textarea>`）—— 体量由日志环形上限与单条 2000 字符上限约束；
   - 「清空当前角色记忆 / 快照还原」等确认文案里的「建议先导出备份」不受影响（引导到本轮的导出入口）。
5. **未取得真机证据**：本机宿主页面运行的是 v3.45.5（部署副本已是 v3.45.6，但未刷新）→ 「10 MB 存档点导出不再卡死」只有**无宿主单测 + 体量推算**，
   真机复测请在刷新到 v3.45.7 后点一次导出；量化口径见 §1 与调试桥 `ftt.fileTransport.lastWrite.bytes`（本机实测 10,432,694 字节）。
