## 1. 诉求（`D2` §5.2 两条口径）

| 时机 | 要求 |
| --- | --- |
| **落库前** | AI 给的「依据」必须指向**真实存在的楼层 / 条目**，否则拒收（**防幻觉**） |
| **落库后** | 机械派生 + 校验 → `finding` 进体检报告与调试页（形态 `{code, level, dim, id, field, value, detail}`），**只报告不改数据**（`N4`） |

## 2. 改法

### ① 新模块 `core/constraint-check.js`（纯内核 · **只读**）

| 导出 | 作用 |
| --- | --- |
| `CONSTRAINT_CODES` | `ref-orphan` · `ref-floor-missing` · `causal-inverted` · `evidence-invalid` |
| `CONSTRAINT_REF_DIMS` | 哪个维度允许引用哪些维度（平行/传言/计划/悬念/记忆） |
| `entryRefs(entry)` | 读依据（认 `sourceRefs` / `关联来源` / `来源`，字符串与对象两种写法）→ `[{dim, refId, floor}]` |
| `entryEvidence(entry)` | 读条目自带 `evidence`（数字 / 「见第 7 楼」/ 对象） |
| `buildConstraintIndex(state)` | 建 `id 集 + 楼层表`（因果倒挂判定要用） |
| `filterInvalidRefs(dim, entry, ctx)` | **落库前**：剔除悬空 / 未来楼层的依据，返回 `{entry, kept, dropped}` |
| `constraintFindings(state, opts)` | **落库后**：产出 finding（`level` 恒 `warn`） |
| `constraintCheckOn()` | 总开关（`cfg.constraintCheckEnabled`，默认开） |

### ② 接线（3 处，都很薄）

1. **体检**（`core/data-health.js#dataHealthReport`）：在返回前并入约束 finding —— 因为形态与既有完全一致，
   **报告 / 调试页 / 文本摘要三处出口零改动**即可显示；
2. **入库前**（`core/ingest.js` 的 `parallels.add` 分支）：归一化后先 `filterInvalidRefs`，
   **剔除依据、保留条目**（一次幻觉不该丢掉整条好数据），剔除数量写调试日志；
3. **配置**：`cfg.constraintCheckEnabled`（默认 `true`）+ 设定页控件（投喂范围 → 🛠 自动修复节）——
   对应用户可「关校验器开关」的回退口径。

## 3. 校验项（全部可机械判定，零 AI）

| code | 判据 | level |
| --- | --- | --- |
| `ref-orphan` | 依据指向的条目在当前 state 里不存在 | warn |
| `ref-floor-missing` | 依据楼层 > 已见最大楼层（引用未来楼层） | warn |
| `causal-inverted` | 依据条目的发生楼层**晚于**本条（因果倒挂） | warn |
| `evidence-invalid` | 条目自带 `evidence` 解析不出有效楼层/条目 | warn |
