# P10c168 · 快照链只保留 5 条 + 删楼备份只保留 3 个（v3.52.15）

> 文档版本：v1.0 ｜ 日期：2026-11-17 ｜ 状态：生效（v3.52.15）
> 用户要求（原话）：「1. 修正快照只保留5条。2. 如果存在备份，修正备份只保留3个。」
> 关联：`core/snapshots.js` · `adapters/floor-backup.js` · `host/floor-trim.js` · `index.js` · `docs/D11` / `docs/D13`

## 1. 快照链：总量上限 30 → **5**

* `core/snapshots.js#SNAP_CAP`：**30 → 5**（根 + 增量**合计** ≤5；含根快照）；
* `SNAP_BATCH`：15 → **2** —— 整理时每次把最早的 2 个增量**并入根**（可多轮至 ≤5；内容一个字节不丢，只是不再作为独立可回滚档位）；
* `SNAP_RETAIN_DAYS`（保留窗 30 天）**不变**：两条规则互不代替（超窗并入根 + 总量整理）；
* 创建增量时就按 `SNAP_CAP` 整理（`snapshotCreateIncr → trimSnapshots`），因此**不会先涨到 30 再收敛**；
* UI：快照区块「整理快照链」按钮提示改为「总量超上限（5 条）时把最早的增量并入根（每次 2 个）」。

## 2. 删楼明文备份：只保留 **3 个**（名单兜底）

原实现已是 **3 槽轮转**（`FLOOR_BACKUP_SLOTS = 3`）：写新文件后删该槽位上一份。但「上一份文件名」来自
`floorTrimLog.names`，**该记录丢失**（旧存档 / 换设备 / 保存失败）时轮转会失效 → 目录里可能多于 3 份。

本版补一条**名单兜底**：

* `adapters/floor-backup.js`：新增 `FLOOR_BACKUP_KEEP = 3`、`floorBackupScopePrefix(scope)`、
  `selectFloorBackupPrune(list, scope, keep)`（纯函数：只认本作用域前缀，按时间保留最新 3 份，返回最旧待删名单）；
* `host/floor-trim.js`：每次备份成功后把 `{name, at, scope}` 记入 `floorTrimLog.recent`（有界 ≤24），
  调 `selectFloorBackupPrune` 算出超出者 → 经 `hooks.deleteBackup` 删除（只删本插件 `ftt2-floor-backup-<角色>-` 前缀）；
* `index.js`：接线 `deleteBackup: (name) => deleteStateFile(name)`；
* 失败姿态不变：删除旧备份失败**不影响**本次备份与删楼结果（只影响目录整洁）。

> 边界（如实登记）：酒馆文件通道**没有列目录 API**，因此只能对「插件自己记得的文件名」兜底清理；
> 历史遗留、已无记录的旧备份文件无法枚举清除（不会误删用户自己的文件）。

## 3. 测试

新增 `tests/unit/backup-rotation.test.js`（**4 项**）：
A1 常量（`SNAP_CAP=5` / `SNAP_BATCH=2`）· A2 根 + 8 增量后链长 ≤5（创建时即整理、覆盖不丢）·
B1 `selectFloorBackupPrune` 语义（5→删最旧 2、跨作用域不动、keep=0 不清理）·
B2 端到端：**槽位名记录被清空**（模拟旧存档）连续删楼 4 次 → 备份文件仍只保留 3 份。

同步更新 `snapshot-retain` A1（`SNAP_CAP === 5`）。全量单测 **269 文件**（断言数以门禁实测为准）；冒烟 224 项；`npm run gate` 全绿。

## 4. 边界

1. 快照「档位变少、内容不丢」口径不变（并入根 ≠ 删除内容）；
2. 备份上限 3 = 槽位轮转 + 名单兜底双保险；**不能**枚举目录里无记录的遗留文件；
3. 备份上限只针对**删楼明文备份**；服务端主文件备份 `.bak.json` 仍是**单文件覆写**（恒为 1 份，不参与该上限）。
