## 1. 核对结论（用户推测「把服务端的方法用在了前端」—— 基本成立）

| 事实 | 证据 |
| --- | --- |
| v3.28~v3.37 的本地层只有**宿主**机制（TauriTavern `plugin:fs\|*`、`api.dev` 文件命名空间）+ 一个**本会话**的文件夹句柄（File System Access） | `adapters/local-disk.js#localDiskCapability` / `diskWriteText` |
| 纯浏览器（PC 酒馆网页版 / Firefox）两者都没有 → `localDiskCapability().ok === false`，但 `localDiskOn()` **仍为 true** | 实测（无 `__TAURITAVERN__` / 无 `__TAURI_INTERNALS__` / 无 `showDirectoryPicker`）：`on()=true`、`capability.ok=false`、`probe.error='no-bridge'`、`write.reason='no-capability'` |
| 于是「设置看起来生效、实际一次都写不进去」：每次保存失败 → 回退浏览器本地存储 + 弹告警（用户看到的通知） | `index.js` 载入回退分支 + `ui/sync.js#localDiskProbe` 的失败文案 |
| 相对目录名（如 `fft_v2_store`）解析不出宿主基准目录 → 直接失败（**PC 端不可用**的直接原因） | `localDiskResolveDir` 旧实现 `no-base-dir` |
| 「手机端必须用内置路径」= Android 没有文件夹选择器（`showDirectoryPicker` 缺失）→ 旧文案只能让用户**只填目录名**落到宿主应用数据目录 | `localDiskPickDir` 旧第 ②/③ 步 + 失败文案 |

**一句结论**：本地层把「能不能写盘」**整体押在宿主**上，浏览器能力（除了一个刷新即失效的句柄）完全没被使用 ——
PC 网页版因此不可用；而跨设备时宿主路径本身又不通用。

## 2. 修复：新增**浏览器内置目录**（OPFS，纯浏览器方法）

- **后端**（`adapters/browser-fs.js`）：`navigator.storage.getDirectory()`（Origin Private File System）——
  浏览器自带、按源沙箱化、**不需要任何宿主接口**；`write/read/exists/remove/list/probe` 六个入口，
  逐段建目录、拒绝 `..` 与绝对路径、不抛错（失败如实返回）。
- **标记**：`@browser/<目录名>`（`BROWSER_PREFIX`）。**设备中立** —— 手机与 PC 的同一份配置都成立，各自写各自的浏览器目录；
  `localDiskPathKind()` 单列 `browser`（绝不被当成相对名去解析宿主目录，也不再有跨平台路径告警）。
- **路由按路径判定**（`diskWriteText` / `diskReadText` / `localDiskList` / `localDiskExists` / `diskRemove`）：
  `@browser/…` → 浏览器目录；`@handle/…` → 会话文件夹句柄；其余 → 宿主 fs。
  结构化分片 / 快照 / 日志（`localDiskWriteShards` / `localDiskWriteParts` / `…Read…`）**统一走路由**（不再各自内联一套句柄分支）。
- **能力如实**：`localDiskCapability()` 把 OPFS 也算作可用机制（`mechanism='browser-opfs'`、`browserFs:true`），
  文案从「宿主未提供…」改为「本机没有可用的本地目录机制（…、浏览器也不支持内置目录）」。
- **相对目录名兜底**：本机没有宿主基准目录但有 OPFS 时，`fft_v2_store` → `@browser/fft_v2_store`，
  且 `localDiskEnsureResolved()` **不写回**（保持设备中立的目录名，绝不写死成某台设备的路径）。
- **一键入口**：设定 → 存储「🧩 浏览器内置目录」（动作 `localDiskBrowserDir`，已登记进 `SYNC_ACTIONS`）；
  `localDiskPickDir()` 的顺序变为 宿主对话框 → 浏览器文件夹选择器 → **浏览器内置目录** → 宿主 `api.dev`，
  全失败时才报「没有可用的选择器」。

## 3. 顺带修掉的两处既有缺陷

| # | 缺陷 | 修复 |
| --- | --- | --- |
| ① | **探针假成功**：`diskWriteText` 在任何路径下都优先用「本会话文件夹句柄」（`fsHandle && handleUsable()`），于是选过文件夹之后，校验一个**显式绝对路径**也会写进那个文件夹并回读自洽 → 探针永远通过 | 句柄只在**配置就是句柄标记**（或配置为空且句柄在）时接管（`handleActive()` / `relForHandle()`）；显式路径如实走宿主机制 |
| ② | **「留空 + 有句柄」写不出文件**：`effectiveDir()` 在配置为空时返回 `''` → `localDiskWrite` 直接 `{ok:false, reason:'off'}`，与 `localDiskOn()`（句柄在即开启）自相矛盾 | `effectiveDir()` 在配置为空且有句柄时返回**句柄标记**，各入口口径一致 |

另：`diskRemove` 一并支持三后端 —— 否则浏览器目录里的探针文件会**留在**用户目录中（清理失效）。

## 5. 说明（仍然成立的老边界）

- 浏览器内置目录是**按源沙箱**的：同一个源（同一台设备的同一个浏览器）才看得见；换设备需各自写各自的目录
  —— 这与「本机路径不随服务端同步」（v3.33.0）一致，也正是本修补的语义。
- 宿主接口仍然可用且**优先于**浏览器兜底（手机端行为不变）：宿主给的是**可见的真路径**，更适合想直接去文件管理器翻文件的用户。
- 浏览器不给绝对路径（`@handle` / `@browser` 都是标记），所以界面一律用标记 + 「文件落在哪」两行讲清楚，绝不假装有绝对路径。
