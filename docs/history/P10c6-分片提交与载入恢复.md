## 1. 回滚的三个成因，逐条堵死

用户报告的「退出应用后数据大量回滚」不是一个 bug，而是**三条**互相独立的路径。v3.0.21 三条都处理：

| # | 成因 | 修法 |
| --- | --- | --- |
| ① | **本机缓冲整体覆盖**：旧口径按 `updatedAt` 在「本机缓冲 / 服务端文件」之间**二选一** → 一旦本机缓冲时间戳更"新"却是**残缺/陈旧**数据，就把服务端的好数据整体盖掉 | **载入改为「服务端文件为基底 + 本机缓冲只作并集补充」**（同名按时间取新、墓碑生效）——本机缓冲再也无法整体覆盖；它独有的「尚未成功上传」的改动仍并集进来（不丢） |
| ② | **主文件写入滞后/失败**：保存时若主文件那次上传超时/被杀进程/切后台，改动只在内存里，退出即回滚 | **按维度分片提交**（见 §2）：改动先落**分片**，主文件只是提交点；下次载入会把「比主文件更新」的分片应用回来（每片带内容哈希校验） |
| ③ | **残缺状态写覆盖**：内存里偶然拿到一份残缺状态（聊天未就绪 / 作用域切换 / 载入竞态）时，后续保存把这份残缺状态覆盖到本机缓冲与服务端 | **「无墓碑的大规模缩水 → 拒绝写盘」守卫**（见 §3）：条目数比上一次成功写入少 30% 以上、且少掉的条数远超本次新增删除墓碑数 → 判为异常，本次一律不写（用户显式操作走 `force`，如清空记忆 / 导入 / 手动同步） |

## 2. 分片提交（用户要求「每次数据变动立刻分片提交到服务端存储，实现实时存储能力」）

新增 `adapters/shards.js`：

```text
ftt2-shard-<角色>-atoms.json          ← 每个原子维度一片（atoms / memories / items / plans / … / currencies）
ftt2-shard-<角色>-meta.json           ← 小容器合一片（时钟 / 变量 / 统计 / 墓碑账本 / 快照链 / 已处理台账 / 越界标记）
ftt2-shard-<角色>-manifest.json       ← 分片清单（每片 {at, hash, bytes, n}；载入只读它 1 次）
ftt2-state-<角色>.json                ← **主文件仍是完整信封**（提交点；跨端同步 / 备份 / 导入 / V1 迁移全部照旧）
```

- **写**：只上传**内容哈希变化过**的片（未变的片一个字节都不发）；分片全部写完后再写主文件（提交点）。
  实测（2000 情节 / 1.33MB 信封）：首次完整保存 **185ms**（14 片 + 清单 + 主文件）；
  **改一条情节后的即时保存 = 46ms、只上传 3 个文件**（变化的 atoms 片 + 清单 + 主文件）——即「实时存储」。
- **读**：`loadFromServerFile()` 解析主文件后调用 `applyNewerShards(st, payload.updatedAt)`：
  只读**比主文件严格更新**（或时间戳相同但该维度内容与清单记录不符）的片，逐片校验内容哈希后覆盖对应维度。
  主文件写入滞后/失败时，改动照样回来（**根因回归**：单元 `shards` B1）。
- **失败姿态**：分片缺失 / 损坏 / 哈希不符 / 上传失败 → 一律**静默忽略**，绝不影响主文件与主流程；
  分片是**附加**通道，主文件单独一份即可完整恢复。
- **流量**：退出/切后台的落盘是「强制完整保存」（最后一次写主文件的机会），但**分片仍按内容哈希判定**
  （无变化时只补写主文件 1 次，分片 0 重传）。v3.0.18 的「内容签名短路」照旧：无变化的保存整体跳过。

## 3. 「无墓碑的大规模缩水」守卫（一劳永逸的那道闸）

`adapters/store.js#shrinkGuardCheck`（**放在保存流水线最前面**，必须早于 `tombstoneSweep()` ——
否则本次缩水会被自己记成墓碑，看起来与「用户显式删除」一模一样，守卫就失效了）：

```text
before = 上一次成功写入（或载入来源）的条目数
after  = 本次要写的条目数
dropped = max(0, before - after)
tombstoned = 本次新增的删除墓碑数（deleted + deletedH）
判定异常 ⇔ before ≥ 30 且 (dropped - tombstoned) ≥ 20 且 dropped / before ≥ 30%
异常时 → 本次**不写**（本机缓冲 / 分片 / 主文件一律不动），只留调试日志 + 告警「疑似读到残缺状态」
```

- 用户**显式删除**会写墓碑（`deleteEntry` / 清理动作）→ 不会被拦；
- **清空记忆 / 导入 / 手动同步**等明确动作走 `force` → 不受限；
- 载入完成后立刻用**载入态**登记基线（`primeShrinkBaseline`），避免「本来就只有这么多条」被误判。
