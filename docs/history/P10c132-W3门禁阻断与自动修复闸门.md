## 1. `应-6`：`check-ui-spec` 升为**阻断**

| 面 | 之前 | 现在 |
| --- | --- | --- |
| 默认模式 | **warning**（永远 `exit 0`） | **阻断**：有违规即 `exit 1` → `npm run gate` 整体失败 |
| 逃生阀 | `--strict` 才失败 | **`--warn`**（只报告、`exit 0`）；`--strict` 保留为**同义**（兼容旧调用） |
| 环境变量 | `UI_SPEC_STRICT=1` | `UI_SPEC_WARN=1` 降级（旧变量不再需要） |
| 输出文案 | 「warning 模式：不阻断」 | 「阻断模式：`npm run gate` 会因此失败；排查可用 `--warn` 临时降级」 |

**验收**（`D19` §8）：「构造违规 → `npm run gate` 失败」→ 本轮的 **`A2` 反向探针**就是这样锁的：
往 `ui/row-select.js` 临时注入一处多余 `<table>`（触发 C12 真表格额度）→ 默认模式 **exit 1**、`--warn` **exit 0**，然后还原文件。

## 2. `应-17`：自动修复的触发与闸门修正（`D25` Q1/Q2 裁决）

| # | 缺陷（`U145`） | 修法 |
| --- | --- | --- |
| ① | `state.autoRepair.lastAt` **只读不写** → 判据退化为「累计 ops ≥ N」= 一旦达标**永久放行** | 新增 **`markAutoRepairDone()`**，在 `runRepair` **真的有改动**时（`made>0` 或 AI 修订/删除）写 `lastAt = ops` → 恢复「**距上次修复 N 次**」原意 |
| ② | `cfg.autoRepairEveryOps` 注释宣称「周期触发」，实际**没有周期触发点** | 按 **Q1 裁决收敛为「仅合并失败」**：注释改为**限流**口径（距上次成功修复已过 N 次提取/摘要才放行），不改行为 |
| ③ | `cfg.autoRepair` 是**死键**（设定页渲染「生成后自动修复」却无人读） | 处置为**别名**：`scheduleAutoRepairOnMergeFail` 认 `autoRepairOnMergeFail === true \|\| autoRepair === true` → 用户既有勾选**真的生效**；默认值仍 `false`（开箱行为不变） |

**新语义的连锁影响（已同步既有测试）**：`repair-ai-golden#P3` 原本断言「第二次自动修复立刻撞同楼层上限」——那是 **lastAt 不写**导致的假象；
现在第二次会被**频率闸门**挡下（`auto-repair-frequency`），再累积 N 次提取/摘要后才撞上限。测试已按新语义改写（并新增 `auto-repair-gate` 8 项断言锁死）。
