## 1. 复现（修复前，实测）

```text
初始发酵度 60，剧情日期 1919-11-20（条目 date 同）
第 1 次「立即演化」→ 59     第 2 次 → 58     第 3 次 → 57
第 4 次 → 56                第 5 次 → 55     第 6 次 → 54
```

**同一天、同一个剧情节奏，点几次掉几点**，线性、可掉到 0。有载体时同向线性**涨**（同一 bug 的反方向）。

## 2. 根因

`core/rumor-evolve.js#rumorFermentDelta(r)`：

```text
gain = 2 + 媒体加权(≤8) + min(6, 载体数×2) + (有平行联动 ? 2 : 0)
loss = min(12, floor(days/30)×2) + (无活跃载体 ? 3 : 0)        // days = r.date → 当前剧情日期
delta = gain - loss
```

而 `runRumorEvolve` 的步骤 ⑤ 每次都会 **`r.date = today`（当前剧情日期）**。于是：

| 情形 | 每次增量 | 连点后果 |
| --- | --- | --- |
| 无载体（`gain 2 < loss 3`） | **-1** | 线性掉热度（用户报告的现象） |
| 有载体（`gain > loss`） | **+N** | 线性灌水 |

**一句话**：一个**按剧情时间度量**的量（`days`），被**按调用次数**施加了 —— 因为"已经施加过"这件事**没有被记住**，
而 `r.date` 的跟新又恰好把时间基准**每次清零**。

## 3. 口径：把剧情时间归一化为乘子（用户要求）

新增 `rumorFermentFactor(r)` → `f ∈ [0,1]`：

```text
有剧情时钟：f = min(1, 距上次变化经过的剧情天数 ÷ cfg.rumorFermentWindowDays)     // 默认窗口 = 1 剧情天
无剧情时钟：f = (墙钟距上次变化 ≥ 10 分钟) ? 1 : 0                                  // 退化节流，不冻结
```

应用点：`delta = sign(raw) × max(1, round(|raw| × f))`；`f = 0` → **不施加**并计 `out.fermentSkipped`（**不静默**）；
一旦变化，记 `fermentAt`（剧情日期）/ `fermentAtMs`（墙钟）作为下次基准。

| 情形 | 结果 |
| --- | --- |
| 剧情时间**没推进** | **不施加**（同节奏内连点无效） |
| 推进**满一个窗口**（默认 1 剧情天） | 施加**完整**增减（与旧行为在「每次推进都演化」时一致） |
| 推进**不足一个窗口** | 按比例，**至少 1 点、方向不变**（不因取整抹成 0） |
| **无剧情时钟** | 退化为墙钟节流（10 分钟内不重复施加） |

**新增配置** `rumorFermentWindowDays`（默认 `1`；越小越敏感，`0.25` = 每 6 小时可施加一次）。

**边界（明确不做）**：

1. 不改「**沉寂 + 无载体不回涨**」的既有守卫；
2. 不改裂变 / 联动 / 酝酿变化的掷骰口径 —— 用户明确「**立即演化没问题**」（本修复只让**热度变化**受剧情时间约束，演化本身照常可点、照常出结果）；
3. **不并入 `docs/D18` `业-6`** 的「衰退」范围（那是 `rumorDecayBreakdown` / `parallelDecayScore` 的**衰退基准**问题，`业-6` 自身范围不变）。本条是同一原则（§4「一律按剧情时间」）在**另一个量**（热度增减）上的补齐 —— 二者同族不同物。

## 6. 真机复核建议

| 项 | 怎么看 |
| --- | --- |
| 连点是否还掉热度 | 同一剧情日期下连点「🧪 立即演化」多次 → 发酵度**只在第一次变化**；结果提示里会如实给出「跳过 N 条（剧情时间未推进）」这类计数（`out.fermentSkipped`） |
| 推进后是否恢复 | 剧情日期推进 ≥1 天后（或正文里推进剧情时间）再点 → 热度按窗口施加一次 |
| 窗口是否可调 | 设定 → 传言页 → 「发酵度剧情节奏窗口」；调小 = 更敏感，调大 = 更慢 |
| 无剧情时钟时 | 退化为墙钟节流（同一 10 分钟内只施加一次）—— 若希望完全按剧情时间，请确保剧情时钟可用（总览的日期/时间） |
