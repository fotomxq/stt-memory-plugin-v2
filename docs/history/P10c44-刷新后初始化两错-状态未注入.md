# P10c44 · 刷新后初始化两错（内核状态未注入）（v3.24.1）

> 文档版本：v1.0 ｜ 日期：2026-10-05 ｜ 状态：生效（v3.24.1）
> 用户报告（原话）：「刷新后初始化阶段，插件会抛出两个错误，均可能是初始化顺序异常导致的数据错乱，引发报错。请核对并修复。」
> 用户提供的错误原文（其中一条）：「**已处理楼层漂移防呆失败 Cannot read properties of null (reading 'processedFloors')**」（另一条同类）。

## 1. 取证过程（先证「不是数据坏了」，再证「是顺序坏了」）

| 证据源 | 结果 | 推断 |
| --- | --- | --- |
| 插件调试日志环（300 条） | kinds 里**没有「异常」** | 报错没走 `warn` 的日志出口 |
| 交互时间线 | levels 只有 `debug` / `info`，**无 error/warn** | 同上 |
| 宿主后端日志 | 只有 git 握手 / LLM 连接失败（与本插件无关） | 不是宿主侧错误 |
| 宿主前端日志 | `getConsoleCaptureEnabled = false`（未开捕获）→ 列表为空 | 拿不到 WebView 控制台 |
| 写队列 / 载入顺序 | 263 次写 0 失败；载入（09:34:29）**早于**首次写（09:34:38） | 不存在「先存后读」的错序 |
| 用户提供原文 | `Cannot read properties of null (reading 'processedFloors')` | **`state` 为 null** —— 状态未注入 |

> 「日志全空 + 弹窗可见」本身就是线索：`warn()` 的三个出口里，`persistHooks.warn` 与 `chatHooks.dbgLog`
> 都要等 host 接线（在 `loadMemoryState()` 里才接），初始化早期只剩 toast 能生效。

## 2. 根因（初始化顺序）

```text
init()
  ├─ installHostBridges()                    // 537
  ├─ panelStatusSnapshot()                   // 545 / 562  ← 状态还没注入！
  │     └─ pendingFloors({}) → listUnprocessedFloors() → scanPendingFloors()
  │           └─ 台账维护块 → processedDriftGuard() / reconcileProcessedFloors()
  │                 └─ state.processedFloors   ← state === null → TypeError
  │                       └─ catch → warn('已处理楼层漂移防呆失败', e)  ← 用户看到的那条
  └─ loadMemoryState()                       // 564：内部才 setKernelState + 接线 dbgLog
```

**两条**报错的来源：`processedDriftGuard`（漂移防呆）与 `reconcileProcessedFloors`（归位对账）各一条 ——
它们同在这一个维护块里，catch 里都有 `warn(...)`，而 `migrateProcessedFloorsV170` 的 catch 不告警（所以正好两条）。

**为什么必须「整块延后」而不是「容错继续」**：状态未注入时 `hashFloorText()` 可能全为空，而台账维护的口径是
「无正文 → 丢弃该标记」/「过半失配 → 按当前算法全量刷新」——「容错继续」等于**把台账建在空哈希上**，
正是用户担心的「数据错乱」。所以口径是：**未就绪 → 一个字节都不动，并如实回报原因**。

## 3. 修复

| 位置 | 改动 |
| --- | --- |
| `host/floors.js` | 新增 `kernelStateReady()`；`processedDriftGuard` / `reconcileProcessedFloors` / `migrateProcessedFloorsV170` / `handleFloorShrink` / `recordProcessedFloors` / `clearProcessedFloors` 六个入口短路并回报 `'state-not-ready'` |
| `host/floors.js` | `scanPendingFloors`：维护块整体跳过 + `skipped.stateNotReady`；覆盖判定传空容器；**返回语句里的裸访问** `state.processedDropped` 抽出为 `droppedMarksCount()`（此处不在 try/catch 内，是同一类缺陷的漏网之鱼，由新单测逮到） |
| `index.js` | `panelStatusSnapshot()` / `extraForStatus().extractPending` 未注入时**不问**待分析楼层；模块加载期的 `installGlobalInterceptor()` / `bindDocumentReady()` / `startReadyProbe()` 由裸调用改为包住（原来一旦抛错会让整个扩展加载失败） |
| `core/model/runtime.js` | `warn()` 先落**有界暂存**（20 条），`setChatHooks()` 接线时**一次性补记**进调试日志（`kind='异常'`）；新增 `warnBacklogList()` / `clearWarnBacklog()` / `flushWarnBacklog()` |

> 与 v2.87.0 的 `chatReadyForFloors()`（聊天未就绪守卫）是**两条正交的守卫**：那条守「宿主聊天是否同步」，
> 本批这条守「内核状态是否注入」。两者都在，才覆盖刷新后的完整窗口。
