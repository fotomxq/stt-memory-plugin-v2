## 1. 缺陷（`docs/D33` §8 `技-47`）

九个「单域修复」入口的**候选选择器 / 提示词构造器 / 应用器 / 上限键 / 入口**分散在 6 个模块里
（`group-repair` / `item-repair` / `plan-repair` / `state-repair` / `scene-repair` / `character-repair` / `repair`），
只能靠读代码才知道「某域的全套零件在哪、上限是什么」—— 于是 `技-48`（AI 聚合器）无法机械地
「按域分节 → 一次请求 → 按域拆回」，只能硬编码。

## 2. 修法

新增 **`core/repair-registry.js`**（纯内核，只做索引）：

| 导出 | 作用 |
| --- | --- |
| `REPAIR_REGISTRY` | **九域各一行**（顺序 = 全面修复执行顺序：结构类在前），字段 = `id / label / kind / inTotal / aggKey / limits / buildSection / apply / entry / pick` |
| `REPAIR_DOMAIN_IDS` · `REPAIR_REGISTRY_FIELDS` · `REPAIR_KINDS` | 域序 / 字段清单 / 种类枚举 |
| `repairDomain(id)` · `repairTotalDomains()` · `repairAggKeys()` · `repairLimitKeys(id)` | 查询助手（域项 / 计入全面修复的域 / 聚合契约键 / 上限键） |
| `repairRegistryIssues()` | **自检**：字段齐否 / id 唯一 / kind 合法 / 三类函数齐备（返回问题列表，空 = 通过） |

**行为零变化的关键**：`buildSection` / `apply` 是**原样透传**的薄适配器 ——
`buildSection: (pick) => buildMemoryRepairPrompt(pick)`（**不做 `pick || []` 之类的强制转换**：
实测 `undefined` 与 `[]` 在两个域上走**不同分支**，加了转换就会改变产出）。

## 3. 测试（`tests/unit/repair-registry.test.js`，**11 个断言**）

| # | 断言 |
| --- | --- |
| `A1` | 九域各一行、id 唯一且顺序 = 既定执行顺序、自检 0 问题 |

| `A3` | 每行可用（三类函数 / `pick` 函数或 `null` / `kind` 合法 / `limits` 数组） |

| `B1` | **双跑对照（九域整体）**：各域**自己的 pick 产物**喂进两边，返回值 / 抛错**逐字一致** |
| `B2` | 对照**不是空转**：至少 3 个域产出非空提示词 |
| `B3` | 空库同样逐字一致（不改调用契约） |
| `B4` | 行为零变化：`inTotal` 全 true、总域数 = 9（与面板 9 个 🔧 一致） |

调试过程留痕（如实登记）：首版给 `buildSection` 加了 `pick || []` 强制转换 → `plans`/`suspense` 两域双跑对照**不一致**
（`undefined` 与 `[]` 走不同分支）→ 去掉全部 16 处强制转换后 **11/11 全绿**。这正说明「零变化」不能靠直觉。
