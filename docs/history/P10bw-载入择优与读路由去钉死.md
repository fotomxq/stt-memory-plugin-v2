## 1. 现场取证（v3.0.10 运行中，只读调试桥实测）

用户在真机上复现后，用 **v3.0.10 自带的只读诊断**取证，一次就定位到方向：

| 观测（只读） | 值 | 含义 |
| --- | --- | --- |
| `ftt.loadDiag().memory.marks` | **13** | 内存里台账是**在长**的（用户手动重析过），不是丢了 |
| `ftt.loadDiag().file` | **202674B** · 版本 **2.75.0** · 台账 **11** 条（70,179,183,…,199） | 「与载入同一条读取」返回的却是**很旧的副本** |
| `ftt.loadDiag().localBuffer` | 71243B · 版本 **2.84.0** · 台账 **0** 条 · `hashOk: true` | 本机缓冲很旧、台账还是空的，但**信封自洽**（所以哈希校验这一关不会丢弃它） |
| `ftt.fileTransport().backend` | `tt-native` | 后端判定是原生存储 |
| `ftt.fileTransport().lastWrite.backend` | `tt-native` | **写入确实落在原生** |
| `ftt.fileTransport().routes` / `misses` | **5** / 4 | 会话内已记下若干路由；存在未命中抑制记录 |

**判据**：**写进原生、读回陈旧的酒馆用户目录副本** —— 原生里另有更新的一份（340912B / 12 条）。
所以「刷新后总是显示旧的」是**读侧**问题，既不是哈希不稳，也不是写入失败。
用户观感是「数据丢失」，实际**丢的是台账记账的可见性**，数据本身在原生里好好的。

## 2. 根因：读侧四处 + 载入一处，同源

1. **路由钉死**（`adapters/file-transport.js#readAutoRouted`）：任何一次文件通道命中都会把该 key 的路由记成
   `st-files` 并**排在最前**；读取循环首个命中即 `return` → 原生从此**永远不再被尝试**。
2. **降级结果被固化**：把「原生未就绪时的回退命中」也记成路由 —— 把某一刻的无奈当成了永久事实。
3. **未命中抑制掩盖真值**（`adapters/tt-store.js`）：同键 **30s** 的 miss 抑制，且**成功读取不清该记录** →
   「先探测未命中 → 期间原生已有新值 → 再次读仍判未命中 → 又回退旧副本」。
4. **启动早期把「尚未就绪」当「没有数据」**：扩展 `init()` 里的 `await loadMemoryState()` 可能早于
   TauriTavern 注入 `window.__TAURITAVERN__`（那一刻只有运行特征可见，`api.extension.store` 不在位）
   → 旧实现直接回退读酒馆用户目录的**陈旧副本**，这一份会被当成「今天的状态」载入内存。
5. **载入被旧副本遮蔽**（`index.js#loadMemoryState`）：旧口径是「**第一个有货的就用**」——
   本机缓冲（`localStorage` 的 `ftt2_state_<scope>`）一旦非空就直接采用，**从不比较 `updatedAt`**，
   也不与服务端文件合并 → 那份台账为 0 条的旧缓冲把更新得多的服务端文件**永久遮蔽**。

## 3. 交付（逐条对应）

| # | 位置 | 修法 |
| --- | --- | --- |
| 1 | `adapters/file-transport.js#readAutoRouted` | 缓存为 `st-files` 而原生**当前可用**时视为**降级残留** → 不采用该缓存（重新原生优先） |
| 2 | 同上（命中分支） | **只有原生确实可用时**的一次真实未命中，才允许记下文件通道路由 |
| 3 | `adapters/file-transport.js` + `adapters/tt-store.js` | 去钉住时的复核探测走 `force`（绕开 miss 抑制）；`ttGetBytes` 命中即 `missClear`（**读到即清未命中抑制**） |
| 4 | `adapters/file-transport.js#awaitNativeOnce` | 识别到宿主而原生 API 未就位时**短暂等待一次**（上限 `TT_READY_WAIT_MS = 1500ms`，本会话只等一次）；就位即原生优先，仍不就位照旧回退（**绝不阻塞启动**） |
| 5 | `index.js#pickNewerState`（新纯函数）+ `loadFromServerFile` 接线 | 两个源**都读**、按 `updatedAt` 取新；**相等（含都为 0）以服务端文件为准**；只有一个时用那个；择优结果进调试日志（`对账 · 载入择优`） |

设计纪律（保持既有硬约束）：

- **酒馆原生兼容**：非 TauriTavern 宿主 → `ttNativeOn()` 为假 → 就绪等待**零等待**、
  读取路径**零行为变化**（返回形状与请求序列不变，`A1` 组的逐拍微任务断言继续守住）；
- **不阻塞启动**：就绪等待有上限，超时即回退；本会话只等一次，后续读取不再付出该成本；
- **数据不丢**：旧副本里的数据仍由既有对账/合并口径并入（`crossComputeInfo` / `applyRemoteMergeToState`）。

## 4. 行为变更（有意，已按新语义重写旧断言）

**记路由不再等于钉死**：命中过文件通道的 key **仍会复核原生**，原生一旦有了该键**即刻改用原生**。
代价是每次读取多一次宿主内探测（由 `listBlobKeys` 与 miss 抑制缓存兜底，**不产生额外网络请求、不下载大文件**）；
收益是「原生里已有新值却读不到」不再可能。原 v2.77.0 的「同键再读原生探测次数不增」断言据此**重写为**
「原生补上同键后同键再读立刻改用原生」。

## 6. 明确未做 / 遗留（诚实登记）

- **不做一次性台账重建标记**（用户明确排除）：用户手动点「分析」即可消除未摘要楼层。
- **不做**「刷新即强制重读服务端文件覆盖内存」这类激进同步 —— 会在「本机有未同步改动」时造成反向覆盖；
  择优口径（取 `updatedAt` 较新者）已覆盖该风险。
- 仍**未修**的相邻隐患（不在本次授权范围，留档备查）：`handleFloorShrink` 在未过 `mass-mismatch` 时无条件
  收缩台账、并把条目的 `floorStart/floorEnd` 清成 `0/0` + `floorStale`（`core/floor-cover.js#meaningfulFloorRange`
  会忽略 `0/0`，覆盖兜底随之失效）；`reconcileProcessedFloors` 只扫 `0..lastId`；越界旧标记
  （如 179–199）与不一致的 `lastKnownFloor` 会残留。
