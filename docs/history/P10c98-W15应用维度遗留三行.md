## 1. `应-1`：列表分页（50 条 / 屏 + 「显示更多」）

### 1.1 口径（`docs/D9` §10 **U1** 原话）

> 列表页默认 **50 条 / 屏**，超出给「显示更多」；**搜索或筛选变更即重置到首屏**，不做跨条件的隐式累积。
> 本项是**渐进展示**（一次渲染仍是这些条，只是不一次给完），**不含虚拟滚动 / 真分页** —— 后者按 `docs/D13` §7 Q8「暂不做」执行。

### 1.2 落点（`docs/05` §5 **C11**：新功能落新模块）

| 文件 | 职责 |
| --- | --- |
| `ui/list-pager.js`（新） | 每维度展开态（缺省首屏 50）· `LIST_PAGE_STEP=50` · 外框 `LIST_PAGE_MAX=300` · `pageLimitOf` / `pageShowMore` / `pageReset` / `pageInfoOf` |
| `ui/list-of.js`（新） | 可见范围查询的**纯函数**实现（原 `ui/panel.js#listOf` 逐字外移）+ **截断前的匹配总数** |
| `ui/panel.js` | 4 处必要接线：`dimBodyList` 取 `info.list`/`info.pager` · `showMore` 动作 · 三处**重置首屏** · 「显示更多」按钮与「已显示 N 条」读数 |

### 1.3 外框为什么仍是 300

U1 管的是「**一屏给多少**」，`docs/D13` §2 管的是「**总量硬上限**」—— 两者正交。本轮把外框固定为切页前的
`listOf(kind, q, 300)` 截断值：**不撤销**渲染成本上限（`D13` Q8「暂不做真分页」），也不让「显示更多」变成无限渲染。
到 300 后按钮消失、读数如实显示（`list-pager.test.js` 的 C4 / E 段锁死）。

### 1.4 顺带更正的一处显示缺陷（如实登记）

计数行的**分子**此前是 `list.length`（**截断后的行数**）：300 条数据下恰好 300=300 才看不出问题，
一旦改成 50/屏，分子会变成「匹配 50 / 共 300 条」——语义错误。现改为 `info.total`（**真实匹配总数**）。
这不改任何筛选/排序语义（`listMatch` 与原实现逐字等价，只多返回一个总数）。

### 1.5 体量棘轮实测（`技-14`）

* 首版直接把分页写进 `ui/panel.js` → `check-file-size` 当场报红：**+46 行**（上限 +40）。
* 按 C11 抽出 `ui/list-pager.js` + `ui/list-of.js`（含依赖注入）后收到 **+33 行**（`ui/panel.js` 4012 → 4033 行，基线 3983）。

## 2. `应-8`：最近删除 + 恢复（清墓碑）

### 2.1 口径（`docs/D19` §8 实施规格原话）

> 在「设定 → 数据管理」危险区**之前**增加「🕳 最近删除（N 条）」只读列表 + 「♻ 恢复选中」；
> 恢复 = 清除对应 id 墓碑，范围限**本机当前作用域**；界面写明「对端仍以墓碑为准」。

### 2.2 落点

| 文件 | 职责 |
| --- | --- |
| `core/recycle-bin.js`（新） | 数据层纯函数：`recycleBinList()`（只读清单）· `recycleBinRestore()`（清墓碑）· `recycleDimLabel()` |
| `ui/recycle-bin.js`（新） | 界面层：勾选集合 · 区块渲染 · 落盘（`saveState()`）· 动作处理（`rbToggle` / `rbAll` / `rbNone` / `rbRestore`） |
| `ui/settings-pages.js` | 1 行接线：`pageExtraHtml('data')` 的本地缓冲之后、`DANGER_ZONE_BANNER` 之前 |
| `ui/panel.js` | 1 处分发分支 + `DANGER_ACTION_PROMPTS.rbRestore`（二次确认）+ `change` 分支读取 `data-ftt-rb-dim` / `-rb-id` |

### 2.3 恢复的精确口径（本轮技术要点）

删除动作写的是 `state.deleted[维度][id] = 时刻`（`core/merge.js#tombSet`），**没有**写内容哈希墓碑；
内容哈希墓碑（`state.deletedH`）由清扫在**学到的时刻按同一时间戳**补记（`core/sweep.js#applyDeletedToArray`）。

**只清 id 墓碑的漏洞**：对端把**同内容、新 id** 写回来时，`deletedH` 仍会拦住它 → 恢复时灵时不灵。
故 `recycleBinRestore()` 成对清除，且**宁可少清不可误清**：

| 情形 | 配对判据 |
| --- | --- |
| 条目**仍在**容器里（删的是重复记录 / 该条被重新写入） | 现算 `atomIdentityHash(dim, live)`，**只清这一条** |
| 条目**已不在**容器里 | 退化为「**同维度 + 同一时间戳**」成对清除；**时间戳不等的一律保留** |

### 2.4 零数据副作用与边界（如实登记）

* 不新增 / 不修改 / 不移动**任何**记忆条目。条目正文早在删除时移除；「恢复」**不把它搬回来** ——
  它只解除「不许在跨端同步里复活」的约束（对端此后可重新写入）。
* 二次确认文案（`DANGER_ACTION_PROMPTS.rbRestore`）把「不会把正文搬回来」说在最前 ——
  避免被误解为「删除可撤销」而削弱双墓碑的严肃性（`docs/D19` §7 **R2** 的要求）。
* 界面同时写明「**对端仍以墓碑为准**」（`docs/D9` §6 的状态说明口径）。
* 清单外框 `RECYCLE_BIN_MAX=200`：超出**只影响本视图**渲染，并如实显示「共 N 条」（不是截断数据）。

### 2.5 勾选框属性是**真实读取**（不是白名单豁免）

新增的 `data-ftt-rb-dim` / `data-ftt-rb-id` 在 `change` 分支被真实读取（`tg.dataset.fttRbDim` / `fttRbId`）——
`tests/unit/panel-audit.test.js#L5`「委托属性完整」对新增属性照常生效（该断言曾在本轮中途变红，逼出这次接线）。
