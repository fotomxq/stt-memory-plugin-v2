## 1. 取证（先量了再改）

| 项 | 真机读数（只读调试桥） |
| --- | --- |
| 调试日志环构成 | `n: 300 / cap: 300`，其中 **`读取: 208`（69%）**；其余 发送记忆 31 / 摘要 24 / 修复 15 / 校对 7 / 时钟 5 / 楼层 5 / **对账仅 4** |
| 本机缓冲读取 | 19 次 × 1.05MB（≈**19.9MB**）；`bySrc.local.maxMs = 12ms` —— **单次 1–12ms** |
| 最慢读取 | **233ms 是「解析主文件」**（服务端主文件，62KB→639 条），**不是本机缓冲** |
| 本机缓冲写入 | 3 分钟内 **11 次**全量重写，每次 **1,117,460 B**（同步写） |
| 配额 | 单键常驻 1.11MB（localStorage 通常 5–10MB）；v3.1.0 已有字符预算守卫（1.8M 字符） |

**关键纠偏**：体检清单里把「读放大」记在 A4，但真机数据显示本层单次只有 1–12ms ——
真正的重活是**每次读取都要 `JSON.parse` 1MB + 计算信封哈希**，以及**每次保存都同步重写 1.11MB**。
因此修法对准这两处，而不是去动「读的次数」。

## 2. A5 交付：日志环只收「值得的」

| 位置 | 改动 |
| --- | --- |
| `core/read-ledger.js#readLedgerMirrorWorthy(item)` | 纯函数：`ok === false`（失败）/ `miss === true`（未命中）/ `ms ≥ 100`（慢读）→ 值得镜像 |
| `core/read-ledger.js#readLedgerRecord` | 出口改为 `quiet !== true && (mirror === true \|\| readLedgerMirrorWorthy(item))` —— **策略在核心里**，宿主无法把环灌满 |
| `index.js`（读取台账接线） | 保持「缺省 no-op」的原样接线（不再需要宿主侧过滤） |

**顺带削掉的写放大**：`adapters/debug-log.js` 每次 push 都会 `localStorage.setItem(DEBUG_KEY, JSON.stringify(list))`。
那 208 条「读取」噪声每条都触发一次整体重写；A5 之后这部分同步写随之消失。

## 3. A4 交付：解析缓存 + 等值跳过

| 位置 | 改动 |
| --- | --- |
| `adapters/store.js#loadFromLocalStorage` | **解析缓存**：每次仍然读原始文本（真相优先），文本与上次**逐字符相同** → 复用解析结果，跳过 `JSON.parse` + 信封哈希；文本一变（含外部改动）立即重新解析 |
| `adapters/store.js` 保存流水线 ④ | **等值跳过**：信封与上次写入**逐字节同源**（同 `hash` + 同长度）→ 不重写 localStorage，如实记 `unchanged` |
| `adapters/store.js#removeLocalKeys` | 删本机键 → **解析缓存失效**（否则「刚清空却仍能读回旧信封」） |
| `adapters/store.js#localBufferStats()` | 计数：`reads / parseHits / writes / unchanged / idbWrites / overBudget / failed`，随 `localBufferState().stats` 进面板与调试包 |

### 刻意不做（取舍登记）

1. **不做时间节流**：本机缓冲是「**保存后必须立刻可读**」的一层（v3.0.23 的读写对齐纪律，
   由 `store-chat` 的 `S2/S3/S7` 断言直接读 localStorage 原始值锁定）。按时间推迟写入会让该层
   短暂落后于内存态 —— 试过并回退（回退过程见 §5）。真机上写入次数由**内容真实变化次数**决定；
   把它降下来的另一半来自 A5 的日志写削减。
2. **不做 IndexedDB 等值跳过**：IDB 是**异步**写、不阻塞主线程，且与 localStorage 是**两层独立真相**
   （本层写失败后仍需自愈）。用 localStorage 的签名去跳过 IDB 会在「IDB 曾写失败」时留下
   **永远补不上**的缺口 —— 试过并回退。

## 5. 过程中的一次自我纠错（如实登记）

初版 A4 用了「**TTL 读取缓存**（5s 内连读都不读）+ **时间节流写**（最小间隔 2s，超时补写）」，
跑全量单测时红了 **5 个文件**：`store-chat`（S2/S3/S7 直接读 localStorage 原始值）、`load-pick`（外部注入后
期望立刻可见）、`load-align` / `local-copy`（期望每次保存都写 IDB）。
判定：这不是「测试过时」，而是**我把两层的真相语义改坏了**（延迟写 / 陈旧读）。
于是回退为「解析缓存（不陈旧）+ 等值跳过（不改语义）」，并保留 A5 那块真实的写削减。
**教训**：优化前先确认该层的**语义契约**（本机缓冲 = 保存后即可读），不要用 TTL 去换吞吐。

另：改版本号时又一次误用 PowerShell `Get-Content -Raw | Set-Content`，把新测试文件写成 **BOM + 乱码**
（该文件未跟踪，git 无法还原）→ 用文件工具**整篇重写**并核对（无 BOM、中文正常、11/11 通过）。
**纪律重申**：含非 ASCII 的仓库文件一律用读写工具，禁止 `Get-Content/Set-Content` 往返。

## 6. 部署后请这样验收（需刷新页面）

1. 刷新页面 → 打开「调试 → 🔌 调试桥」；
2. `ftt.debugLogStats` → **`kinds.读取` 应从一个数量级上掉下来**（只留失败/未命中/慢读）；
   对账/摘要/修复/异常 不再被冲掉；
3. `ftt.reads` / `ftt.readLedgerText` → `bySrc.local` 的**字节数不再无意义增长**（台账里会出现
   「命中解析缓存」的说明，`bytes` 仍如实记读取体积，因为**真的读了**）；
4. 面板「存储」或调试包 → `localBuffer.stats`：`parseHits > 0`（省下重复解析）、
   `unchanged > 0`（省下等值重写）、`overBudget/failed` 应为 0。
