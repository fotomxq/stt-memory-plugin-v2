# P10c1 · 删楼后无法衔接继续分析（活值末楼号 + 删后刷新）（v3.0.16）

> 文档版本：v1.0 ｜ 日期：2026-09-30 ｜ 状态：生效（v3.0.16）
> 触发（用户原话）：「新版本 使用内置删除楼层后，无法衔接继续分析，新增正文无法分析。」
> 相关：`docs/history/P10bf`（楼层骤减处理）· `docs/D12`（楼层骤减的数据安全）· `docs/history/P10bz`（管线收尾）

---

## 1. 根因：区间用了**过期的末楼快照**

内核的 `getLastMessageId()` 是**聊天同步时的快照**（`host/chat.js#wireKernelChatHooks` 在
「载入 / 生成结束 / 消息渲染 / 切聊天」时刷新），**不是活值**。而内置删楼走的是酒馆官方
`getContext().deleteMessage(id)`（`docs/D12` §4 的既定实现）——它只发出 **`MESSAGE_DELETED`**，
而我们**没有订阅该事件**（`HOST_EVENTS` 只含 9 个事件，不含删除）→ **删完那一刻快照仍是被删前的旧值**。

于是 `runAutoSummary`（「⚡ 立即 AI 摘要」/ 面板批量）的区间直接算错：

```js
const lastId = Number(getLastMessageId());   // 删楼后仍是旧值（如 199，而聊天只剩 10 楼）
const effLast = Math.max(0, lastId - skip);
let start = Math.max(0, effLast - feedN + 1);   // → 188（远在聊天之外）
let pendingIds = listUnprocessedFloors({ endFloor: effLast });
```

复现（本仓库直跑真实宿主层，30 楼删到 10 楼后新增 1 楼）：

```text
修复前：批量摘要 → floors "18-27" · made 0（全部 missing）→ 面板「本次没有可分析楼层」
修复后：批量摘要 → floors "0-8"   · made 1 · 新增 1 条
```

即：**不是数据坏了，而是区间指向了已不存在的楼层** → 扫描结果全被 `missing` 吃掉 → 用户看到
「删楼后新正文无法分析」。

## 2. 修复（两处）

| # | 落点 | 做法 |
| --- | --- | --- |
| ① | `host/floors.js#liveLastFloorId()`（新增） | **活值**末楼号：宿主 `getContext().getLastMessageId()` → `chat.length - 1` → 内核快照兜底；`host/extract.js#runAutoSummary` 的 `lastId/effLast/pendingIds` 全部改用它（与 `scanPendingFloors`「区间一律按实时聊天长度取」的既有口径对齐） |
| ② | `host/floor-trim.js#floorTrimApply` 步骤 ⑥b（新增） | 删完立刻 ① `wireKernelChatHooks()` **刷新聊天视图**（内核快照 = 活值，不依赖后续事件）；② 把「按末楼推进」的基线一起收紧：`lastKnownFloor`（已有）+ **`weaveLastFloor`**、**`rumorTick.lastFloor/parallelFloor`** → 推演间隔与传言轮次不因删楼错位 |

口径提示：`skip 最近 2 楼`（`cfg.timelyAnalysis` 关闭时的 V1 语义）保持不变 —— 最新楼层由
`GENERATION_ENDED → autoExtractLatest`（本来就走活值扫描）负责，两者互补。
