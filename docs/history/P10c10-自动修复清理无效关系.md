## 1. 为什么需要「补一步」

关联层（`state.links`）自 v1.165 起就是「谁知道 / 谁相关」的唯一来源，V1 的机械维护 `relRepairMaint()`
**逐字移植**在 V2 里照常运行（`core/rel-maint.js`），它负责：

① 孤儿关联行（目标条目已不存在）→ 清 + 墓碑；② 同 `(dim, refId, who)` 去重（保留更可靠者并并集信息）；
③ 角色名按**档案全名**归一（只在档案里确实存在同名角色时改写）；④ 锚行的悬空引用清理（概念按名称，其余按 id）；
⑤ `how` / 偏差非法值归一；⑥ 孤儿**条目**按 `cfg.relOrphanAction` 处置（默认 `keep` 只提示）。

它**不判断「这个角色到底存不存在」** —— 于是下面这些行会长期留在关系表里：

| 现象 | 来源 |
| --- | --- |
| 关系行上的角色是**已删除的档案**（或改名后的旧名） | 用户删档案 / 档案重建 / `relKnownNames` 只认当前档案 |
| 关系行上的角色是 **AI 幻觉名**（正文里的人名没进档案） | 分析 / 修复 / 推演的产物 |
| `dim` 非法（不在 记忆/计划/悬念/平行）或 `refId` 为空 | 历史数据 / 导入残留 |
| 无角色、且没有任何锚属性的**纯空行** | 早期手工/导入残留 |

本轮把「清掉这些结构上就没有意义的行」做成**自动修复里的一步**（用户要求），并给出可读的统计与手动入口。

## 2. 实现（口径 + 纪律）

新增 `core/rel-maint.js#cleanInvalidRelLinks(opts)`：

```text
dangling  目标条目不存在（state[dim] 里找不到 refId）        ← 与既有孤儿口径一致
badDim    dim 不在 REL_LINK_DIMS（记忆 / 计划 / 悬念 / 平行）
badRef    refId 为空
empty     无 who，且条目级属性（kind/public/各 ref/refs）与语义字段（how/from/at/view/note）全空
ghost     有 who，但该名字不在**任何已知名册**
```

**已知名册**（宽松优先 —— 宁可漏删，不可误删人工关联）：角色档案 `snapshots[].name` · 名册 `npcs[].name/title` ·
主角字段 `protagonist.name/subject` · **玩家名**（宿主身份视图 `identityView.characterName`）· 状态主体 `currentStates[].subject`
（含「全名·名」的前半段）· 记忆归属 `memories[].owner` · 货币归属 `currencies[].owner` · 平行事件「相关角色」`parallels[].characters`；
此外 `snapFindByName()`（**档案名前缀模糊匹配**）命中即视为存在。

**纪律**
- 被清行**写删除墓碑**（`tombEntries('links', …)`）→ 跨端合并不会复活；
- **幂等**（无无效行时零改动、零分配）+ `dryRun` 只报告不改动；
- **关联层总开关关闭时不清理**（层关闭 = 不读写关联行，与 `relRepairMaint` 同口径）；
- 明细（最多 50 条：类别 / 维度 / 目标 / 角色）进 `dbgLog('摘要')`，事后可核对清掉了什么。

**接线点**

| 位置 | 行为 |
| --- | --- |
| `core/repair.js#runRepairMech`（自动修复第 1 段，零 AI） | 关联维护之后执行本步；有清理 → `saveState()` + 摘要并入修复提示（`stage1.notes`）+ 调试日志 `relInvalid:{removed,reasons}` + `stage1.relInvalid` |
| 通知文案 | 「机械清理完成（零 AI）」末尾追加「· 清理无效关系 N 行（孤儿… · 幽灵角色… · 空行…）」 |
| 设定 → 约束 → 🔗 关系表 | 统计行新增「**无效 N**」；新增「🧹 清理无效关系（N）」按钮（**与自动修复同源**，想立刻清一次时用）；动作回报「已清理无效关系 N 行（…）」 |
| `FTT` | `relInvalidStats()`（只读统计）/ `relCleanInvalid()`（显式写入口：写墓碑 + 落盘） |

## 4. 兼容与回退

- **V1 口径不动**：`relRepairMaint()` 的六项行为与黄金样本完全不变；本步只在它之后**补它没覆盖的类别**。
- **删除语义**：清掉的行同时写 id 墓碑与（若有内容）内容墓碑，走既有跨端删除传播 —— 与「🧽 清扫孤儿关联」同一套机制。
- **可回退**：本步是独立函数，`core/repair.js` 里的一处调用；去掉调用即回到 v3.1.0 行为（关系表统计行的「无效 N」与按钮仍可只读使用）。
- **误删兜底**：名册判定宽松（多来源 + 模糊匹配）+ 手动入口 + 明细日志；`dryRun` 可先预览（`FTT.relInvalidStats()` 即预览口径）。
