## 1. ① 计划/悬念修复接进自动修复

**现状**：总览「🛠 自动修复」= `core/repair.js#runRepair` 的三段式（① JS 机械清理 → ② 候选筛选 → ③ 窄契约 AI 修订）；
而「设定 → 计划悬念 → 🔧 修复计划/悬念」是另一条链路 `core/plan-repair.js#runPlanSuspRepair`
（悬念同内容机械去重 → 关联维护 → 悬念聚类核对 → 窄契约 AI → 应用 + 计划了结/合并）。两者此前**互不触发**。

**改法（就是调用一下那一个函数）**
- `runPlanSuspRepair` 加 `opts.silent`（进程内静默位，提示统一由修复汇总给出）；手动按钮不传 → 行为不变。
- `runRepair` 在三段之后新增 **③-c**：经宿主钩子 `repairHooks.planSuspRepair` 调
  **同一个** `runPlanSuspRepair({silent:true})`（`index.js` 接线处没有第二份实现）。
- 结论并入修复提示与调试日志，`planSusp.made` 计入 `made`；跳过路径如实标注：
  `disabled`（`opts.planSusp=false`）/ `ai-off`（自动模式 + `cfg.repairAutoAi=false`）/ `no-hook`（宿主未接线）。

## 2. ② 楼层突变识别与修正

**判据（用户口径）**：`最新情节对应楼层 − 当前末楼 ≥ 9` → 楼层出现大幅手动删减。
（`host/floors.js#latestPlotFloor()` = 可见情节里最大的 `floorEnd`；`liveLastFloorId()` = 实时末楼。）

**修正**：复用 v2.93.0/v3.0.19 的 `handleFloorShrink({force:true})` ——

1. **台账按内容哈希归位**：只保留「当前仍然存在的楼层」里、命中历史已处理哈希的标记 →
   仍然存在的楼层保持「已处理」（不会成片重分析），已消失楼层的标记剔除；
2. **越界区间降级**：`floorEnd/floorStart > 末楼` 的条目改判为未知区间 + `floorStale`（**只改编号，不删条目**）；
3. **基线收紧**：`lastKnownFloor = 末楼` → 之后新增的楼层照常进入未摘要清单 → **「避免无法正常分析楼层」**。

**低噪声**：修正后记 `state.floorJumpAt`；越界情节楼层已被降级为未知区间 → 下一次检测如实 `no-data`，
不会每次自动修复都刷笔记；聊天未就绪时如实 `chat-not-ready` 跳过。

**位置**：`runRepairMech`（第 1 段，零 AI）固定顺序的末段 —— 机械去重 → 遗忘清扫 → 条数裁剪 → 垃圾清理 →
衰退清扫 → 关联层维护（V1 口径）→ 无效关系清理（v3.2.0）→ **楼层突变识别与修正（v3.5.0）**。

## 4. 兼容与回退 / 风险

- **手动入口零变化**：`runPlanSuspRepair` 不传 `silent` 时行为与以前完全一致（提示照旧）；
  「🔧 修复计划/悬念」按钮路径未改动。
- **自动模式门槛**：`cfg.repairAutoAi === false` 时新步骤与 AI 段一起跳过（该开关语义 = 自动修复只做机械清理）；
  手动点击「🛠 自动修复」不受该开关限制（与既有 AI 段一致）——两步都会执行。
- **楼层突变不会误删数据**：修正只动编号与台账；`force` 仅用于「已确认是大幅删减」这一步，不改变缩水守卫对保存的保护。
- **幂等**：修正后不再重复判定（避免噪声与重复写盘）；`handleFloorShrink` 本身幂等。
- **未核实**：真机上「最新情节楼层」在极端编辑（用户手改情节楼层号）下可能偏大 → 会触发一次修正（只清越界标记，
  不删条目）；如需更保守，可把 `FLOOR_JUMP_MIN_GAP` 调大（常量集中在 `host/floors.js`）。
