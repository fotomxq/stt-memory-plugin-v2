## 1. 问题（第 2 项）

`index.js#onFloorChanged()` 绑在 `CHARACTER_MESSAGE_RENDERED` / `USER_MESSAGE_RENDERED` / `GENERATION_ENDED` / `CHAT_CHANGED` 四个宿主事件上，
内部**直接** `pushMemoryInject({queryText:''})` —— 每渲染一条消息就重建整份注入体（4000 条目 ≈16 ms/次）。
而真正「发送前」的注入由 `host/interceptor.js#fttGenerateInterceptor` 在生成时刻**权威构建** → 事件路径这一份只需保持新鲜。

## 2. 修法（`host/inject-schedule.js`，口径与 `技-50` 一致）

```text
CHARACTER_MESSAGE_RENDERED ─┐
USER_MESSAGE_RENDERED      ─┼─► scheduleInjectRefresh ─► 排一次 1.5s ─┐
GENERATION_ENDED           ─┤      （窗口内重复 → coalesced，不重排）  │
CHAT_CHANGED               ─┘                                        ▼
                                    1.5s 到 / 被 flush → pushMemoryInject（一次）
GENERATION_STARTED ─┬─ 拦截器开着 → cancelInjectRefresh（它自己会权威构建，避免重复构建）
                    └─ 拦截器关着 → flushInjectRefresh（立刻补做，绝不让发送用上过期注入）
```

* **延迟 1500ms**（与既有 `scheduleClockExtract` 的 1.8s 同量级）；
* **窗口内信号合并且不重排**（`setTimeout` 1 次 / `clearTimeout` 0 次）；
* **发送前一定最新**：拦截器开着 → 它构建；关着 → `GENERATION_STARTED` 补做；
* **不重复构建**：拦截器自建前也作废一次待做；
* **读数**：`ftt.injectSchedule()`（信号 / 合并 / 构建 / 补做 / 作废 / 失败 + 原因环形 ≤20）；
* **不动**：拦截器的内容与时机、落盘、两个心跳、`wireKernelChatHooks`。

## 3. 三条不变量（安全性论证）

1. **发送时一定最新**：拦截器开着 → 生成时刻构建；关着 → `GENERATION_STARTED` 补做。
2. **不会重复构建**：拦截器路径先作废；`GENERATION_STARTED` 在拦截器开着时只作废不构建。
3. **失败静默**：推送抛错 → 计 `failed`，绝不影响聊天与生成（与旧实现 `.catch(()=>{})` 同口径）。

## 6. 边界（如实登记）

1. **只改「何时构建」**：`buildMemoryBodyForInject` 的召回打分与预算择优（16ms）**一字未动** —— 优化构建本身另立条目。

3. **保留项逐条给理由**（§0 表）：不是遗漏，而是「已有机制覆盖 / 成本可忽略 / 不得延迟」三类。
