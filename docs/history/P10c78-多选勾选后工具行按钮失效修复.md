# P10c78 · 修复「列表多选**直接勾选**后顶部按钮无效，必须全选才激活」（用户报告 · v3.43.1）

> 文档版本：v1.0 ｜ 日期：2026-10-10 ｜ 状态：生效（v3.43.1，**修复轮**）
> 用户要求（原话）：「新版本v3.43.1 / 修正各大类的多选设计，当直接选择对应选项后，顶部的删除等按钮无效。必须选择全选才能激活，请修复该问题。」
> 关联：`CHANGELOG.md` v3.43.1 · `docs/D19` v1.2（§2 **K14** · §3.6 · §8 **`应-24`**）· `docs/D17` v1.13（**§1.15 U182**）·
>   `docs/D22` v1.3（§4.4 `应-24` ✅）· `docs/D9` v0.5（§5.1 / §5.2 第 5 条）· `docs/04` §5（U11 / U12）· 上一轮 `P10c77`（v3.43.0）

## 1. 用户看到的现象与我的第一判断

用户描述：**多选模式下直接勾选条目 → 顶部「删除」等按钮无效；必须点「全选」才激活。**

第一判断（也是最后的结论）：**这不是删除逻辑坏，而是按钮的 `disabled` 没被更新** —— 理由很直接：
「全选」能让按钮生效，说明**动作本身是可用的**，差别只在「勾选状态怎么进到按钮上」这一环。
按这个方向读代码，一次就命中了（见 §3）。**若一开始按「删除功能坏」去查 `bulkDelete`，会白跑很久**。

## 2. 复现与事实（`docs/D19` §2 K14）

| # | 事实 | 证据 |
| --- | --- | --- |
| ① | 多选模式下 0 勾选渲染出的三个按钮**带 `disabled`**，文案为 `（0）` | 渲染产物实测：`<button … data-ftt-action="bulkDelete" data-kind="atoms" disabled>🗑 删除选中（0）</button>` |
| ② | **直接勾选**条目后，按钮的 `disabled` 与文案**不变** | 触发 `change` 委托（`data-ftt-select`）后重新读按钮，仍是 `disabled` + `（0）` |
| ③ | 点「全选」后**按钮生效** | 「全选」是 `data-ftt-action="selectAll"` 动作 → `panelAction` → **整页重绘** → 按钮按新的 `sel.size` 重新渲染 |
| ④ | 但**数据通路是好的** | 直接勾选 1 条后调 `panelAction('bulkDelete')` → `{ ok: true, deleted: 1 }`（只删勾中的那条） |

**结论**：缺陷**纯在按钮可用态**。用户体感是「点了没反应」，不是「删错了」。

## 3. 根因（一行代码的事，但很隐蔽）

`ui/panel.js` 的 `change` 委托里，`data-ftt-select` 分支的**全部内容**是：

```js
const k = String(tg.dataset.fttSelect);
const set = selOf(k);
if (tg.checked) set.add(...); else set.delete(...);
// ← 到这里就结束了：没有重绘，也没有任何局部同步
```

而按钮的 `disabled` 与「（N）」是**渲染时**用 `sel.size` 拼进 HTML 的：

```js
+ (sel.size ? '' : ' disabled') + '>🗑 删除选中（' + sel.size + '）</button>'
```

**渲染快照不会因为内存集合变化而更新** —— 这就是全部原因。

**为什么「必须全选」**：`selectAll` 是 `data-ftt-action` 动作，走 `panelAction` 分支，链路末端是整页重绘；
只有它会**重新执行渲染**，于是按钮拿到新的 `sel.size`。其余勾选框路径都不重绘。

## 4. 为什么这个缺陷能长期存在（比缺陷本身更值得记）

三件事同时成立，缺一件它都会被发现：

| # | 条件 | 说明 |
| --- | --- | --- |
| ① | **文案与可用态被写了两处** | 渲染处拼一份字面量，动作层再改一次 —— 只要两处不同步，就必然有一处是旧的。**这是根因的结构条件** |
| ② | **没有运行态测试覆盖这条链路** | v3.43.0 刚落地的 `应-5`「交互契约全量对齐」覆盖的是**设定控件**的 `input`/`change` 分工；**列表勾选链路不在其内** |
| ③ | **静态门禁抓不到** | `check-ui-spec` 看 markup 形状（有没有空态 / title / 二次确认），看不到「渲染快照不随状态更新」这种**时间维度**的错误 |

②③ 合起来就是本轮暴露的**门禁盲区**：`docs/D22` §4.4 的「本版口径」第 5 条如实登记了它。
**修完缺陷只做一半**；补一条**运行态**测试（含反向探针）才算收口 —— 因为下次同类缺陷还会落在同一个盲区里。

## 5. 修复方案

### 5.1 新增 `ui/select-bar.js` —— 唯一事实源

| 导出 | 作用 |
| --- | --- |
| `SELECT_DEP_LABELS` | 动作名 → 文案函数（`bulkDelete` / `atomMergeSummary` / `plotSegmentSummarySel`）。**登记一行 = 同时得到勾选同步能力** |
| `selectDepButtonState(action, size)` | → `{ text, disabled }`；**未登记的动作返回 `null`**（= 该按钮不依赖勾选，同步时一律不碰） |
| `selectDepButtonParts(action, size)` | 渲染侧便利函数：返回 `disabled` 属性（含前导空格 / 空串）与文案两段 → **属性顺序与既有 markup 逐字不变** |
| `syncSelectButtons(root, sizeOf)` | 遍历 `root` 的 `[data-ftt-action]`，按**每个按钮自己的** `data-kind` 取勾选数并同步 `disabled` / `textContent`；返回实际更新数 |

**防御口径**（都在测试里锁）：无 `root` / 无 `sizeOf` / `querySelectorAll` 抛错 → 返回 0 不抛；
未知动作的节点**原样保留**；单个按钮同步失败不影响其余（DOM 被换掉的竞态）。
勾选数归一：`undefined` / `null` / `NaN` / 负数 / 非数字 → 0（`disabled`），数字字符串与小数按数值取整。

### 5.2 三处渲染改用同一张表

`ui/panel.js#dimBodyList`（列表页）· `ui/panel.js#statesBody`（状态页）· `ui/scene-tree.js#scenesTreeHtml`（场景树）。
**三个页面的复选框都带同一个 `data-ftt-select` 标记，共用同一个 `change` 委托** → 一次 `syncSelectButtons(el, …)` 全部覆盖。

### 5.3 勾选后局部同步（不整页重绘）

```js
if (tg.dataset.fttSelect !== undefined) {
    const k = String(tg.dataset.fttSelect);
    const set = selOf(k);
    if (tg.checked) set.add(...); else set.delete(...);
    syncSelectButtons(el, (kind) => selOf(kind).size);   // v3.43.1
    return;
}
```

**为什么不做整页重绘**：勾选是**高频**动作；单次重绘要重建渲染期上下文（`buildRowCtx` 行索引），
300 行列表里连勾 20 条 = 20 次整页重绘 —— 只为改两个按钮的 `disabled` 与计数不值得。
局部同步**不动列表、不重建索引、不影响滚动位置**（测试断言 `panelRenderStats().renders` 不变）。
规则写进 `docs/D9` §5.2 第 **5** 条。

## 6. 测试（`tests/unit/select-bar.test.js`，10 项）

| # | 断言 |
| --- | --- |
| E1 | 单一事实源：三个动作已登记；`selectAll` / `selectNone` / `multiToggle` / `delete` / 空串 / `null` / `undefined` → `null` |
| E2 | 勾选数归一 + `selectDepButtonParts` 的 `attr`（0 → ` disabled`，1 → `''`） |
| E3 | **渲染侧与同步侧同源**：渲染出的三按钮文案与 `disabled` **逐字等于** `selectDepButtonState` 的返回 |
| E4 | **用户场景**：不经「全选」只勾 1 条 → 三按钮当场可用、计数为 1 |
| E5 | **双向**：取消勾选 → 回 `disabled` + `（0）`；再勾两条 → `（2）` |
| E6 | **不整页重绘**（`renders` 不变）+ 坏入参（`null` root / `null` 取数 / `querySelectorAll` 抛错）→ 0 且不抛 |
| E7 | 同步**只碰**依赖勾选的按钮：`全选`/`清空选择` 与未知动作的节点原样保留 |
| E8 | 覆盖面：`states` 页与 `scenes` 场景树**同一张表**，勾选后同步同样生效 |
| E9 | 数据通路：直接勾选后 `bulkDelete` 只删 1 条（**证明修复前不是删除逻辑坏**） |
| E10 | 端到端：勾 1 条后按钮 `disabled === false` → 动作被受理并返回 `ok` |

### 6.1 反向探针（本轮真的跑了）

把 `syncSelectButtons(el, …)` 那一行注释掉重跑：

```text
❌ E4 用户场景：只勾 1 条 → 三按钮当场可用、计数变 1
❌ E5 勾选 → 取消勾选 → 回到 0
❌ E8 覆盖面：states / scenes
❌ E10 端到端：勾 1 条后按钮真的可点
结果: 6 通过, 4 失败
```
恢复后 **10 / 10 通过**。**没有反向探针的回归测试是「写了就算」** —— 它只能证明今天不红，不能证明它测的是这个缺陷。

### 6.2 一个测试自身的坑（记下来）

第一版 `attachDom` 里 `querySelectorAll` **每次都新建按钮对象** → 「局部同步」改的是新对象的 `disabled`，
断言读到的永远是初始值 → **假失败**。改成「同一次渲染产物内返回**同一批对象**、只有整页重绘后才换新节点」后通过。
这正是真实 DOM 的节点同一性；**桩 DOM 若丢掉同一性，就会把「改没改」测成「测不到」**。
