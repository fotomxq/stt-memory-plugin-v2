## 1. 只读取证（真机事实，未改任何数据）

| 项 | 实测（离线复算，方法可复现） |
| --- | --- |
| 聊天 | 231 层（0..230）；首楼为 AI 楼 → **AI 楼 = 偶数层**；`lastChatFloor = chat.length - 1` 与实际一致（宿主 `ctx.chat` 不含元数据头） |
| 台账 `processedFloors` | 68 条，**每一条的哈希都等于其楼层当前正文的哈希** → 台账没有整体错位，也不是哈希算法漂移 |
| 未分析清单 | 按插件判据（台账 + 覆盖 + 非 AI/隐藏/无正文跳过）离线重算 = **41 层**：2,4,6,…,98（全是 AI 楼） |
| 这 41 层的证据 | **无标记、无丢弃留痕（`processedDropped` 只有 6 条且都不在这批里）、覆盖判据也不认**（仅 8 条条目的来源区间沾到，且都带 `originGone`） |
| 旧副本 | 本机缓冲（16:30 的明文信封）里同一台账有 **104 条**标记 → 低楼层标记是在此之后**被丢弃**的 |

**判定**：这不是「哈希口径变了导致的显示错」，而是**台账里的标记真的少了**——且旧版本丢标记时不留痕，事后无从归位。

## 2. 根因（四条，都是「丢标记」的入口）

| 环 | 事实（代码证据） | 后果 |
| --- | --- | --- |
| 删楼不留痕 | `core/floor-trim.js#remapAfterTrim` 把「被删段内的标记」直接丢弃（`f < M` → `continue`），不像 `reconcileProcessedFloors` / `handleFloorShrink` 那样写 `processedDropped` | 删楼后撤销 / 恢复聊天 / 切回更长分支 → 那批楼层既无标记也无留痕 |
| 「读不到正文」= 丢标记 | `host/floors.js#migrateProcessedFloorsV170` 与 `#processedDriftGuard`：`hashFloorText(f) === ''` → `dropped++; continue;` | 宿主只交进来一部分聊天（或该楼暂时取不到正文）时，**整片低楼层标记被刷掉**，并写上当前版本签名 → 事后再也查不出「这里原来有标记」 |
| 留痕被覆盖 | 归位对账的「丢弃前留痕」按**楼层号**判断（`!keptFloors.has(f)`）→ 「删楼 + 恢复聊天」时记下的是**错位的新哈希** | 真正能救回楼层的旧哈希被覆盖 → 那批楼层从此既无标记也无留痕（真机 41 层的直接成因） |
| 聊天变长无人管 | 只有 `handleFloorShrink`（判据：`lastId < known - 5`，即**收缩**）才跑内容复核与归位 | 聊天**变长**（撤销删楼 / 恢复备份文件 / 切回更长分支 / 换同角色另一条聊天）没有任何路径把标记找回来 |

## 3. 修复（五条，统一「内容哈希 = 唯一锚点」）

| # | 落点 | 口径 |
| --- | --- | --- |
| ① 丢弃一律留痕 | `core/floor-trim.js#remapAfterTrim` 返回值新增 `dropped`；`host/floor-trim.js` 调用 `rememberDroppedMarks(remap.dropped)`；`migrateProcessedFloorsV170` / `processedDriftGuard` 丢弃前同样留痕 | 与 v3.11.1 的「丢弃留痕」同口径（有界 600、按楼层去重） |
| ② 读不到 ≠ 不存在 | 两处维护函数改为：**只丢 `f < 0` 或 `f > lastId`（楼层确实不存在）**；`hashFloorText(f) === ''` 时**保留原标记**并计入 `keptNoText` | 「无正文 → 丢弃标记」的 V1 旧口径在「部分载入」下会毁掉整本台账，故收窄 |
| ③ 留痕回填自愈 | `reconcileProcessedFloors`：把 `processedDropped` 的历史哈希并入 `oldHashes`（**留痕也是「在册证据」**），内容找得到 → 该楼重新在册；随后把「内容已找到」的留痕失效，只保留「内容确实没了」的 | 归位仍按内容哈希，不看楼层号 |
| ④ 原文已移除复核 | 新增 `recheckOriginGone()`：只对带 `floorNowHash` 的 `originGone` 条目复核，指纹找得到 → `clearGone` + 归位；找不到 / 无指纹 → 保持（保守方向）。与对账同 20s 节流窗口，顺序 = 对账 → 回填 → 复核 | 不再要求「先检测到收缩」 |
| ⑤ 显式补救 + 只读量表 | 新增 `markFloorsProcessed(list)`（`index.js#markPendingFloors` → 总览「✔ 登记为已分析」按钮 + 数据管理同名按钮；**二次确认**；只写记账、不调用 AI、不动任何记忆条目、可被「清除已处理楼层记录」撤销）；新增 `ledgerHealth()`（调试桥 `ftt.ledger` 新增 `health` / `droppedMarks`） | 登记只认「存在、非隐藏、非用户、有正文」的楼层，逐项计数如实回报 |

## 4. 边界与纪律（如实）

* 真机上那 41 层的标记**在旧版本里已被丢弃且不留痕**，数据中也再无证据（来源区间要么被裁掉、要么已判「原文已移除」）→ 插件**无法自动证明**「这 41 层当初分析过」；因此本批给的是**显式出口**，而不是替用户猜测；
* 「登记为已分析」写的是**当前内容哈希** → 之后该楼正文若被改写，仍会照常重新分析（「正文变了必须重分析」的语义不变）；
* ③ 的方向是「只增不减」：留痕只有在**内容确实在当前聊天里找到**时才失效，找不到的照旧保留（`droppedContentChanged` 的「正文被改写」判据不受影响）；
* ④ 只解除、不新增：无位置指纹的条目保持「原文已移除」，绝不臆断；
* 本批**不动**数据契约：`processedFloors` / `processedDropped` 字段与格式一字未改（`dropped` 只是 `remapAfterTrim` 的返回值，不落盘）。

## 6. 结论

「未分析楼层」的判据链现在三路互相兜底：**台账标记**（主）→ **丢弃留痕按内容回填**（新）→ **已有记忆数据覆盖**（既有）；而「丢标记」的三个入口全部补齐留痕，且「读不到正文」不再等于「楼层不存在」。用户侧另有一条**显式**的登记出口，用于历史遗留、数据中已无证据的楼层。
