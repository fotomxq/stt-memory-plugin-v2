# P10c135 · 大年份出生日期与年龄（v3.50.26）

> 文档版本：v1.0 ｜ 日期：2026-10-19 ｜ 状态：生效（v3.50.26）
> 用户要求（原话）：「角色出生年月和年龄需支持更大的年份，如 -9999-01-01，对应公元前9999年。
>   其次还有一些玄幻故事线，本身年月是百万计的，如果卡死也是问题。
>   1. 出生年月的结构必然是"正负年份-月份-月份"的结构，且年份不应限制死范围，确保计算不溢出即可。
>   2. 年龄应支持各种大年份的计算，而且如过超过一定量级，需加入单位简化，如102万岁、300亿岁等。」

## 0. 问题

| 层 | 改造前（卡点） |
| --- | --- |
| 出生日期 | `parseBirthDateParts`：`\d{1,4}` + `y < -9999 \|\| y > 9999` → `-12000-01-01`、`3000000-05-01` 一律非法 |
| 剧情日期 | `clock.js`：`±9999` + `new Date(ms)` 往返校验（Date 上限 ±273,790 年）→ 玄幻纪元存不进去 |
| 全仓 | **14 文件 30 处** `\d{1,4}` 年份假设（含 `core/model/scalars.js` 的**第二份** `clockDateTrim` 副本 —— 正是「出生日期已放宽、年龄却仍算不出」的隐藏卡点） |
| 展示 | `'年龄：' + age + '岁'` → 十万 / 百万年读不出量级 |

## 1. 方案（`core/model/bigdate.js` 单一事实源）

* `bigDateParse`：`[正负]年-月-日` / 年-月 / 年；`-` `/` `.` 等价；BC 文本（`公元前9999年1月2日` / `前9999年` / `9999 BC`）；允许时间后缀；
* `BIG_YEAR_MAX = 1e13`：**溢出护栏**（非业务范围）；`0 年` / 2 月 30 日 / 13 月 / 超护栏仍非法；
* `bigDayNumber`：`days_from_civil` 整数日序（1970-01-01 = 0），**不经 Date**；历史纪年 ↔ 天文纪年偏移 1 年；
* `bigAgeYears`：day/month/year 三精度 + **跨纪元 -1** 修正；
* `bigAgeText`：岁 / 万岁 / 亿岁 / 万亿岁（最多 1 位小数；空值 ≠ 0 岁）。

接线：`snapshot.js`（出生解析 / 年龄）· `clock.js`（范围 / 位数 / 整数校验 / 年份格式化）· `ui/list-rows.js`（展示）·
其余 13 文件仅正则位数放宽。

## 4. 测试期发现的两个真实问题（留档）

1. **`core/model/scalars.js` 有第二份 `clockDateTrim` 副本**（同样卡 4 位）：只改 `snapshot.js` 的话，
   出生日期能解析、但 `ageAnchorDate` 仍因副本把大年份剧情日期裁成空串 → 年龄恒为「待算」。**全仓 grep `\d{1,4}` 才找到它**。
2. **`emptyState` 的 `state.date` 未注入时面板走首屏闸门**（「正在读取数据…」）→ 端到端断言一开始读不到行；
   这不是 bug，而是测试需 `setLoadPhase('ready')`（已写入测试注释）。

## 5. 边界（如实登记）

1. **提示词逐字锁定不动**：角色档案 / 角色修复两支模板与 V1 逐字绑定（`v1-golden-character-repair.json`）→ 本轮只放开解析层。
2. **毫秒域（按天衰减）明确降级**：`storyDateMs` 仍按 Date 实现，`|年| > 275,760` → `NaN` → 调用方按「无日期」处理（不崩、不误判）；
   大跨度排序与相差用整数日序。
3. **`DATA_VERSION` 不变**：字符串字段，无契约变更、无迁移。
4. **年龄存储语义不变**：`identity.age` 仍是数字字符串；单位简化只在展示层。
