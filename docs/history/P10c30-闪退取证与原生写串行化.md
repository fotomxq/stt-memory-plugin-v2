## 1. 先定性：崩的是**原生进程**，不是 webview 里的 JS

| 证据源 | 观察 |
| --- | --- |
| Windows 事件日志（Application · Application Error id=1000） | `tauritavern.exe` v2.3.0.0 **两次崩溃**：`23:15:03` → `0xc0000005`（访问违例，偏移 `0x20806f9`）；`23:21:51` → `0xc0000409`（fastfail / abort，偏移 `0xfedc34`）。均伴随 WER `APPCRASH` / `BEX64`（report id 已记录） |
| 宿主日志 `logs\tauritavern.log.2026-10-04` | 两次崩溃之后各有一次 **`Initializing application in Standard mode`**（15:15:09 / 15:22:01 UTC）= 应用重启；**崩溃前没有任何 ERROR/WARN 与崩溃相关**（只有常规的模型列表连接失败、聊天备份、设置读取） |
| 宿主目录 | 无 `.dmp` / crashpad 转储（WER 未落盘到应用目录） |
| LLM 请求索引 `logs\llm-api-index.json` | 5 次生成**严格串行**（36–53s 一次，起止互不重叠）→ 排除「插件与宿主同时发 AI 请求」 |
| 磁盘 | C: 剩 188GB / D: 剩 228GB → 排除写满 |
| `settings.json` | **12.35MB**，其中 **99.2% 是其它扩展**（`tavern_helper` 5.75MB · `theater_generator` 1.24MB · `SoulLink` 1.05MB · `variables` 0.87MB · `__userscripts` 0.83MB · `TavernHelper` 0.63MB …）；**本插件块仅 105KB（0.8%）** |
| 插件调试/同步日志 | 崩溃前 **1.3s** 恰有一条「保存后镜像 → 分片推送（清单命中，207ms）」；两次崩溃都落在「生成结束 → 保存 → 镜像」之后 |
| WebView2 `settings_diagnostic.log` | 全为 INFO，含 `PrefStore write completed: success=true` → 排除「偏好写盘失败」 |

结论：**不是 JS 异常**（插件日志里没有异常记录，宿主日志也没有错误行），而是**原生进程静默失效**（AV / fastfail）。
因此「插件引起」只能通过**宿主 API 的使用方式**（大载荷、写入节奏、并发）体现。

## 2. 定位：插件确实存在**并发写原生存储**

`adapters/sync.js#storageWriteAll` 的实际形状（改前）：

```text
stateFileWrite(env)          await   ← 主文件（本机 2.0MB）
snapshotFilePushNow()        await   ← 快照文件（1.2MB）
metaFilePushNow(...)         .then() ← **fire-and-forget**：分片清单（1.4MB）
```

而 `adapters/tt-store.js` 里每个 key 都是一次独立的宿主 API 调用（`setBlob` / `setJson`），
**没有串行化**：于是「上一次保存还在写的 1.4MB 清单」与「下一次保存的主文件写」会**重叠**；
一次保存的原生写合计约 **7MB**（主文件 + 备份 + 快照 + 清单 + 变化的分片），
且宿主扩展存储是「一个 key 一个文件」，本机实测写入节奏与宿主 `lan_sync` 缓存刷新（宿主日志可见）天然存在竞争面。

> 说明：宿主 API 的**并发安全不在本插件控制范围内**（我们没有宿主源码），所以正确做法是**从插件侧消除并发写**。

## 3. 修复

| 改动 | 位置 | 说明 |
| --- | --- | --- |
| 原生写 **FIFO 串行队列** | `adapters/tt-store.js#runSerialized` | 覆盖 KV 的 `put/del` 与 Blob 的 `put/del`（含 `ttPutBytes` 的 Blob→KV 回退链）：任意时刻**至多一个写在飞**；不丢写；不改变先后语义（同键后写仍然后写）；单次失败**不阻塞**队列，失败如实回给调用方。**只在最底层四个函数包装** —— `ttPutBytes` 内部会调它们，若也包装会**自锁** |
| 分片清单 **改为 await** | `adapters/sync.js#storageWriteAll` | 由 fire-and-forget 改为等其完成：`storageWriteAll` 返回即代表本轮原生写全部结束；镜像的 `storageSyncRunning` 守卫真正覆盖到最后一次写 |
| 诊断出口 | `adapters/tt-store.js#ttWriteStats` / `ttWriteStatsReset` | `queued / done / failed / pending` + **历史峰值并发**（应为 1）+ 最近一次写的标签与耗时；单次写 ≥3s 记一条 `kind='存储'` 日志（**崩溃前留痕**） |
| 调试桥只读方法 | `ui/debug.js` → `ftt.writeStats` | 真机核对入口：`bridge> call ftt.writeStats`。若 `maxInFlight > 1` 说明仍有并发写；崩溃前最后一次原生写的标签/耗时也在这里 |

## 4. 顺带量到的写入量事实（**本次未改**）

`adapters/shards.js#META_KEYS` 收录了 `snapStore`（本机 1.2MB 快照链）→ 同一份内容每次保存被写**三遍**：

| 载体 | 本机大小 |
| --- | --- |
| 主文件 `ftt2-state-<角色>.json` | 2029 KB |
| 备份 `ftt2-bak-<角色>.json` | 2029 KB |
| 快照 `ftt2-snap-<角色>.json` | 1245 KB |
| `meta` 分片 `ftt2-shard-<角色>-meta.json` | **1409 KB（几乎全是 snapStore）** |
| 变化的分片 + 清单 | 数十 KB ～ 1.4MB（依变化维度） |

**为什么不动**：`snapStore` 进分片是「主文件损坏 → 从分片重建」恢复路径的一部分；
把它从 `META_KEYS` 移除会让该恢复路径**丢快照链**，必须先审计恢复链路（并确认 `ftt2-snap-*` 在该路径上可读）才能改。
登记待后续单独决定。

## 6. 未验证项（如实登记）

- **崩因未 100% 坐实**：现有证据只能证明「崩在原生进程」+「插件此前确有并发写原生存储」，
  **不能证明**宿主崩溃一定由并发写引起（宿主自身或 WebView2 也可能另有缺陷）。本版消除了插件侧唯一的原生并发写路径；
- **串行化后的真机表现未实测**：需用户刷新页面后跑一轮（生成 → 保存 → 镜像），并 `bridge> call ftt.writeStats`
  确认 `maxInFlight === 1` 与 `pending === 0`（刷新后调试桥按设计回到关闭，需在面板「调试 → 🔌 调试桥」重新开启）；
- **若仍闪退**，请保留三样东西以便继续定位：① Windows 事件日志里新的崩溃偏移；
  ② `bridge> call ftt.writeStats` 的结果；③ `logs\tauritavern.log.<日期>` 尾部（看崩溃前宿主最后在做什么）；
- 第 4 节的 `snapStore` 三写问题未改（需先审计分片恢复链路）；
- 顺带观察（与本版无关）：宿主 `settings.json` 已 12.35MB，其中 99.2% 来自其它扩展；它每次保存都要整体序列化+写盘，
  是**宿主侧**的既有负担（本插件只占 105KB），已在此登记。
