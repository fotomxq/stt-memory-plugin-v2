## 1. 问题（用户报告）：「无法分析、跳过」

此前删楼/楼层突变后，条目的 `floorStart/floorEnd` 会被**就地改写**：
- 完全落在被删段 → 置「未知区间」`0/0` + `floorStale: true`；
- 幸存段 → 两端 `-= M`；跨越删除线 → 起点置 0。

「只改编号」的方向没错，但有两个真实缺陷：

| # | 缺陷 | 后果 |
| --- | --- | --- |
| ① | **来源楼层被抹掉**（`0/0`）→ 条目「在哪儿产生的」永久丢失，无法复核、无法回溯、跨端合并后互相打架 | 用户看到「未知区间」，也无法判断这份记忆到底来自哪一楼 |
| ② | 按**楼层号**推断「这一楼还是我的」，而不是按**内容** | 楼层被替换/前移后，旧条目仍宣称覆盖若干楼层 → 这些楼层被判「已有记忆数据」而**永久跳过**，新正文**无法分析** |

## 2. 口径（本版裁决）：来源与当前位置彻底分开

| 字段 | 含义 | 可变动？ |
| --- | --- | --- |
| `floorStart` / `floorEnd` | **原始来源楼层（provenance）**：条目在哪几楼产生 | **创建后永不变动** |
| `floorNowStart` / `floorNowEnd` | **当前位置**：按内容哈希匹配出的新位置；缺省（无字段）= 与来源相同 | 每次突变可重算 |
| `floorNowHash` | 当前位置那一段的**内容指纹** —— 让「当前位置」也**可复核** | 随位置重算 |
| `originGone` / `originGoneAt` | **原文已移除**：按哈希找不到该楼层原文时打标；**内容与来源楼层都保留**，但**不再占用任何楼层** | 原文重新出现即解除 |
| `floorStale`（历史） | 老数据的「当前位置未知」 | 兼容读：不占用任何楼层，由下次突变识别自动升级 |

三条纪律：**不删任何条目**、**不改来源楼层**、**只有找不到内容时才判「原文已移除」**。

## 3. 突变识别：以**内容哈希**为准（`host/floors.js#handleFloorShrink`）

```text
①-0 快照突变**前**的台账（原始楼层号 → 内容哈希）        ← 权威依据（此前被第 ① 步覆盖，导致「找不到原始位置」）
①   台账归位：当前聊天里内容仍能对上的楼层保持「已处理」
②   逐条目核算位置（不删、不改来源）：
      原文哈希在当前聊天里找得到           → 写 floorNow*（当前位置）+ floorNowHash，解除「原文已移除」
      floorNowHash 在当前聊天里找得到      → 当前位置整体平移（同一段内容搬了家）
      floorNowHash 也找不到                → 当前位置的内容也没了 → 转「原文已移除」
      有精确当前位置（删楼量已知）且该楼在册 → 补记 floorNowHash（供下次复核），**不臆断**
      无任何哈希信息、原始区间已不存在      → 判「原文已移除」
      其余                                 → 保守保留（不动）
③   收紧 lastKnownFloor（新楼此后照常可分析）
```

覆盖判定同步改为**按当前位置**（`core/floor-cover.js#currentFloorRange` → `meaningfulFloorRange` → `floorRanges/floorCoverage`）：
`originGone` / `floorStale` → **不覆盖任何楼层**；有 `floorNow*` → 以它为准（含 `0/0`：删楼重映射里「跨越删除线、
只有原第 M 楼幸存」的条目恰恰落在新第 0 楼，是**精确位置**而非未知）。

**这就是「修复无法分析、跳过的问题」的关键**：旧条目不再用旧楼号压住新正文 → 那些楼层重新进入未摘要清单 → 可正常分析。

## 4. 删楼路径同步对齐（`core/floor-trim.js`）

| 情形（删除头部 M 层） | v3.7.0 行为 |
| --- | --- |
| 区间完全落在被删段 | 打「原文已移除」，**来源楼层原样保留**（不再置 0/0） |
| 区间跨越删除线 | 来源楼层保留；写 `floorNowStart=0`、`floorNowEnd=max(0, floorEnd−M)`（精确：只有原第 M 楼及之后幸存） |
| 区间完全在幸存段 | 来源楼层保留；`floorNowStart/End = 两端 −M`（精确前移） |

`countStaleEntries()` 统计口径 = `originGone === true || floorStale === true`（设定 → 存储「🧱 楼层校准」只读诊断行）。

## 5. 溯源字段在归一化 / AI 更新后不丢

- `core/floor-cover.js#preserveFloorProvenance(raw, norm)`：归一化后补回溯源字段（各维度 normalizer 会丢弃未知字段）；
- `core/model/atom.js#normalizeAtom`：直接保留 `floorNowStart/floorNowEnd/floorNowHash/originGone/originGoneAt`；
- `core/ingest.js#mergeDelta`：**所有**维度归一化调用点统一走 `preserveFloorProvenance`；情节「更新」路径
  从旧条目**继承**溯源（否则每次 AI 更新都会把「原文已移除」标记冲掉）；
- 这些字段**不参与内容哈希**，因此不影响去重、瘦身与跨端合并的判定。

## 8. 兼容与回退 / 风险

- **兼容**：老数据没有 `floorNow*` → 行为与 v3.6.0 完全一致（覆盖判定回落 `floorStart/floorEnd`，`floorStale` 照旧不覆盖）；
  已存 `floorStale` 的条目在下次突变识别时自动升级为「当前位置未知 / 原文已移除」语义，**不批量改写旧存档**。
- **回退**：删楼前自动明文备份（v3.4.0）+ 快照链仍在；本版**不删任何条目**，最坏情况只是楼层标签偏保守。
- **风险**：区间「整体平移」的假设是「一段连续内容一起搬家」（删头/删中段都成立）；若用户在区间中间插入了新楼，
  同一条目的跨度会被算大 —— 保守方向（宁可多覆盖、不臆断移除），且下次突变识别会按 `floorNowHash` 重新复核。
