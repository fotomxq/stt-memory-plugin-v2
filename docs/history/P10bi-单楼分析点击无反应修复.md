# P10bi · 总览「可点击单楼分析」点击没任何反应（v2.96.0）

> 文档版本：v1.0 ｜ 日期：2026-09-28 ｜ 状态：生效（v2.96.0）
> 触发（用户原话）：「总览的可点击单楼分析，点击没任何反应。」
> 核对对象：`ui/panel.js#panelAction`（动作分发与收尾）· 点击委托 `bindOverlay()` · 总览未摘要区渲染 · 对应 V1 实现 `runSummaryFloor`（`FTT记忆组件-v1.205.js:15177`）

---

## 1. 先把「没反应」拆成两类

「点击没反应」可能有两种完全不同的成因，本版**两类都命中**：

| # | 成因 | 现象 | 影响面 |
| --- | --- | --- | --- |
| ① | **长耗时动作零即时反馈** | 点下去到 AI 返回（数秒~数十秒）之间，界面上**没有任何变化** | 所有耗时动作（单楼分析 / 批量摘要 / 提取记忆…），单楼分析最典型 |
| ② | **动作早退绕过统一收尾** | 前置条件不满足时 `setNote()` 写下的提示**永远不显示**；返回对象连 `html`/`state` 都没有 | `panelAction()` 内 **11 处**早退（提取 / 注入 / 批量摘要 / 导出 / 导入 / 旧版导入 …） |

## 2. 成因①：V1 有的反馈，V2 一个都没接

比对 V1 `runSummaryFloor`（v1.205:15177~15216）与本版 V2 实现：

| 环节 | V1 行为 | V2 修复前 | 本版 |
| --- | --- | --- | --- |
| 占用检查 | `pipelineOccupied()` → 警告「已有摘要/推演/修复任务在运行，请稍候再试」 | **无**（可无限连点 → 并发多条 AI 请求） | 同楼在途 → 拒绝并提示；批次在途 → 拒绝并提示 |
| 按钮反馈 | `btn.classList.add('ftt-loading'); btn.disabled = true; btn.title = '分析中…'` | **无**（CSS `#ftt-panel .ftt-floor-btn.ftt-loading` 早已在 `style.css`，JS 从没接上；`ftt-floor-pulse` 同理） | 点击**同步**加态 + **由渲染状态持续保持**（见 §3） |
| 状态文案 | `busy.activeSeg` + `updateFloorAnimDom()` / `updateAnalysisStatusDom()` | 只在**动作结束**后的重绘里出现提示 | 提示同帧写入 + **立即重绘**；总览「管线状态」行同时显示「正在处理：单楼分析 · 阶段：请求 AI（第 N 楼）」 |
| 结果通知 | `notify('success'/'warning'/'error', …)` 弹窗 | **无**（只有总览底部一行小字） | 开始 `info` + 结束 `success`/`warning` 各弹一条 |

> V1 那两行 CSS 在 V2 里是**死代码**（`grep ftt-loading` 在 V2 的 JS 中零命中）—— 这正是「V1 有、V2 没有」的证据。

## 3. 关键细节：转圈态必须**由状态驱动**

点击委托给按钮叠的 `.ftt-loading` 会被**紧随其后**的那次「立即重绘」换掉（`renderPanel()` 替换 `.ftt-modal` 内层 HTML，
节点被重建）。故真正的**持续**态必须来自状态 —— 与 V1 `updateFloorAnimDom()` 的做法一致：

```text
singleFloorBusy: Set<number>          // 正在分析中的楼层
  → 点击委托：同步给节点加 .ftt-loading / disabled（首帧反馈）
  → 渲染总览：在途楼层渲染成 class="… ftt-loading" disabled title="分析中…"（持续反馈）
  → 动作结束：从集合移除 → 下次重绘自动复原
```

## 4. 成因②：统一收尾（`finalizePanelAction`）

**修复前**：`panelAction()` 末尾才有「通知 + `renderPanel()` + 组装 `html`/`state` + 交互留痕」，而函数体内
十余处「前置条件不满足」直接 `return { ok:false, reason:'no-hook' }` 跳过了这一段。

后果有两层：

1. `setNote('提取入口未就绪')` 写进状态却**不重绘** → 用户什么都看不到（本报告的主诉）；
2. 若该分支是在点击委托里走到（按钮刚被加上 `.ftt-loading` + `disabled`），**这两个态永远不被清除** ——
   按钮就此变成灰的、点了也不动的「死按钮」。

**修复**：抽出 `finalizePanelAction(result, traceOp, traceT0, action, params)`，把原尾部原样搬入；
`panelAction()` 内定义 `const done = (extra) => finalizePanelAction(Object.assign(result, extra || {}), …)`，
**11 处早退**全部改为 `return done({ … })`，异常分支与正常结束也统一由它返回。
于是「不论怎么结束，界面一定更新、提示一定可见、交互一定留痕」。

## 5. 顺带修正

| 项 | 说明 |
| --- | --- |
| 楼层号非法 | `Number(p.floor)`：空串 → `0`、`'abc'` → `NaN`、`-1` → 负数。修复前空串会被当成「分析第 0 楼」；现在如实拒绝并提示「无效楼层」 |
| toast 通道缺 `success` | `index.js` 的通知接线只映射 `error`/`warning`，其余一律 `info` → V1 的 `notify('success', …)` 语义丢失。已补 `success`（`toastr.success`，缺失回落 `info`） |
| 面板钩子 | 新增 `hooks.notify(kind, text)`（面板动作的用户可见通知；未接线时静默，提示行仍在） |

## 6. 修复后的可见序列（真实读数）

```text
点击「第4楼」的同一帧：
  按钮 → class 含 ftt-loading / disabled / title「分析中…（等本次 AI 返回；结果会写回记忆并刷新本页）」
  提示行 → 正在分析第 4 楼…（AI 生成中，结果会写回记忆并刷新本页）
  通知   → info 第 4 楼：开始分析…
  总览管线状态 → 正在处理：单楼分析 · ⏱ 3s · 🪙 1.2k tok · 预计剩 6s · 阶段：请求 AI（第 4 楼）
AI 返回后：
  提示行 → 第 4 楼：新增 2 条（共 9）
  通知   → success 第 4 楼分析完成：本次提取 2 条
  该楼从未摘要列表消失；若无可分析正文 → warning「…当前刷次下没有可分析正文（或已被投喂白/黑名单过滤）…」
在途期间再点：
  提示行 → 第 4 楼已在分析中（或批量摘要正在运行），请等本次完成后再点   （且**不重复发起**）
```
