## 1. 核对结论：**是**，v3.0.15 的性能优化把一类数据丢失风险重新引回来了

先核对「前期修复」是否还在（这一层**没有**被破坏，逐项实测）：

| 前期修复 | 现状 | 证据 |
| --- | --- | --- |
| v3.0.11 载入择优 `pickNewerState`（两个源都读、按 `updatedAt` 取新、相等以服务端文件为准） | ✅ 未被改动 | `tests/unit/load-pick.test.js` **18 项通过** |
| v3.0.11 读路由**去钉死**（命中过的 key 仍复核原生存储）＋ 启动早期就绪等待 | ✅ 未被改动 | `tests/unit/file-transport.test.js` **36 项通过** · `tt-store` **46 项通过** |
| v2.91.0 墓碑删除判据加严 | ✅ 未被改动 | 冒烟 `AH3` 与 sweep 黄金样本通过 |
| v2.93.0/v2.94.0 楼层骤减处理与删楼校准 | ✅ 未被改动 | `floor-shrink` 5 项 · `floor-trim` 28 项通过 |

**但 v3.0.15 的「数据无变化 → 保存短路」引入了新的丢失路径**（正是用户说的那一类现象）：

```js
// v3.0.15 的判据（缺陷版）
function noopSaveOk(o) {
    if (touchSeq > pushedSeq) return false;     // ← 只信「内核 saveState() 钩子」打的序号
    return (Date.now() - lastFullPushAt) < noopWindowMs;
}
```

`touchSeq` 由**内核 `saveState()` / `persistNow()`** 刷新 —— 这等于假设「**所有**会改数据的地方都记得调 `saveState()`」。
事实并非如此，仓库里确实存在**不调**的路径，例如：

- `ui/snapshots.js#snapshotAction('snapDelete')`：直接 `state.snapStore = arr.filter(...)`，**不落盘**
  （同文件 `snapshotClear` / `snapshotCreate` / `snapshotRestore` 都落盘，只有「删除单个快照」漏了 —— 这是它自身的缺陷）；
- `core/migrate.js` 载入期对 `state.state.present` 的归一（由迁移完成，不落盘）。

后果链（用户看到的「重开应用后存档丢失」）：改动只在内存 → 之后的保存被短路（窗口内 `touchSeq === pushedSeq`）
→ 本机缓冲与服务端文件都还是旧内容 → 重开应用时两个源都一样旧 → **改动消失**。
另外 v3.0.15 的合流补跑也依赖同一个信号：**保存期间到达的、不走内核钩子的改动**会被静默吞掉。

还有一条**一直存在**的风险被这次检查翻出来：保存是 **800ms 防抖**（+ 落盘后镜像 3s 防抖），
若在这段窗口内关闭/刷新/被系统杀掉，那段「只差几百毫秒就写下去」的改动同样会丢。

## 2. 修复

| # | 落点 | 做法 |
| --- | --- | --- |
| ① | `adapters/store.js#noopSaveOk` | **判据换成内容签名**：只有「当前数据」与「上次**成功上传**的内容」**逐字节相同**才跳过。比对用 `storageEnvelope` 已算好的**信封哈希**（零额外成本）+ 该信封的 `scope`/`payload.updatedAt`（复现同一份载荷）。⇒ **任何改动（无论有没有调 `saveState()`）都不可能被吞掉** |
| ② | `adapters/store.js#saveStateNow` 合流补跑 | 内核路径仍按「信封取数之后是否真有变更」判定（避免保存自身的派生写入造成循环）；**其它调用方（事件防抖保存 / 控制台 / 导入 / 清空…）一律补跑一次**（它们的改动不一定经内核钩子）。「同在途的已是强制完整保存」时，一个同样 `force` 的合流请求视为已满足（不重复写） |
| ③ | `ui/snapshots.js#snapshotAction('snapDelete')` | **删除快照立即 `saveState()`** —— 补上这条自身缺陷（此前删掉的快照会在重开后回来） |
| ④ | `index.js#bindExitFlush`（新增） | `visibilitychange(hidden)` / `pagehide` / `beforeunload` 各触发一次**立即落盘**（`flushStateNow`：同步写本机缓冲 + 服务端文件；无变化时按内容签名短路，不浪费流量）。`teardown()` 解绑 |

**性能对比**（2000 情节 = 1.33MB 信封，同一桩环境）：

| 场景 | v3.0.14（优化前） | v3.0.15（缺陷版） | v3.0.18（本次） |
| --- | --- | --- | --- |
| 真实保存（有改动） | 479ms | 183ms | **182ms** |
| 无变化保存（事件驱动常态） | 180ms | 0ms ⚠️ 不安全 | **20ms** ✅ 安全（内容逐字节比对） |

即：拿回 **2.6×** 的真实保存提速，同时只用 20ms 换回「改动绝不丢」。
