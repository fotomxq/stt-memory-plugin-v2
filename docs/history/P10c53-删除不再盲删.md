# P10c53 · 删除不再「盲删」：修掉 v3.26.6 引入的宿主后端错误（v3.26.7）

> 文档版本：v1.0 ｜ 日期：2026-10-07 ｜ 状态：生效（v3.26.7）
> 用户报告（原话，附宿主报错）：「错误信息：后端错误 Failed to delete extension store entry: Not found:
>   Extension store entry `…\_tauritavern\extension-store\ftt2-files\kv\main\ftt2-state-char1xbib3t.json.json`: 系统找不到指定的文件。」
> 关联：`adapters/tt-store.js#ttPutBytes` / `#ttGetBytes` / `#ttDelete` / `#ttIsNotFound` · `adapters/file-transport.js#fileTransportDelete` ·
>   `docs/history/P10c52`（v3.26.6 的孪生副本清理 —— 本次报错的来源）

---

## 1. 现象

宿主弹出「后端错误」：删除 `kv/main/ftt2-state-char1xbib3t.json.json` 失败 —— **系统找不到指定的文件**。

## 2. 根因（自己引入的回归）

v3.26.6 为修「KV 旧孪生副本冒充服务端主文件」，在写入侧加了**无条件**孪生清理：

```js
if (ch === 'blob') { const r = await ttBlobPut(…); if (r.ok) { await ttKvDel(name, o); return r; } }
```

问题：**KV 侧常常根本不存在同名副本**（尤其是那些从来没写进过 KV 的键）。宿主原生 API 的
`deleteJson` 对缺失键**抛错**，TauriTavern 会把底层失败**如实报成「后端错误」**（插件侧虽在 `ttKvDel`
里把 `Not found` 当幂等成功，用户仍会看到报错弹窗）—— 每次保存都刷一条。

同理，`ttDelete`（删除总入口：删两个通道）与目录模式的 `localFileDelete`（一次轮删主名 / 平铺名 / 旧命名空间名，
其中多数不存在）也在对不存在的条目发删除。

## 3. 修复（一律「先探存在，再删」）

| # | 落点 | 口径 |
| --- | --- | --- |
| ① | `ttPutBytes` | 大载荷写进 blobs 后，**先确认 KV 侧确有同名副本**（本会话登记表 `twinSeen` 优先，否则 `tryGetJson` 探一次）→ 有才删；删成功即清登记 → 不会重复发 |
| ② | `ttGetBytes` | 双通道读取时先登记「落选通道确有副本」再删，删完清登记（供写入侧复用同一判据） |
| ③ | `ttDelete` | 探两侧（`tryGetJson` / `listBlobKeys`，**都不抛错**）→ 只删确实存在的那一侧；两侧都没有 → 直接 `{ok:true, alreadyAbsent:true}`（**零请求**） |
| ④ | `ttIsNotFound` | 补上宿主真实文案（`Failed to delete … Not found …`、「找不到」）→ 万一收到缺失类错误也按幂等成功、**不记错误** |

## 4. 边界（如实）

* 删除**确实存在**的副本时行为与 v3.26.6 一致（该删就删；真实失败仍如实回报并记错误）；
* 本批只消除「对不存在的东西发请求」这类无谓调用（也是用户看到的报错来源），**不改变**任何数据语义；
* 代价：删除前多一次**非抛错**的存在性探测（`tryGetJson` / `listBlobKeys`，均带短 TTL 缓存与未命中抑制）。

## 5. 测试与门禁

* `tests/unit/tt-store.test.js` 新增 **E6–E9**（4 项）：无同名副本时**零删除请求** / 有副本时删除**恰好一次**且不重复发 / 缺失键删除按幂等成功且不记错误 / `ttDelete` 只删存在的一侧、两侧都缺则零请求；
* 既有断言按新语义更新：`tests/unit/tt-write-queue.test.js#Q8`（队列计数 `+4 → +2`，并断言 `alreadyAbsent`）；
* 全量：**160 文件 / 2490 断言** + 冒烟 **220 项**；静态门禁（含 `docs-facts` 的 C8/C9）全绿。

## 6. 纪律（写进本档）

* **绝不盲删**：宿主原生 API 对缺失键会抛错并上报「后端错误」，任何删除前都应能证明「它存在」；
* 删除类操作的**幂等**要落在**调用方**（先探存在），而不是只靠 `catch` 里吞掉 `Not found`；
* 修「读到旧副本」类缺陷时，清理动作要**同一判据、同一登记表**（本次 `twinSeen`），避免两侧逻辑各删各的。
