## 1. 本版落地（D12 S1 + S2 核心）

| 裁决 | 内容 | 实现 |
| --- | --- | --- |
| **Q2** | 补上 V1 遗留但**缺失的「断裂检测」** | 新增 `host/floors.js#handleFloorShrink()`：`lastId < lastKnownFloor - 5` **且聊天已就绪**（复用 v2.87.0 `chatReadyForFloors`）→ 判定楼层骤减 |
| **Q3** | 收缩时**绕过**节流与 `mass-mismatch` 守卫，**强制**跑一次台账哈希归位 | 同函数内逐楼算哈希，保留「当前内容哈希 ∈ 历史已处理哈希集」的标记（归位 + 丢弃已消失楼），刷新 `processedVer` |
| **Q1** | **只改编号、不删数据** | 逐维（`DIMENSIONS` 全维 + `plotSegments`）检查 `floorStart/floorEnd`（分段为 `start/end`）是否超过当前末楼 → 置「未知区间」`0/0` + `floorStale: true`；**条目数量不变** |
| **Q9** | `lastKnownFloor` **收紧**为当前末楼 | `state.lastKnownFloor = lastId`，并写 `state.floorShrinkAt` |
| **§8-A** | 删楼是**常态**，收缩必须**低噪声** | ① 调试日志（`kind=楼层`）必记；② 人工确认项**按类型合并计数**（同类只累加 `count`，用户「全部已确认」一键清账）；③ 不做任何弹窗 |
| **§8-C/F** | 与同步配合 | `index.js` 注入收缩钩子 → 登记一条「楼层收缩」（计数）+ 说明「台账已归位 N 条 / M 条条目楼层信息失效（记忆数据保留）」 |
| 接入 | 扫描路径自动处理 | `scanPendingFloors` 维护阶段**先**跑 `handleFloorShrink()`（幂等，无收缩即短路） |

> **未做（下一批）**：D12 **S4** 的「设定 → 数据管理」三按钮（保留最近 6/10/12 层）与删前吸收预检 —— 需要宿主「删除聊天楼层」API 的能力探测与降级路径（`D12` Q6），以及 `D11` S1 的 `chatMetadata` 只读接入；本版先把**事后自愈**（用户手动删楼也能安全）做扎实。

## 2. 关键行为（600 → 删前 590 → 剩 10）

| 环节 | 本版行为 |
| --- | --- |
| 台账 | 幸存 10 楼的标记按**内容哈希**归位到 0..9；已消失楼的标记丢弃（**不再停在旧台账**） |
| 条目编号 | 旧号（如 100-105、590-599）→ `0/0` + `floorStale`；**条目一条不删**；`0/0` 是既有「未知区间」口径（`core/floor-cover.js` 已按未知处理，不会误跳过新楼） |
| 基线 | `lastKnownFloor` 599 → 9（后续断裂检测不再失真） |
| 用户感知 | 总览/设定「⚠️ 待确认」出现一条**合并计数**项；调试日志 `kind=楼层` 有明细 |
| 数据 | **全保留**（聊天减小、记忆不减） |
