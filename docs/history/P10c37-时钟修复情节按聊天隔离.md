## 1. 现象与取证（**先取证再改代码**：调试端口 + 落盘状态 + 插件自己的修复日志）

| 取证面 | 读数 | 出处 |
| --- | --- | --- |
| 页面版本 / 桥 | v3.18.0（页面未刷新）· 调试桥 8791 在线 · 34 个只读方法 | `sys.info` / `ftt.chatReady` |
| 时钟取值追踪 | date / time / location 三个字段都标 `from=plot`（来源是「情节」），`applied.changed=false`（落盘值与解析值一致 → **不是没落盘，是取错了源**） | `ftt.clockTraceInfo` |
| 当前聊天 | 24 楼，正文头连续 **628-07-09/10**（同一条时间线）；`lastKnownFloor = lastChatFloor = 23` | 聊天文件正文头 + 落盘状态 |
| 情节库 | `atoms = 115` 条，但**只有 14 条**的当前位置落在本聊天（≤ 23 楼）；其余 101 条是**别条聊天**的旧情节（198 / 327 / 438 三条线），楼层号最高 **508** | 落盘状态（`ftt2-state-*.json`） |
| 插件修复日志（今日 10:25~10:29，4 条） | 「楼层突变：**最新情节在第 508 楼、当前只有第 13 楼**（相差 495 层，疑为大幅手动删减）」·「**剧情时钟：已是最新（本轮无改动）（日期 198-02-21 · 时间 上午 · 地点 <旧线地点>…）**」 | `state.repairLog` |

**结论**：时钟的取值链路本身是通的（解析 → 落盘 → 追踪三条都一致），
**错在「最新情节」这条候选不是本聊天的** —— 拿的是**别条聊天**的旧情节（198 年线），
所以「最新情节已经变化（本聊天确实更新了），时间还是错的（取自旧线）」。

## 2. 根因链（四个环节，缺一不可）

```text
① 记忆容器按**角色**存（scope: char:xxxx）
     → 同一角色的**每条聊天共用同一份 atoms**（cross-chat 污染的结构性来源）
② 「最新情节」按**楼层/位置**排序取第一条（v3.16.1 口径）
     → 别条聊天情节的楼层号在本聊天里没有意义，却会长期压住本聊天最新情节
       （真机：508 楼的旧线压住 24 楼的本聊天新线）
③ 删楼处理 `handleFloorShrink` 拿**按角色共用的台账哈希**当条目原文指纹
     → 陈旧情节被「代理定位」到当前聊天的楼层上、并 `clearGone` **解除「原文已移除」**
       → **每次删楼都把旧情节洗白成「位置有效」**（用户说的「已经出现过很多次」= 每次删楼复发）
④ 时钟逐字段取值（v2.98.0）在候选本身脏的情况下进一步放大
     → 日期取自一条、时间/地点取自另一条（甚至跨日、跨故事线），拼出一个自相矛盾的时钟
```

真机时间线（今日）：10:25 修复把 342 条越界条目降级，但 **10:27 用户删楼**后，
`floorShrinkAt` 更新 → 旧线情节（当前聊天楼层 11/21/22/23 上）仍在册，
时钟被锁在旧线；直到本聊天继续推进到 19/21/23 楼的新情节，时钟才「自己回到」628 年线 ——
即用户观察到的「有时对、有时错，且总是删楼之后错」。

## 3. 修法（四道闸；一律**只降级不排除**，判不出来就不改行为）

| 闸 | 落点 | 口径 |
| --- | --- | --- |
| ① 聊天归属分级 | `core/chat-scope.js#chatTier` + `core/recall.js#trustedPlotList` | 新落库条目带 `chatKey`；排序档位 **本聊天 0 → 归属未知 1 → 已确认别条聊天 2**；档内沿用原有全部判据 |
| ② 位置越界降级 | `core/chat-scope.js#plotOverflow/plotDemoted` | 当前位置 > 当前聊天末楼（`lastChatFloor`/`lastKnownFloor`）→ 与「原文已移除」同档降级 |
| ③ 逐字段一致性守卫 | `core/clock-extract.js#resolveStoryClock` | 时间/地点不得来自**与已选日期不同日**的更早情节；跳过条数写进时钟追踪 |
| ④ 删楼不再洗白 | `host/floors.js#mapEntry` | 条目**自己有** `floorNowHash` 却在本聊天找不到 → 直接判「原文已移除」；**没有指纹**的历史条目仍走台账代理（不倒退） |

配套接线：

| 落点 | 作用 |
| --- | --- |
| `host/chat.js#currentChatKey/noteChatKey` | 聊天标识来源：`chatMetadata.chat_id_hash` → `ctx.chatId` → `chatMetadata.integrity`；**读不到就写空串**（宁可归属未知，也不能把新聊天的新情节错打成上一条聊天的） |
| `host/chat.js#wireKernelChatHooks` | 启动 / 切聊天 / 每次消息渲染都会同步标识 |
| `host/preflight.js#calibrateBasics` | **所有分析路径**（单楼 / 批量 / 自动）都经过这里，合并之前单点同步 |
| `index.js#onChatChanged` | 载入新作用域后：标识变了就**立即按本聊天的最新情节重解析时钟**（此前会把上一条聊天的时钟一直显示到本聊天有新楼层被分析） |
| `core/model/atom.js` + `core/entry-meta.js#stampChatScope` | 归一化保留 `chatKey`（**条件展开**，V1 黄金样本逐字节不变）；新条目打标、更新既有条目**继承**原归属 |
| `ui/debug.js` + `adapters/debug-bridge.js` | 只读诊断 `ftt.plotScope`（白名单 34 → 35） |

## 4. 兼容与边界（本轮**不**做什么）

| 事项 | 处置与理由 |
| --- | --- |
| 升级前的历史情节没有 `chatKey` | 归入「归属未知」档（保守：它们**可能**就是本聊天的，不能一律降级）；真正隔离要等本聊天**下一次分析**落了带归属的新情节 |
| 已污染的条目（指纹被写坏成当前聊天楼层的） | **不做批量改判**：改判需要内容级核对（台账哈希是按角色共用的，自证不成立），风险高于收益；如真机再犯，用 `ftt.plotScope` + `ftt.clockTraceInfo` 取证后另定一轮 |
| 跨聊天的情节共享 | 本轮**不改存储结构**（`scope` 仍是按角色）：记忆 / 物品 / 世界书等维度的跨聊天共享是既定设计，改结构属于大版本；本轮只让**时钟/在场角色**不再被别条聊天的情节带偏 |
| 位置越界判据的基准 | 刻意**不用现场末楼**（宿主未载入完 / 合成数据下会误降级有效情节），只用状态里记的末楼（每次楼层巡检已刷新）；且它只是兜底，主判据是聊天归属 |
| `DATA_VERSION` | 不变（1）：`chatKey` 是**可选**字段，缺失即「归属未知」，无需迁移 |

## 6. 未验证项与后续（如实登记）

- **真机待核对**：刷新后 `ftt.plotScope` 的 `current` 应等于「本聊天情节条数」、`other` 为别条聊天遗留、`overflow` 为越界条数；`ftt.clockTraceInfo` 的 picks 仍应全部 `from=plot`；
- **归属未知档的过渡期**：升级后本聊天旧情节（无 `chatKey`）与别条聊天旧情节（同样无 `chatKey`）同档，**仍可能被旧线压住**；本聊天下一次分析落库后即转为第一档，此后不再受影响。若用户希望立刻隔离，可在「调试 → `ftt.plotScope`」确认后按后续版本做一次性改判；
- **冒烟 `BH9`（本地缓冲清理）既有偶发时序失败**：本轮同一份代码 11 次里 3 次失败、上一版（v3.19.0 干净检出）11 次里 1 次失败 → 与本版无因果关系，另行登记处理（重跑即过）。
