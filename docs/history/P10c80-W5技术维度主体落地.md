## 2. `技-11`：覆盖率 —— 「先观测」是一条**必须写进实现**的约束

`docs/D21` §8 `技-11` 的原文是「用 Node 原生覆盖率产出报告（**先观测不阻断**）；记录 `core/` 基线」。
「不阻断」不是一句口号，它决定了三处实现细节：

| # | 决定 | 为什么 |
| --- | --- | --- |
| ① | **不进 `gate`**，单独 `npm run coverage` | 覆盖率会随「刚加还没测的模块」下降 —— 阻断等于禁止先写实现后补测试 |
| ② | CLI **`process.exit(0)`**（单测 C8 静态锁住） | 与 ① 同一件事的实现层保证：报告产出即成功 |
| ③ | 「基线写进文档」= **指向命令**，不写死百分比 | `docs/D14` §7 Q1 的既成口径：会随版本变的数字不写进正文 |

**口径必须自己写清，否则数字会被误读**：输出里固定打印
「**行覆盖**（一行被任一 `count>0` 的区间命中即算覆盖）· **空行与注释也算** → 百分比**保守偏低** · 非分支/函数覆盖」。
本仓库红线是「源码即发布物、无运行时依赖」，故**连 `c8`/`nyc` 都不引**（`D21` Q5 裁决）——自己算的代价就是要自己把口径讲明白。

## 3. `技-16`：桩化回归要「**能失败**」才有意义

`docs/D21` §5 **R7** 点名了风险：「新增门禁脚本本身不合规（无反向探针、静默通过）」。
桩化测试的风险形态不同但同源：**它很容易写成「桩返回什么就断言什么」**。本轮的 70 项按矩阵组织：

| 矩阵维度 | 断言什么 |
| --- | --- |
| `probeCapabilities()` 能力子集 | `ok` / `missingRequired` / `missingOptional` **逐项**正确（必需表来自 `host/st-api.js` 本身，不抄一遍） |
| 三后端路由 | 原生可用 → `tt-native`；原生不可用 → `st-files`；原生**未命中** → 回退 `st-files`（且读路由被记住） |
| 「探针 → 回读 → 删」 | **成功**：探针文件写入 → 回读逐字节一致 → 删掉（桩里不留残骸）；**失败**：降级并给**可读原因**（不许静默成功） |

**顺带发现的真缺陷**（登记为 `D17` **U194**，只报告未修）：`adapters/local-disk.js#localDiskProbeDir` 的「删」在 `api.dev` 机制下**不可达** →
探针文件可能残留。这属宿主/数据行为面，不在 W5「无前置」6 行内，且修复须连同「探针残留的清理口径」一起定。

## 4. `技-24`：把「必须同时改」变成机械判据

`docs/D17` §0 从一开始就写着：「本表按来源记事实，`D22` 按维度序给执行视图，两者**销账时必须同时改**」——
但这句话在此之前**只靠人记**。已有的门禁都核不了它：`check-drafts` 核的是**单份**稿子的结构（9 块 / 9 字段），
`check-docs-facts` 核的是**数字与引用**，没有一条判据跨「设计稿 ↔ 清单」。

C12 的四条判据（实现在 `scripts/ledger-sync-lib.js`，纯函数、可单测）：

| # | 判据 | 反例 |
| --- | --- | --- |
| ① | 每份设计稿的实施规格编号 → 必须有 `D22` 行 | 设计稿新增一条、清单没加 |
| ② | 清单每个编号 → 必须在**某份**设计稿有实施规格定义 | 清单凭空多一行 |
| ③ | 清单引用的 `U<n>` → 必须在 `docs/D17` 登记 | 引用了一个不存在的台账条目 |
| ④ | 同编号不得在**两稿**重复定义 | 同一编号被两份稿各写一遍（销账时必然只改一处） |

**第一版的坑**：编号解析只认「`| **数-1** |`」这种**干净**形态 —— 于是两条真实存在的行
（`| **数-3** **[契约]** |` 与 `` | `技-6`（后半） | ``）被误判成「双向不一致」。
**教训**：跨稿一致性判据面对的是**人手写的历史文本**，解析必须容忍装饰，否则第一版就会给出假阳性（假阳性会让人关掉这条门禁）。

## 6. `技-26`：为什么**不能**标 ✅

本机没有真机（SillyTavern 页面）—— 这一条决定了本轮交付的边界：

| 能确定的（已落成代码 + 单测） | 不能确定的（如实登记） |
| --- | --- |
| 探针逻辑（有序候选、逐个安全查询、抛错计数并写进原因） | **真机上哪一档真的可用** |
| 追加语义（**只追加不覆盖**、派发 `input` 事件、可选 focus） | 候选选择器表 `#send_textarea` 等是否正确 —— 它来自 ST 前端**既有约定**，**不是本仓库实测所得** |
| 降级链（宿主输入框 → 剪贴板 → 人工；每档带可读原因；绝不抛错） | 真机剪贴板权限被拒时的表现（单测只能用桩模拟） |
| **不写数据**（跑完整条链后 `cfg` / `state` 逐字不变） | —— |

留下的出口：**`FTT.inputBox()`**（只读，报 `via` / `selector` / `reason`）+ `host/input-box.js#inputBoxVerifySteps()` 的**六步清单**。

## 8. 踩坑与教训（本轮实证）

| # | 坑 | 教训 |
| --- | --- | --- |
| ① | **覆盖率文件两种形态**：新版 Node 写 `{ "result": [...] }`，老版写顶层数组 —— 只认数组时，209 个文件全在而报告是「0 条 / 0%」 | **失败看起来像成功**是本仓库最忌讳的形态；形态识别抽进 lib 并单测（`D17` U192） |
| ② | `--from <dir>` 跑完**把调用方的目录删了**（清理分支写成「非 `--keep` 即删」）→ 第二次同样的命令得到 0% | 清理只删**自己建的**临时目录（`D17` U193） |
| ③ | C12 编号解析不容忍装饰 → 两条真实行被误判「不一致」 | 跨稿判据面对**人手写的历史文本**：假阳性会让人关掉门禁，必须容忍装饰 |
| ④ | 两个并发 round 同时写 `D17`/`D22` 头注 → 小节编号 `1.18` 与 `U188–U190` **撞号** | 并发写入时**编号必须从「当前最大 +1」取**、并且**先看一眼同批是否已有人占号**（本轮已把 W5 的发现右移到 `U192–U194` / §1.19） |
