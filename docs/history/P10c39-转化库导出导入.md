## 1. 需求落定（把用户那句话拆成可核对的四条）

| 用户原话 | 落定口径 |
| --- | --- |
| 「**转化库**新增支持导出」 | 导出**当前生效**转化库（`nsfwRuleList()`：自定义非空用它，否则内置标准库），而不是只导出「自定义那份」——否则内置 329 条会凭空消失 |
| 「支持**导入**」 | 导入 = **合并**（只新增、不覆盖既有匹配词、绝不删除）；逐条走 `nsfwRuleAdd()`，与「＋ 新增」按钮同一套修剪/40 字上限/大小写不敏感去重口径 |
| 「导出**和导入**」都要能用 | 导出走**真实下载文件**（与数据管理页同一个 `downloadTextFile`）+ 剪贴板 + 页面文本框兜底；导入支持**粘贴 JSON** 与 **📂 选择文件** 两条路径 |
| 不能出错就静默 | 每条计数如实回报（新增 / 已在库 / 缺词 / 格式不合格 / 写入失败 / 超长截断），失败给出具体原因且**零副作用** |

## 2. 数据格式（信封）

```text
{
  "app": "ftt-memory-v2",
  "kind": "nsfwRules",        // 防误导入别的库：kind 存在且不符 → 直接拒绝（reason=kind）
  "schema": 1,                // 备将来换格式时判版本
  "exportedAt": "2026-10-05T…Z",
  "source": "custom" | "builtin",
  "count": 329,
  "rules": [ { "from": "做爱", "to": "亲近" }, … ]
}
```

导入端**宽容解析**（`nsfwRulesParseImport`）：

| 形态 | 例 |
| --- | --- |
| 信封 | 上面的对象 |
| 裸数组 | `[{ "from": "甲", "to": "乙" }]` |
| 其它容器键 | `rules` / `nsfwRules` / `list` / `items` / `规则` / `转化库` |
| 字段别名 | `from|match|匹配词|词|source|fromWord` → `to|replace|替换词|转化词|target|toWord` |
| 字符串条目 | `"甲→乙"`、`"甲->乙"`、`"甲=>乙"` |
| 逐行文本 | 每行 `匹配词→转化词`（`#` 注释与空行跳过；一行都没成形 → `bad-json`，不伪装成功） |

## 3. 为什么是「合并不覆盖」

转化库是**手工编辑过就可能与内置不同**的资产（改任意一条即转自定义）。导入若覆盖，等于「想补充别人的词表」变成「自己的改动被悄悄冲掉」——这是**不可逆**的数据损失。
因此本轮**不做**覆盖模式，也不做静默删除；要整体替换的官方口径是：先「♻ 恢复内置默认」再导入（页面已写明）。

## 5. 未验证项与后续

- **真机待核对**：刷新后 `设定 → NSFW弱化 → 转化库` 应看到「⬇ 导出转化库」「⬆ 导入转化库」；导出后浏览器应落一个 `FTT转化库_YYYYMMDD-HHMMSS.json`；
- **「📂 选择文件导入」在真机宿主上的文件选择器行为未验证**（单测/冒烟走的是桩；同一 `pickTextFile` 已由数据管理页导入长期使用，风险低）；页面当前仍是 v3.18.0（`sys.info` 读数），需刷新后才生效；
- 导入**不做 AI 语义校验**（例如「替换词本身仍露骨」不拦）：规则库层面的合并由使用者把关，后续如需可加「按识别词条库自检」提示，本轮不做；
- 大库导出体积：内置 329 条约 20 KB 级（`count` 与字符数在提示里回报），未见需要分片；若将来词库涨到万级再评估。
