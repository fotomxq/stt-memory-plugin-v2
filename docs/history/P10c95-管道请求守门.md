## 1. 核对结论（用户要求「核对相关按钮是否存在排重点击的机制」）

| # | 核对项 | 实测结论 |
| --- | --- | --- |
| 1 | 货币融合 / 履历补全 / 联动构建 有没有**自己的**在途闸？ | **没有** —— 只调用共享的 `aiBusy()` |
| 2 | `aiBusy()` 是什么？ | `core/ai-hooks.js` 的 `busy` 钩子 = 「**摘要 / 提取 / 同步在途**」（`host/extract.js#extractBusy`）——**不含自己这次 AI 请求** |
| 3 | 连点两下会怎样？ | **两次 `aiBusy()` 检查都为假 → 真的发两次 AI 请求**（重复消耗 token / 重复占管道） |
| 4 | `runResumeRepair`（📜 补全 / 修复履历） | 此前**连 `aiBusy()` 都没有**（三个动作里最裸的一个） |
| 5 | 在途期间按钮状态 | **不 `disabled`** —— 用户看不出「已经点过了」 |
| 6 | 有没有通用闸？ | 没有。`panelAction` 只有「载入未完成」一道闸（`loadBlocked()`），与重复点击无关 |

**结论**：**排重机制此前不存在**（不是"有但不灵"）。故本轮从零建立。

## 2. 设计：三条口径 + 一条安全阀（`docs/D9` §10 U15）

### 2.1 登记表（唯一事实源，24 项）

`ui/pipe-guard.js#PIPE_ACTIONS`：`action → { label, selfNotice? }`。

| 类别 | 动作 |
| --- | --- |
| 写库（提取 / 摘要） | `summary`* · `summaryFloor`* · `plotSegmentSummarySel` |
| 自动修复族 | `repair` · `characterRepair` · `resumeRepair` · `stateRepair` · `memoryRepair` · `conceptRepair` · `sceneRepair` · `itemRepair` · `planSuspRepair` |
| 压缩 / 合并 | `atomCompactNow` · `atomMergeSummary` |
| 平行事件 / 推演 | `parallelAdvance` · `parallelAdvanceAll` · `parallelCustomRun` · `parallelWeaveNow` |
| 三域联动 / 货币融合 | `triLinkBuild` · `currencyMergePick` |
| NSFW / 时钟 | `nsfwSoften` · `nsfwAnalyze` · `clockRepair` |
| 通道 / 向量测试（**真实网络请求**） | `apiTest` · `apiModels` · `testLayer` |

\* `summary` / `summaryFloor` 标 **`selfNotice`**：它们**自己**已经弹过开工提示（`AI 摘要：开始分析…` / `第 N 楼：开始分析…`），
本模块**只做排重与禁用、不再补弹** —— 同一次点击绝不弹两条。

### 2.2 三件事

| # | 口径 | 要点 |
| --- | --- | --- |
| ① | **开工弹窗提示** | `🔄 <label>：已发起 AI 请求（管道请求），等待返回…`（`docs/D9` §7 **U7** 进行中图标口径） |
| ② | **同动作在途排重** | 再点**挡下整条动作**：`ok:false` / `reason:'in-flight'` + 提示行 + `⚠️` warning 弹窗。**不静默忽略** |
| ③ | **在途按钮禁用** | 渲染期给在途动作的 `<button>` 注入 `disabled`（`<a>` 形态不注入；点击仍由 ② 兜底） |

### 2.3 两条不变量

* **排重按「动作名」**，不是全局串行 → **同一按钮防连点，不同动作仍可并行**（与 `aiBusy()` 的分工不变，
  不会把「摘要 + 推演」这类既有并行能力误杀）；
* **一定会释放**：释放点放在 `panelAction` 的**统一收尾** `finalizePanelAction` —— 成功 / 失败 / **异常** / 早退
  **都**经过那里（这正是 v2.96.0 为「早退也要重绘」而抽出的同一条收尾路径，复用它最稳）。

### 2.4 安全阀（`PIPE_MAX_MS = 5 分钟`）

万一某次请求卡死（宿主不回调 / 释放点被绕过），超过上限后**自动放行本次并如实计数** `timeouts`，
开工提示里写明「上一次请求已超时 Ns（已放行本次）」。
**宁可放行，也不把按钮永久锁死** —— 与 `docs/D22` `技-1` 落盘守门同一套哲学（失败要**可见**，不要静默卡死）。

## 2.5 实测修正：`summary` / `summaryFloor` **不进登记表**（首版 26 项 → **24 项**）

首版把它们也登记了 → **`npm run smoke` 立刻变红两项**（BA3 · BJ1）。定位结论：

| 事实 | 说明 |
| --- | --- |
| 它们**本来就有自己的在途闸** | `summaryFloor` 走 `singleFloorBusyState()`，**按楼层**判重；`summary` 走批量管线忙位 |
| 粒度**更细** | 统一守门按**动作名**判重 → 「3 楼正在分析」会把「5 楼」也挡下（**更粗的闸覆盖更细的**） |
| **开工提示本就自己弹** | `AI 摘要：开始分析…` / `第 N 楼：开始分析…` → 用户要的「弹窗提示」对它们已成立 |
| 并入的后果（实测） | 第二次点击的**拒因文案被本表改写** → BJ1 断言失败（原本由更细的机制给出更准的原因） |

**处置**：登记表 **24 项**（去掉这两项），并补单测 **B6** 专门锁定「这两项不在册」，
防止日后有人「顺手补全」又把 smoke 弄红。
**口径**：「全部管道请求类动作」=「**全部没有自己更细在途闸的**管道请求类动作」——
同一类风险同一口径的前提是**别用粗粒度覆盖细粒度**。

### 4.1 反向验证（本轮固定动作）

只回退 `ui/panel.js` 的接线（保留 `ui/pipe-guard.js`）→ **15 通过 / 5 失败**（B4 · C3 · D1 · D3 · D4）；
恢复接线 → **20 / 0**。→ 新用例**确实**锁住了「守门挂在调度上」这件事，而不是只自测模块。

### 4.2 又一个必须记下的教训（第二次假绿）

首版本文件里 `AX`（异步断言助手）**忘了 `await`** → 断言在 `R.done()` 之后才落账 → **只登记了 12 / 20 项**，
输出仍是「12 通过, 0 失败」（**看起来全绿**）。发现方式 = **人工数了一遍用例数**（写 20 项却只报 12）。
改法：全部 `await AX(...)`；并把「用 `R.done()` 的最终计数与手写用例数对账」纳入本轮自检。
（v3.46.3 那次是「同步 `A()` 把 Promise 变 true」，这次是「忘了 await」——**同类陷阱的两种形态**，
`docs/D9` §9 **C13** 用本单测承担检查项，正是为了让这类回归在门禁上可见。）

## 6. 未做 / 风险

| 项 | 说明 |
| --- | --- |
| 真机 UI 复核 | 本环境无浏览器（`docs/D13` §8.6 已登记该环境限制）→ 由**渲染 HTML 断言**（C3）与**真实调度**（D 组）锁定；建议真机连点两次任一管道按钮，确认「弹一次开工提示 + 第二次被挡下并提示」 |
| 中断入口（U6） | 本轮只做「开工告知 + 排重 + 禁用」；**中断入口**（U6 的「可中断」）仍按 U6 原清单推进 —— 二者互补，不互相替代 |
| 「不同动作并行」是否该进一步收紧 | 本轮**保持**：排重只按动作名（不同动作仍可并行，与 `aiBusy()` 分工不变）。若日后希望「同时只允许一个管道请求」，应另立设计项（那会改掉既有的并行能力，属口径变更，不适合塞进本版） |
| `PIPE_MAX_MS` 取值 | 5 分钟（远大于已知最长管线耗时）；若真机出现「正常操作被误判超时放行」，再按实测调整 |
| 其它**非 AI** 的长耗时动作（同步 / 导入合并） | 它们同样受本守门保护（`pipeEnter` 只对登记动作弹开工提示，但**排重对所有动作生效**）——这是有意的：用户要求的是「避免反复点击触发」，不限 AI |
