## 2. BUG：调试桥大载荷读不到（现象 / 根因）

**现象（真机，可复现）**：

* `node tests/local/bridge.mjs --call ftt.snapshot` → **必然** `E_TIMEOUT 30000ms`；
* 超时前先打两条 `[bridge] 收到非 JSON 帧，已忽略`；
* `sys.batch` 批量调用**同样超时**；而**单个小方法全部正常**（`ftt.memoryShape` / `ftt.dataHealth` / `sys.info`…）。

**根因（不在插件里）**：**大消息被对端拆成多个 WebSocket 帧**，而桥的收帧循环**对每一片各自 `JSON.parse`**：

| 出口 | 真机分片数 | 重组后字节数 |
| --- | --- | --- |
| `ftt.snapshot` | **2 片** | **130,313 B** |
| `sys.batch`（8 个只读方法） | **3 片** | **141,410 B** |

`0x1`（首片，非 FIN）与 `0x0`（续片）都**不是**完整 JSON → 逐片丢弃 → **没有任何一帧**进入 `handleIncoming` →
调用方永远等不到答复，只能超时。**与插件侧数据无关**：插件只是回了一份大一点的只读结果。

**为什么第一眼会被误判**：调试桥是唯一的真机取证通道，它自己出问题时的表现是「**某个大方法超时**」，
看上去就像**被测插件**的某个方法卡住（本轮前半程确实按「插件方法卡住」排查过）。

## 3. 修复与自检（只动调试工具，不动插件运行时）

| # | 落点 | 改动 |
| --- | --- | --- |
| ① | `tests/local/bridge.mjs` | 按 RFC 6455 **分片重组**：`0x1` 非 FIN 起头 → `0x0` 续片累积 → **FIN 收尾后再解析**；孤立续帧如实记日志并忽略；重组总量上限 **64 MB**（超出如实丢弃并记账）；收帧主循环抽成 `parseMessage()`，非 JSON 帧日志**带上字节数** |
| ② | `tests/local/bridge.mjs --selftest` | 新增**第 ⑤ 项**：浏览器 `WebSocket` 客户端不会主动分片 → 用 **raw socket 手工握手 + 手工造帧**（`0x1` 非 FIN 首片 + `0x0` FIN 续片）发一条 hello，断言桥**重组后认得它**（修前必 ❌）；`passAll` 同时要求 `pass && fragOk` |

**修复后真机复测**：

* `ftt.snapshot` → `ok:true`（版本 / 作用域 / probe / settings 全部可读），桥日志 `已重组分片消息：2 片 / 130313 字节`；

→ **`docs/D13` §8.7 的「快照链」一行**（链长 20 / 4.37 MB / `snapFp` 593，上一轮只能靠落盘文件间接核算）

## 7. 方法学留档（写给下一轮）

> **判别口诀**：*单方法通 / 批量挂 / 桥日志报「非 JSON 帧」⇒ 先查桥的帧处理，再查插件。*

调试桥是**唯一**的真机取证通道。它一旦在大载荷上失效，「快照链 / 批量诊断」这类核对在真机上就**做不了**，
验收口径会被静默堵死（本轮 W1 的快照链一行因此只能降级为落盘核算）。因此：

1. 桥的**自检必须覆盖它自己的传输边界**（本轮之前只测了「小消息 + 一次调用」）；
2. 凡「桥读不到」的现象，先区分**通道问题**（分片 / 超时 / 帧类型）与**被测对象问题**，再下结论；
3. 「超时」在文档里必须写成**可复现步骤 + 观察点**（本轮即为：超时前缀两条非 JSON 帧日志），否则下一轮无法自证。
