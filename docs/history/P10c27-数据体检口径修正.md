## 3. 查出的 4 处缺陷（全部先复现再修）

### ① 体检维度重复 → 该维被扫两遍

`core/data-health.js#HEALTH_DIMS = ATOM_DIM_KEYS.concat(['currencies','npcs','plotSegments'])`，
而 `ATOM_DIM_KEYS` **已含** `plotSegments` → 列表 16 项、唯一 15 项。

- 真机证据：`scanned.dims = 16`（唯一维度 15）；
- 构造证据：1 条分段（`uses:-5` / `floorStart:9>floorEnd:3` / `nsfw:'STRONG'`）→ 明细 **6 条**、`counts` 每类 **2**；
- 修法：维度列表去重（`HEALTH_DIMS` / `HEAL_DIMS` 各一处），`scanned.dims` 回到 15。

### ② 摘要等级被 `cap` 截断影响 → 低估严重度

`out.level` 原先由 `out.findings`（上限 200，超出计入 `truncated`）推导：
205 条 `field-too-long`(info) 把 1 条 `ledger-bad-mark`(warn) 挤出明细 → 摘要显示「数据体检：**info**」，
而 `counts` 里明明有 warn（面板 / `/ftt` / 调试桥都用这个摘要）。

- 修法：`add()` 里累计**最严重级别**（`info < warn < error`），`ok = worst < error`、`level` 由 `worst` 给出 —— 与 `counts` 一致、不受截断影响。

### ③ 丢弃留痕台账与两个辅助字段**体检与自愈都没覆盖**

v3.11.1 引入的 `state.processedDropped`（台账丢弃留痕）与 `lastChatFloor` / `processedVer`
既不在 `dataHealthReport` 的检查范围，也不在 `healthSelfHeal` 的修复范围：

| 脏标记放哪 | 体检 | 自愈 |
| --- | --- | --- |
| `processedFloors` | 报 `ledger-bad-mark` + `ledger-dup-mark` | 丢弃非法、去重 |
| `processedDropped`（修复前） | **「未发现异常」** | **一字未动**（原样 4 条） |
| `lastChatFloor: 'NaN'` / `processedVer: 12345`（修复前） | 不报 | 不修（`lastKnownFloor` 却会被修成 `-1`） |

- 修法：体检抽出 `checkMarks(pf, dim)` 对两个台账**同口径**校验；新增 `lastchatfloor-invalid`（应为 ≥-1 整数）与
  `processedver-invalid`（应为字符串）两个 code；自愈对留痕台账同口径丢弃/去重、`lastChatFloor` 非整数 → `-1`、
  `processedVer` 非字符串 → 删除（下游一律 `String(state.processedVer || '')`，删除与垃圾值同效但状态更干净）。

### ④ 自愈「不留痕、不保证落盘」

`index.js` 载入链只有 `st = migrateState(st)`，**丢弃了** `healthSelfHeal` 的 `changed`；
该载入函数（300–397 行）内没有任何保存调用 → 修了什么看不到，且修复只活在内存里
（磁盘仍是脏数据，直到下一次任意保存、或切后台/关页的 `flushStateNow` 强制落盘才写回；幂等所以不会损坏）。

- 修法：`core/migrate.js` 新增 `lastHealInfo()`（`{changed, ledger, dropped, entries}`，条目级按「被修过的条目数」计）；
  `index.js` 在 `attachKernelState(st)` **之后**（避免把上一份内存态写回磁盘）：
  有修复则 `debugLogPush('载入', {...})` 留痕 + `scheduleSave('载入期数据自愈')`。

  - **真实数据侧新发现（本次核对期间，用户在玩，存档从 724 条长到 778 条）**：体检报出 **38 条 `link-orphan`**

    是否要在载入期**自动**清扫孤儿行属于行为变更（会动用户数据），本次**不擅自改**，登记待定；
