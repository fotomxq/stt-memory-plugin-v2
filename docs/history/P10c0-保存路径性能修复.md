## 1. 取证（本仓库直跑真实适配层，2000 情节 = 549KB 容器 / 1.33MB 信封）

一次「保存记忆文件」的**同步**耗时拆解（`node --cpu-prof` + 分段计时）：

| 步骤 | 耗时 | 说明 |
| --- | --- | --- |
| `textToBase64`（信封 → base64） | **348ms** | ⚠️ 逐字节 `bin += String.fromCharCode(b)`：1.3M 次字符串拼接 + `btoa` 再走一遍 |
| `storageHash(payload)`（crc32） | 66ms | 信封哈希（内层还要 `JSON.stringify` 一次） |
| `tombstoneSweep()` | 51ms | 删除留痕：**又**全量哈希一遍 |
| `maintainSnapshots()` | 47ms | 快照维护 |
| `entryIndexBuild(true)` | 38ms | 全量原子哈希（**与墓碑扫重复**） |
| `JSON.stringify(envelope)` | ~8ms | 信封序列化 |
| `localStorage.setItem(1.33MB)` | 10~30ms | 本机缓冲（同步写） |
| **合计** | **≈ 500ms+** | 每次事件驱动的保存都会**阻塞主线程**这么久 |

而**事件驱动的空保存是常态**：`GENERATION_ENDED`（每次生成结束）→ `scheduleSave('generation')`，
数据其实没变，却照样把上面这一整套重活跑一遍 → 用户感受到的就是「正文保存特别卡顿、可能直接卡死」。

另外两处「无变化也重算」的浪费：

- 保存流水线先 `entryIndexBuild(true)` 再 `tombstoneSweep()`，而后者内部 `atomIndexCur || entryIndexBuild(true)`
  —— `atomIndexCur` **从未被赋过值** → 同一份数据每次保存**完整哈希两遍**（v1.200 的「一次遍历」优化没接上）。
- `mergeDelta` 的调试日志里 `chars: JSON.stringify(state).length` —— 每次增量合并把整库序列化一遍，只为记一个长度。

## 2. 修复（五处，全部只动「重复/无谓」的工作，不改任何数据语义）

| # | 落点 | 做法 | 收益（实测） |
| --- | --- | --- | --- |
| ① | `adapters/user-file.js#textToBase64` | 改**分块 `String.fromCharCode.apply`**（32KB/块，与 `gzip.js#bytesToBase64` 同款）；有 `Buffer` 的环境直接走原生 base64 | 348ms → **16ms**（Result 与旧实现**逐字节一致**，S11 锁定） |
| ② | `adapters/store.js`（保存流水线） | **「数据无变化」保存短路**：内核 `saveState()`/`persistNow()` 都刷新**变更序号** `touchSeq`；完整上传成功后对齐 `pushedSeq`。`touchSeq === pushedSeq` 且在 `SAVE_NOOP_WINDOW_MS`（60s）窗口内 → 直接返回 `{skipped:'no-change'}`，**不算索引、不建信封、不 base64、不上传、不排镜像** | 空保存 180ms → **0ms**（每次生成结束的那一次） |
| ③ | `adapters/store.js#saveStateNow` | **保存合流**：同一时刻只开一行、只做一次完整保存；期间到达的请求在其结束后**按需补跑一次**（仅当「信封取数之后」数据又变）。卡死同样可重开（与 v3.0.14 的 flush 层共用 `FLUSH_STUCK_MS` 旋钮） | 并发触发不再各写一遍 1.3MB 信封 |
| ④ | `core/sweep.js#primeAtomIndex` + `adapters/store.js` | 把已建好的索引**交给墓碑扫复用**（补上 v1.200 漏掉的交接） | 每次保存少一遍全量哈希 ≈ **38ms** |
| ⑤ | `core/ingest.js#mergeDelta` 调试日志 | 不再为记长度而整库 `JSON.stringify`（改为 `chars:-1`，`dims` 已给出各维条数） | 每次增量合并少 7~60ms（随容器增大） |

**安全性设计**（短路的边界）：

- 任何数据变更都经内核 `saveState()` / `persistNow()` → `markDataTouched()` 刷新序号；**直接写入**路径
  （清空记忆 `reset` / 导入 V1 / 导入 JSON / 数据台编辑与删除）显式 `force: true`，**永不短路**；
- 用**变更序号**而非时间戳判断（同一毫秒内的「变更 + 保存」不会被误判成无变化）；
- 窗口（60s）之外**一律完整保存** —— 万一某条变更路径漏了标记，最多 60s 后自愈；
- 短路只发生在「上一次**完整**上传成功之后」且期间没有任何变更时。
