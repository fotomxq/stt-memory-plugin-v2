## 1. 要补的假设

v3.17.0 把删楼默认路径改成「一次批量截断」，依赖 `getContext()` 导出的三个官方接口：

| 用途 | 现行 `st-context.js` 的键 | 备注 |
| --- | --- | --- |
| 落盘 | `saveChat`（= `saveChatConditional`） | **部分宿主/旧版直接导出 `saveChatConditional`** |
| 重画（首选） | `clearChat` + `printMessages` | 两个都要在才用这条路线 |
| 重载（兜底） | `reloadCurrentChat` | 会重读磁盘并广播 `CHAT_CHANGED` |

风险：键名对不上 → 本机从「批量」掉成「只能逐层」→ 大批量删除会被**拒绝执行**（比卡顿更难用）。
本机 ST 前端是 Tauri 内嵌资源（HTTP 缓存里也没有明文），**离线无法逐字核对**，故按「两种键名都认」加固。

## 3. 真机自查口径（刷新后，只读）

1. `node tests/local/bridge.mjs --call ftt.probe` → 看 `need.saveChat` / `need.clearChat` / `need.printMessages` /
   `need.reloadCurrentChat` 四项；四项能凑出「落盘 + 任一种重渲染」即本机会走批量截断；
2. 设定 → 数据管理 → 「✂️ 删除聊天楼层」的**只读诊断行**直接写「删除方式 批量截断（一次完成）／逐层删除（慢）」；
3. 删一次楼后看调试日志 `kind=楼层 action=删楼 via=bulk ms=<小数值>`（旧口径是 `via=api`，逐层才出现）。

## 5. 未验证项（如实登记）

- 本机**恰好**导出的是 `saveChat` 还是 `saveChatConditional`（或两者都有）待刷新后由 `ftt.probe` 读出；
  两种情形都已覆盖，不影响可用性；
- 逐层路径（≤3 层）与「拒绝执行」在本机真机未复现（本机有批量能力），由单测覆盖；
- 本加固不改变 v3.17.0 的性能结论：默认路径仍是**一次**落盘 + **一次**重渲染 + **一次**广播。
