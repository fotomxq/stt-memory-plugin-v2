# P10c5 · 「清除已处理楼层记录」真正归零并可整段重做（v3.0.20）

> 文档版本：v1.0 ｜ 日期：2026-09-30 ｜ 状态：生效（v3.0.20）
> 触发（用户原话）：「设定-数据存储-清除已处理楼层记录，该功能异常，应该直接将已分析楼层统计归零，
>   确保可以在总览中重新看到第0层之后的所有待分析楼层。」
> 相关：`core/floor-cover.js`（v2.64.0「已有记忆数据」覆盖判据）· `docs/history/P10bd`（未摘要楼层跳过机制）·
>   `docs/history/P10c1`/`P10c4`（删楼后的编号与台账归位）

---

## 1. 根因

「🧹 清除已处理楼层记录」（设定 → 数据管理，动作 `clearFloors` → `host/floors.js#clearProcessedFloors`）
此前只做三件事：清空 `processedFloors`、复位 `lastKnownFloor`、更新版本签名。**台账确实归零了**，但待分析清单
还有**第二条跳过判据** —— `core/floor-cover.js` 的「**该楼已有记忆数据**」（v2.64.0 按用户要求新增）：

```js
// scanPendingFloors
const mark = processedMarkOf(i);
if (mark && isFloorProcessed(i)) { skipped.processed++; continue; }
if (!contentChanged && skipCovered && cov.has(i)) { skipped.covered++; continue; }   // ← 台账清了还会被这条拦住
```

分析过的楼层本来就带着情节数据（`floorStart/floorEnd` 覆盖自己）→ 台账清空后它们**仍然**被 `covered` 跳过。

实测（12 楼 / 6 个 AI 楼 / 全已分析 + 情节覆盖 0..11）：

```text
清除前：台账 12 条 · 未摘要 [] · skipped { processed: 6 }
清除后（修复前）：台账 0 条 ✅ · 未摘要 [] ❌ · skipped { covered: 6 }   ← 用户看到的「清了没变化」
清除后（修复后）：台账 0 条 · 未摘要 [1,3,5,7,9,11] ✅ · skipped { covered: 0 }
```

（V1 的 `clearFloors` **只有台账判据**，所以清空即全部重现 —— 本版把这条语义补回来。）

## 2. 修复

| # | 落点 | 做法 |
| --- | --- | --- |
| ① | `host/floors.js#clearProcessedFloors` | 清空台账的同时记下**清空时的末楼号**：`state.coverReset = { at, upTo }`，并随状态落盘 |
| ② | `host/floors.js#scanPendingFloors` | 「已有记忆数据」跳过对 **`i <= coverReset.upTo`** 的楼层**不再生效**；再往后的新楼层照旧按该判据跳过（v2.64.0 语义只在被显式清空的区间让位） |
| ③ | `host/floors.js#processedStats` | 诊断多一项 `coverResetUpTo`（调试页/命令可直接核对「覆盖失效到什么楼层」） |
| ④ | `ui/panel.js` | 清空动作**把结果并入返回值**（`cleared` / `coverUpTo` / 清空后的 `pending`），提示改成「已清空 N 个 · 待分析 M 楼已重现」，并给出兜底入口（若仍有旧数据未出现 → 设定 → 存储 → 🧱 楼层校准） |
| ⑤ | `ui/settings-pages.js` | 按钮 title 补上「清除后总览重新列出第 0 层之后的所有待分析楼层」；危险动作确认文案同步（仍是只重置计数、不删条目） |

**不会永久改变既有语义**：重新分析后 `recordProcessedFloors` 把台账重新记上 → 这些楼层照常从清单消失
（单元 H/F 断言：`refilled.floors === []`）。
