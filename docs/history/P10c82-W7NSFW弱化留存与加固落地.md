## 2. `数-30`：一个「必然发生、只是还没被看见」的正文截断

原文（V1 移植）的两段代码各自都「合理」，合起来才出问题：

| 侧 | 原实现 | 单独看 | 合起来 |
| --- | --- | --- | --- |
| 投喂（`buildNsfwSoftenPrompt`） | 每条只取 `String(e.text).slice(0, 600)` | 省 token：合理 | AI **看不到**第 601 字之后的内容 |
| 落地（`applyNsfwSoftenResult`） | 结果长度 ≤ `Math.max(24, Math.min(600, round(原文长度×1.4)))` | 防「结果膨胀」：合理 | 原文 800 字时上限仍是 **600** → **AI 的 600 字覆盖 800 字原文 = 尾部 200 字静默消失** |

**为什么这条特别危险**：它不报错、不计数、通知里还写着「已弱化 1 条」。用户要过很久才可能发现某条情节的后半段没了。

**本轮的处置（用户裁决：按长度判超限，不做分段）**：

| # | 闸门 | 位置 | 行为 |
| --- | --- | --- | --- |
| ① | 打包侧 | `nsfwSoftenPack` | `text.length > NSFW_TEXT_CAP` → **不入本批** + 计入 `oversize`（小字段照常填满这一批） |
| ② | 落地侧 | `applyNsfwSoftenResult` | 拿到**旧清单**也能拦住：写回前按**实测长度**复核，超限 → `oversize++` 并写进 `details`，**绝不写回** |
| ③ | 只读口径 | `nsfwSoftenState().oversize` + 设定页扫描行 + 通知 + 调试日志 | 三处都如实说「超长跳过 N 条」并讲明原因，避免被误读成「功能漏了」 |

**为什么两道闸门都要**：`pack` 可能来自**上一次运行**（`runNsfwSoften` 内部先跑固定规则替换再用新包，但外部/测试可以传任意包），
且字段长度可能在两次之间被改写 —— 打包侧是「别把不该交的交给 AI」，落地侧是「无论清单从哪来，都不许写坏原文」。**深度防御，不是重复**。

**测试与反向探针**（`tests/unit/nsfw-golden.test.js`）：
- `W2` 打包侧：超限字段被排除、`oversize=1`、只读读数同步；
- `W3` 落地侧：构造**旧清单**直接调 `applyNsfwSoftenResult` → 正文逐字不变且 `oversize=1`；
- `W4` 端到端：回报与**通知**都含「超长跳过 1 条」，同批短字段照常弱化（正文完好）；
- 反向探针：拆掉打包侧闸门 → `W2`/`W4` 红；拆掉落地侧闸门 → `W3` 红（两条都实跑并恢复）。

## 3. `应-23`：把「跑完了但说不清跑成什么样」补成可核对的一行

弱化是**手动**动作：跑完只弹一条通知，**页面上不留痕**。刷新一次，用户就再也答不出「上次什么时候跑的、提交几条、改了几条、丢了几条、还剩多少」。
同页的「🧠 词条分析」早就用 `last` 解决了同类问题（`core/nsfw-analyze.js#nsfwAnalyzeState`），弱化侧只是没补 —— 本版按**同一形态**补齐：

| 决定 | 理由 |
| --- | --- |
| 账本**只存计数与时刻**（不存正文） | 与读取台账同一纪律：留痕不能变成第二份数据副本 |
| 落 **ST 扩展设置** `nsfwSoftenLog`（`adapters/settings.js#DEFAULT_SETTINGS` 登记） | 运行时账本而非记忆数据 → **刷新后仍在**、`DATA_VERSION` 不变、不进跨端同步（与 `nsfwAnalyzeLog` / `pipelineEta` / `floorTrimLog` 同族） |
| **装配期**接线（`index.js#wireNsfwSoftenHooks`） | 与词条分析同理：设定页状态行要**立刻**读得到，不能等用户先点一次动作 |
| **五处收尾都记账**（完成 / 无命中 / 仅剩超长 / AI 无返回 / 异常） | 「上次弱化」要能回答**任何**结局，包括失败（`ok:false` + 原因） |
| **忙位被拒不记账** | 那一次**没有真的跑**；记进去会让「上次弱化」指向一次空转（`W6` 锁住这条） |

验收（`nsfw-golden.test.js`）：`W5`（时间 + 提交 / 已弱化 / 丢弃 三项计数 + 页面含时间与计数 + **账本真的落到宿主**（用内存对象模拟 ST 扩展设置）⇒「刷新后仍在」）；
`W6`（忙位被拒不记账）。**未取得**：真机在真实 ST 界面刷新后复读 —— 本机没有真机，故不声称已验证。

## 4. `技-36`：一个「值相同所以看不出问题」的重复键

`NSFW_REPLACE_PAIRS` 的对象字面量里 `'口交'` 写了**两次**（V1 段与 v3.10.0 段各一条，值同为 `'亲昵'`）：JS 对象**后者胜**，
所以**当前没有任何行为差异** —— 这正是它危险的地方：日后只改其中一条，改动会**静默失效**（改的那条被另一条覆盖，或反过来）。

本轮：删掉 v3.10.0 段那条（V1 段已登记该词，且那条本就不对应任何 `NSFW_KEYWORDS_V310` 词条 —— 它连「逐条对应」的注释都对不上），
并在原处写明原因。**守门判据三条**（`W1`）：

1. `NSFW_RULES` 的 `from` 集合大小 == 数组长度（无重复）；
2. `NSFW_KEYWORDS` 每个词都有转化词；
3. **源码级**：对象字面量**无重复键** —— 重复键在求值后**不可见**，只能读源码核；再交叉核对「字面量键数 == 求值后键数」。

第 3 条是本轮对设计稿的**加强**（`docs/D30` §8 只点名了前两条）：前两条都查不出 U181 这类「字面量重复键」，
因为对象求值后重复键已经合并掉了。反向探针：把 `'口交'` 写回去 → `W1` 红。
