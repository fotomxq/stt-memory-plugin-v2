# P10c105 · 弱化NSFW 计数改事件触发与延迟去抖（v3.49.0）

> 文档版本：v1.0 ｜ 日期：2026-10-14 ｜ 状态：生效（v3.49.0）
> 用户要求（原话）：「总览弱化NSFW按钮的数量统计背后应该有被动或定时器，这个机制会造成性能浪费。
>   可做延迟执行，管道完成某个操作后（注意排除弱化NSFW功能），自动触发一个信号，然后延迟10秒检查；
>   在延迟期间可能会频繁触发信号，但自动忽略多余信号，以避免频繁更新。」
> 开发项：`docs/D41` **`技-50`**（新建设计稿）· `docs/D22` §4.21 **W21** ｜ 台账：`docs/D17` **U238**

>   `ui/panel.js`（两处读数改读缓存 + 弱化后作废缓存）· `tests/unit/nsfw-count-tick.test.js`（新）· `tests/smoke-test.js#CN1`

## 0. 先核对事实：用户的推断对了一半

用户说「背后应该有被动或定时器」。核对结论：

| 项 | 事实 |
| --- | --- |
| 有轮询定时器吗？ | **没有**（总览只有两个心跳：管线状态 500ms / 调试桥状态 1s，都与这个数字无关） |
| 那这个数字怎么来的？ | `core/nsfw.js#nsfwSoftenState()` → **`nsfwScan()` 全库全字段扫描** |
| 多久算一次？ | **总览每次渲染**（`ui/panel.js#overviewBody`）—— 面板每次动作都整块重绘 → **点一下就扫一遍** |
| 实测代价（4000 条目：3000 记忆 + 1000 情节） | `nsfwSoftenState()` **≈243 ms/次**；`nsfwLabelStats()` 0.3 ms/次 |

**所以：问题的确存在，而且比「轮询」更糟** —— 轮询至少是固定频率，这里是「用户每点一下付 243ms」，
而这个数字**不会因为看它一眼而变化**。这一条已写进设计稿 §0/§2（事实与推断分开记）。

## 1. 改造后的机制

```text
管道完成(提取记忆) ──signal──► 排一次 10s 检查 ──┐
管道完成(自动修复) ──signal──► 忽略(coalesced)     │  ← 窗口内多余信号一律忽略，且**不重排**（时间点不后移）
管道完成(推演)     ──signal──► 忽略(coalesced)     │
管道完成(弱化NSFW) ──signal──► 排除(excluded)      │  ← 连排都不排（用户明确要求）
                                  … 10s 到 ──────┘
                                  ├─ 看得见 → 扫一次 + **就地**更新按钮（不整页重绘）
                                  └─ 看不见 → 跳过（skipped）：算力留给用户真的在看的时候
```

| 件 | 落点 | 要点 |
| --- | --- | --- |
| 内核广播 | `core/pipeline.js#endPipeline` | 新增 `hooks.onRunEnd({label, ms, ok, at})`（**默认 no-op**，内核零宿主依赖）；**合流未归零不算完成**，故不广播 |
| 接线 | `index.js#wirePipelineHooks` | `onRunEnd → signalNsfwCountRefresh(label)`（2 行） |
| 延迟检查器 | `ui/nsfw-count-tick.js`（新） | 缓存 / 10s 延迟 / 合并不重排 / 排除 / 可见性 / 就地更新；全部 try-catch 兜底 |
| 渲染层 | `ui/panel.js#overviewBody` | 两处读数改读缓存（并移除两个直接的全库扫描调用）；弱化动作结束时 `invalidateNsfwCount()` |

## 2. 逐条落实用户口径

| 用户要求 | 落实 | 单测 |
| --- | --- | --- |
| 「管道完成某个操作后自动触发一个信号」 | `endPipeline` → `hooks.onRunEnd` → `signalNsfwCountRefresh` | 冒烟 `CN1`（真实 `beginPipeline/endPipeline` 走一遍） |
| 「延迟10秒检查」 | `NSFW_COUNT_DELAY_MS = 10000`；信号只排一次，**期间不执行** | `nsfw-count-tick` B1/B2 |
| 「延迟期间频繁触发信号，自动忽略多余信号」 | 窗口内一律 `coalesced`，计入 `dropped`；**不重排定时器**（`setTimeout` 1 次 / `clearTimeout` 0 次） | C1/C2 |
| 「注意排除弱化NSFW功能」 | `NSFW_COUNT_SKIP_LABELS = ['弱化NSFW','nsfwSoften']` → `excluded`，连排都不排 | D1/D2 |
| （附加）不再每次渲染全库扫描 | 渲染读缓存；缺失 / 过期才就地算一次 | A1/A2/A3 |
| （附加）看不见就不扫 | 执行时检查 `#ftt-nsfw-btn` 是否存在，不存在则 `skipped` | E1 |
| （附加）就地更新而非整页重绘 | `updateNsfwCountDom()` 只写那一个节点，文本未变不写 DOM | E2/E3 |

## 3. 一个必须讲清的口径关系（设计稿 §3.4）

「排除 `弱化NSFW`」= 不让**它**去排那个延迟检查。但弱化跑完，用户**正在看着那个数字** ——
若继续显示旧数，用户会以为「点了没反应」。故：**该动作结束时作废缓存**（`invalidateNsfwCount()`），
紧接着那次重绘**就地算一次**（只算这一次）→ 点完立刻看到新数。

两条口径并不冲突：**一个管「谁触发延迟检查」，一个管「用户主动动作后立刻给对的数」。**

## 5. 边界（如实登记）

1. **只改「何时算」，不改「怎么算」**：`nsfwScan()` 的关键词 / 规则 / 字段范围 / 上限**一字未动**；
   扫描本身的优化（243ms 这个数）**另立条目**（设计稿 §6 Q6 明确本轮不做）。
2. **数字最多滞后一个 10s 窗口**：这正是用户要的延迟口径；用户主动动作（弱化）后立刻给新数，
   渲染层发现缓存过期也会就地算一次，不会长期陈旧。
3. **不引入轮询**：新机制只在信号到来时排一次延迟；两个既有心跳（管线状态 / 调试桥状态）**未改动**，
   它们各自的「离开页面即停表」口径保持不变。
4. **内核保持零宿主依赖**：`onRunEnd` 是默认 no-op 的观测钩子，报文里不含任何 UI 概念；
   失败静默（观测绝不能影响管道本身）。
