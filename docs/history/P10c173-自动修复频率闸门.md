# P10c173 · 自动修复频率闸门：分析 10 次才触发 1 次（v3.52.20）

> 文档版本：v1.0 ｜ 日期：2026-11-20 ｜ 状态：生效（v3.52.20）
> 用户要求（原话）：「避免高频触发自动修复，尤其是非手动形式的触发，必须在分析10次及以上才会触发1次。」
> 关联：`core/repair.js` · `core/config.js` · `host/extract.js` · `ui/settings-pages.js`

## 1. 事实核对（改前）

* 频率闸门 `autoRepairOpDue()` 早已存在，但默认 `cfg.autoRepairEveryOps = 8`；
* **计数口径不全**：`bumpRepairOp()` 只在「解析出 JSON 并合并」后调用 → AI 失败 / 无 JSON 的路径**不计数**，
  连续失败时 `ops` 不动，闸门可能长期停在「已放行」；
* **手动/自动的界线按「silent + cause」判定**：`silent:true` 但没带 `cause` 的静默触发会**绕过闸门**；
* 自动修复**跑空（无变更）时不计为一次触发**：`markAutoRepairDone` 只在有产出时写入 → 下次分析立刻又能触发。

## 2. 修复

| 项 | 改动 |
| --- | --- |
| 默认节奏 | `cfg.autoRepairEveryOps` **8 → 10**（0 = 不限）；设定页文案「每 N 次分析后最多 1 次自动修复（默认 10）」 |
| 计数口径 | **每一次分析**（单楼 / 分段，含 AI 失败 / 无 JSON / 合并失败）都 `bumpRepairOp()` 计 1 次 —— 计数点在分析**开始** |
| 自动判定 | `isAuto = o.silent === true`：**所有静默触发**（不论有无 cause）都必须过频率闸门；手动（不带 silent）不受限 |
| 配额消耗 | 自动路径**放行即消耗配额**（`markAutoRepairDone()` 在闸门通过后立即写入）—— 本次即便无变更也算触发过 1 次，不会「跑空后下次分析又触发」 |

## 3. 测试

新增 `tests/unit/auto-repair-frequency.test.js`（7 项）：
A1 默认 10 · A2 每次分析都计数（含 AI 失败 3 次 → ops=3）· A3 9 次不放行 / 第 10 次放行 / 放行后第 11 次又不放行 ·
A4 静默无 cause 也过闸门 · A5 放行即消耗配额（连续两次：第一次执行、第二次被拦）· A6 手动不受限 ·
A7 合并失败排期开关仍有效。

同步：`config-clock-golden` 把 `autoRepairEveryOps` 列入「有意偏离」白名单。

全量单测 **272 文件**（断言数以门禁实测为准）；冒烟 224 项；`npm run gate` 全绿。

## 4. 边界（如实登记）

1. 闸门只做**限流**，不改变自动修复的触发源（仍是「提取合并失败」后的延迟修复）；
2. `autoRepairEveryOps = 0` 仍表示**不限**（用户显式选择）；
3. 手动修复（面板按钮 / `cause:'手动'`、不带 silent）**不受该闸门限制**。
