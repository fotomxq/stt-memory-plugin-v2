### 2.3 实测结论（`docs/D28` §3.3.5 留档；脚本用完即删）

一次「**只改 1 条** → 保存 + 载入」（200 条情节 + 60 条记忆 · 桩宿主）：

| 侧 | 读数 |
| --- | --- |
| 写 | **3 次 / 192.1KB**：本机层 82.1KB · **分片 1 片 27.9KB** · 主文件 82.1KB（**提交点全量**）· 镜像跳过（防抖 3s） |
| 读 | **11 次 / 316.9KB**：`file` 52% · `local` 26% · `shard` 22% · `meta` 1% |
| 耗时 | 保存 4ms · 载入 3ms（小语料，仅记录） |

**结论**：① 读放大**集中在载入期**（多候选主文件 + 分片清单 + 变化片），保存路径**无多余回读** → 与"每次保存写完再读回来对账"的猜测**不符**（那个来源**不存在**）；
② 载入期那些读取**正是恢复能力的代价**（v3.40.2 的"多候选按信封时间戳取新"）→ 按纪律**只定位、不收敛**（不删任何校验）；
③ **新发现**：分片是**维度级**增量 —— 1 条目变化只重传 1 片，但**该片是整维重写**（27.9KB）→ 设计稿验收②「写字节与变化量同阶」**只在维度粒度成立**（条目级同阶要等 `数-27` 区间分片）。

### 2.4 `[契约]` 项：只评估不实施（原文如此）

主文件基准化（基准 + 变更集 / 分片即权威）要动**信封 / `storageHash` / 载入候选顺序** → 须 `DATA_VERSION` 递增 + 双端兼容 + 迁移，
故按 `docs/D28` §8 `数-31` 第 ③ 步「**本轮只评估不实施**」执行；改造成本与风险已记在 §3.3.5。
