## 1. 更正理解 + 真正的问题

**理解更正**：删除楼层是**本插件「设定 → 数据管理」自带的能力**（`host/floor-trim.js`，`docs/D12` §4），
   插件**自己发起的动作**，不依赖「订阅宿主事件」—— v3.0.16 把重点放在「官方 `deleteMessage` 不触发我们订阅的事件」
   上是**偏的**（那部分修复本身有效：活值末楼号 + 删后刷新视图；但没覆盖用户遇到的那条路径）。

**真正的问题**：删楼后的「编号校准」**只按删除层数 M 整体前移**（`remapAfterTrim`）——这个口径**只在
「被删的正好是连续的、最初 M 层，且每一层都真的删掉了」时成立**。一旦：

- 删除**只成功了一部分**（宿主中途失败 / 某一层没删掉 → 前缀里出现「洞」），或
- 实际删掉的下标与 M 对不上（宿主实现差异、隐藏楼、并发改动），

则「整体前移 M」会把台账与条目的楼层号**挪错位置**：

```text
例：30 楼全已分析；保留最近 10 层（M=20，删 19..0），但 id=5 没删掉
  → 实际删掉 14 层，聊天变成 [0,1,2,3,4,5,20..29]（16 楼）
  → 按 M=14 前移：台账标记 14..29 → 0..15（**哈希跟着标记走**）
  → 但 0..5 楼的实际内容仍是老三 0..5（其标记因 f<M 被丢弃）→ 这 6 楼哈希对不上
  ⇒ 台账错位：仍然存在、早已分析过的楼层**又冒出来当未摘要**（成片重分析）；
     反过来某些情形下新楼层会被误判为「已处理」→ 用户看到的就是「删除后无法正常继续分析」
```

实测（30 楼 / 洞在 id=5 / 保留 10）：

```text
修复前：未摘要 = [1, 3, 5, 16]   ← 1/3/5 是**已分析且仍存在**的楼（会被重复分析）；
                                  台账 16 条里 0..5 的哈希与实际内容全对不上
修复后：未摘要 = [16]            ← 只有真正的新楼层；0..15 全部保持「已处理」
```

## 2. 修复

| # | 落点 | 做法 |
| --- | --- | --- |
| ① | `host/floor-trim.js` 步骤 ⑥c（新增） | 编号前移之后，**再跑一次「楼层收缩处理」**（`handleFloorShrink({force:true})`）：按**内容哈希**把台账归位、越界区间降级为未知区间、基线收紧。幂等、只改编号不删条目 |
| ② | `host/floors.js#handleFloorShrink(opts.extraHashes)` | 支持传入**「重映射之前」的全部台账哈希** —— 于是那些「内容仍在、但标记被前移丢弃」的楼层被**找回**成「已处理」，不会在删楼后成片重分析 |
| ③ | `index.js#wireFloorTrimHooks` | **补齐 `writeBackup` 的第 4 个参数透传** —— v3.0.17 的备份名带时间戳后靠它删掉「该槽位的上一份」；此前只传 3 个参数 ⇒ 生产环境里**轮转删除从不执行、备份无限累积**（v3.0.17 的缺陷，本轮一并修） |

## 3. 附带修复：测试完整性（本文件此前是「假绿」）

`tests/unit/floor-trim.test.js` 的断言助手是 `(n, c, e) => R.assert(n, !!c, e)` —— **`!!` 把 Promise 变成
`true`**，于是该文件里所有 `A('…', (async () => {…})(), …)` 的断言（D1–E3、G2、以及本轮的 F/G/H 组）
**从未真正执行过**。本轮改成「thenable → 返回 Promise，调用点 `await`」后立刻暴露 3 条**过期期望**：

| 断言 | 问题（此前被假绿掩盖） | 处置 |
| --- | --- | --- |
| D3（备份 3 槽轮转） | 直接沿用上一断言残留的台账槽位 → 轮转起点不是 0 | 断言前先清空账本（`bootHooks()`），此后跨轮持久 |
| D4（只读诊断的插件条数） | 期望 6，实际 7（4 原子 + 1 记忆 + 2 分段） | 改为 7 |
| G1（备份名） | 期望 `…-abc-s1-…`，实际 `slugify('char:abc')` = `charabc` | 期望改为 `charabc` |
