## 1. 计划悬念「长期未推进」清理（新增第 ① 段第 10 步）

新模块 `core/plan-cleanup.js#planSuspStaleCleanup()`（零 AI、确定性）：

| 口径 | 规则 |
| --- | --- |
| 范围 | 仅 `status === 'open'` 的计划 / 悬念（已了结 / 已揭晓跳过） |
| 年龄 | 条目自身剧情日期 → 当前剧情日期（`core/plan-aging.js#entryAgeDays`；无剧情时钟 → 整项跳过，不猜） |
| 动作 | **>120 剧情天 → 了结**（计划 `closed` / 悬念 `resolved`），写 `autoClosed: true` + `statusNote`（含上次推动日期）；**不删除**（`docs/D28`） |
| 老化档 | 30–120 天 → **只计数提示**，不动数据 |
| 开关 | `cfg.repairAutoCloseStale === false` 可关闭 |
| 幂等 | 已了结条目不再重复计数；重复调用零副作用 |

接入：`core/repair.js#runRepairMech` 第 10 步（`REPAIR_MECH_STEPS` 9 → **10 步**），
统计进 `mech.ageClean` 与 `stage1.notes`（「计划/悬念老化清理：…」）。

> **设计口径变更（如实登记）**：`docs/D20` §3.4 `数-12` 原定「不自动了结，交用户一键闭环」；
> 本轮由用户明确要求并入自动修复 → 改为**自动了结**，但保留三条边界：只了结不删除 · `autoClosed` 留痕 · 配置可关。

## 2. 修复数量「合计」统计（唯一口径）

`core/repair.js` 新增：

* `repairTotals(r)` —— **合计口径唯一源**：机械去重 / 垃圾清理 / 遗忘清扫 / 条数裁剪 / 无效条目 / 衰退清理 /
  关联清理 / 计划悬念了结与合并 / AI 修订与删除 / **老化了结**（`ageAging` 只提示、不计入 `total`）；
* `repairTotalsText(r)` —— 一行文案：`合计修复 N 处（合并去重 a · … · 老化了结 b）；另有 M 条计划/悬念进入老化档（仅提示）`；
* `runRepair` 的 `made` 改用合计 `total`，返回值新增 `totals` / `totalsText`；`repairReport` 内嵌合计文案。

## 5. 边界（如实登记）

1. 自动了结只改 `status` 与留痕字段，**不删除**条目（`docs/D28` 不删数据）；用户可在计划/悬念页重开；
2. 老化判定依赖**剧情日期**；无剧情时钟 → 整项跳过（不按现实墙钟猜）；
3. 「合计」是「改动处数之和」，不等于「条目数减少」（合并/了结/清理都算一处；老化档只提示不计入）。
