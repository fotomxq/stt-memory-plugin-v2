## 1. 核对：确实在逐层删

`host/floor-trim.js#floorTrimApply` 第 ⑤ 步（v2.94.0 起）：

```js
for (let id = plan.removeCount - 1; id >= 0; id--) {
    await del(id);                                  // = ctx.deleteMessage(id)
    if (chatLen() >= before - deleted) { … break; }
    deleted++;
}
```

一步一层 → **N 次** `deleteMessage`。ST 的 `deleteMessage` 每次做：
`chat.splice` + DOM 消息节点移除 + `chat_metadata.tainted` + **`updateViewMessageIds()`**（给**其后所有消息**重新编号）
+ `saveChatDebounced()` + `eventSource.emit(MESSAGE_DELETED)`。
其中 `updateViewMessageIds` 让总代价变成 **O(N²)**；几千层时非常吃资源（用户报告的现象成立）。

v2.94.0 当初选 `deleteMessage` 是**因为**它自带全部官方副作用（别的插件能收到 `MESSAGE_DELETED`）——
本轮改成「酒馆自带命令」同样满足这一点（命令本身就在 ST 内部执行），且一次到位。

## 2. 改法：命令优先 + 逐层回退

| 路径 | 触发条件 | 动作 |
| --- | --- | --- |
| `command`（首选） | 宿主有 `executeSlashCommandsWithOptions` | 一次 `executeSlashCommandsWithOptions('/cut <保留层数>')` —— 酒馆自带截断命令，ST 内部一步删完整段 |
| `command+api`（回退） | 命令抛错（ACL 拒绝等）**或命令没生效**（`chat` 未变短） | 记一条告警 + 记 `command+api`，再按「还剩多少要删」**逐层** `deleteMessage` 补完（下标从 `removeCount-1-deleted` 起，仍是删更早的楼层、仍从后往前） |
| `api`（无命令能力） | 宿主没有该命令 | 逐层 `deleteMessage`（**v2.94.0 口径完全不变**） |

命令口径：ST 的 `/cut N` = 把聊天截断到**前 N 条**；我们保留最近 `keep` 层 → 命令为 `/cut <chatLen - removeCount>`。

**效率**（Node 等价复现 `deleteMessage` 的 splice + `updateViewMessageIds` 重编号 + 保存调度；N=2000、保留 10）：

| 路径 | 总耗时 | 重编号次数 | 保存次数 |
| --- | --- | --- | --- |
| 逐层删除（旧） | 2.0ms | **19,900** | **1,990** |
| 命令截断（新） | ≈0ms | 0 | **1** |

> ≈ **199×**（重编号少 19900×）。浏览器里旧路径还有 N 次重排/重绘与 N 次 await 往返 —— Node 无 DOM，**未计入（未核实）**。

## 5. 兼容与回退 / 风险

- **宿主差异安全**：命令不存在（老版本酒馆 / 受限宿主）→ 自动回退逐层；命令存在但被 ACL 拒绝 → 也回退。两条回退路径都不会「什么都不做还报成功」。
- **其它插件**：命令在 ST 内部执行，与 `deleteMessage` 一样属于官方路径；此外我们自己的编号校准不依赖逐条事件
  （`handleFloorShrink({force:true, extraHashes})` 按**内容哈希**归位，v3.0.19 起如此）。
- **`/cut` 语义依赖**：我们按「保留前 N 条」实现并在**调用后核对 `chat` 长度**；若某宿主的 `/cut` 语义不同（例如需要参数 0 基），
  核对不通过就回退逐层 → 不会删错。**真机需要一次实测确认**（已列为本轮未核实项）。
- **回退开关**：`floorTrimApply({ _runCommand })` 可注入自定义命令执行器（测试 / 特殊宿主），传 `null` 即强制逐层路径。
