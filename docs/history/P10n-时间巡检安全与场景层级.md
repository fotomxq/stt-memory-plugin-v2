## 1. 「时间巡检修复会改错时钟数据」—— 两处真缺陷（**V1 故障明确修正 #7**）

oracle 证据：`tests/fixtures/v1-golden-clock-repair-safe.json`（生成器 `gen-v1-golden-clock-repair-safe.cjs`，
真实 V1 v1.206，两次运行逐字节一致）固化了 V1 的两个危险行为：

| # | 危险行为 | oracle 实测 | 后果 |
| --- | --- | --- | --- |
| ① | `clockPatrolRepairItem` 对**所有**异常都先「按内容重解析」——包括「格式合法但年份漂移(jump/backward)」的条目 | 条目 `date=2035-05-05`、正文里提到「1919年11月20日」→ 被改写为 `1919-11-20` | 一条日期本是对的记录，只要正文顺带提到别的年份就会被覆盖（安全闸门只挡「异常值」，挡不住这种误覆盖） |
| ② | 总览「🩺 时间巡检修复」按钮走 `runClockPatrolRepair({ force: true })`（v1.206 27505） | 手工锚点 1800-01-01 + 库内 4 条 1919 → **4 条年份全改成 1800**（不带 force 时才是 `blocked: 'anchor-conflict'` 只统计） | 锚点一旦错，点一次按钮就整库改错；这是用户报告的直接来源 |

**修复**：

1. `clockPatrolRepairItem` 收紧：**只有 `reason === 'invalid'`（格式非法/日期不存在）才允许按内容重解析**；
   「年份漂移」只允许**保留月日、把年份改为锚点年**（`clockReplaceYear`，仍过 `clockPatrolSafeDate` 闸门），
   改不动就**保留原值**（note 明写「不按内容重解析」）。
2. UI 手动巡检改为**两步**：`clockPatrol`（默认，等价 `runClockPatrolRepair({})`）在锚点与库内多数年份冲突时
   **只统计不修改**，note 给出两条正确出路（① 先用「✏️ 手工改写」把锚点改成正确日期；② 或点提示里的
   「按锚点强制校正」）；新增显式动作 **`clockPatrolForce`**（`{ force: true }`）才按锚点整库校正，
   写回前照旧先建**全量快照**（可回滚）。

**保持不变**：无锚点/锚点分歧 → 一律只统计；真正格式非法的条目仍按内容重解析或清空（与 V1 同值）；
`clockAnomalyJumpYears` 阈值、绝大多数派/共识口径、写回前快照闸门都不变。

## 2. 「场景收纳能力异常」—— 层级被悄悄拍平

**根因**：V2 的编辑器缺了 V1 的 `findSceneParentId()`，且父级下拉只列裸 `name`、未排序、无缩进、无完整路径。
于是编辑一条**嵌套场景**时下拉恒为「（顶层）」——用户不改任何东西直接点「💾 保存」，
`deconstructEntry` 按「父级为空」重建 `pathArr = [name]` → **该节点被拍平到顶层**（场景树里层级消失）。

**修复**（对齐 V1 v1.206）：

- 新增 `findSceneParentId(scene)`（V1 23352 逐字）：`pathArr` 去掉末段即父级路径 → 在场景库按路径找到父级记录并返回其 id；
- 父级下拉（V1 23300~23313 逐字）：全部场景**按完整路径排序**，标签 `'　'.repeat(depth) + name + （完整>路径）`，
  选中项 = 预设父级（`addChildScene`）**或该条自身的父级**。
