## 1. 核对结论：②是**三个真实 bug**，而且都在**载入路径**

v3.0.21/v3.0.22 两轮都在修**保存**侧（分片提交、保存对齐所有存储），而「初次激活读取的数据没有对齐」
发生在**读**侧。逐层核对后，读侧有三处与写侧**不对称**：

| # | 成因 | 证据（代码事实） |
| --- | --- | --- |
| ① | **本机内存库写而不读** | 保存流水线的第 ⑤ 步 `localforage.setItem('ftt2_state_<scope>', envelope)` 一直在写；而 `loadFromLocalStorage()` 只读 `localStorage` —— **IndexedDB 这一层从来没有被读过**。浏览器本地变量被清掉（清缓存 / 隐私模式 / 换存储分区）而 IndexedDB 还在时，数据看起来整个丢了 |
| ② | **主文件不可用时分片一片都不读** | `loadFromServerFile()` 在 `if (!r || !r.ok) return null;`、`env.hash !== h → return null` 等处**先返回**，而 `applyNewerShards()` 在**返回之后**才调用 —— 于是**恰恰在分片存在的场合**（主文件写入滞后 / 被杀进程 / 被清理）它一片都不读，v3.0.21 的实时通道形同虚设 |
| ③ | **聊天元数据不参与载入** | `chatMetadata` 是 `docs/D12` §8-C 用户裁决的「**主载体**（随聊天存活 / 随聊天备份与同步一起走）」，但 V2 只把它当**差异报告**读（S1 只读不写）——「换设备 / 恢复聊天备份 / 初次激活」时，聊天自带的那份记忆一个字节都不参与载入 |

核对过程还暴露两个**竞态 / 时序**问题（同样属于「没对齐」）：

| # | 成因 | 复现 |
| --- | --- | --- |
| ④ | **载入无条件覆盖** | 载入是「读各层 → 合并 → 注入」的异步过程。期间用户导入 JSON / V1 导入 / 跨端合并注入了更新的状态，随后**载入完成并把它覆盖掉**。实测：`init` 的载入落在导入之后 → **导入的 2 条变成 0 条**（单测 `load-align` LA6 现在锁死这条） |
| ⑤ | **作用域未就绪** | 初次激活 / 宿主早期加载时角色稳定键可能还是空的 → `scopeId()` 回落 `char:<hash('default')>`，那一次读的是**别人的文件**；`init` 之后不会自动纠正 |

## 2. 修法：载入分层对齐（`index.js#alignLoadedLayers`，纯函数）

```text
① 服务端主文件     有则必为基底（哈希不过 → 不丢整次载入，转 ②）
② 分片 + 清单      主文件缺失 / 哈希不过 / 无数据体 → 以 mainAt=0 应用全部片重建
③ 本机缓冲         localStorage   ┐ 无 ①② 时按 updatedAt 竞争基底；
④ 本机内存库       IndexedDB      ┘ 有基底时**始终**并集（保存流水线同步写它们，清空/导入也写 → 不会复活旧数据）
⑤ 聊天元数据       chatMetadata   **只在比基底更新时**才并集（V2 不写它，无条件并集会让「清空记忆」被旧副本复活）
```

- 各层只作**并集补充**（`mergeDataObjects`：同名按时间取新、墓碑生效、快照链并集、已处理楼层并集），**绝不整体覆盖**基底；
- 返回值 `{st, via, base, baseAt, unioned, skipped, contributed, report}` —— 逐层给出「时间戳 / 条数 / 是否采用 / 贡献条数」；
- ⑤ 一律取**深拷贝快照**：`raw.state` 是 chatMetadata 里的活对象，直接挂进内核后保存流水线（墓碑扫 / 瘦身 / 索引）
  会就地改它 = 「写 chatMetadata」，违反本阶段纪律（`docs/D11` §5 S1）。单测 LA4 显式断言「内核里的对象 ≠ 聊天里的对象」。

**竞态**：内核新增 `stateSeq`（`core/model/runtime.js#setKernelState` 递增、`kernelStateSeq()` 读出）。
载入在读盘前记下序号，注入前比对：**序号变了就不注入**（那一份更新），回报 `superseded` + 调试日志一条。

**作用域**：作用域为空时如实记账（`reason:'scope-key-empty'`）并回报 `scopeEmpty`；
`init` 据此安排**一次** 1.5s 的延迟重载（`scheduleScopeReload` / `cancelScopeReload`，经内核 `timerHooks`，`teardown` 撤销）。

## 3. 读取台账（用户要求 ①）

新增 `core/read-ledger.js`（纯内核，与 `core/pipeline.js` 分工互补：管线回答「正在做什么、还要多久」，
台账回答「**读到了什么、从哪一层读的、花了多久、为什么没读到**」）：

- 记录字段：`{来源 · 动作 · 目标 · 耗时 · 体积 · 条数 · 字段数 · 哈希 · 结果(成功/未命中/失败) · 原因}`，**绝不记正文**；
- 内存恒定：环形缓冲固定 `READ_LEDGER_CAP = 240` 条（最新在前）+ 分来源累计（次数 / 成功 / 失败 / 未命中 / 累计与最慢耗时 / 体积 / 条数 / 字段数）；
- 出口全部由宿主注入（`setReadLedgerHooks({now, log})`；默认 no-op）→ 内核零宿主依赖；`log` 抛错也不影响记录（台账绝不弄坏主流程）。

**覆盖到的每一层读取**（用户原话「任何从服务端、本地、内存读取数据等的行为」）：

| 层 | 埋点 | 记下的内容 |
| --- | --- | --- |
| 文件通道（**所有服务端读取的唯一入口**） | `adapters/file-transport.js#fileTransportReadAuto / ReadBytes` | 文件名、走哪个后端（`tt-native` / `st-files`）、字节数、耗时、是否 gzip、gz/明文、失败原因（**只挂 `.then` 记账 → 不改变返回的 Promise 与装配时序**） |
| 服务端主文件 | `adapters/store.js#loadFromServerFile` | 信封哈希、主文件时间戳、条数、是否落到分片重建、应用的维度 |
| 分片 + 清单 | `adapters/shards.js#readShardManifest / readShard / applyNewerShards` | 清单有几片、需要读哪几片、逐片字节/条数/哈希校验结果、应用哪几片 |
| 本机缓冲 | `adapters/store.js#loadFromLocalStorage` | 信封校验结果、字节、条数、哈希（哈希不一致 → 明确记 `hash-mismatch`，不再静默丢弃） |
| 本机内存库 | `adapters/store.js#loadFromIndexedDB` | 同上（含「宿主没有 localforage」的如实未命中） |
| 聊天元数据 | `adapters/chat-meta.js#chatMetaLoadState / chatMetaRead` | 条数、体积、写入时间、命名空间 |
| 内存态 | `index.js#loadMemoryState`（注入后） | 载入来源、内存现有条数、逐维条数、是否因竞态让位 |

**界面与出口**：调试页新增「📥 读取台账（服务端 / 本地 / 内存）」区块（分来源统计 + 最近 20 行 + 「🧹 清空读取台账」）；
`FTT.reads()` / `FTT.readsText()`；调试包新增 `readsText` / `reads`；`storeStatus().reads` / `.serverLoad`。
每条记录同时进调试日志（`kind='读取'`）；慢读（≥150ms）或失败额外进交互时间线（避免正常读取刷屏）。
