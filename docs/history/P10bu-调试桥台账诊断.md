## 1. 症状与已取证事实

用户报告：**页面刷新 / 插件重载后，之前已分析的楼层成片变回「未摘要」**，且「每次刷新必定出现」。

用调试桥 + 宿主持久层 + 聊天文件离线复算，取得以下**实测事实**：

| 事实 | 数据 |
| --- | --- |
| 实时聊天长度 | **144 楼**（聊天文件 145 行 = 1 头 + 144 楼… 实为 145 条消息，楼层 0–144） |
| 界面未摘要 | 刷新前 **66 楼** → 刷新后 **67 楼**；列表为偶数楼（0/2/4/6…） |
| 刷新前后的变化 | **第 2、4 楼由「已分析」变成「未摘要」**；**第 70 楼反而由「未摘要」变成已分析** |
| 台账（持久层） | 13 条：`2, 4, 70, 179, 183, 185, 187, 189, 191, 193, 195, 197, 199`；`lastKnownFloor = 70` |
| 离线复算（仓库自己的 `hashText`） | 标记 2 → 文件第 2 楼 ✅ 同位；标记 4 → 第 4 楼 ✅ 同位；**标记 70 与其余 10 条在文件中已找不到对应内容** |
| 覆盖兜底 | 未摘要清单里恰好缺 `30/32/34/36/38/70` 六楼 → 与「刷新后视台账为空」的推算完全吻合（73 个偶数楼 − 6 = 67） |

**矛盾点（本次定位的关键）**：界面把**哈希一致**的 2、4 判为未摘要，却把**哈希不一致**的 70 隐藏
—— 与 `host/floors.js#isFloorProcessed` 的判据**方向相反**。因此**页面侧算出的取值与聊天文件不同**，
不能只靠离线分析定因。

## 2. 已完成的三条排除

| 假设 | 结论 |
| --- | --- |
| 「分析结果没落盘」 | ❌ 排除。用户分析 2、4 后，持久层台账由 11 → **13 条**（含 2、4），维度也在增长（atoms 31→33） |
| 「哈希跨重载不稳定（swipes vs mes）」 | ❌ 不成立。离线复算：这三楼 `swipes[0]` 与 `mes` **完全相同**（`swipe_id=0`、`swipes` 数=1），两种取法哈希一致 |
| 「骤减处理洗掉台账」 | ⚠ 未触发。刷新后持久层仍是 13 条、`lastKnownFloor=70`（若触发会收紧为末楼）；且 `reconcileProcessedFloors` 的 `mass-mismatch` 守卫会挡住写回。**但该路径本身确有隐患**（见 §5） |

## 3. 本版交付：只读诊断（不改台账行为）

**刻意不做行为修改** —— 定因前改台账逻辑等于拿用户数据做实验。本版只加观测：

| 方法 | 作用 |
| --- | --- |
| `ftt.ledger` | 台账标记 + `processedVer` 与当前签名的**一致性** |
| `ftt.chatReady` | 聊天就绪判定（`ready/reason/total`）—— 用于验证「就绪竞态」假设 |
| `ftt.pendingScan` | 未摘要清单 + **逐项跳过计数**（user / hidden / missing / noText / processed / covered / chatNotReady） |
| `ftt.pendingFloors` | 未摘要清单（与执行侧同源） |
| `ftt.floorDiag(i)` | **单楼逐项判据**：是否用户楼/隐藏、swipes 数与长度、`mes`/稳定正文长度、`hashStable`/`hashMes`、台账标记值与是否同哈希、签名是否一致、可分析文本长度、是否被覆盖、最终是否会进未摘要 |

两条硬约束：

1. **零副作用**：全部走 `scanPendingFloors({ maintain: false })` 与纯比较；
   `floorDiag` **不调用 `isFloorProcessed()`** —— 后者在签名不符时会触发 `migrateProcessedFloorsV170()` 写入。
   该不变量由单测 **F8** 锁定（含「越界悬空标记必须原样保留」）。
2. **仍然只读**：不新增任何写操作；`--deploy` 等写路径未变。

工具侧另补：`bridge.mjs --params` / `--params-file`（一次性调用可传参；后者绕开 shell 引号问题）。

## 5. 下一步（定因）与已识别的隐患

**下一步**：用户更新扩展 → 刷新一次 → 读取 `ftt.floorDiag(2)`、`ftt.floorDiag(70)`、`ftt.pendingScan`、`ftt.ledger`。
四者对照即可定因：

- 若 `floorDiag(2).hashStable === '1hzkdfp'`（= 台账值）而 2 仍在清单 → 问题在**清单/UI 路径**（例如缓存）；
- 若 `hashStable ≠ '1hzkdfp'` → 页面侧正文与文件不一致，问题在**取文口径**；
- 若 `pendingScan.skipped.chatNotReady === 1` → **就绪竞态**（清单在聊天/状态就绪前算了一次并被沿用）。

**已识别但本版未改的隐患**（待定因后一并处理）：

1. `handleFloorShrink` 的台账重建是**无条件写回**（`state.processedFloors = keep`，第 414 行），且刻意绕过
   `mass-mismatch` 守卫 —— 收缩后若哈希整体对不上，**整本台账会被洗掉**；
2. 同处把条目的 `floorStart/floorEnd` 置 `0/0` + `floorStale`，而 `core/floor-cover.js#meaningfulFloorRange`
   **明确忽略 `0/0`** —— 覆盖兜底随之失效，两道保险同时没了；
3. `reconcileProcessedFloors` 只扫 `0..lastId`，越界标记处理不一致（当前依赖 `mass-mismatch` 不写回才没爆）；
4. 台账残留悬空标记（179–199）且 `lastKnownFloor=70` 自相矛盾；
5. 用户手动分析第 0 楼时得到「没反应/报错」，且台账没有 0 —— 需单独看该次报错原因。
