## 1. 现场取证（只读；2026-10-05 01:59:58 → 02:05:43）

不启用调试桥、不改用户数据，只读三处现场：

| 来源 | 读到什么 |
| --- | --- |
| 插件调试日志（WebView2 localStorage 键 `SPreset_FTTMemoryDebug`，LevelDB 里 UTF-16LE 值） | `01:59:58 [异常] 内核告警：删楼：酒馆自带命令 /cut 未生效 → 回退逐层删除 chat 242 > 12` |
| 交互时间线（键 `SPreset_FTTMemoryTrace`） | `02:01:11 → 02:05:06` 共 **119 条** `{"cat":"host","kind":"deleteMessage","site":"host/floor-trim.js:253:floorTrimApply"}`，相邻间隔 **0.85–1.84 秒**（首条 01:59:58 起算） |
| 聊天文件 / 进程 | `书籍 - 2026-09-19@21h53m33s597ms.jsonl`：01:59:58 起 242 层（4.32MB）→ 02:05:40 才到 14 行；期间 WebView2 渲染进程工作集 **3.1GB**，操作卡顿 |

- 每层 `deleteMessage` 的代价 = ST 内部 `chat.splice` + DOM 元素移除 + `chat_metadata.tainted` + `updateViewMessageIds` +
  `saveChatDebounced()` + `await eventSource.emit(MESSAGE_DELETED)`（**订阅该事件的每个扩展各自全量刷新**）。
- 于是删 230 层 = **230 次**落盘调度 + **230 次**重编号 + **230 次**广播 → 实测 ≈1.5 秒/层 → **5 分 45 秒**界面几乎不可用。
- 同日 02:05:43 状态落盘：`processedFloors 12 / lastKnownFloor 12 / originGone 567` —— 数据侧最终是对的，**错的是用时**。

## 2. 根因：v3.4.0 探错了对象

`floorTrimCapability()` 当时探的是「宿主有没有 `executeSlashCommandsWithOptions`」= **命令执行器存在**，
并不等于「`/cut` 命令存在且生效」。本机宿主的 `/cut` 调用**不抛错也不生效**（`chat` 长度不变），
于是必然走到 `floor-trim.js` 的「逐层回退」—— 也就是 v3.4.0 想消灭的那条路。
换言之：**「命令优先」在本机从未成功过，每次删楼都在逐层删**。

补充一条硬约束：`/cut` 的保留语义（保留头部还是尾部）在删前**无法验证**，一旦判错就是「删掉最新的、留下最旧的」。
故本次不再依赖它。

## 3. 修法

### 3.1 默认路径：**一次批量截断**（全部由官方上下文 API 组成）

| 步 | 调用 | 说明 |
| --- | --- | --- |
| ① | `ctx.chat.splice(0, M)` | 官方会话数组（`getContext().chat` 是活引用；本机其它扩展同款用法） |
| ② | `ctx.chatMetadata.tainted = true` | 官方字段；与官方 `deleteMessage` 同口径（条件保存据此落盘） |
| ③ | `await ctx.saveChat()` | 官方落盘（`st-context.js` 的 `saveChat: saveChatConditional`） |
| ④ | `await ctx.clearChat(); await ctx.printMessages()` | 官方 DOM 重建：**先清显示再按内存 chat 一次画完**（不用 `printMessages` 单独调用 —— 它按 `mesid=startIndex` 删除旧元素，批量前移后元素对不上会残留/重复）；缺一即退 `await ctx.reloadCurrentChat()` |
| ⑤ | `await eventSource.emit(MESSAGE_DELETED, chat.length)` | **一次**广播，payload 与官方 `deleteMessage` 同口径（删除后的 `chat.length`） |
| 核对 | `chatLen() === target` | 对不上即如实失败；`saveChat` 抛错则 `unshift` **原样放回**（绝不留下「内存删了、盘上没删」的半截状态） |

代价对比（242 层聊天删 230 层）：落盘 230 → **1**；DOM 重建 230 次局部改动 → **1** 次整聊重画；广播 230 → **1**。

### 3.2 最后手段：逐层 `deleteMessage`（≤3 层）+ 硬预算

- 只在「宿主连批量截断都不可用」时使用，且**待删 ≤ `FLOOR_TRIM_SLOW_MAX`（3）层**；
- 超过即**拒绝执行**：不做备份、不动聊天，摘要写明「预计约 N 秒（界面会卡顿）→ 已拒绝执行；请到酒馆聊天界面自行删除更早的楼层」；
- 执行时每步核对 `chat` 真的变短；累计超 `FLOOR_TRIM_SLOW_BUDGET_MS`（20s）立即中止并如实回报 `partial`；
- 预估口径：`FLOOR_TRIM_SLOW_MS_PER_FLOOR = 1500`（本机实测上界），用于确认框与预检文案。

### 3.3 配套（两处「不自伤」）

| 位置 | 问题 | 处置 |
| --- | --- | --- |
| `index.js#onChatChanged` | 批量路径的兜底会调 `reloadCurrentChat()` → 发 `CHAT_CHANGED` → 我们自己去重读落盘状态；而此刻编号重映射还没落盘（写队列异步）→ 重读等于**无声撤销重映射** | 删楼全程 `floorTrimBusy()`；删楼期间 `onChatChanged` 跳过重读（内存态才是权威）；重入调用直接返回 `busy` |
| `index.js#wireFloorTrimHooks().afterMutate` | `clearChat()` 是 ST 官方行为，会顺手清空 `extension_prompts` → 「删楼后这一轮注入为空」 | 真的删掉后回调一次：重推注入 + 刷新内核视图 |

## 5. 未验证项（如实登记）

- **真机复现待刷新后核对**：本机页面需刷新才跑在 v3.17.0；刷新后删一次楼应**秒级完成**，提示「方式 批量截断」，调试日志出现 `kind=楼层 action=删楼 via=bulk ms=<小数值>`；
- 逐层路径（≤3 层）与「拒绝执行」在**本机真机**上未复现（本机有批量能力），仅单测覆盖；
- 1.5 秒/层是**本机**实测（242 层聊天 + 本机扩展集），它只影响预估秒数，不影响「不再逐层」的结论；
- `clearChat()` 清空 `extension_prompts` 是 ST 官方行为，我们以 `afterMutate` 重推兜住；**其它扩展**是否也重推取决于它们自己，刷新/下一轮生成时会各自恢复。

## 6. 影响面

- 采集层（`DATA_VERSION`）不变：删楼仍只改编号（`originGone` / `floorNow*` / 台账前移），**记忆条目一条不删**；
- 配置键不变（`floorTrimLog` 照旧，仅 `via` 取值由 `command`/`command+api`/`api` 变为 `bulk`/`api`，旧账本仍可读）；
- 用户可见变化：删楼从「几分钟卡死」变为「秒级完成」；宿主不支持批量时**明确拒绝**而不是默默卡住。
