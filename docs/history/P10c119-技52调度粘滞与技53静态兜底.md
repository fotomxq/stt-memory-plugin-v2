## 1. `技-52`：延迟触发器「拿不到定时器」时不再永久 pending

**缺陷**（`docs/D45` §2.4 F3，实测）：两个模块都写成「`pending = true` → `timer = setT(...)`」，而 `setT` 在**受限宿主**
（或测试注入的空实现）下**返回 `null` 而不抛错** → `pending` 永久为 `true`：

```text
[inject-schedule] 1st={"accepted":true,"reason":"scheduled"} 2nd={"accepted":false,"reason":"coalesced"} 3rd={"accepted":false,"reason":"coalesced"}
[inject-schedule] pending=true scheduled=false signals=3 coalesced=2 runs=0
```

→ ① 读数**说谎**（`pending:true` / `scheduled:false` 自相矛盾）；② 之后所有信号都被判 `coalesced` **吞掉**，再也排不出刷新。
同口径**先例** `core/clock-extract.js#scheduleClockExtract` 只用句柄、不设 `pending` → 没有粘滞态。

**修法**（与先例对齐）：

| 文件 | 变化 |
| --- | --- |
| `host/inject-schedule.js` | `const h = setT(...)`；**`h` 为假值 → `pending = false`** + `stats.noTimer += 1` + 返回 `{accepted:false, reason:'no-timer'}`；`stats` 增 `noTimer` 计数 |
| `ui/nsfw-count-tick.js` | `schedule()` 内部同样回滚（`h` 假 → `pending=false` + `noTimer` + 返回 `false`）；**`signalNsfwCountRefresh` 改为按 `schedule()` 的返回值如实回报 `no-timer`**（此前恒报 `scheduled`，即使根本没排上） |

**降级语义不变**：「拿不到定时器 = 本轮不刷新」，只是不再留下粘滞态。

## 2. `技-53`：补上 `static:full`（并**真的跑通**）

**缺陷**：仓库有 **5 处**文档引用 `npm run static:full`，但 `package.json` 里**没有这个 script** →
`check-static.js` 的语法检查**默认关**，而它唯一的触发方式就是这条命令 → **「发版前全量 `node --check` 兜底」事实上从未执行过**。

**修法**：`package.json` 补 `static`（默认模式）与 `static:full`（`--syntax`）；`docs/05` §1 速查 + 检查项表补两行说明，
并写明「**故意不塞进 `gate`**」（25s 的兜底不该进每次门禁）。

**跑通时立刻发现存量问题（这就是该兜底的价值）**：

```text
$ npm run static:full
结果：错误 0 条 · 告警 220 条（基线 218 条）
❌ 告警变多的规则（基线只减不增）：empty-catch 218 → 220
```

→ 其中 **2 处是我自己**（v3.50.5 的 `pushCat` 内层 catch、v3.50.7 的 `import-v1` 判重 catch）—— 已就地写明忽略原因；
另外把 `core/atom-compact.js` 的 3 处旧空 catch 一并注明（`技-55` 的小口），并把基线**收紧到 217**（`--write`，只减不增）：

```text
结果：错误 0 条 · 告警 217 条（基线 217 条）
✅ 静态检查通过（0 错误 · 告警未超基线）
```
