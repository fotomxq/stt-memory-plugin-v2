## 3. `技-37`：九步逐步留痕

### 3.1 实现

| 件 | 作用 |
| --- | --- |
| `REPAIR_MECH_STEPS` | 九步**名单常量**（`{step, name, note}`）—— 跑的时候按它记、测试按它断言 → **名单与实跑同源**（防「文档说九步、代码跑八步」） |
| `repairStepRecord(step, name, t0, err)` | 纯函数：`{step, name, ok, ms, err}`，`err` 截断 **160** 字 |
| `runRepairStep(steps, spec, fn)` | 包装器：抛错**不中断**，把记录 push 进 `steps`，返回 `{ok, val, err}` |
| `repairStepFailures` / `repairStepsSummary` | 只列非 ok / 一句话摘要（`机械清理 9/9 步 ok` 或点名失败步） |
| 日志 | `dbgLog('修复', …)` 增 `stepsFailed`（非 ok）/ `stepsOk` / `stepsTotal` —— **正常时为空**，不膨胀 |
| 返回值 | `runRepairMech` 与 `runRepair` 增 `steps` / `stepsSummary` |

### 3.2 顺带修掉的隐藏缺口（**行为改动，如实登记**）

`docs/04` §2.2 早就写着第①段「**每步独立 `try/catch`**」，但**第 1 步（机械去重）是裸调用** `const m1 = repairMergeDedupe();` ——
它一抛错会**直接中断整段机械清理**（后续 8 步全不跑），且面板只会看到一个失败动作。本批把它一并纳入 `runRepairStep`：

- **变化**：第 1 步失败不再中断整段（后续步照跑）；
- **不静默**：失败记为 `ok:false + err`，进日志（`stepsFailed`）与返回值（`steps`），并进 `docs/04` §2.2 的口径；
- **回归判据**：单测含**源码级**断言 —— 九步全部经 `runRepairStep(steps, S(1..9)` 包裹，且旧的裸调用形态 `const m1 = repairMergeDedupe();` **已消失**。

### 3.3 两处落点差异（已登记于 `docs/D25` §8 落地状态）

1. 断言落在**新档** `tests/unit/repair-steps.test.js`（8 项），**未**改 `tests/unit/repair-golden.test.js` —— 后者是 V1 逐字 oracle 档，不该混入「新增可观测性」的断言；
2. 「人为让**第 3 步**抛错」实现为**第 8 步**：第 1–7 步都是内部函数且**各自内部已有 `try/catch`**（外部无法可靠让它们抛），只有第 8 / 9 步是**注入钩子**、外部可控 →
   用 `floorJump` 抛错证明「记 `ok:false+err` 且**第 9 步仍执行**」，另用 `runRepairStep` 的**单步契约**覆盖「任一步抛错都不中断后续步」。

## 5. 未做与风险（如实登记）

1. **`steps` 目前只进日志与返回值**，未进面板/调试页的**界面**读数 —— 用户要看「哪一步失败」仍需开调试日志（设定 → 调试 → 日志 的 `修复` 类目）。
   若要一行界面读数，属**新增读数**（与 `应-25` 无关），建议另立开发项（可在下一轮与 `docs/D33` 的「八处联动点」一起做）；
2. **`steps` 不落盘**（不进 `state.repairLog`）：它是**本次运行**的逐步结果，跨端无意义 —— 与 `repairLog`（末 5 条运行记录）职责不同，避免把逐步骤流水塞进运行时槽位；
3. **`ms` 为墙钟**，步与步之间含 `saveState()` 的耗时 —— 口径是「这一步**连同它的落盘**花了多久」，不做纯计算耗时的细分；
4. **U183 的 `README` 提法保留**（缺陷叙述）→ 机械守门靠「豁免标记」放行；若将来有人把「缺陷叙述」误写成「事实陈述」，`docs-cfg-keys` 的反向探针与 C3 会拦（豁免只在含标记的行生效）。
