## 1. 覆盖范围（V1 `src/modules/09-AI摘要与楼层处理.js` v1.192 传言引擎段：行 13261~13820 + 行 23377）

设计口径（V1 原文）：① 抽取与其它分析记忆维度**同批**（模板 `rumors`）→ `rumorApplyAiDelta()` 落库；
② 演化**零 AI**，每满 `rumorChangeEveryRounds`（默认 5）个楼层轮次演化一次；③ 所有变化先写入 `pending`
（需 `rumorChangeNeedRounds` 轮才提交 ——「传言的变化不可能立刻发生」）；④ 裂变以「父 id + 变体名」派生稳定子 id；
⑤ 衰退复用 `calcTimeDecay` 通用多级时间衰退，命中阈值自动移除并留墓碑；⑥ 概率全部由 `rumorRoll(seed)`
（`hashText` 种子哈希）决定 —— **确定性**，两端各自演化结果一致。

## 2. 与 V1 的差异（逐条明示）

1. **ESM 化 + 视图注入**：V1 直接读模块内全局 `state` / `cfg`、调用 `saveState` / `dbgLog` / `getStoryNow` / `getLastMessageId` /
   `hashText` / `normText` / `tombMany` / `tombEntries` / `calcTimeDecay` / `repairSimilarity` / `repairTagSetOf` / `repairJaccard` /
   `clockDateTrim` / `storyDateMsFromStr` / `normalizeRumor*`；V2 全部改为 `import`（`core/model/runtime.js`、`core/clock.js`、
   `core/merge.js`、`core/ingest.js`、`core/repair.js`、`core/util.js`、`core/model/rumor.js`），内核零宿主依赖。
2. **弹窗**：V1 `notify(kind, {title, text})` / `toast(msg, type)` → 本模块局部 `notify(kind, title, text)` / `toast(text, kind)`，
   与 `core/repair.js` / `core/group-repair.js` 既有写法逐字一致（经 `notifyHooks.toast`）。**文本逐字符一致**，
   黄金样本比对时把 V1 的 `[kind, title, text]` 归一为 V2 的 `[kind, title + ' ' + text]`。
3. **延迟调度**：V1 `setTimeout(…, 3000)` → `timerHooks.set(…, 3000)`（内核不握有宿主定时器，行为等价：3 秒堆叠 + 在途去重）。
4. **AI 通道**：本引擎**零 AI**，不调用 `callChatCompletion`；`rumorApplyAiDelta` 只消费已归一化的 AI 增量对象
   （V1 同）。因此本批不需要 `stubFetch`，`cfg.apiUrl/model/apiPreset` 对引擎无影响。
5. **`rumorInjLine` 复用**：该函数已在 `core/recall.js` 逐字移植（V1 同一函数），本模块只 **re-export**，不重复实现。
6. **`mergeRumorListBy` 上移**：V1 把它定义在段 09 的引擎里，但 V1 导出清单将其列为**模型助手**；B8-7 起移到
   `core/model/rumor.js` 并导出（V2 引擎与后续 UI 回填共用一份，避免两处实现漂移）。引擎侧同名 re-export 保持 API 完整。
7. **`RUMOR_VARIANTS` 随模型层导出**：V1 行 9802 的常量在 V2 `core/model/rumor.js` 中补齐并导出，引擎从模型层引入。
8. **`core/ingest.js` 存在**私有副本**（已知重复，如实记录）**：B3 落库批次已把 `rumorEnabledOn` / `rumorTickState` /
   `rumorStoryDate` / `rumorChainPush` / `mergeRumorListBy` / `rumorAiHas` / `rumorMergeAiInto` / `rumorApplyAiDelta`
   **内联**在 `core/ingest.js`（未导出，供 `mergeDelta` 落库用）。本文件是引擎的完整实现，同一 V1 源行，二者行为一致；
   建议后续批次把 `ingest.js` 改为 `import` 本模块以消除重复 —— 本批受并发「只新增文件」约束**未改动 `ingest.js`**。
9. **V1 未导出的内部助手**：`rumorActiveMediaCount` / `rumorAiHas` / `rumorMergeAiInto` **不在 V1 `__FTT` 导出清单**里，
   故无法直接取黄金值。处理：`rumorActiveMediaCount` 用「全载体 `durability = 1` 时 == V1 的 `rumorMediaWeight` == 活跃载体数」
   做等价校验；`rumorAiHas` / `rumorMergeAiInto` 的**公开效果**由 `rumorApplyAiDelta` 七段黄金值覆盖，另在测试中以
   语义断言固化（标注为非黄金值）。`rumorActiveMedia`（模型层，V1 行 10049）在 V1 中**定义后无任何调用**，本批未补。
10. **`rumorVariantFor` 的 V1 越界怪癖原样保留**：`rumorRoll` 返回 `NaN` 时 `Math.max(0, Math.min(4, NaN)) = NaN`，
    数组取 `undefined` → 变体为 `undefined`（落进 `pending.target` 后为 `''`）。V2 逐字保留，**不做顺手修正**；
    黄金样本已把该情形固化为 `null`。
11. **`extractJsonObject` 未被引擎使用**：V1 传言引擎段内不解析 JSON 文本（AI 增量由落库管线传入对象），
    该助手仍归 `core/util.js`，本批不引入。
12. **接线未做**：`index.js` / `devtools.js` / `ui/**` 未改，`FTT.rumorEvolve`、面板「传言」动作尚不存在
    （本批明确不交付，见文首警示）。
13. **黄金样本的时间确定性处理（非行为改动）**：V1 `rumorApplyAiDelta` 选「同主体最新者」时按 `updatedAt` 排序，
    两次落库若落在**同一毫秒**，并列者按数组序取首个 → 结果取决于宿主耗时。黄金样本在每次落库后按数组序
    固定 `updatedAt`（oracle 与 V2 测试同口径），使该分支可复现；另 `rumorDecayScore` 依赖 `Date.now()`，
    样本用**饱和时间戳**（2001 年 → 打分恒 1；2100 年 → 恒 0）锁定精确值。
