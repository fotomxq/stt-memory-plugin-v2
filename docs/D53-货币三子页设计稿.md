>   前景预判分为**三部分**：① 文字说明 ② 多个变动节点的记录 ③ 结合变动节点**预测下一个节点**可能发生的费用变动（数据）和变动可能的方向（增加或减少）。」

## 0. 一页摘要

货币页从**单页**拆成**三个子页**；并为此新建**两个原子容器**：

| 子页 | 内容 | 数据 |
| --- | --- | --- |
| **① 货币总览**（= 当前页，行为不变） | 统计胶囊 · 说明 · 已标定胶囊 · 工具行 · 货币列表 | 既有 `currencies` |
| **② 收支记录**（记账） | 明细列表 + 「＋记一笔」+ 筛选与合计 | **新建 `ledger`** |
| **③ 长期收支** | 标的物列表 + 详情（现状 + **前景预判三段** + **触发器状态**） | **新建 `deals`** |

**七条硬口径（对应用户 v1.1 的 7 条修订）**

| # | 口径 |
| --- | --- |
| **1** | 记在货币条目内的**摘要流水上限 = 60 笔**（`cfg.currencyHistoryMax`，**设定可改**，默认 60）；`ledger` 账本**同样受上限约束**（但按 `D28` 进**冷存**而非删除） |
| **2** | 长期收支有 **`desc`（约定内容）** —— 记录这笔约定的实质条款（分成比例 / 利率 / 期限 / 结算方式等） |
| **3** | **货币消失 → 其流水一并消失**（级联删除 + 写墓碑防跨端复活），**不做孤儿记录** |
| **4** | 长期收支**孤立于提取管线**：**建立 / 变更可经 AI**；但**流水生成、触发器执行一律走固定代码**（只看 `forecast` 数据），**不经 AI** |
| **5** | 自动生成流水时**若锚定货币丢失 → 不生成**，并如实留痕（原因 + 跳过条数） |
| **6** | 长期收支**必有锚定货币**（`currencyId` 必填）；**每个预测节点都带预测日期**（`forecast.nextDate` 必填） |
| **7** | **剧情时间跳动后**，在**总览自动分析完成时**自动处置**长期收支触发器**；跳动**猛烈**时按 `cycle` **确定性补齐**后续预测节点（**不经过 AI**） |

**决定性论据（决定了必须新建容器）**

> `currencies` 在本项目里是**非原子容器**：`core/cross-sync.js` 对它做**整容器哈希**（`storageHash(JSON.stringify(...))`）且它在 `excludes` 名单内 —— 跨端是**整份替换**。
> 因此若把记账继续写在 `currencies[].history` 里：① 跨端会**整份覆盖**（一端记账、另一端保存别的内容就丢）；② 该字段现被 `core/model/money.js#normalizeMoneyHistory` **硬编码截断到 12 笔**。
> **结论：流水与长期收支必须各建原子容器。**

**成本定性（与 `docs/D27` 地图同级别、略重）**：两个新原子容器 → **六处接线 ×2** + **`DATA_VERSION` 2 → 3** + 维度数 **15 → 17** / 原子层 **14 → 16**（`docs/README.md` §3 由门禁 C1 逐行实测）+ `STORE_LIMITS` 两项 + 面板/字段表/编辑器/测试接入。

**待确认 5 项 + 新增 2 项**（§6.2）：两容器是否都进原子层 · 是否回填老 `history` · 长期收支是否注入 · `forecast` 的产生方式 · 容器命名 · **新增**：`cycle` 取值域 · 跳动与补齐的阈值。

## 3. 方案

### 3.1 三子页划分

| 子页 | 键 | 内容 | 与现状的关系 |
| --- | --- | --- | --- |
| **① 货币总览** | `currencySub: 'overview'` | 统计胶囊 · 说明 · 已标定胶囊 · 工具行 · 货币列表 | **= 当前货币页，行为与文案一字不改**（K9） |
| **② 收支记录** | `'ledger'` | 明细列表（日期 / 货币 / 收或支 / 金额 / 说明 / 来源）+ 「＋记一笔」+ 筛选（货币 / 角色 / 收支 / 日期区间）+ 合计 | 新增；**记账必须选货币**；显示「账本 N 笔（上限 …）」 |
| **③ 长期收支** | `'deals'` | 标的物列表 + 详情（**约定内容** / 现状 / **前景预判三段** / **触发器状态**） | 新增 |

- 子标签沿用 `ui/panel.js` 的页内子状态（K8），默认 `'overview'`（打开货币页仍是现在的总览）。
- **不新增面板分页**（N6）。
- 空态：收支记录空 → "还没有收支记录，从「货币总览」的某条货币上点「＋记一笔」开始"；长期收支空 → "＋新建标的物"。

### 3.2 为什么必须新建容器（而不是扩展 `history`）

| 判据 | 扩展 `currencies[].history` | **新建原子容器** |
| --- | --- | --- |
| 跨端合并（K5） | ❌ 整容器替换 → 一端记账被另一端覆盖 | ✅ 逐条合并、按条目 `updatedAt` 仲裁 |
| 上限（K3） | ❌ 硬编码截断 12 笔 | ✅ 60 笔**可配** + 账本冷存（不删） |
| 独立寻址（`02` I1） | ❌ 子数组无独立 id，无法墓碑/引用 | ✅ 每条一 id，可墓碑、可被 `deals` 引用 |
| 跨货币聚合 | ❌ 需遍历全部货币拼接 | ✅ 天然是一个列表 |
| 成本 | 低 | **高**（六处接线 + `DATA_VERSION`） |

> **结论**：`history` 保留，但**降级为"该货币条目内的最近 60 笔摘要视图"**；**权威账本是 `ledger`**。派生**单向**：`ledger` → `history`，**禁止**直接手改 `history` 当作记账手段。

### 3.3 `ledger`（收支记录）字段模型

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `id` | 是 | `led_<hash(currencyId\|date\|delta\|note)>` —— 重复提交得到同一 id（**幂等**） |
| `currencyId` | **是** | **必须**指向现存 `currencies[].id`（用户硬要求） |
| `owner` | 否 | 归属角色（记账时从货币带出） |
| `date` | 是 | **剧情日期**（与 `history.date` 同口径） |
| `delta` | 是 | **带符号金额**（收入 `+` / 支出 `−`），**不得为 0** |
| `note` | 否 | 说明（≤ 80，与 `history.note` 同口径） |
| `source` | 否 | `manual` / `quick` / `ai` / **`deal`**（长期收支触发器生成）/ `repair` |
| `dealId` | 否 | 由触发器生成时，指向来源标的物（便于回溯） |
| 通用元字段 | 否 | `floorSeen` / `floorStart` / `nsfw` 等沿用 `02` §1.3 |

**上限与可配置（v1.1 第 1 条）**

| 项 | 口径 |
| --- | --- |
| **条目内摘要**（`currencies[].history`） | 默认 **60** 笔；`cfg.currencyHistoryMax`（**设定可改**，建议范围 10–200）；**取代**原先硬编码的 12 |
| **账本总量**（`ledger`） | 受 `storeMaxLedger` 约束（与其它原子容器一致）；超限按 `D28` 进**冷存**、**不删除**；面板显示「N 笔（上限 M）」 |
| **对账口径** | `amount`（权威余额）vs Σ`ledger.delta`；**只报不改**（§3.5） |

### 3.4 `deals`（长期收支 / 标的物）字段模型

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `id` | 是 | `deal_<hash(name\|startDate)>` |
| `name` | **是** | **标的物名称** |
| `desc` | 否 | **描述 / 约定内容**（v1.1 新增）—— 分成比例、利率、期限、结算方式等实质条款 |
| `kind` | 否 | `investment` 投资 / `royalty` 创作长期收益 / `loan` 贷款长期支出 / `other` |
| `startDate` | **是** | **最初确定的日期** |
| `lastChangeDate` | 否 | **最后一次变动的日期**（由 `outlook.nodes` 最大日期**自动维护**，界面只读） |
| `endDate` | 否 | **截止日期**（贷款截止 / 合作截止）；空 = 无固定期 |
| `status` | 否 | **标的物现状**（一段文字） |
| `currencyId` | **是** | **锚定货币**（v1.1 第 6 条：由"可选"改为**必填**）—— 触发器生成流水时用它；丢失则不生成（第 5 条） |
| `cycle` | 否 | **周期**（v1.1 新增，触发器补齐所需）：`monthly` / `quarterly` / `yearly` / `weekly` / `custom:<天数>`；缺省时由 `nodes` 相邻间隔**推断**，推断不出则**不自动补齐** |
| `outlook` | 否 | **前景预判**（三段，见下） |
| `trigger` | 否 | **触发器状态**（代码维护，用户不可编辑）：`lastFiredDate` · `lastFiredNodeDate` · `catchUpTruncated` · `skippedReason` |

**`outlook` 三段（严格对应用户要求）**

| 段 | 字段 | 内容 |
| --- | --- | --- |
| **① 文字说明** | `outlook.text` | 自由文字（整体判断） |
| **② 多个变动节点的记录** | `outlook.nodes[]` | 每节点 `{ date, delta?, note }` —— **已经发生**的变动（`lastChangeDate` 取其最大 `date`） |
| **③ 下一节点预测** | `outlook.forecast` | `{ nextDate, delta?, direction: 'increase' \| 'decrease', note, source: 'ai' \| 'manual' }` —— **`nextDate` 必填**（v1.1 第 6 条）；`delta` = 费用变动数据；`direction` = 增或减 |

> **`direction` 与 `delta`**：可**独立缺失**但**不得矛盾**；矛盾时以 `delta` 符号**纠正** `direction` 并留痕。
> **建立 / 变更**：可经 **AI 辅助**（用户触发，AI 建议字段），但**落库结构由固定代码归一**（第 4 条）—— AI **不直接写流水**。

### 3.5 双向联动与完整性

| 场景 | 口径 |
| --- | --- |
| **记一笔** | ① 校验 `currencyId` 存在 → ② 写 `ledger` → ③ `currencies[currencyId].amount += delta`（**复用 `#applyQuickCurrencyFlow` 的取整与计算**）→ ④ 向 `history` 追加同一笔（受 **60 笔** 摘要上限）→ ⑤ 一次 `saveState()` |
| **删除一笔** | 仅**用户显式删除**（危险动作二次确认）时反向冲正 `amount -= delta`，并写墓碑；**不得**因超上限自动删（`D28`） |
| **货币被融合**（`D36`） | 融合后主条 id 可能变化 → **同一事务内**把被并掉 id 上的 `ledger[].currencyId` **重指向主条**，并留痕"重指向 N 笔" |
| **货币消失**（v1.1 第 3 条 · **推翻 v1.0**） | `ledger` 中指向它的条目**一并删除**：逐条 `tombMany` 写墓碑（**防跨端复活**）+ 从容器移除，并**如实报数**"随货币删除流水 N 笔"；**不保留孤儿** |
| **记账时货币不存在** | **拒绝**并如实提示（禁止无主流水）；**不得**自动新建货币 |
| **对账** | 体检比对 `amount` vs Σ`ledger.delta`：**只报不改**（历史 `amount` 可能由 AI 直抽，与流水本不同源） |

> **级联删除的边界**：只删**流水**（`ledger`）；**不删** `deals`。若 `deals.currencyId` 指向已消失的货币，该标的物**保留但触发器停摆**（第 5 条），详情页显示"锚定货币已失效"。

### 3.8 护栏：预测 ≠ 事实（三处）

| 处 | 要求 |
| --- | --- |
| **数据结构** | `forecast` 与 `nodes` **分属不同字段**，不得混写；`forecast.source` 必填（`ai`/`manual`） |
| **界面** | 详情页「已发生（节点）」与「预测（下一节点）」**分区呈现**，预测区**样式可辨识**并标来源 |
| **注入 / 台账** | 若将来注入（§6.2 Q3），预测文字**必须**带"（预测）"前缀；**禁止**把 `forecast.delta` 写成已发生的事实 |

> **额外**：触发器**兑现**一笔预测时，生成的流水标 `source: 'deal'` 且 `dealId` 指向标的物 —— 此时它已是**事实**（已兑现），与 `forecast`（仍是预测）区分。

### 3.9 长期收支触发器（v1.1 第 4/5/7 条 · **确定性，不经 AI**）

**定位**：把 `deals.outlook.forecast` 的**预测**在适当条件下**兑现**为 `ledger` 流水。全部为**固定代码**（本节不含任何 AI 调用）。

| 项 | 口径 |
| --- | --- |
| **挂载点** | **总览自动分析完成之后**：`index.js` 的 `onGenEnded` → `runAutoExtract()` 返回后调用 `runDealTriggers()`（K14）；失败静默、**绝不阻塞聊天与注入** |
| **跳动判据** | 取**解析前后的剧情日期**：`core/clock.js#clockDateAnomaly(cur, prev)` 的 `reason === 'jump'`，**或** `storyDateMs` 跨度 ≥ `cfg.dealJumpMinDays`（默认建议 30 天）→ 视为跳动；`backward` / `invalid` **不触发**兑现 |
| **普通处置（逐 deal）** | 若 `forecast.nextDate <= 当前剧情日期`：① 锚定货币存在 → 生成一笔流水（`date = forecast.nextDate`、`delta = forecast.delta`、`currencyId = deal.currencyId`、`source: 'deal'`、`dealId`）；② 该节点**并入 `outlook.nodes`**；③ 更新 `lastChangeDate`；④ 清空/推进 `forecast` |
| **货币丢失**（第 5 条） | **不生成**，写 `trigger.skippedReason = 'currency-missing'` 并计入体检；**不阻塞**其它标的物 |
| **跳动猛烈**（第 7 条） | 判定：本次跨度 ≥ **`cfg.dealStrongJumpCycles`**（默认建议 3）个 `cycle`。处置：按 `cycle` **确定性补齐** —— `nextDate = 上一节点 + cycle`，逐节点生成流水并入 `nodes`，**直到覆盖当前剧情日期**；补齐后 `forecast` 置为新算出的下一节点（同样带 `nextDate`） |
| **上限** | `cfg.dealCatchUpMax`（默认建议 **24** 节点/次）：超出则**只补到上限**并置 `trigger.catchUpTruncated = true`、如实提示"尚有 N 个周期未补齐"（**不静默丢弃**） |
| **`cycle` 缺失** | 由 `nodes` 相邻间隔推断；推断不出 → **不自动补齐**，只做"到期一笔"的普通处置，并在详情页提示"缺周期" |
| **幂等** | 以 `dealId + nodeDate` 为键去重：同一笔预测**只兑现一次**（重跑 / 多端都不重复生成）；`trigger.lastFiredDate` 记录水位 |
| **与 `D25` 自动修复的关系** | **不新增** `D25` 第 ① 段步骤；触发器挂在**分析完成**路径，与修复编排解耦 |
