### 2.2 F1 · 注入体的区块级隔离只做了货币（应用 · P1）

**结论**：`core/recall.js#buildMemoryBodyForInject` 的**整个函数体共用一个兜错**（函数末尾 `catch (e) { warn(...); return ''; }`），
**只有 `[货币]` 区块有自己的一层兜错**（v3.46.5 用户报告「货币根本没注入成功」时补的）。
其余任何大类只要出现**一条坏数据**，整个函数抛错 → 返回空串 → **AI 一条记忆都看不到**。

**证据（本轮实测，构造数据逐维驱动真实代码路径）**：

| 构造 | 坏数据形态 | 实测结果 |
| --- | --- | --- |
| `memories` / `parallels` / `plans` / `suspense` / `items` / `scenes` / `concepts` / `snapshots` | 数组里混入 `null` | **整份注入被清空**（正文长度 `0`；`warn` 记「本地召回失败: Cannot read properties of null (reading …)」） |
| 上表 9 维（含 `rumors`） | 该维度**不是数组**（脏数据，如 `{}`） | **整份注入被清空**（`(st(...).X || []).slice is not a function`） |
| `rumors` / `states` / `currencies` / `npcs` / `vars` / `maps` | 数组里混入 `null` | 正常（该区块自带逐条过滤） |
| `currencies` | 不是数组 | **只丢货币区块**，其余照常（v3.46.5 的隔离生效） |

**已有登记但不进清单的那句结论**：`docs/D17` 的 `U231` 处置④原文写着「**登记待办：其余大类也应逐块隔离**（本轮只做了货币区块，见批次档『未做』）」，

**为什么算 P1**：失败形态与用户报告过的 v3.46.5 完全同类（用户看到的就是「记忆根本没注入」），而脏数据来源是现成的 ——

### 2.4 F3 · 延迟触发器在「拿不到定时器」时进入永久 pending（技术 · P2）

**结论**：两个新模块（`技-50` / `技-51`）都写成「`pending = true` → `timer = setT(...)`」，
但 `setT` 在**没有 `setTimeout` 的宿主**（或测试注入的空实现）下**返回 `null` 而不是抛错** → `timer` 为 `null`、`pending` 永久为 `true`。
此后：① `…State()` 读数**说谎**（`pending: true` / `scheduled: false`）；② **后续所有信号都被判 `coalesced` 吞掉**，再也排不出一次刷新。

**证据（本轮实测）**：

```text
[inject-schedule] 1st={"accepted":true,"reason":"scheduled"} 2nd={"accepted":false,"reason":"coalesced"} 3rd={"accepted":false,"reason":"coalesced"}
[inject-schedule] pending=true scheduled=false signals=3 coalesced=2 runs=0
[nsfw-count]  1st={"accepted":true,"reason":"scheduled"} 2nd={"accepted":false,"reason":"coalesced"}
[nsfw-count]  pending=true scheduled=false signals=2 dropped=1 runs=0
```

**与先例的差异（这是「新代码引入的」而非既有风格）**：同一套口径的**先例** `core/clock-extract.js#scheduleClockExtract`
**只用句柄、不另设 `pending` 标志**（`clockTickTimer = timerHooks.set(...)`）→ 定时器拿不到时句柄为 `null`，下一次调用照常重排，**没有粘滞态**。
两个新模块的注释都写着「无 `setTimeout` … 一律静默」，但实际行为不是「静默跳过」而是「**永久占位**」。

**修复要点**：`setT` 返回假值时**回滚 `pending`**（或改为只用句柄判定，与 `core/clock-extract.js#scheduleClockExtract` 对齐），并补两条断言：
① 空定时器下连续两次信号**不进入 `coalesced` 粘滞**；② 读数里 `pending` 与 `scheduled` 不得互相矛盾。

### 2.5 F4 · `npm run static:full` 不存在（技术 · P2）

**结论**：仓库有 **5 处**引用这个命令，但 `package.json` 的 `scripts` 里**没有** `static:full`。

**证据**：

```text
$ npm run static:full
npm error Missing script: "static:full"
```

引用位置（逐条实测）：`docs/05-开发指南.md` · `docs/D21-技术维度缺陷完善设计稿.md` · `docs/D17-未落实事项台账.md` ·
`docs/history/P10c89-W5技术门禁与真机核对工具.md` · `scripts/check-static.js` 头部注释。

**为什么算问题（不是纯文案）**：`scripts/check-static.js` 的**语法检查默认关**（`--syntax` 才开），其设计意图是
「**发版前跑一次全量 `node --check` 兜底**，覆盖『既没被 import、也没被执行』的孤立文件」——
而这条兜底**只能靠文档写的那条命令**去跑；命令不存在 = **这条兜底事实上从未被执行**（门禁里跑的是默认模式）。
另外 `docs/05` §5 的门禁速查表也没列它（只在 §3 表内文字提到），可发现性更弱。

**修复要点**：在 `package.json` 补 `"static:full": "node scripts/check-static.js --syntax"`（零依赖、无副作用），
并把它写进 `docs/05` §5 速查；验收 = `npm run static:full` 退出码 0 且输出含「含全量 `node --check` 语法检查」。
